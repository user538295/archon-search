## 1 — Real llama-server window (S8, S11)

**Why manual:** needs a real `llama-server`. `/props` and `/tokenize` are exercised elsewhere in the repository only against `FakeModelServer` and `httpx.MockTransport`, so only a real server proves the field names and the exact counts.

**Steps:**
- [ ] Start a server with a known window and one slot, using a model whose training context is at least 4096 (the reported `n_ctx` is capped at it): `llama-server -m /path/to/model.gguf -c 4096 -np 1 --port 8080` (the config default is `llama_cpp_base_url = "http://localhost:8080"`; the llama-server default port differs, so pass `--port 8080`).
- [ ] Read the window the code reads: `curl -s http://localhost:8080/props | jq '.default_generation_settings.n_ctx'`. Expected: `4096` (note it as `N_CTX`). With several slots or a unified KV pool, `n_ctx` is the per-slot value the code will trust; record what it reports.
- [ ] Count a text exactly the way the client does: `curl -s -X POST http://localhost:8080/tokenize -H 'Content-Type: application/json' -d '{"content": "The quick brown fox jumps over the lazy dog."}' | jq '.tokens | length'`. Expected: an integer; `jq '.tokens'` is a list of token ids (the code reads `body["tokens"]` and takes its length).
- [ ] Run the client against the server. Save the snippet as `/tmp/lcd-t2/llama.py` (not committed) and run `uv run python /tmp/lcd-t2/llama.py`:

```python
import asyncio
from archon_search.llm_client.llama_cpp_client import LlamaCppClient

async def main() -> None:
    client = LlamaCppClient(model="local", base_url="http://localhost:8080")
    window = await client.probe_context_window(5.0)
    print("window:", window.size, window.source.value)
    template = "The quick brown fox jumps over the lazy dog."  # stands in for the longest template form, retry reminder included
    budget = await client.input_budget(template, max_output_tokens=200)  # `input_budget(template, *, max_output_tokens, think=DEFAULT)`: the ceiling of the call the budget is for is required (200 = HyDE's)
    print("budget:", budget.tokens)

asyncio.run(main())
```

  Expected: `window: 4096 probed`, and `budget` equals `N_CTX - <max_output_tokens (200 here)> - <the /tokenize count of the template as the server's chat template frames it> - 4` (the 4 is `LLAMA_CPP_JOIN_SLACK_TOKENS`, added 2026-11-01 after this checklist found the 4097-token overrun at the template/query join; corrected 2026-11-01: the count is of `POST /apply-template` `{"messages":[{"role":"user","content":<template>}]}` answered `{"prompt": ...}`, that prompt then sent to `/tokenize`; the bare-text count left the framing, 29 tokens on Qwen2.5, uncounted and the next step failed; the answer space held back is the caller's own `max_output_tokens`, since 2026-11-01 (before, every call held back `ANSWER_RESERVE_TOKENS = 1024`, which is now only the description call's base ceiling); `exact_budget` in `archon_search/llm_client/budget.py`).
- [ ] The budget really fits (S11, exact arm): build a prompt of `budget.tokens` tokens by tokenizing a long text with `/tokenize`, keeping the first `budget.tokens` ids and turning them back with `POST /detokenize` (`{"tokens": [...]}` answers `{"content": "..."}`), then send template plus that prompt to `POST /v1/chat/completions` with `max_tokens` equal to the `max_output_tokens` the budget was asked for (200). Expected: HTTP 200 and `usage.prompt_tokens + 200 <= N_CTX` in the reply (observed 2026-11-01 on a query cut to exactly the budget: `prompt_tokens + 200` was `N_CTX + 1`, the template and the query are counted apart and the blank line of the empty template is one token where the same lines around a query are two; the server answers 200 and the answer can only lose its last token; the production fit (`fit_query_to_window`, 90 to 100 percent of the budget) stayed 78 inside) (a bare 200 proves little: llama-server rejects only when the prompt alone reaches `n_ctx`). Record the difference between `usage.prompt_tokens` and `budget.tokens + <the framed template tokens above>`; it is the chat-template overhead the budget does not count and must be 0 to within the one token a `\n` join may add (observed 0 on the first run; +1 on the re-run of 2026-11-01 for a query cut to exactly the budget, see "Re-run with the per-call answer ceiling").
- [ ] Start Archon with the window read at startup. Config (plus the isolation keys of the prerequisites; truncate the log first):

```toml
[hyde]
enabled = true
provider = "llama_cpp"
model = "local"
llama_cpp_base_url = "http://localhost:8080"
```

  Expected: the server boots, the log holds no `llama_cpp: the server at ... is not reachable` line, and a `GET /props` request from Archon reached the server (otherwise the probe never ran and the missing WARNING proves nothing). Corrected 2026-11-01: llama-server 0.7.0 logs no request lines at all, not even with `--verbose`; point `llama_cpp_base_url` at a small recording proxy that forwards to the server (a 15-line scratch script that forwards every request and prints its method and path) for this step.

- [ ] Failure arm (S8): stop `llama-server`, restart Archon with the same config. Expected: it still boots and the log holds exactly one WARNING for that server, from the logger `archon_search.llm_client.llama_cpp_client`: `llama_cpp: the server at localhost:8080 is not reachable (<reason>); requests to it fail until it answers, and where its context window could not be read, 4096 tokens are assumed` (`ASSUMED_CONTEXT_TOKENS = 4096`; the label is the lower-cased host and the port only (`the configured host` for a value with an `@` outside its authority), the reason is the failing request's own one-line cause, here `cannot connect to the llama-server`). Changed after this checklist was written: the context-window lookup, the startup `llama_cpp_ok` probe (earlier `llama-server unreachable at http://localhost:8080: ...`, which asks every server an enabled feature uses and ignores a disabled section) and, with `[description]` on `llama_cpp`, the description probe all report a down server through that one text and one key per `host:port` label, so no second line is expected for one server (`LOCALHOST:8080` and `localhost:8080` are one label; `localhost` and `127.0.0.1` are two, and a second server on another host or port gets its own WARNING too). A log filter keyed on `archon_search.model_validation` or `archon_search.server.description_backfill` no longer sees this line.

**Pass criterion:** the `/props` value equals the window the client reports (`probed`), the client budget matches the arithmetic above to the token, a prompt of exactly the budget is accepted, and the failed probe logs the one `is not reachable` WARNING (which says that where the window could not be read it assumes 4096).

## 2 — Estimate margin on real text (S11)

**Why manual:** needs a real Ollama tokenizer. The unit tests stub the gpt2 counter and the fake Ollama server reports no token counts at all, so only a real model shows whether the 20% margin covers the difference between the token estimate and what Ollama actually counts.

**Rule under test:** for an `ollama` feature the budget is `(window - max_output_tokens - 64) // 1.2 - estimate_of_template` in estimate tokens (`64` is `OLLAMA_CHAT_FRAMING_TOKENS`, real chat-template tokens held back before the division, added 2026-11-01; `max_output_tokens` is the caller's own ceiling: 200 for HyDE, 150 per variant for RAG Fusion, since 2026-11-01; it was a fixed 1024 before) (`OLLAMA_ESTIMATE_MARGIN = 0.20` in `archon_search/constants.py`, `estimated_budget` in `archon_search/llm_client/budget.py`, the estimate is `TokenCounter.count`). The margin is sufficient when the real count of any input is at most 1.2 times its estimate; the template is counted once with the same estimate and must satisfy the same bound.

**Steps:**
- [ ] Prepare one file per text class under `/tmp/lcd-t2/`, each long (about 3000 gpt2 tokens; short samples distort the ratio): `english.txt` (prose), `python.txt` (source code, for example a few concatenated modules of this repository), `hungarian.txt`, `chinese.txt`, `japanese.txt`, `emoji.txt` (emoji-dense), `digits.txt` (digit-heavy: tables, hashes, numbers).
- [ ] Models: at least three families. Run 2026-11-01: `llama3.1:8b` (llama BPE), `qwen2.5:1.5b` (qwen2, pulled for this run; `qwen3.6:35b-a3b-128k` is a 23 GB load and shares the family), `gemma3:1b` (gemma, pulled) and `tinyllama` (Llama 2 sentencepiece, pulled; its window is 2048, so use 600-token samples: longer digit and emoji samples are truncated by Ollama and read falsely low, `prompt_eval_count` identical across classes is the tell). Per-digit tokenizers were the worst case on `digits.txt` (1.68x plain gpt2).
- [ ] For each file get the estimate the server uses (`TokenCounter.count`, `archon_search/llm_client/token_counter.py`; the pinned gpt2 `tokenizer.json` downloads on first use). Since 2026-11-01 it is gpt2 plus a surcharge for digits and astral-plane characters; also record the plain gpt2 count (`load_gpt2_tokenizer().encode(text, add_special_tokens=False).ids`) to see the surcharge:

```bash
uv run python -c "import sys; from archon_search.llm_client.token_counter import TokenCounter; print(TokenCounter().count(open(sys.argv[1], encoding='utf-8').read()))" /tmp/lcd-t2/english.txt
```

- [ ] For each file and model get the real Ollama count with a raw prompt (no chat template), a one-token answer and a context large enough for the file:

```bash
jq -n --rawfile p /tmp/lcd-t2/english.txt '{model:"llama3.1:8b", prompt:$p, raw:true, stream:false, keep_alive:0, options:{num_predict:1, num_ctx:16384}}' | curl -s localhost:11434/api/generate -d @- | jq '{prompt_eval_count, prompt_eval_cached_count: (.prompt_eval_cached_count // null)}'
```

  The first token (BOS) may add 0 or 1; ignore it. `keep_alive:0` unloads the model so no prefix is reused; if `prompt_eval_count` is missing, repeat the call. Truncation guard: if `prompt_eval_count` is close to the effective context (the smaller of `num_ctx` and the model maximum), Ollama truncated the prompt and the ratio is falsely low; shorten the file and repeat.
- [ ] Template overhead probe: send a one-word user message through `/api/chat` (`{"model":"llama3.1:8b","messages":[{"role":"user","content":"hi"}],"stream":false,"options":{"num_predict":1}}`) and read `prompt_eval_count`; subtract the raw count of `hi` from `/api/generate`. This is the chat-template cost Ollama adds; the budget holds back `OLLAMA_CHAT_FRAMING_TOKENS` = 64 for it (real tokens, taken off the window before the margin division since 2026-11-01); record it and check it stays below 64.
- [ ] Compute `ratio = ollama_count / estimate` per file and model (and `ollama_count / gpt2_count` for the record).
- [ ] The budget really fits (S11, estimated arm). Save the script as `/tmp/lcd-t2/ollama_budget.py` and run `uv run python /tmp/lcd-t2/ollama_budget.py english` and again with `digits` (it needs the two files of this item; the window is 4096 so a 3000-token file is cut):

```python
import asyncio, json, sys
from archon_search.hyde import HYDE_PROMPT_TEMPLATE
from archon_search.llm_client.ollama_client import OllamaClient
from archon_search.llm_client.token_counter import TokenCounter, load_gpt2_tokenizer

MODEL, WINDOW = "llama3.1:8b", 4096
client = OllamaClient(model=MODEL, base_url="http://localhost:11434", context_tokens=WINDOW)
budget = asyncio.run(client.input_budget(HYDE_PROMPT_TEMPLATE, max_output_tokens=200)).tokens  # HyDE's own ceiling; default think (the estimate ignores think)
counter, tokenizer = TokenCounter(), load_gpt2_tokenizer()
ids = tokenizer.encode(open(f"/tmp/lcd-t2/{sys.argv[1]}.txt", encoding="utf-8").read(), add_special_tokens=False).ids
lo, hi = 0, len(ids)  # the longest gpt2-token prefix whose estimate is within the budget (callers measure with the estimate)
while lo < hi:
    mid = (lo + hi + 1) // 2
    if counter.count(tokenizer.decode(ids[:mid])) <= budget:
        lo = mid
    else:
        hi = mid - 1
cut = tokenizer.decode(ids[:lo])
print("budget:", budget, "estimate of cut:", counter.count(cut), "gpt2 tokens in cut:", lo)
body = {"model": MODEL, "stream": False, "keep_alive": 0, "options": {"num_ctx": WINDOW, "num_predict": 1},
        "messages": [{"role": "user", "content": HYDE_PROMPT_TEMPLATE.format(query=cut)}]}
json.dump(body, open("/tmp/lcd-t2/ollama_body.json", "w"))
```

  Then `curl -s localhost:11434/api/chat -d @/tmp/lcd-t2/ollama_body.json | jq .prompt_eval_count` (the client sends `/api/chat`, so the chat template is included). Expected: `prompt_eval_count + 200 <= 4096` (HyDE's own answer ceiling; the budget above was asked for it) and no truncation (no `truncating input prompt` line in `~/.ollama/logs/server.log`). Template check (corrected 2026-11-01): the raw `/api/generate` count of the empty-query `HYDE_PROMPT_TEMPLATE` against its estimate must be at most 1.2 (observed 0.78 to 1.03); the same text through `/api/chat` also carries the chat framing of the template probe above (9 to 33 tokens, Qwen 29), which the budget holds back as `OLLAMA_CHAT_FRAMING_TOKENS` = 64 since 2026-11-01 (before, the old 1024 reserve absorbed it, at least 387 tokens beyond it): record it as an absolute number and check the at-budget call leaves room for it (see "Re-run with the boundary allowances" in the Results).

**Pass criterion:** for every text class and every model tried, `ollama_count <= 1.2 * estimate` where the estimate is `TokenCounter.count` (corrected 2026-11-01: the first run measured against the plain gpt2 count and failed, see Results; the estimate now adds the digit and astral-plane surcharges), and the at-budget prompts fit. A ratio above 1.20 for any class is a failure: record the class, the model and the ratio, and fix the estimate or the margin with tests. A ratio below 1.0 only means the estimate is conservative and is not a failure.
