# Feature Brief: Server-Side Multi-Collection Search Primitive (B3 — item 8)

> **Order**: Ships AFTER A1 (metadata schema — `SearchResult` already grown), A3 (search-failure semantics — per A3, once `/search` returns HTTP 500 on pipeline failure, B3 inherits that contract, with 503 reserved for meta-lookup failures; today `/search` still returns 200-with-empty on pipeline failure, `routes_search.py:94-96`), and A4 (explain endpoint — B3 reuses A4's `MultiCollectionRouter.rank_with_scores()` and the `ScoredSearchCandidate` trace path). Lands in Phase B after B1 (per-stage timings) so the new fan-out is observable from day one. B3 changes the cross-collection merge/ranking, so — by the same principle as roadmap sequencing rule 2, which eval-gates ranking changes (rule 2 enumerates items 9–11, 14, 19, 31; B3 is item 8 and not in that explicit list, but the merge change is squarely ranking-affecting) — it is **gated by the eval harness** (`tests/eval/`), specifically the *deterministic* harness, which runs independently of B6's production-model eval lane, so B6 is **not** a prerequisite.

## Problem
A query that should draw from several collections cannot be served in one server-side call. Today the only search primitive is single-collection: `SearchPipeline.search(query, collection, namespace)` embeds the query once via `self._embedder.embed_one(query)`, calls `self.store.hybrid_search(collection, vector, query, top_k=self._top_k_retrieve)` against **one** collection, applies the ACL filter, and runs **one** rerank pass (`pipeline.py:317-324`). REST `/search` (`routes_search.py:17`, `SearchRequest.collection: str`) and the MCP `search` tool (`mcp.py:48-55`, single `collection: str | None`) both expose only this single-collection shape. The `/route` endpoint (`routes_route.py:63`) tells a caller *which* collections are relevant but does not search them.

The consequence is that any multi-collection query is assembled **client-side**: the caller loops, issuing one `/search` per collection. That has three costs:

1. **Redundant embedding.** Each `/search` re-embeds the identical query string — `embed_one` has no cache (`embedder.py:66-68`) — so an N-collection query pays N forward passes for one vector.
2. **No global ranking.** Each collection is reranked in isolation (`reranker.rerank` runs per `/search` call), then the client must stitch the N result sets together. The per-collection RRF `score` is rank-based within one collection's candidate pool (`_rrf_score(rank) = 1/(60 + rank + 1)`, `store.py:66`; ranks are local `enumerate` positions, `store.py:656,664`) and is therefore **not comparable across collections** — a top-1 in a 3-chunk collection and a top-1 in a 30 000-chunk collection both score `1/61`. The client has no sound way to merge them.
3. **No debuggable routing path.** Because the fan-out lives in the client, `/explain` (A4) can only explain a single pinned collection; it cannot show why collection X out-contributed collection Y for a multi-collection query.

The cross-encoder reranker is already collection-agnostic — it scores `(query, candidate.text)` pairs and returns a globally sorted slice (`reranker.py:49-67`) — and the internal `ScoredSearchCandidate` diagnostic type already carries a `collection` field plus a full `SearchScoreBreakdown` (`_diagnostics.py:44-65`). But the pieces do not yet compose into a production fan-out, and wiring them is a genuine type-unification refactor, not glue. There are **two diverging candidate type systems** today: production `SearchPipeline.search()` → `store.hybrid_search()` returns plain `SearchResult` (no rank provenance, no `collection`, `_types.py:64-75`) and is reranked by `reranker.rerank(list[SearchResult])` (`reranker.py:49-51`); the provenance-carrying `ScoredSearchCandidate` only flows through `_hybrid_search_with_trace`, which is explicitly marked **"private, eval/debug-only ... must NOT appear in the public exports"** (`store.py:921-924`) and is reranked by the separate `_rerank_with_trace(list[ScoredSearchCandidate])` (`reranker.py:69-`). B3's correct server-side merge needs the provenance path (`collection` + `score_breakdown`) on the **production** hot path — so the real work is promoting the trace-style candidate path to production and **unifying** the two rerank surfaces, not merely calling existing functions.

## Goal
B3 ships a server-side multi-collection search **primitive**: embed the query **once**, fan out hybrid retrieval across an explicit set of collections **in parallel**, merge the candidate pools into one provenance-tagged set, and run **one** global rerank pass — returning a single unified, ranked result list in which each result is tagged with the collection it came from. Success is observable as:

- (a) A `/search` request carrying `collections: ["a", "b", "c"]` (mutually exclusive with the singular `collection`) returns one merged, reranked result list; each result reports a `collection` field naming its origin.
- (b) The query embedding is computed exactly once for the whole request, regardless of collection count (asserted by a spy/mock on `embed_one`).
- (c) Reranking is one pass over the **merged** candidate pool, not per collection (asserted by a spy on the candidate-based rerank call count == 1). On `/search` (and MCP `search`) reranking is **unconditionally on** — B3 adds no `rerank` toggle to those surfaces (see Out of Scope), so there is no `rerank=false` to reject there. The `rerank=false`+multi → 422 guard lives **only on `/explain`** (A4's surface, which is the only one that exposes `rerank: bool`), because the explain merge would otherwise be unsound (see Key Decisions).
- (d) Collections outside the caller's namespace, or whose `embedding_model` differs from the single server embedder's model (and thus whose vectors would be wrong-dimension or wrong-space), are excluded from the fan-out (the latter is a documented C1 boundary, not a silent wrong-vector search).
- (e) The MCP `search` tool accepts the same `collections` list and tags results identically.
- (f) `/explain` (A4) renders multi-collection provenance — which collection each candidate came from and its per-stage breakdown — through the shared `ScoredSearchCandidate` path.
- (g) The eval harness still passes against `tests/eval/baselines/baseline.json` (B3 adds a multi-collection **merge** fixture that exercises merge correctness over a **fixed** collection set — not routing selection, which is B4's concern; thresholds unchanged unless waived per `tests/eval/README.md`).
- (h) The 85% coverage gate holds on the default pytest run.

## Users & Context
- **REST/MCP integrators** building assistants that span multiple corpora (e.g. "code" + "docs" + "tickets") and today pay N round-trips and N embeddings, then merge results with an unsound rank-based heuristic.
- **The decomposer / routing layer** (consumer of `/route`, `routes_route.py`): once a set of collections is chosen, B3 is the single call that actually searches them. B3 is the execution half of the routing story whose selection half already exists.
- **Maintainers tuning ranking**, who need the merge + rerank to be visible through `/explain` (A4) rather than buried in client loops.
- **B4 (stronger routing)**, which will produce better collection shortlists; B3 is the primitive B4's output feeds into. B3 deliberately does **not** own the "which collections" intelligence (see Out of Scope).

Triggered whenever a query's relevant content is spread across more than one collection — the common case for any non-trivial knowledge base.

## Core Flow
1. **Request.** Caller sends `POST /search` with **either** `collection: str` (existing single-collection path, unchanged) **or** `collections: list[str]` (new, 1–`MAX_FANOUT` entries, deduplicated, each validated non-empty). Supplying both is a 422 validation error. MCP `search` gains the same optional `collections` parameter with identical exclusivity. `top_k` semantics are unchanged.
2. **Resolve + scope.** The handler loads collection metadata via `store.get_all_collections_meta()` (already used by `/route`, `routes_route.py:88`) and keeps only collections whose `CollectionMeta.namespace` equals the caller's `request.state.namespace` — the same namespace-scoping rule `/route` applies (`routes_route.py:89`). This metadata lookup is a *meta-lookup*, not a pipeline stage: if it fails, the request returns **HTTP 503** (per A4's taxonomy, mirroring `/search` at `routes_search.py:80-83`), distinct from the HTTP 500 a leg/pipeline failure returns. **Precedence of checks (see Edge Cases):** existence/namespace validation runs **first** — a **whole-request strict 404** fires if *any* requested name is missing-or-out-of-namespace (so a mixed request of valid + cross-namespace + model-mismatch resolves to strict 404, never a partial success). Only once **all** requested names are confirmed present-and-in-namespace does model-mismatch exclusion (HTTP 200 + `excluded_collections`) apply. A requested collection that is missing or out-of-namespace therefore **returns an identical 404 whether the name does not exist at all or exists only in another namespace** — the two cases must be indistinguishable so a caller cannot probe cross-namespace existence (`get_collection_meta` already filters by namespace, `store.py:339`). Collections whose `embedding_model` differs from the single server embedder's `model_name` are **excluded** and reported (mirrors the router's existing treatment of mismatched models as unscored, `router.py:142`); true cross-model search is deferred to C1. The implementable gate is **`embedding_model` name-equality only**: `CollectionMeta` carries `embedding_model` (`collection_meta.py:19`) but **no `embedding_dim`** — the per-collection dimension lives only in the LanceDB Arrow schema (`store.py:188`), which resolve+scope never reads — so name-equality is the actual gate. Under the single-`Embedder` invariant (exactly one embedder today), name-equality *implies* dimension-equality, and a genuine wrong-length vector would additionally error per-leg inside `table.vector_search` (defense in depth, not the primary gate). C1 will add a stored `embedding_dim` when multiple models coexist (see Key Decisions). Embedding once before the fan-out also initializes `embedder.embedding_dim` (the property raises until the first `embed()`, `embedder.py:53-56`).
3. **Embed once.** `SearchPipeline.search_many(query, collections, namespace)` (new) calls `self._embedder.embed_one(query)` exactly once and reuses the resulting vector for every collection leg.
4. **Fan out in parallel.** For each in-scope collection, the pipeline runs the hybrid retrieval leg concurrently inside a single `asyncio.TaskGroup` (Python 3.12 structured concurrency; the repo is `>=3.12`), passing the **shared** query vector. TaskGroup is chosen over bare `asyncio.gather` precisely because if any leg raises, the TaskGroup **cancels the surviving siblings** before propagating — so no detached leg keeps a LanceDB handle open after a failure (see Edge Cases). Each leg produces `ScoredSearchCandidate` objects (carrying `collection` + `score_breakdown`), fetching its local candidate pool (the existing `max(top_k * 3, 20)` amplification per leg, `store.py:652`). A **whole-fan-out** timeout (config) wraps the entire fan-out — `asyncio.wait_for` around the TaskGroup — and exceeding it fails the whole request with **HTTP 504** (following `/route`'s whole-operation-timeout precedent: `asyncio.wait_for` around the entire operation → 504, `routes_route.py:94-101,122-135`) rather than blocking on the slowest leg or returning a silent partial result. A per-leg budget is a Future Iteration (it pairs with relevance-aware leg budgeting).
5. **Merge with provenance + trim.** Before merging, each leg is trimmed to its top-N by local RRF (N a config knob, decoupled from `MAX_FANOUT`) so the merged pool stays bounded. The trimmed legs' candidate pools are then concatenated into one pool, each candidate retaining `collection` provenance. RRF scores from different collections are **not** compared, re-fused, or sorted directly: per-leg `vector_rank`/`fts_rank` are *local* `enumerate` positions within their leg (`store.py:656,664`), so a rank-0 in collection A and a rank-0 in collection B both score `1/61` — re-running RRF over their union would reproduce exactly the cross-collection incomparability the Problem section condemns. Cross-collection ordering is therefore deferred entirely to the reranker, the only sound global comparator. (Reranking on `/search` is unconditional, so there is no `rerank=false` merge path to define here; the only surface exposing a `rerank` toggle is `/explain`, where a `rerank=false`+multi request is rejected — see step 6.) **Recall ceiling:** the per-leg local-RRF trim is a hard recall ceiling — the reranker only ever sees the survivors of the trim and cannot recover candidates dropped before merge, so the "reranker is the sole sound comparator" claim holds only *within the trimmed pool*. N must therefore be set generously relative to `top_k_return`; relevance-aware leg budgeting (Future Iterations) is the principled fix.
6. **One global rerank (unconditional on `/search`; guarded on `/explain`).** A single candidate-based rerank pass — the same path A4 uses for `/explain`, taking `list[ScoredSearchCandidate]` — scores the merged pool against `(query, candidate.text)` and returns the unified top-`top_k_return` (collection-agnostic by construction, `reranker.py:55-56`). On `/search` (and MCP `search`) reranking is **always on**: those surfaces expose no `rerank` toggle (B3 does not add one — see Out of Scope), so there is nothing to disable and no 422 to raise there. The merge is sound by construction because the reranker is the only cross-collection comparator. The `rerank=false`+multi → **422 guard applies only on `/explain`**, which is the sole surface exposing `rerank: bool` (introduced by A4): `/explain` with multiple `collections` + `rerank=false` is a **422 validation error** ("reranking cannot be disabled for multi-collection search in v1"), because without the reranker the explain merge would have no sound cross-collection comparator. ACL filtering runs on the merged pool **before** rerank, against the caller's namespace, using the existing `apply_acl_filter` helper (`pipeline.py:322`) over A4's candidate-level `acl` field on `ScoredSearchCandidate` — so `/search` and `/explain` share **one** ACL pass over the same merged candidate pool, not two divergent ACL surfaces. `acl_filtered: bool` reflects whether anything was dropped across the whole pool. The surviving top-`top_k_return` candidates are then converted to `SearchResult` (now carrying `collection`) for the response.
7. **Response.** `SearchResult` gains a `collection: str` field; `SearchResultSchema` (`routes_search.py:39`) mirrors it; the MCP `asdict()` payload surfaces it automatically. The response shape is `SearchResponse{results, acl_filtered, excluded_collections}` — the existing `results` + `acl_filtered` plus the additive `excluded_collections` (names + reason for model-mismatch exclusions; empty list for single-collection or all-compatible requests). `acl_filtered` is a single pool-wide boolean in v1: it tells the caller that *something* was ACL-dropped, not *where* (an accepted simplification; per-collection `acl_filtered` is a Future Iteration). Whole-collection exclusion (model mismatch) is read from `excluded_collections`, **not** from `acl_filtered`. Per the strict-404 decision, no `skipped_collections` field exists in v1; one would appear only if the deferred lenient mode is ever adopted (see Open Questions). For a single-collection request, `collection` is simply that one collection's name on every result and `excluded_collections` is empty (no behavior change beyond the new fields).
8. **Explain co-design.** `/explain` (A4) consumes the same `search_many` merge path: its near-miss + result breakdowns are built from the provenance-tagged `ScoredSearchCandidate` pool, so the routing path (which collections, per-collection centroid score via A4's `rank_with_scores()`, per-candidate origin) is debuggable end-to-end.

## In Scope
- **Type-unification (the core refactor)**: B3 promotes a trace-style candidate path to the **production** fan-out and unifies the two diverging candidate/rerank type systems (Problem). Concretely: the fan-out legs produce `ScoredSearchCandidate` (carrying `collection` + `score_breakdown`); the merged pool is reranked via the **candidate-based** rerank path (the same `list[ScoredSearchCandidate]` path A4 introduces for `/explain`); the surviving top-`top_k_return` candidates are converted to `SearchResult` (now with `collection`) for the response. This **relaxes the current eval/debug-only boundary** on `_hybrid_search_with_trace` (`store.py:921-924`) — either by extracting a shared production helper from it or by promoting it — and **unifies** the `SearchResult`-based `reranker.rerank` (`reranker.py:49-51`) and the `ScoredSearchCandidate`-based `_rerank_with_trace` (`reranker.py:69-`) into one production-grade candidate rerank surface. **Blast radius onto already-shipped A4 code (acknowledged):** because B3 ships AFTER A4, this is partly a *retroactive* refactor of A4's shipped code — A4's `SearchPipeline.explain()` calls `store.hybrid_search_with_trace` + `reranker._rerank_with_trace` by their current signatures, and `eval/_tracing.py:102,107` call `_hybrid_search_with_trace` and `reranker._rerank_with_trace` by exact signature. B3 must migrate **both** the A4 `explain()` call sites **and** `eval/_tracing.py` to the unified surface **in the same commit** (commit 2), pinning the new unified helper/rerank signature, or it breaks them. The "co-design with A4" is therefore partly retroactive. **Production cost of promoting the trace path:** the trace path allocates a per-candidate `SearchScoreBreakdown`; promoting it to production puts that allocation on *every* production search. Mitigate by keeping raw-score / breakdown capture **lazy/optional** so single-collection `/search` does not pay for breakdowns it discards; B1's per-stage timings quantify the residual cost. It is **in scope** and lands as its own commit (see Stacking Order).
- **New pipeline primitive** `SearchPipeline.search_many(query: str, collections: list[str], namespace: str = DEFAULT_NAMESPACE) -> SearchPipelineResult`: embed once, parallel fan-out (producing `ScoredSearchCandidate` legs), merge, single mandatory rerank, convert to `SearchResult`. The existing single-collection `search()` is folded into `search_many(query, [collection], namespace)` **only if** the **retrieval-stage** tie-break between the production retrieval sort (`store.py:687`, score-desc, no explicit tie-break — relies on stable sort / dict-insertion order) and the candidate/trace retrieval sort (`store.py:1027`, `(-rrf_score, chunk_id)`) is first reconciled to a single explicit `(-score, chunk_id)` rule **and** the single-collection observable contract holds (identical result set + ordering, modulo the new `collection` field — see the equality contract below); otherwise `search()` stays as-is and shares helpers. Note this reconciliation is purely at the **retrieval** stage; the **rerank** sort stays stable (input-order-preserving, `reranker.py:67` / `reranker.py:99-100`) and gains **no** secondary tie-break key — multi-collection rerank determinism comes from a deterministically-ordered merge *input*, not a new rerank tie-break (see Edge Cases "Determinism"). The single-collection eval baseline must not move.
- **Parallel fan-out** via a single `asyncio.TaskGroup` (Python 3.12 structured concurrency) over per-collection hybrid-retrieval legs, each receiving the **one** shared query vector. Any leg raising cancels the siblings and the request returns HTTP 500 (per A3); no detached leg outlives the request holding a LanceDB handle. Bounded concurrency (`MAX_FANOUT`, default proposed in Open Questions) caps simultaneous LanceDB table opens.
- **Whole-fan-out timeout**: a single timeout (config value) wraps the entire fan-out via `asyncio.wait_for` around the TaskGroup; exceeding it fails the whole request with **HTTP 504** ("search timed out"), never a silent partial result — following `/route`'s whole-operation-timeout precedent (`routes_route.py:94-101,122-135`) and A3. A per-leg budget is deferred to a Future Iteration (it pairs with relevance-aware leg budgeting).
- **Per-leg pool trimming + decoupled rerank cap**: each leg keeps only its top-N by local RRF (N a config knob) **before** merge, so the merged rerank pool is bounded and grows sub-linearly in collection count instead of `MAX_FANOUT * max(top_k*3, 20)`. The rerank-pool cap is an explicit config value, **decoupled from `MAX_FANOUT`**. Known constraint (forward-noted, not solved in v1): the single cross-encoder `Reranker` instance reranks on one thread (`asyncio.to_thread`, `reranker.py:56`), so concurrent multi-collection requests serialize at that instance; B1's per-stage timings make this measurable, and relevance-aware leg budgeting is a future option.
- **Provenance**: extend `_types.SearchResult` with `collection: str`; populate it at the single row-to-`SearchResult` site (`store.py:694-708`) — which `search_with_context` also flows through — and in the candidate→`SearchResult` conversion at the end of the merge. `ScoredSearchCandidate.collection` already exists and is reused unchanged.
- **Cross-collection merge semantics**: the reranker is the sole global comparator. Per-collection RRF scores are never compared, re-fused, or sorted across collections (they live in incomparable local rank spaces). On `/search` (and MCP `search`) reranking is therefore **unconditionally on** — there is no `rerank` toggle on those surfaces (B3 adds none; see Out of Scope), so the merge is always sound and there is nothing to reject. The `rerank=false`+multi → **422 validation error** lives **only on `/explain`** (A4's surface — the only one exposing `rerank: bool`), where disabling rerank for a multi-collection request would leave the merge with no sound cross-collection comparator. A sound `rerank=false` fan-out path is deferred (see Future Iterations), not shipped.
- **Namespace scoping**: fan-out restricted to collections in the caller's namespace, reusing the `/route` rule (`routes_route.py:89`). Missing vs. out-of-namespace requested collections return an **identical** 404 (no cross-namespace existence leak).
- **Embedding-model gating**: collections whose `embedding_model != embedder.model_name` are excluded and surfaced (count + names) rather than searched with an incompatible vector. The gate is on **`embedding_model` name-equality only** — `CollectionMeta` carries `embedding_model` (`collection_meta.py:19`) but **no `embedding_dim`** (the per-collection dim lives only in the LanceDB Arrow schema, `store.py:188`, which resolve+scope does not read), so the name check is the actual gate. Under the single-`Embedder` invariant name-equality implies dimension-equality, and a genuine wrong-length vector additionally errors in `table.vector_search` (defense in depth). C1 will add a stored `embedding_dim` when multiple models coexist. This is the explicit C1 boundary.

## Out of Scope
- **Collection selection intelligence ("which collections to fan out to")** — that is the router's job. B3 consumes an **explicit** `collections` list (or, optionally, the existing router shortlist passed in by the caller). Smarter selection — summary embeddings, multi-centroid, description-aware routing — is **B4**. B3 is the execution primitive, not the routing brain.
- **Cross-model multi-collection search** — collections with differing `embedding_model` cannot share one query vector. B3 **excludes** mismatched-model collections and reports them; honoring per-collection models (re-embedding per model, or routing by model) is **C1**.
- **Server-side auto-routing on `/search` when no collection is given** — B3 does not change the "collection required" contract. A future item may let `/search` call the router itself; B3 keeps the caller explicit. (Open Question retained.)
- **Streaming / partial-results delivery** for large merged pools — **E1**.
- **HyDE / query expansion (C4) and RAG Fusion / multi-query (C5)** — those expand the *query*; B3 expands the *collection set*. Orthogonal; B3 must not pre-build their hooks.
- **Stronger / incremental centroids (B5, CON-4)** and **production-model eval lane (B6)** — separate Phase B items; B3 only consumes centroids if the caller routed via them.
- **New auth / ACL model** — B3 reuses `apply_acl_filter` and the existing namespace map; per-collection ACL policy is **E4**.
- **`MAX_FANOUT` as a tunable per-request override** — v1 ships a single config-level cap; per-request tuning is deferred unless an Open Question resolves otherwise.
- **Deduplicating the *same document* indexed into multiple collections** — if a doc lives in two collections, both copies may surface. Cross-collection content de-dup is a ranking-quality follow-up, not B3.
- **A `rerank` toggle on `/search` or MCP `search`** — B3 does **not** introduce one; reranking on those surfaces is unconditional (existing behavior, `pipeline.py:323`). The only surface exposing `rerank: bool` is `/explain` (A4), where `rerank=false`+multi is a 422. A sound no-reranker multi-collection path is a Future Iteration.

## Key Decisions
- **The reranker is the cross-collection comparator, not RRF.** Per-collection RRF scores share no scale (rank-based, local pool), so merging on RRF float is unsound. The cross-encoder scores `(query, text)` relevance independent of collection (`reranker.py:55-56`), making it the only sound global ordering when `rerank=true` (the default). This is the central design choice and the reason multi-collection merge is correct rather than approximate.
- **`/search` reranking is unconditional (no toggle); the `rerank=false`+multi 422 guard lives only on `/explain`.** B3 adds **no** `rerank` parameter to `/search` or MCP `search` — reranking there is always on (existing behavior, `pipeline.py:323`), so there is nothing to disable and no 422 to raise on those surfaces (see Out of Scope). The only surface exposing a `rerank: bool` toggle is `/explain` (introduced by A4). There is no sound way to order across collections without the reranker in v1: per-leg `vector_rank`/`fts_rank` are *local* `enumerate` positions within each leg (`store.py:656,664`), so a global RRF over their union would reproduce the exact cross-collection incomparability the Problem section condemns (a rank-0 in collection A and a rank-0 in collection B both score `1/61`); a genuine global re-fusion would need raw `_distance`/BM25 `_score`, and even then BM25 is not comparable across collections because IDF depends on per-collection document frequencies. Therefore `rerank=false` combined with multiple `collections` is a **422 validation error** ("reranking cannot be disabled for multi-collection search in v1") **on `/explain`** — the only surface where the toggle exists — because without the reranker the explain merge would have no sound cross-collection comparator. A sound `rerank=false` fan-out path is possible later (see Future Iterations) but deferred.
- **Embed once, fan out parallel under structured concurrency.** One `embed_one` call, one shared vector, an `asyncio.TaskGroup` (Python 3.12; the repo is `>=3.12`) across legs — **not** bare `asyncio.gather`, whose default propagates the first exception but leaves the surviving siblings running detached (they may keep LanceDB handles open). TaskGroup cancels the siblings before propagating, so a single leg failure tears the whole fan-out down cleanly and the request returns HTTP 500 (per A3). This is the headline efficiency win and the literal roadmap text ("embed the query once; one merge + rerank pass").
- **Explicit collections in, routing intelligence out.** B3 is a *primitive*. It takes the collection set as input; B4 decides the set. This keeps B3 shippable without waiting on routing improvements and keeps the eval story clean (merge correctness vs. routing quality are tested separately).
- **Mismatched embedding models are excluded and reported, never silently searched.** A query vector from model A is meaningless against a collection embedded with model B. The server has **exactly one `Embedder`** today (`embedder.model_name`), so "the query embedder's model" is unambiguous — state that invariant explicitly, because C1 (per-collection model) will break it. The implementable gate is **`embedding_model` name-equality only**: `CollectionMeta` carries `embedding_model` (`collection_meta.py:19`) but **no `embedding_dim`** — the per-collection dimension lives only in the LanceDB Arrow schema (`store.py:188`), which resolve+scope never reads — so the name check is the actual gate. Under the single-`Embedder` invariant, name-equality *implies* dimension-equality; a genuine wrong-length vector would additionally error per-leg inside `table.vector_search` (defense in depth, not the primary gate). C1 will add a stored `embedding_dim` to `CollectionMeta` when multiple models coexist. B3 surfaces the exclusion (count + names) so callers aren't surprised by missing collections; honoring those collections is explicitly C1. Mirrors the router's existing `embedding_model` guard (`router.py:142`).
- **Grow `SearchResult` with `collection`, mirror it in `SearchResultSchema`.** Provenance is the difference between a usable merged list and an opaque one. The field-parity test (introduced in A1) is extended so REST and MCP cannot silently diverge on it.
- **REST additive, MCP breaking — distinguish in `BREAKING.md`.** Same posture as A1: tolerant JSON clients see a new key; strict MCP clients see a shape change. The new `collections` request field is additive on both.
- **Single-collection path is sacrosanct (equality contract: identical except `collection`).** `/search` with `collection:"x"` must return the **same result set and ordering** as today, **except** for the additive `collection` field — a **field-subset equality** test, *not* byte-for-byte (byte-for-byte is unachievable once the new field is added). Because C2 routes the fan-out through the candidate/trace path, and the production *retrieval* sort (`store.py:687`, score-desc with no explicit tie-break — relies on stable sort / dict-insertion order) diverges from the trace *retrieval* sort (`store.py:1027`, `(-rrf_score, chunk_id)`), folding `search()` into `search_many(query, [collection])` is allowed **only if** the **retrieval-stage** tie-break is first reconciled to a single explicit `(-score, chunk_id)` rule **and** the field-subset equality holds. This reconciliation is purely at the **retrieval** stage. The **rerank** sort stays **stable** (input-order-preserving, `reranker.py:67` / `reranker.py:99-100`) and gains **no** secondary tie-break key — adding a `(collection, chunk_id)` rerank tie-break would invalidate the stable-sort contract pinned by `tests/test_reranker.py::test_P14_6_reranker_stable_order_on_equal_scores` (and the trace-path stable-order test) and would move single-collection ordering on rerank-score ties. Multi-collection rerank determinism instead comes from a deterministically-ordered merge *input* (see Edge Cases "Determinism"), not a new rerank tie-break. If the retrieval tie-break is not reconciled, `search()` **stays separate** and shares helpers. The eval single-collection baseline is the guardrail and must not move.
- **Partial failure leans on A3.** A pipeline-stage failure on any leg fails the whole request with **HTTP 500** + standard error envelope (A3/A4's contract: pipeline-stage failures return 500; 503 is reserved for meta-lookup failures only), not a 200 with a quietly shorter result set — silent partial success is exactly the bug A3 closes. A failure in the **resolve+scope metadata lookup** (`store.get_all_collections_meta()`) is the 503 case, mirroring the existing `/search` handler (`routes_search.py:80-83`). A *requested* collection that is missing or out-of-namespace is a request-shape problem (strict 404), handled separately (see Edge Cases) — and the 404 reason/shape is **identical** whether the name is genuinely nonexistent or merely lives in another namespace, so the response never leaks cross-namespace existence (`get_collection_meta` already filters by namespace, `store.py:339`).
- **Co-design with A4, don't fork it.** `/explain` and `/search` share the `search_many` merge + the `ScoredSearchCandidate` provenance path. One merge implementation, two surfaces — so explainability tracks search behavior automatically.

## Edge Cases & Constraints
- **One leg fails (store/pipeline error).** Whole request fails with **HTTP 500** + standard error envelope, consistent with A3/A4 (`/search` must not return 200-with-empty on pipeline failure; pipeline-stage failures are 500, never 503). Because the fan-out runs in an `asyncio.TaskGroup`, the failing leg's exception causes the TaskGroup to **cancel the surviving sibling legs** before propagating — no detached leg outlives the request holding a LanceDB handle (this is precisely why TaskGroup is chosen over bare `asyncio.gather`, whose default leaves siblings running). Rationale: a silently-dropped collection produces a plausible-but-wrong result set — the worst failure mode for a search system. Tested by injecting a store failure on one leg and asserting the siblings are cancelled (not left running) and the request returns 500.
- **A leg is too slow (timeout).** A **whole-fan-out** timeout (config value) wraps the entire fan-out — `asyncio.wait_for` around the TaskGroup — and exceeding it fails the whole request with **HTTP 504** ("search timed out") — never a silent partial result — following `/route`'s whole-operation-timeout precedent (`asyncio.wait_for(..., timeout=30.0)` around the entire operation → 504, `routes_route.py:94-101,122-135`) and A3. Without this, the embed-once/parallel win evaporates because the request blocks on the slowest leg. A per-leg budget is deferred to a Future Iteration (it pairs with relevance-aware leg budgeting). Interaction note: a leg whose collection is mid-FTS-rebuild may be slow or degrade to vector-only (the FTS `search` either lags or raises the index-missing path, `store.py:665-670`); the timeout bounds the former and the vector-only degrade handles the latter, so neither hangs the request. Tested with an injected slow leg → 504.
- **The resolve+scope metadata lookup fails.** The `store.get_all_collections_meta()` call in Core Flow step 2 is a *meta-lookup*, not a pipeline stage. Under A4's taxonomy this is the **HTTP 503** case (service unavailable), mirroring the existing `/search` handler's 503-on-meta-lookup-failure behavior (`routes_search.py:80-83`). This is the one place B3 returns 503 rather than 500. Tested by injecting a failure in the metadata lookup.
- **A requested collection is missing or out-of-namespace.** Firm decision: the whole request is a strict 404, because the caller asked for a specific set and got a different one — silent scope reduction is exactly the failure B3 must avoid. *Not* the same as a transient leg failure. **Critically, "missing" (the name exists nowhere) and "out-of-namespace" (the name exists only in another namespace) return an identical 404 reason/shape** — the two cases must be indistinguishable so a caller cannot probe cross-namespace existence (`get_collection_meta` already filters by namespace, `store.py:339`). The response may echo the caller-supplied name(s) (the caller provided them), but it must **not** reveal whether a name exists in another namespace. The v1 response schema is fixed by this decision (no `skipped_collections` field). A lenient skip-with-warning mode is a clearly-deferred enhancement, not a live contingency (see Open Questions).
- **A requested collection has an incompatible `embedding_model`.** Excluded from fan-out, reported as `excluded_collections` (names + reason) — a non-fatal, explicit signal. Distinct from "missing": the collection exists and is in-namespace but cannot share the query vector. This is the C1 seam.
- **Same `chunk_id` across collections (expected by design).** chunk_ids are `doc_id`-derived and `doc_id` is a hash of the resolved absolute path (`pipeline.py:142,187`), so the same file ingested into two collections yields the **same** `chunk_id` in both — this is expected, not an error. The merge keys candidates by `(collection, chunk_id)`, not `chunk_id` alone, so both copies survive into the rerank pool; a guard test asserts no cross-collection dedup silently drops one. (Cross-collection *content* dedup is out of scope.) **Within a single leg**, the store already collapses a repeated `chunk_id` via a dict keyed on `chunk_id` (`store.py:673-675`), keeping one row — in the stale-row case it keeps whichever row the dict retains; the merge inherits this and does not re-dedup.
- **One collection lacks an FTS index.** That leg degrades to vector-only (existing behavior, `store.py:665-670`); the request still succeeds and the merged pool simply has weaker FTS signal for that collection. Tested.
- **Empty fan-out after scoping** (all requested collections out-of-namespace or model-mismatched). Returns the decided status — strict 404 (missing/out-of-namespace) or an empty `results` with populated `excluded_collections` and `acl_filtered: false` (model mismatch: no ACL drop occurred, so the flag is false; the exclusion is reported separately via `excluded_collections`). Clients read **whole-collection exclusion from `excluded_collections`, not from `acl_filtered`** — `acl_filtered: false` here means "no per-candidate ACL drop", which is unrelated to a collection being excluded wholesale for model mismatch. Not a 500; the pipeline did not fail.
- **`collections` of length 1.** Behaves exactly like `collection`; verified by an equality test against the single-collection path.
- **Large fan-out.** `MAX_FANOUT` caps concurrent legs to bound LanceDB table opens and embedding-pool memory; over-limit requests are 422 before any work. `MAX_FANOUT` bounds *list length*, not rerank cost — so the rerank pool is bounded **separately**: each leg is trimmed to its top-N by local RRF (N a config knob) **before** merge, and the rerank-pool cap is an explicit config value **decoupled from `MAX_FANOUT`**. The merged pool therefore grows sub-linearly in collection count instead of the naive `MAX_FANOUT * max(top_k*3, 20)` (e.g. ~160 pairs at the defaults). Known constraint (forward-noted, not solved in v1): the single cross-encoder `Reranker` reranks on one thread (`asyncio.to_thread`, `reranker.py:56`), so concurrent multi-collection requests serialize at that one instance; B1's per-stage timings make this measurable, and relevance-aware leg budgeting is a future option (see Future Iterations).
- **ACL across the merged pool.** A single `apply_acl_filter` pass over the concatenated pool against the caller's namespace; `acl_filtered` is true if any candidate from any leg was dropped. It is a **pool-wide boolean in v1** — an **accepted simplification**: it tells the caller *something* was ACL-dropped, not *where* (which collection). This loses per-collection signal that the rest of the brief's provenance theme would otherwise want; per-collection `acl_filtered` is a Future Iteration. No per-collection ACL semantics change.
- **`top_k` semantics.** Each leg fetches its local `max(top_k*3, 20)` pool (`store.py:652`), is then trimmed to its top-N by local RRF (see "Large fan-out"), and the merged trimmed pool is reranked down to `top_k_return`. The returned count never exceeds `top_k_return`, regardless of collection count — fan-out widens recall, not result-list length. Rerank cost would otherwise scale with collection count regardless of where relevance concentrates; the per-leg trimming above is what bounds it, and relevance-aware leg budgeting (spend the rerank budget where recall is strongest) is a Future Iteration.
- **Telemetry privacy.** The search telemetry entry records `fanout_collections` (a count) and collection names — the latter already permitted in route telemetry (`routes_route.py:113`) — but **never** the query. The recorded collection names fall under the **same "accepted risk" umbrella as path-derived `doc_id`s** (they may carry filesystem-derived information), consistent with how `/route` telemetry already treats collection names; this is an accepted, documented risk, not a new exposure. The no-raw-query structural invariant is preserved; no `query` parameter is added to any telemetry factory.
- **Determinism (two distinct stages — do not conflate).** Determinism is achieved at the retrieval stage and the rerank stage separately:
  - **(1) Retrieval tie-break.** The production retrieval sort (`store.py:687`, score-desc, no explicit tie-break) and the trace retrieval sort (`store.py:1027`: `candidates.sort(key=lambda c: (-c.score_breakdown.rrf_score, c.chunk_id))`) are reconciled (commit 2) to a single explicit `(-score, chunk_id)` rule. This is the retrieval RRF sort, **not** the rerank sort.
  - **(2) Rerank stays stable.** The rerank sort is and remains **stable** (input-order-preserving, `reranker.py:67` and `reranker.py:99-100`) with **no** secondary tie-break key — adding a `(collection, chunk_id)` rerank tie-break would invalidate the stable-sort contract pinned by `tests/test_reranker.py::test_P14_6_reranker_stable_order_on_equal_scores` (and the trace-path stable-order test) and would change single-collection ordering on rerank-score ties (moving the eval baseline that must not move). Instead, multi-collection rerank determinism comes from a **deterministically-ordered merge *input*** to the stable rerank: legs are concatenated in a deterministic collection order (sorted ascending by collection name), and within each leg candidates are in their reconciled retrieval order (`(-score, chunk_id)` from (1)). Feeding this deterministic order into the existing stable rerank yields deterministic output **without** any new rerank tie-break key — preserving the stable-sort contract and leaving single-collection ordering unchanged.
- **Eval coupling.** `tests/eval/` may construct `SearchResult` directly; adding `collection` requires updating those fixtures in the same PR (same hazard A1 flagged for its new fields).

## Open Questions
- **`MAX_FANOUT` default and rerank-pool cap.** `MAX_FANOUT` proposed `8`; its drivers are concurrent LanceDB table opens and embedding-pool memory. The **rerank-pool cap is a separate config value, decoupled from `MAX_FANOUT`** (because `MAX_FANOUT` caps list length, not rerank cost): each leg is trimmed to its top-N by local RRF before merge, so the merged pool is bounded by `~MAX_FANOUT * N` rather than `MAX_FANOUT * max(top_k*3,20)`. Resolve both `MAX_FANOUT` and the per-leg trim N / pool cap with a quick latency probe in planning (B1 timings make the single-thread cross-encoder cost measurable); all are single config values, not per-request, in v1.
- **Lenient skip mode for missing/out-of-namespace collections (deferred enhancement).** v1 is firmly strict 404 (no silent scope reduction); the v1 response schema is settled on that basis. A lenient skip-with-report mode — friendlier for "fan out to everything I might have" clients — would be revisited **only if integrators request it**, and would land as an additive `skipped_collections` response field with its own partial-failure tests. Like A1's `schema_version` question, this is a deferred enhancement, not a contingency that destabilizes the v1 contract.
- **Should `search()` be refactored into `search_many(query, [collection])`, or kept separate?** Only if (a) the production/trace tie-break is reconciled to one explicit `(-score, chunk_id)` rule, and (b) the single-collection observable contract holds — **identical result set and ordering except the additive `collection` field** (field-subset equality, not byte-for-byte) — and the eval baseline does not move. Planning verifies via the single-collection equality test before collapsing the two paths; if either condition fails, `search()` stays separate and shares helpers.
- **Should `/search` ever auto-route when neither `collection` nor `collections` is given?** Out of scope for B3 (keeps the caller explicit), but the hook (call the router, feed its shortlist into `search_many`) is cheap once B4 lands. Tracked as a future item, not built here.
- **Cross-collection content dedup** (same document in two collections surfacing twice). Deferred; revisit if integrators report duplicate-result complaints. Would need a content/`doc_id`-based merge key rather than `(collection, chunk_id)`.

Deferred from v1, where `rerank=false`+multi is a 422.

## Recommendation
This is the right primitive to build now: it is the execution half of a routing story whose selection half (`/route`, the router) already exists but currently dead-ends — the server can tell you *which* collections matter and then makes you search them one-by-one from the client. The hardest and most important decision is the **merge semantics**: per-collection RRF scores are not comparable (they are local rank spaces), so the merge defers cross-collection ordering entirely to the reranker (sound, collection-agnostic by construction, `reranker.py:55`). There is no sound RRF-only fallback in v1 — re-fusing the union of local ranks would reproduce the very incomparability the Problem section condemns — so reranking is **unconditional** for multi-collection requests: `/search` and MCP `search` expose no `rerank` toggle at all (B3 adds none), and the only surface exposing `rerank: bool` is `/explain`, where `rerank=false`+multi is a 422. Get the merge wrong and B3 ships a plausible-looking but incorrectly-ranked result set, which is worse than the honest client-side loop it replaces. The second subtlety is the **embedding-model boundary**: one query vector is only valid for collections sharing its model, so B3 must exclude-and-report mismatches rather than search them with the wrong vector — the clean handoff to C1. The third — and the bulk of the actual work — is the **type-unification**: the production hot path returns plain `SearchResult` with no rank provenance, while the provenance-carrying `ScoredSearchCandidate` only flows through the eval/debug-only `_hybrid_search_with_trace` (`store.py:921-924`); B3 promotes that candidate path to production and merges the two diverging rerank surfaces into one. This is not glue — it is a real refactor, co-designed with A4 (which already needs the candidate path for `/explain`). What must not be compromised: **the single-collection path stays observably identical** — same result set and ordering **except** the additive `collection` field (a field-subset equality test, not byte-for-byte; the production/trace tie-break must be reconciled before `search()` is folded into `search_many`, else `search()` stays separate), **embed-once and rerank-once are observable invariants** (spy-asserted), and **provenance (`collection`) is mandatory on every result** so the merged list is debuggable through `/explain`. Co-designing the merge with A4's `ScoredSearchCandidate` path means one implementation serves both search and explain, and the per-stage timings from B1 make the fan-out's cost a number with a story rather than a mystery.
