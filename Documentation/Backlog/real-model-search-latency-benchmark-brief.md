# Feature Brief: Real-Model Search Latency Benchmark

## Problem
The production `pipeline.search()` code path — including the real fastembed embedder (`BAAI/bge-small-en-v1.5`) and the real cross-encoder reranker (`Xenova/ms-marco-MiniLM-L-6-v2`) — has zero CI performance gate; every existing latency benchmark uses `EvalEmbedderBackend` (SHA-256 hash) or `EvalRerankerBackend` (BM25-like stub), so regressions in fastembed config, ONNX runtime, or reranker usage ship to users undetected.

Note: embedding batching regressions during ingest are not caught by this benchmark — `pipeline.search()` embeds a single query per call. Ingest batching is exercised during the module-scoped fixture setup, not measured. This limitation is accepted — batching during search is not a separate regression concern.

## Goal
Every pull request runs a real-model benchmark with separate steady-state and cold-load p95 gates against measured thresholds; "real-model performance drift" becomes a blockable regression class instead of an invisible one.

## Users & Context
- **Primary**: maintainers reviewing PRs — today they can merge a fastembed/ONNX/reranker regression without CI catching it.
- **Secondary**: operators and end users — who only feel the regression at runtime after release.
- **When it activates**: every PR build in `.github/workflows/archon-search-pr.yml`, before merge — same lane that already runs unit and integration tests.

## Core Flow
1. Developer opens or updates a PR (no per-PR opt-in; runs on every build).
2. CI restores the fastembed + HuggingFace model cache (key includes `uv.lock` hash, same as `archon-search-eval-live.yml`).
3. A dedicated workflow step prefetches the required models with retries (≈3 attempts, exponential backoff). Network/CDN flake fails at this step, not inside the assertion.
4. `pytest -m live_benchmark` runs two tests:
   - `test_real_model_search_steady_state_p95` — ingests the code subset of the eval corpus (23 documents from `tests/eval/corpus/code/`) once at module-scoped fixture setup, warms 5 iterations, measures 100 iterations of `pipeline.search()` with real models, asserts p95 ≤ `steady_state_p95_ms` from `live_thresholds.toml`.
   - `test_real_model_search_cold_load_p95` — constructs a fresh `ModelEmbedder` + `ModelReranker` inside the test N=10 times, measuring from construction start to first `encode()` + first `predict()` completion, asserts p95 of N=10 iterations ≤ `cold_load_p95_ms`. This measures ONNX session creation cost (not OS/linker cold-load, since ONNX runtime and shared libraries persist in-process); this is the meaningful and controllable regression class. "Fresh-process" iterations within a single pytest run are not architecturally feasible: pytest runs in one process and Python module cache, ONNX runtime, and shared libraries persist across loop iterations.
   - Steady-state test call signature: fixed query string from `queries.jsonl` entry #0 (`"async HTTP client with retry logic and timeout"`), `collection="code"` (matching the query's target collection), `embedder=<the pipeline's real ModelEmbedder-backed Embedder instance>`, `rag_fusion=False`, `filters=None`, `namespace=DEFAULT_NAMESPACE`. Note: `pipeline.search()` has no `top_k` parameter — result count is controlled by `top_k_return` and `top_k_retrieve` passed to the `SearchPipeline` constructor (these are required positional params with no defaults — production values come from `SearchConfig`: `top_k_retrieve=15`, `top_k_return=5`). The benchmark fixture must pass these values explicitly: `SearchPipeline(..., top_k_retrieve=15, top_k_return=5)`. Changing either requires re-calibration. Also note: the module-scoped fixture must ingest the code subset of the eval corpus into a collection named `"code"` to match the search call.
5. On regression: CI fails with the measured value, threshold, and headroom — reviewer sees the failure in the PR.
6. On success: standard green path; no manual action.

## In Scope
- One steady-state benchmark of full `pipeline.search()` with real embedder + real reranker (no stubs).
- One cold-load benchmark of fresh `ModelEmbedder` + `ModelReranker` first-call latency.
- New `live_benchmark` pytest marker, registered in `pyproject.toml`; tests carry `@pytest.mark.xdist_group("live_benchmark")` for serialised execution on a single worker.
- New `[real_model_search]` section in `tests/eval/live_thresholds.toml` (currently an empty stub — this is exactly what that file is for) with `steady_state_p95_ms` and `cold_load_p95_ms`. A new dedicated threshold loader function (e.g., `load_benchmark_thresholds(path)`) that reads `[real_model_search]` directly from TOML is required — the existing `load_thresholds()` function in `archon_search/eval/runner.py` requires `[quality_floors]` and its specific keys; it cannot be reused for this purpose. The `[real_model_search]` section is silently ignored by the current `load_live_thresholds()` in `archon_search/eval/live_report.py`.
- New "prefetch models" step in `archon-search-pr.yml` with HF + fastembed cache restoration and download retries.
- Calibration is done on a GitHub Actions ubuntu-latest runner via `workflow_dispatch` before codifying thresholds. Record 10 runs on CI hardware. Use `steady_state_p95_ms = CI_measured_p95 × 2` and `cold_load_p95_ms = CI_measured_p95 × 3` (higher multipliers account for CI noise). Run locally first to validate model loading works, then run on CI to get the authoritative calibration baseline. Include a provenance comment recording date, runner type, and the 10 raw samples.
- A `conftest.py` in `tests/eval/live_benchmark/` that: (1) removes all three stub keys from `sys.modules`: `fastembed`, `fastembed.rerank`, and `fastembed.rerank.cross_encoder` (all installed by `install_stubs()`). Removing only the top-level `fastembed` key is insufficient — `from fastembed.rerank.cross_encoder import TextCrossEncoder` resolves via its own `sys.modules` entry. This undoes stub patching from `tests/conftest.py:31`; (2) resets `ORT_NUM_THREADS`, `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS`, and `RAYON_NUM_THREADS` to production-appropriate values (delete from `os.environ` or set to `str(os.cpu_count() or 4)`) using direct assignment (not `setdefault`) to override values installed by root conftest and `install_stubs()`. Rationale: `tests/conftest.py` and `_search_stubs.py` throttle all thread pools to 1 for test stability; the benchmark must measure multi-threaded performance matching production, otherwise calibrated thresholds encode single-thread latency. `RAYON_NUM_THREADS=1` throttles fastembed's Rust tokenizer thread pool — omitting this reset causes the same calibration distortion as leaving `ORT_NUM_THREADS=1`. `TOKENIZERS_PARALLELISM=false` (also set by `install_stubs()`) is lower priority since the benchmark embeds a single query, not a batch; include in the reset as a precaution.
- A `pytest.mark.skipif` or `conftest.py` skip hook that skips `live_benchmark` tests when the fastembed model cache is absent (e.g., `BAAI/bge-small-en-v1.5` not found in `~/.cache/fastembed/`). This enables default `pytest` runs to skip gracefully on developer machines without cached models.
- Update `archon-search-pr.yml` default test step to add `not live_benchmark` to the marker exclusion filter, so `live_benchmark` tests are excluded from the default step and only run in the dedicated benchmark step.
- Documentation updates: `Documentation/Architecture/200_testing_strategy.md` (new marker + PR lane), `Documentation/Architecture/210_performance_and_scalability.md` (real-model gating story), `tests/eval/README.md` (live_benchmark section), and a comment block at the top of `live_thresholds.toml`.

## Out of Scope
- **Tightening the existing 6 stub-based thresholds** (`search_filtered.p95_ms_glob_filtered`, `search_hyde_false.p95_ms`, etc.) — separate concern; bundling doubles the change surface and complicates calibration. See *Future Iterations*.
- **Isolated component benchmarks** (`embedder.encode`-only, `reranker.predict`-only) — integration measurement first; isolated tests only if/when attribution proves insufficient.
- **Nightly or scheduled lane** — PR gate is the primary signal; nightly is redundant if PR works.
- **GPU / non-CPU runtime testing** — PR CI is CPU-only; GPU paths are an opt-in production-deployment concern, not a regression-gate concern.
- **Memory-footprint assertions** — not the regression class being addressed.
- **Routing latency gate** — separate uncovered regression class; track in its own brief.
- **Changes to the existing `tests/eval/live/test_live_acceptance.py::test_latency_stability`** — that test stays report-only; the new gated benchmark complements it, doesn't replace it.

## Key Decisions
- **PR CI, gated, not report-only.** Chosen over release-only and nightly because the motivation is catching regressions *before* they ship; report-only is exactly what produced today's gap.
- **Single full-pipeline benchmark + single cold-load benchmark.** User-facing latency comes from the integrated path; one integration measurement covers more attack surface than three isolated ones. Attribution can be added later if regressions are ambiguous.
- **Cold-load measured separately from steady-state.** First-call ONNX session-load cost is ~10× the per-query cost; measuring them in one test forces the same loose-threshold compromise the investigation just diagnosed.
- **Existing eval corpus as fixture — specifically the `code/` subdirectory (23 documents), targeted by the pinned `collection='code'` call.** Real text, already curated, fast ingest with real embedder (~1-2 s), no new fixture to maintain.
- **Calibration on CI hardware before merge — not "land loose, tighten later".** The "we'll tighten later" pattern produced today's 6-17× headroom on stub benchmarks. Calibration is ~15 minutes of work; ship gated. Calibration MUST be done on ubuntu-latest; local darwin/aarch64 measurements are 2-5× faster due to Apple Silicon ONNX acceleration and cannot be used as CI thresholds.
- **Model download is workflow infrastructure, not part of the test.** Prefetch step with retries isolates network flake from the benchmark signal.
- **New `live_benchmark` marker, not extending `live_eval`.** Keeps quality eval and latency benchmark independently selectable; cleaner CI plumbing.
- **`xdist_group("live_benchmark")` distinct from `xdist_group("benchmark")`.** Since `live_benchmark` runs in a dedicated CI step separate from the standard test suite (`pytest -m live_benchmark`), `xdist_group("live_benchmark")` serialises tests within that step only — there is no cross-group contention concern. (Note: under `--dist=loadgroup`, separate groups can run on different workers concurrently; placing both groups in the same group would serialise them onto one worker. That is irrelevant here because the two markers never appear in the same pytest invocation.)
- **Thresholds in `tests/eval/live_thresholds.toml`, not `thresholds.toml`.** The live file is currently an empty stub; using it keeps deterministic and real-model thresholds organisationally separate, matching the existing stub/live test-folder split.

## Edge Cases & Constraints
- **Cold model cache (uv.lock change)**: next PR pays ~150 MB download once. Prefetch step's retries handle transient CDN failures; subsequent PRs hit warm cache. Cache key matches existing `archon-search-eval-live.yml` strategy.
- **Network unavailable after retries**: prefetch step fails as workflow-infra failure (not a benchmark regression), distinguishable from a real perf signal in the PR status output.
- **Local-vs-CI calibration drift**: calibration MUST be done on ubuntu-latest; local darwin/aarch64 measurements are 2-5× faster due to Apple Silicon ONNX acceleration and cannot be used as CI thresholds. Run locally first to validate model loading works, then run on CI to get the authoritative calibration baseline.
- **Timer choice**: real-model benchmarks use `time.perf_counter()` (wall-clock), not `time.process_time()`. Justification: ONNX inference runs in a native C++ thread pool; `process_time` semantics differ by OS — on Linux CI it covers only the calling thread's CPU time and may undercount ONNX worker threads, producing systematically low calibration values that will fail in unexpected ways. Existing stub benchmarks in `tests/test_search_filtered_benchmark.py` continue to use `process_time` (correct for pure-Python CPU work); the new real-model benchmarks use `perf_counter`. Both are valid for their respective contexts.
- **`xdist_group` serialisation**, 5-iter warmup, 100-iter p95 for steady-state — patterns proven in `tests/test_search_filtered_benchmark.py`.
- **ONNX provider default**: CPU; no GPU contention to worry about in PR CI.
- **CalVer release impact**: zero. This is a CI/test-only addition; no public API or schema change; no `BREAKING.md` entry needed.
- **Coverage gate (`--cov-fail-under=85`)**: not affected — benchmark code paths are exercised, not gated against, and the new test file adds to coverage rather than reducing it.
- **`live_benchmark` marker visibility to default test runs**: registered in `pyproject.toml` markers. Tests skip gracefully on developer machines without cached models (via skip hook checking model cache presence). The `archon-search-pr.yml` default test step excludes `live_benchmark` via `not live_benchmark` marker filter; `live_benchmark` tests run only in the dedicated benchmark step.
- **sys.modules stub bypass**: `tests/conftest.py` installs fastembed stubs unconditionally via `install_stubs()`, patching `sys.modules["fastembed"]` with a zero-vector fake. A `conftest.py` in the `tests/eval/live_benchmark/` directory must undo this patching by removing the fastembed keys from `sys.modules` before real model imports. All three keys must be removed: `fastembed`, `fastembed.rerank`, `fastembed.rerank.cross_encoder`. Partial removal silently leaves the reranker stub in place. This is the minimal-invasive approach and does not require changes to the root conftest.
- **Thread count for ONNX inference**: root conftest sets `ORT_NUM_THREADS=1` for all tests. The live_benchmark conftest MUST reset this to production defaults before any ONNX import. If the benchmark measures single-threaded ONNX, the calibrated thresholds will be ~2-5× higher than production latency, making the gate useless for production regression detection.
- **Chunking uses stubbed chonkie (whitespace splitter)**: `install_stubs()` stubs `chonkie.RecursiveChunker` with a whitespace-based fake. The live_benchmark conftest removes fastembed and ONNX thread constraints but does NOT need to un-stub chonkie, because corpus chunking is a one-time fixture setup cost — the benchmark measures query-time ONNX inference latency, not ingest. Chunk boundaries will differ from production (whitespace splits vs. tokenizer-based recursive splits), but this does not affect the measured code path (`pipeline.search()` query embedding + retrieval + reranking).

## Open Questions
- Prefetch retry count and backoff schedule (proposed default: 3 retries, 5 s / 10 s / 20 s). Revisit if the proposed default proves wrong after first CI run.
- Both tests need a hang-guard. The recommended approach (since `pytest-timeout` is not a current dev dependency and adding it would require marker registration) is to use a GitHub Actions step-level `timeout-minutes: 3` on the dedicated `live_benchmark` CI step. This aborts the step if the benchmark hangs. If `pytest-timeout` is added as a dev dependency, `@pytest.mark.timeout(120)` on each test is preferred (more granular, better error message), but then `timeout` must also be added to `pyproject.toml`'s `markers` list.
- Final calibrated threshold values themselves — derived during implementation, not pre-decidable here.

## Future Iterations
- **Tighten existing stub-based latency ceilings**: 25 → ~15 ms (`p95_ms_glob_filtered`, `p95_ms` for hyde_false), 50 → ~25 ms (`rag_fusion_disabled`), 100 → ~50 ms (`rag_fusion_enabled`), 75 → ~50 % (`p95_regression_pct_prefix_vs_unfiltered`). Pair with `_N_ITERS` bump from 100 → 500 to keep flake risk flat. Separate PR.
- **Isolated component benchmarks** (`embedder.encode` only, `reranker.predict` only) — add if/when integration measurement produces ambiguous regression attribution.
- **Nightly canary on a dedicated cloud runner** — only if PR CI variance proves too high to gate aggressively against tighter thresholds.
- **Memory-footprint assertions** tied to the `download_mb` / `memory_gb` fields in `profiles.py` that today are documentation only.
- **Routing latency gate** — a `pipeline.route()` real-model benchmark closing the routing-perf coverage gap.
- **Replace anecdotal threshold-justification comments** ("SQL LIKE adds 15-18%", "30-45% under parallel load") with persisted measurement data from baseline runs.

## Recommendation
This is the right feature to build now — it closes the largest regression-coverage gap (real embedder + real reranker code paths) with the smallest change surface (two tests, one threshold file, one workflow step). The hardest part is calibration: local-vs-CI variance will probably surface one threshold adjustment after the first CI run, and the team must resist the temptation to widen thresholds when that happens. **What must not be compromised: (1) the assertion must actually fail the build — not "fail and continue", not "report and warn"; (2) the prefetch step must isolate network flake from the benchmark signal — if both share a failure mode, the team will start ignoring the gate within a month.** Skipping either turns this into the same report-only / loose-threshold pattern that today's investigation just demolished.
