# Feature Brief: B5 — Incremental Centroid Update (`CON-4`, item 17)

## Problem
Three concrete defects in today's centroid maintenance make the artifact `MultiCollectionRouter.rank` routes on (`router.py:142–143`) wrong, stale, or expensive depending on the path taken:

- **Defect 1 — batch-only overwrite on the common ingest path.** **`SearchPipeline.ingest_directory`** (`pipeline.py:277–309`) is the primary batch ingest path — it backs the CLI (`cli/ingest.py:35`, `cli/collection.py:89`), MCP `ingest_directory` (`server/mcp.py:161`), the REST/job ingest + `/collections/{name}/reindex` flows (`routes_collections.py:320`), the full-sync path (`sync.py:528`), and CLI `reindex` (`cli/collection.py:286`). It computes `centroid = _compute_centroid(all_vectors)` from **only the in-memory vectors collected during the current batch**, and sets `doc_count` / `chunk_count` to **batch-only** counts (`batch_doc_count`, `batch_chunk_count`). It then calls `update_collection_meta`, which **overwrites** the row. **Consequence: ingesting a second batch into a non-empty collection clobbers the cumulative centroid and counts with values that describe only the latest batch.** This is O(batch), not O(chunks) — but it is *incorrect*.
- **Defect 2 — delete ignores the centroid entirely.** **`delete_document` never updates the centroid at all** (`pipeline.py:366–370` just deletes rows). After any delete, the persisted centroid and counts are stale until the next full recompute or the next `ingest_directory` overwrite.
- **Defect 3 — O(chunks) full rescan on the watcher-sync path.** **`SearchPipeline.recompute_collection_meta`** (`pipeline.py:388–421`) is a genuinely O(chunks) path. It does **not** run on `ingest_directory`; it runs on the **watcher-sync path** (`sync.py:708`, after `sync.py:528` calls `ingest_directory` — *not* per-file `ingest_file`) and in eval setup (`eval/runner.py:484`). It calls `store.get_all_vectors` (`store.py:845`, loads **every** chunk vector — O(chunks × dim) memory and transfer) and `store.count_documents` (`store.py:860`, loads **every** `doc_id`). Cost scales linearly with corpus size and is paid on every watcher sync, not every ingest.

So the collection centroid is simultaneously (a) clobbered to batch-only on the common ingest path, (b) never updated on delete, and (c) recomputed at O(chunks) cost on the sync path. There is no single, cheap, correct maintenance routine. This blocks B4 (stronger routing builds on a *correct* centroid) and makes ingest latency grow with corpus size on the sync path.

**Reconciliation note (code-as-source-of-truth).** The roadmap and debt register describe `CON-4` as "`SearchPipeline.recompute_collection_meta` re-reads **all** vectors for a collection and recomputes the centroid on **every ingest**, synchronously, inside the ingest path … O(chunks) per ingest call." That wording is inaccurate against the code: the *common* ingest path is O(batch)-but-wrong (Defect 1), the O(chunks) cost lives on the sync/recompute path (Defect 3), and delete-ignores-centroid (Defect 2) is unmentioned. Per `CLAUDE.md`, the code is the source of truth, so B5 fixes the three real defects above **and** amends the register/roadmap to match (see In Scope → Doc reconciliation).

## Goal
Replace the three inconsistent behaviours with **one** maintenance contract: keep a running `(centroid_sum, chunk_count)` on `CollectionMeta`, update it incrementally on add and delete, derive `centroid = centroid_sum / chunk_count` on write, and reserve a full O(chunks) rescan **only** for an explicit rebuild (drop-and-reingest reindex, or a recovery/initialisation path). Success is observable as:

- (a) Ingesting batch B2 into a collection that already contains B1 yields a centroid equal (within a documented float tolerance) to the mean of **all** B1∪B2 vectors — not B2 alone. Pinned by an integration test that today fails against `ingest_directory`'s batch-only overwrite.
- (b) `chunk_count` and `doc_count` after B1∪B2 reflect the **cumulative** collection, not the last batch.
- (c) Deleting a document subtracts its vectors from `centroid_sum` and decrements `chunk_count`, leaving the centroid equal (within tolerance) to the mean of the remaining vectors. Pinned by a test that today fails (delete is a no-op on the centroid).
- (d) A second ingest into a large collection does **not** call `get_all_vectors` / `count_documents` — verified by a spy asserting zero full-scan calls on the incremental path.
- (e) An authoritative full recompute (`recompute_collection_meta`) over a given table state rebuilds `centroid_sum` from scratch and matches the value the store-maintained incremental tally holds **for that same table state** within tolerance — the drift guard. (The guard compares incremental-vs-full on identical rows; it does **not** compare CLI-reindex vs REST-reindex, which operate on different table states — see Edge Cases.)
- (f) The router routes on the corrected centroid; the eval harness (`tests/eval/`) still passes with thresholds unchanged. Centroid correctness itself is gated by the integration suite, not eval (see In Scope → Tests, integration suite).
- (g) The 85% coverage gate holds on the default pytest run.
- (h) The `CON-4` row in `530_…roadmap.md` and the B5 line in `03_world_class_roadmap.md` describe the as-built behaviour (three concrete defects, O(batch) ingest, store-layer maintenance) — verified by the doc diff included in the same PR.

## Users & Context
Internal hardening — no new user-facing surface. Affects every operator who ingests more than one batch into a collection, deletes documents, or runs a watcher-synced corpus past a few thousand chunks:

- **Operators of growing single-collection corpora**: ingest latency on the sync path currently grows O(chunks); B5 makes it O(batch).
- **Operators of multi-collection deployments**: routing quality silently degrades today because the centroid describes only the last ingested batch (or is stale after deletes). B5 makes the centroid describe the whole live collection, which is what `router.rank` assumes.
- **Contributors building B4 (stronger routing)**: B4's summary-embedding / multi-centroid alternatives are meaningless on top of a clobbered baseline centroid. B5 is the correctness floor B4 stands on.

Symptom today: after re-ingesting or deleting, `GET /collections/{name}` reports `centroid_present: true` (`routes_collections.py:270`) but the centroid points at the wrong region of embedding space, so routing sends queries to the wrong collection without any error.

## Core Flow
Observable maintenance contract. The wiring is **store-layer** (a Key Decision below): the `(centroid_sum, chunk_count, doc_count, derived centroid)` update happens *inside* the store's locked row-mutation critical sections (`ingest_chunks`, `delete_document`). The chunk-table write and the `_META_TABLE` write are **serialized under one per-collection lock and ordered (chunk rows committed first, then the meta row), but they are NOT a single transaction** — the chunk table and `_META_TABLE` are separate LanceDB tables with separate `table.add` commits (`_do_ingest` writes the chunk table at `store.py:513`; `update_collection_meta` writes `_META_TABLE` at `store.py:449`), and LanceDB gives no cross-table atomicity. Lock-serialization eliminates the concurrent lost-update race; it does **not** make the two commits transactional. This is the behaviour regardless of which caller drives it.

1. **Ingest add (N chunks with vectors)** — inside `ingest_chunks`, under the per-collection lock (`store.py:483`): read the existing `(centroid_sum, chunk_count, doc_count)` for the collection; compute `batch_sum = elementwise_sum(batch_vectors)`; commit the chunk rows (`_do_ingest`, `store.py:513`), then persist `centroid_sum' = centroid_sum + batch_sum`, `chunk_count' = chunk_count + N`, `doc_count' = doc_count + (distinct new doc_ids in batch)`, and derived `centroid = centroid_sum' / chunk_count'` to the meta row. The first `ingest_chunks` into a **brand-new collection** has no meta row (and `_META_TABLE` may not exist yet — it is lazily created in `update_collection_meta` at `store.py:421–422`): that case treats the absent meta row / absent `_META_TABLE` as the `(0-vector, 0, 0)` seed and **creates** the row (reusing the lazy `_META_TABLE` create currently in `update_collection_meta`, `store.py:421–422`). This brand-new-collection bootstrap is a **different code path** from the pre-B5 migration case (step 5: the row exists but lacks `centroid_sum_json`) — bootstrap creates the row from a zero seed, migration reseeds an existing row. Both writes happen inside the **same** held per-collection lock, in that order (chunk rows first, then meta), but are **two separate commits** — not one transaction. If the meta write fails after the chunk commit, the implementation SHOULD set a `needs_recompute` stale flag on the meta row so the next caller reconciles it (see step 6). On the add path, `last_indexed` is written by the post-loop `store.update_description` call (which already takes `last_indexed` in its signature), **not** by `ingest_chunks` — which leaves `last_indexed` untouched; this avoids double or zero ownership of the timestamp on add. No full scan.
2. **Document delete (M chunks)** — inside `delete_document`, under the **same** per-collection lock (which `delete_document` must now acquire — it takes none today, `store.py:716–729`): fetch the deleted document's vectors **before** removing the rows (O(M), not O(all)); compute `del_sum`; commit the row delete, then persist `centroid_sum' = centroid_sum − del_sum`, `chunk_count' = chunk_count − M`, `doc_count' = doc_count − 1` (only when rows were actually removed, signalled by the existing non-zero return at `store.py:725`), derived centroid recomputed, and `last_indexed` bumped (so a delete-only sync still refreshes it — see Edge Cases — Delete-only sync). If `chunk_count'` reaches 0, reset `centroid_sum` and `centroid` to `None`; do **not** call `_compute_centroid` on an empty vector set. The row delete and the meta write are **ordered and lock-serialized but not transactional**: same `needs_recompute` stale-flag reconciliation applies if the meta write fails after the row delete commits.
3. **Re-ingest of a changed document (current `ingest_file` = delete-then-add, `pipeline.py:203–204`)**: flows naturally as step 2 (old chunks subtracted, `doc_count −1` because the doc existed) followed by step 1 (new chunks added, `doc_count +1` for the same doc_id) — net `doc_count` change 0, exact. A brand-new document hits a 0-row delete (no decrement) then an add (+1) — net +1, exact. The net effect on `centroid_sum` is correct without special-casing.
4. **Full reindex / recompute** (drop + re-ingest via CLI `reindex`, or REST `/reindex`, or an explicit recompute entry point): the store-maintained `(sum, count)` already tracks actual table rows, so a drop+reingest naturally accumulates from `(0-vector, 0)` and a reingest-over-rows keeps `sum == table` for the rows it touches. To guarantee an **authoritative** reset (and clear any accumulated float drift), an explicit full reindex job SHOULD finish by calling `recompute_collection_meta` (one `get_all_vectors` pass) rather than relying on the incremental net-out. This is the **only** sanctioned O(chunks) path and the authoritative drift reset. (REST `/reindex` does not drop rows; the orphaned-row difference vs. CLI `reindex` is pre-existing and out of scope — see Edge Cases.)
5. **Initialisation / migration on a pre-B5 collection**: a collection whose stored meta has no `centroid_sum` (new field absent/empty) triggers exactly **one** lazy full recompute to seed the sum, after which maintenance is incremental. This is the read-boundary fallback (see Edge Cases). The seed/reseed step (including the NaN/inf reseed) MUST short-circuit to `centroid=None` / `centroid_sum=None` when the table is empty (`chunk_count == 0`) and must **not** call `_compute_centroid([])` — `_compute_centroid` (`pipeline.py:100–104`) reads `len(vectors[0])` and divides by `n`, raising on empty input; mirror the existing `if not vectors: return` guard at `pipeline.py:397`.
6. **Periodic recompute checkpoint (default-on)**: the **store** maintains an "incremental mutations since last full recompute" counter on the meta row and, when it exceeds a configurable threshold (default ~10k mutations) — or when a `needs_recompute` stale flag is set (steps 1–2) — **signals** that a recompute is due (e.g. by returning a flag from the mutation, or leaving the `needs_recompute` marker on the meta row). The store never calls `recompute_collection_meta` itself: that method lives on the **pipeline** and needs the embedder (`self._embedder.model_name`), so a store-layer mutation calling it would be a forbidden upward dependency and would risk contention/deadlock if attempted inside the held lock. Instead the **caller** (pipeline `ingest_directory` / sync, running *outside* the store lock where the embedder is available) checks the signal **after** the mutation returns and invokes `recompute_collection_meta`. This authoritative pass clears the counter, the stale flag, and any accumulated cancellation drift. An explicit reindex also resets the counter.
7. **Router consumption is unchanged**: `MultiCollectionRouter` keeps reading the derived `centroid` field (`router.py:142`, `_ROUTING_FIELDS`); `centroid_sum` is internal bookkeeping and is **not** added to `_ROUTING_FIELDS` or any response surface. A zero-norm / degenerate centroid still scores 0.0 cosine and renders the collection effectively unroutable — this is the router's pre-existing behaviour (`router.py:28`) and is unchanged; B5 only prevents a single NaN/inf vector from permanently poisoning the running sum (see Edge Cases).

## In Scope
- **Add a running-sum field to `CollectionMeta`** (`collection_meta.py`): `centroid_sum: list[float] | None = None`. `chunk_count` (already present) is the count half of the `(sum, count)` pair — no new count field. `centroid` stays the derived mean and remains the routing artifact.
- **Persist `centroid_sum`** in the LanceDB meta table: add `pa.field("centroid_sum_json", pa.utf8())` to `SearchStore._meta_schema` (`store.py:202–219`), JSON-encoded the same way `centroid_json` is (`store.py:444`, `454`). Extend `update_collection_meta` (write, `store.py:416–464`) and `get_collection_meta` (read/parse, `store.py:~300–325`) symmetrically, with the same malformed-JSON → `None` fallback already used for `centroid_json` (`store.py:306–309`).
- **Incremental add on ingest (store layer)**: `store.ingest_chunks` maintains `centroid_sum`, cumulative `chunk_count`, and cumulative `doc_count` inside its existing per-collection-lock critical section (`store.py:483`), committing the chunk rows first and the meta row second (ordered, lock-serialized, not transactional — see Core Flow / Key Decisions). The first `ingest_chunks` into a **brand-new collection** treats an absent meta row / absent `_META_TABLE` as the `(0-vector, 0, 0)` seed and **creates** the meta row (reusing the lazy `_META_TABLE` create currently in `update_collection_meta`, `store.py:421–422`); this bootstrap is a **distinct code path** from the pre-B5 migration reseed (an existing row missing `centroid_sum_json` — Core Flow step 5). `ingest_chunks` accumulates sum/count/`doc_count` and writes the derived `centroid` but leaves `last_indexed` untouched (owned by the post-loop `store.update_description` call on the add path — see the description bullet below). `ingest_directory` (and the per-file `ingest_file` loop it drives at `pipeline.py:257`) therefore **accumulate** onto existing meta with no pipeline-layer overwrite. REST `/ingest` also flows through `store.ingest_chunks`, so it is covered by the same path.
- **In-lock maintenance uses unlocked internal primitives (no lock re-entry)**: `_lock_for` returns a plain non-reentrant `asyncio.Lock` (`store.py:132–140`). The meta read/write done while the per-collection lock is held MUST operate via **unlocked** internal helpers (factor `_do_*`-style helpers mirroring the existing `ingest_chunks`→`_do_ingest` split at `store.py:489`/`493`); the in-lock maintenance path MUST NOT re-acquire `_lock_for(collection)` while already holding it, or it self-deadlocks.
- **`ingest_chunks` is additive — callers MUST delete-first when replacing (explicit precondition)**: LanceDB `table.add` is additive, not an upsert (`_do_ingest`, `store.py:513`). `ingest_chunks` assumes the batch's `doc_id`s are **not already present** in the table; under that precondition `doc_count += (distinct doc_ids in batch)` and the sum/count accumulation are exact. Any caller replacing an existing document MUST `delete_document` the `doc_id` first. All current callers satisfy this via `ingest_file`'s delete-then-add (`pipeline.py:203–204`). REST `/ingest` flows through `ingest_file` and inherits the precondition. (Adding a doc_id already present without a preceding delete would over-count `doc_count` and double-count `chunk_count`/`centroid_sum` — out of contract, not a supported path.)
- **Pipeline description update goes through a dedicated locked store method — never through `update_collection_meta`**: the `description` / `last_described` / `described_at_doc_count` / `last_indexed` logic in `ingest_directory` (`pipeline.py:284–309`) is retained, but the pipeline MUST NOT construct a full `CollectionMeta` and call `update_collection_meta` (a whole-row upsert that would round-trip sum/count/centroid through pipeline-layer code outside the store lock, where a concurrent ingest/delete could clobber the store-maintained fields between the pipeline's read at `:285` and write at `:309`). Instead add a store method — `store.update_description(collection, description, last_described, described_at_doc_count, last_indexed)` — that **acquires the per-collection lock** and does a **partial update writing only the description/timestamp fields**, never touching `centroid_sum` / `chunk_count` / `doc_count` / `centroid`. The pipeline calls this. `update_description` is an **in-place partial update that requires the meta row to already exist** — the row is created by the store-layer add path on the first `ingest_chunks` (see "Incremental add on ingest"). Ordering invariant: any path that reaches `update_description` has already run ≥1 `ingest_chunks` that created the row, because the pipeline calls `update_description` **only** inside `ingest_directory`'s `if all_vectors:` guard (`pipeline.py:278`), which is reached only when at least one file ingested successfully (≥1 `ingest_chunks`). If the meta row is nonetheless absent, `update_description` is a **no-op** (description regen had nothing to attach to). This removes the pipeline from the sum/count write path entirely and closes the lost-update window (see Key Decisions → "Every meta-row writer must read-modify-write"). `update_collection_meta`'s whole-row upsert is thereby reserved for the store's own locked maintenance and the full recompute/seed; the pipeline no longer calls it for description.
- **Incremental subtract on delete (store layer, now locked)**: `delete_document` fetches the target document's vectors before deletion and subtracts them from `centroid_sum`, decrementing `chunk_count` and (when rows were actually removed) `doc_count`, and bumping `last_indexed`. Today delete touches neither the centroid nor any lock (`pipeline.py:366–370`, `store.py:716–729` takes no lock and returns only a row count). This scope makes `store.delete_document` (a) vector-aware (pre-delete vector fetch) and (b) acquire the **same** per-collection lock `ingest_chunks` uses, so subtract + row delete + meta write are ordered and lock-serialized (chunk-table delete first, then meta — not a single transaction; see Core Flow). This is a new locking responsibility on the delete path, and it inherits ingest's busy-handling: the acquire is wrapped in `asyncio.wait_for(..., timeout=INGEST_LOCK_TIMEOUT_S)` raising `StoreBusyError` on timeout, mirroring `ingest_chunks` (`store.py:485–487`), so a delete cannot block unboundedly behind a lock-holding `reindex_metadata` (see Edge Cases — delete lock contention). The in-lock subtract/meta-write uses the **unlocked** `_do_*`-style helpers (no `_lock_for` re-acquisition while held — see the no-lock-re-entry scope bullet). **`last_indexed` is bumped on every delete that removed rows**, so a watcher sync that only deletes files (no adds) still refreshes `last_indexed` even though `recompute_collection_meta` no longer runs on that path (see Edge Cases — Delete-only sync).
- **Derive and persist `centroid` from `centroid_sum / chunk_count`** wherever meta is written on the incremental paths. `_compute_centroid` (`pipeline.py:100–104`) stays the implementation for the full-rescan path; the incremental path divides the maintained sum by the count.
- **Reserve the full O(chunks) rescan for explicit rebuild only**: keep `recompute_collection_meta` (`pipeline.py:388`) as the authoritative full-recompute, but (a) make it also populate `centroid_sum` from the same single `get_all_vectors` pass, and (b) **stop invoking it on the watcher-sync path** (`sync.py:708`) in favour of the incremental maintenance now performed inside the store on each `ingest_chunks` / `delete_document`. Note the sync path calls `ingest_directory` (`sync.py:528`), not per-file `ingest_file` — `ingest_directory` drives the per-file `ingest_file` loop internally (`pipeline.py:257`), which is delete-then-add (`pipeline.py:203–204`), so the store-layer maintenance fires per file regardless. `recompute_collection_meta` is retained for: drop+reingest reindex, the lazy pre-B5 seed, the periodic-checkpoint reset, and a recovery/drift-reset entry point.
- **`doc_count` is exact and incremental at the store layer**: today `ingest_directory` writes batch-only `doc_count` (`pipeline.py:281`) and the full recompute uses O(chunks) `count_documents` (`store.py:860`). B5 maintains `doc_count` incrementally using `delete_document`'s existing return value (`store.py:725`) as the new-vs-replaced signal: on a delete that removed rows (>0), `doc_count −= 1`; on `ingest_chunks`, `doc_count += (distinct doc_ids in the added batch)`. Because `ingest_file` always deletes before adding (`pipeline.py:203–204`), a replacement nets 0 and a brand-new doc nets +1 — exact, with no O(chunks) `count_documents` on the hot path.
- **Embedding-model / dimension / NaN guard**: `centroid_sum` is only valid for a fixed embedding model + dimension and a finite running sum. Reseed (one full recompute) is triggered if: `meta.embedding_model` differs from the writing embedder's `model_name`; a stored `centroid_sum` length ≠ current `embedding_dim`; **or any element of `centroid_sum` (or of a per-vector input being added/subtracted) is NaN/inf**. The NaN/inf guard is load-bearing: without it, one malformed-but-well-typed vector poisons the sum permanently (NaN propagates through every future add/subtract) and the model/dim triggers never fire. Pins against silently summing mismatched or non-finite vectors.
- **Concurrency — which lock**: the incremental update is a read-modify-write of the meta row and must be atomic with the chunk add/delete that produced the vectors. The guarding lock is specifically **`SearchStore._collection_locks`** (`store.py:132–140`, `_lock_for`, `INGEST_LOCK_TIMEOUT_S`, `StoreBusyError`) — the store-layer lock `ingest_chunks` already takes at `store.py:483`. This is **distinct** from `SearchCollectionSync._collection_locks` (the higher sync-layer lock, same key space, different call paths). `delete_document` must be made to acquire this **same store-layer** lock (it takes none today). Two concurrent ingests/deletes into one collection then serialize and cannot lost-update the sum; other collections proceed in parallel. Cross-process safety remains out of scope and documented (consistent with A6).
- **Router cache interaction / A6 sequencing prerequisite**: B5 builds on A6's `MultiCollectionRouter.invalidate()`. The per-request FastAPI router re-reads metadata each request, so the production REST path observes the corrected centroid immediately; but `fetch_metadata` caches `_cached_metadata` indefinitely until `invalidate()` (`router.py:64–124`), so for **any long-lived / shared router (and the eval path) A6 is an explicit sequencing prerequisite** for the routing benefit to be observable. B5 does **not** introduce a shared router or new invalidation funnel; it only guarantees the persisted centroid is correct so the next `fetch_metadata()` (per-request in FastAPI, post-`invalidate()` elsewhere) reads a correct value.

  - Unit: a single `ingest_chunks` call whose batch spans **>1 distinct `doc_id`** increments `doc_count` by the number of distinct doc_ids and accumulates `chunk_count`/`centroid_sum` over all of them (exercises the multi-doc-per-batch path the multi-doc assertion relies on).

## Out of Scope
- **Stronger routing / multi-centroid / clustered or summary-embedding representations** — that is B4. B5 only fixes the *single mean centroid* so B4 has a correct baseline.
- **Router algorithm or confidence-gate changes** (`router.rank`, `_cosine_similarity`) — unchanged. (Note: cosine is scale-invariant, so ranking would be identical on a raw sum vs. the mean; B5 still persists the proper mean for `centroid_present` reporting and any external/non-cosine consumer.)
- **Router cache invalidation API** — owned by A6 (`MultiCollectionRouter.invalidate()`). B5 depends on it but does not re-implement it, and does not introduce a shared `app.state` router.
- **`recompute_collection_meta` removal** — it is retained as the authoritative full-rescan for reindex / seed / recovery; only its invocation on the watcher-sync hot path (`sync.py:708`) is removed.
- **Cross-process locking** of the meta read-modify-write — single-process invariant holds, consistent with A6/A1; documented limitation.
- **`fsync` on the meta-table write** — durability of meta writes is the A7 family's concern; B5 is consistency/correctness of the value, not crash-durability of the bytes.
- **`count_documents` / `list_documents` general optimisation** beyond removing the centroid path's dependence on the O(chunks) full doc-id scan — broader list/aggregate optimisation is not B5.
- **A1 `reindex_metadata`** (`store.py:532`, the per-row `file_type` / `updated_at` / `ingested_by` backfill) — that command does not touch the centroid and is **not** the "reindex" referenced here. B5 does not change it. (Naming collision called out in Key Decisions so the plan doesn't conflate them.)
- **Backfill CLI for `centroid_sum`** — no new opt-in command; the lazy single-reseed on first post-upgrade ingest/recompute is sufficient. Operators wanting an immediate authoritative value run the existing full `reindex`.

## Key Decisions
- **Maintain `(sum, count)`, derive the mean — don't store only the mean.** Storing the mean alone makes incremental add/delete impossible without a full rescan (you cannot back out a deleted vector from a mean without the count and sum). The `(centroid_sum, chunk_count)` pair is the minimal state that makes both add and delete O(batch).
- **Store-layer maintenance, hooked into `ingest_chunks` and `delete_document`, is the load-bearing wiring — not pipeline-layer.** Rationale: re-ingest of a changed document is delete-then-add *inside* `ingest_file` (`pipeline.py:203–204`); the old chunks are removed by `store.delete_document` without their vectors ever reaching `ingest_directory`'s `all_vectors` collector. Only the store sees both the add and the delete, so only the store can keep the sum correct across updates. The pipeline retains ownership of `description` / `last_described` regeneration; the store owns the `(centroid_sum, chunk_count, doc_count, derived centroid)` invariant. The *delete path must be vector-aware at the store layer*.
- **Lock-serialization is the load-bearing correctness guarantee — it is concurrency-safety, NOT cross-table transactionality, and it does NOT exist today.** The per-collection lock (`store.py:483–491`) is currently acquired and released entirely *inside* `ingest_chunks`; the meta read-modify-write happens afterward in `ingest_directory` with **no lock**, and `update_collection_meta` / `delete_document` take **no lock at all**. B5 moves incremental maintenance **entirely into the store's locked critical sections**. Two guarantees, kept clearly separate: **(concurrency)** holding one per-collection `asyncio.Lock` across both writes serializes writers and eliminates the concurrent lost-update race; **(crash window)** it does **not** make the two writes a single transaction — the chunk table and `_META_TABLE` are separate LanceDB tables with separate `table.add` commits (`store.py:513` vs `store.py:449`) and LanceDB offers no cross-table atomicity, so a hard crash between the two ordered commits leaves an at-most-one-batch inconsistency (reconciled by the periodic checkpoint / lazy reseed, and the implementation SHOULD set a `needs_recompute` stale flag if the meta write fails after the chunk commit). Concretely: (1) `ingest_chunks` commits the chunk rows, then updates `(centroid_sum, chunk_count, doc_count, derived centroid)` in the meta row *within the same held per-collection lock* — ordered, serialized, not transactional; (2) `delete_document` is made vector-aware **and** acquires the same per-collection lock (it takes none today) so subtract + row delete + meta update are ordered under one lock; (3) the pipeline never round-trips the store-maintained fields — its description-only update goes through a dedicated locked `store.update_description` partial write (see row-clobber decision below). The "serialized under the same lock as the add/delete" property is *created* by B5, not pre-existing; the cross-table non-transactionality is an acknowledged limitation, not a contradiction.
- **`(sum, count)` is a faithful tally of actual table rows — partial-batch failure does not diverge.** Because maintenance lives inside each store row mutation's locked critical section (chunk write first, then meta write, both under one held lock), the pair always equals the current table rows except for an at-most-one-batch window on a hard crash **between the two ordered (non-transactional) commits** — the chunk commit and the meta-row commit are separate LanceDB writes, not one transaction. A failed add after a committed delete leaves "removed, not re-added" consistently in *both* table and sum. The one residual window is reconciled by the periodic checkpoint and the lazy/stale-marker reseed (and the `needs_recompute` flag set when the meta write fails after the chunk commit); byte-durability is A7's concern. (See Edge Cases — Partial-batch failure.)
- **Every meta-row writer must read-modify-write — and the store-maintained fields are written ONLY by the store, never round-tripped through the pipeline.** `update_collection_meta` deletes-then-inserts the *whole* row (`store.py:442,449`); any writer that doesn't repopulate `centroid_sum` / `chunk_count` / `doc_count` / `centroid` nulls them out. Mandate: those four fields are written **only** by the store's locked maintenance (`ingest_chunks`, `delete_document`) and by the full recompute/seed. The pipeline MUST NOT read-modify-write them at all: a pipeline-layer RMW of the whole row (read at `pipeline.py:285`, write at `:309`) runs **outside** the store lock, so a concurrent ingest/delete into the same collection could update the meta row between the pipeline's read and write and clobber the store-maintained fields back to a stale snapshot — "preserving" the values does not close that lost-update window. Instead the pipeline's description / `last_described` / `described_at_doc_count` / `last_indexed` update goes through a dedicated **`store.update_description(collection, description, last_described, described_at_doc_count, last_indexed)`** that **acquires the per-collection lock** and does a **partial update writing only those fields**, never touching sum/count/centroid. `update_description` is an **in-place partial update that requires the meta row to already exist** (created by the store-layer add path on the first `ingest_chunks`); it is **never** a row creator. Ordering invariant: any path reaching `update_description` has already run ≥1 `ingest_chunks` that created the row, because the pipeline only calls it inside `ingest_directory`'s `if all_vectors:` guard (`pipeline.py:278`), which implies at least one successful ingest. If the meta row is nonetheless absent, `update_description` is a **no-op**. `update_collection_meta`'s whole-row upsert is thereby reserved for the store's own locked maintenance and the full recompute/seed; the pipeline no longer calls it for description. This closes the clobber path that Defect 1 exploits **and** the cross-thread RMW race.
- **`doc_count` is maintained as an exact incremental counter at the store layer.** No longer deferred. Use `delete_document`'s existing return value (`store.py:725`) as the new-vs-replaced signal: a delete that removed rows (>0) ⇒ `doc_count −= 1`; an `ingest_chunks` ⇒ `doc_count += (distinct doc_ids in the added batch)`. Because `ingest_file` always deletes before adding (`pipeline.py:203–204`), a replacement nets 0 and a brand-new doc nets +1 — exact, with no O(chunks) `count_documents` on the hot path.
- **Periodic recompute checkpoint is a default-on Key Decision, not belt-and-suspenders — and the store signals, the caller recomputes.** B5 removes the only frequently-running recompute (`sync.py:708`), so a continuously-watched corpus would otherwise never reset accumulated cancellation drift. The **store** maintains an "incremental mutations since last full recompute" counter on the meta row and, when it exceeds a configurable threshold (default ~10k mutations) or a `needs_recompute` stale flag is set, **signals** the caller (returns a flag from the mutation / leaves the `needs_recompute` marker) — it does **not** call `recompute_collection_meta` itself, because that method lives on the **pipeline** and needs the embedder (`self._embedder.model_name`); a store-layer mutation calling upward into the pipeline would be a forbidden dependency and would risk contention/deadlock inside the held lock. The **caller** (pipeline `ingest_directory` / sync, running *outside* the store lock) checks the signal **after** the mutation returns and invokes `recompute_collection_meta`, which clears the counter and the flag. Explicit reindex also resets the counter. This bounds drift without paying O(chunks) per sync (see Core Flow step 6).
- **A6 (`MultiCollectionRouter.invalidate()`) is an explicit sequencing prerequisite for the routing benefit.** `router.fetch_metadata` caches `_cached_metadata` indefinitely until `invalidate()` (`router.py:64–124`). The per-request FastAPI router re-reads each request, so the **production REST path is fine**; but for any **long-lived / shared router (and the eval path)**, the corrected centroid only becomes observable after A6's invalidation funnel exists. B5 depends on A6 but does not re-implement it (see Future Iterations).
- **Delete must read vectors before removing rows.** `store.delete_document` currently returns a count only. To subtract incrementally it must fetch the target `doc_id`'s vectors first (O(M) for that document, not O(all)). The alternative — marking the centroid "stale" on delete and lazily full-recomputing — reintroduces the exact O(chunks) cost B5 exists to remove, so it is rejected for the steady state (it remains the *recovery* path only).
- **Reconcile the debt register with the code.** The register says O(chunks) "on every ingest"; the code's hot ingest path is O(batch)-but-wrong and the O(chunks) cost is on the sync/recompute path. B5 fixes the real defects (batch-only overwrite + delete-ignores-centroid + sync-path full rescan) and updates the docs to match, per `CLAUDE.md`'s code-as-source-of-truth rule.
- **Full recompute is the drift reset, kept and re-pointed.** float64 accumulation error is ~n·ε (negligible); the real risk is catastrophic cancellation on subtraction over very long histories. The authoritative `get_all_vectors` recompute on reindex, on the lazy seed, **and on the periodic checkpoint** (above) is the correction. Keeping it — rather than deleting it — is deliberate.
- **Embedding-model/dimension change invalidates the sum.** A summed vector is only meaningful within one model + dimension. Mismatch forces a reseed rather than silently summing incompatible vectors. This also future-proofs against C1 (per-collection embedding model).
- **`centroid_sum` is internal; the public surface is unchanged.** It is not added to `_ROUTING_FIELDS`, `SearchResult`, `CollectionDetail`, or any MCP/REST payload. Routing keeps consuming the derived `centroid`. This keeps B5 a pure hardening change with no contract break.
- **NaN/inf is an explicit reseed trigger.** A single non-finite element poisons `centroid_sum` permanently (NaN propagates through every future add/subtract) and the model/dim triggers never fire on a well-formed-but-non-finite sum. B5 guards both per-vector input and the stored sum; the degenerate-centroid → unroutable path (`router.py:28` returns 0.0 cosine for zero-norm) is pre-existing and unchanged.
- **Reuse the store-layer per-collection lock, don't invent a new one.** The guarding lock is specifically `SearchStore._collection_locks` (`store.py:132–140`, `_lock_for`), the one `ingest_chunks` already takes at `store.py:483` — **distinct** from `SearchCollectionSync._collection_locks` (the higher sync-layer lock, same key space, different call paths). `delete_document` must be made to acquire *this same store-layer lock* (it takes none today). REST `/ingest` also flows through `store.ingest_chunks`, so it is covered. A separate lock map would risk a different lock ordering and a deadlock.

## Edge Cases & Constraints
- **Pre-B5 collections (no `centroid_sum_json`)**: first read parses the absent/empty column to `None`; the next ingest (or an explicit recompute) seeds the sum via one `get_all_vectors` pass, then maintenance is incremental. Documented as expected one-time cost on upgrade. No forced migration.
- **Empty collection / count reaches zero**: deleting the last document resets `centroid_sum` and `centroid` to `None` (the normative empty-state phrasing used throughout this brief), `chunk_count`/`doc_count` to 0 — matching the "no-op if empty" semantics of `recompute_collection_meta` (`pipeline.py:397–398`) and the `centroid_present: false` reporting path. For the empty state, `None` and an all-zero vector are **interchangeable** for `centroid_sum` (a zero sum over zero chunks yields no meaningful mean, and the router treats a zero-norm centroid as unroutable, `router.py:28`); the brief states this once here and otherwise uses `None`.
- **Re-ingest (changed file) via `ingest_file`**: delete-then-add must net out correctly — the deleted document's vectors are subtracted and the new ones added; no stale residue and no double-count. Integration test pins this against the watcher re-ingest pattern.
- **Float drift over many cycles**: Python floats are float64, so straight accumulation relative error is ~ n·ε (ε≈2.2e-16) — on the order of 1e-10 even at 1e6 chunk mutations, negligible for cosine routing. The genuine risk is **catastrophic cancellation on subtraction** over very long interleaved add/delete histories, not plain accumulation. This is bounded by the **default-on periodic recompute checkpoint** (Core Flow step 6): an "incremental mutations since last full recompute" counter on the meta row triggers an authoritative `recompute_collection_meta` past a configurable threshold (default ~10k mutations) and on explicit reindex — so drift is reset without paying O(chunks) per sync. The drift-characterisation test documents the envelope; the integration drift guard asserts incremental-vs-full (same table state) stays within tolerance.
- **Embedding-model change mid-life or dimension mismatch**: stored `centroid_sum` length ≠ current `embedding_dim`, or `meta.embedding_model` ≠ writer's model → invalidate and reseed once. Never sum across dimensions.
- **Concurrent ingest into the same collection**: both updates are read-modify-write on the meta row; they must serialize under `store._lock_for(collection)` so neither lost-updates the sum. Ingest into *other* collections proceeds in parallel. Cross-process: not protected — documented.
- **Concurrent delete + ingest into the same collection**: serialized by the same per-collection lock; the resulting `(sum, count)` reflects both operations regardless of order.
- **Delete-only sync refreshes `last_indexed`**: a watcher sync that only deletes files (no adds) still bumps `last_indexed`, because every row-removing `delete_document` writes the meta row (including `last_indexed`) inside its locked critical section — even though `recompute_collection_meta` no longer runs on that path (`sync.py:708` removed). So a pure-delete sync still records that the collection was touched, without paying any O(chunks) cost. (The add path's `last_indexed` is instead written by the post-loop `store.update_description` call — see Core Flow step 1.)
- **Delete now contends for the store-layer lock (acquisition timeout + reindex starvation)**: because `delete_document` now acquires the **same** `store._lock_for(collection)` lock that `ingest_chunks` uses, it becomes subject to the same contention ingest already faces — including the `reindex_metadata` path holding that lock for its **full duration with no timeout** (`store.py:559–560`), which can starve a concurrent delete. Decision: **delete gets the same timeout-on-acquisition translation as ingest** — wrap the acquire in `asyncio.wait_for(..., timeout=INGEST_LOCK_TIMEOUT_S)` and raise `StoreBusyError` on timeout, mirroring `ingest_chunks` (`store.py:485–487`). This keeps the delete path's busy-handling consistent with ingest rather than blocking unboundedly behind a running `reindex_metadata`.
- **Malformed `centroid_sum_json` on disk**: parse to `None` (mirror `store.py:306–309` for `centroid_json`) and reseed; never crash the read path.
- **`recompute_collection_meta` still O(chunks) by design**: that is acceptable because it now runs only on explicit rebuild/seed/recovery, not on the per-sync hot path. The performance win is moving it *off* `sync.py:708`, not making the rescan itself cheaper.
- **`ingest_directory`'s in-memory `all_vectors` collector** (`pipeline.py:253–264`): still useful for description regeneration text (`all_chunks`) and as the batch sum source if the pipeline computes `batch_sum` before handing off, but it must no longer be the *sole* basis for the persisted centroid — the persisted value must fold into the existing meta, not replace it.
- **CLI `reindex` (drop + reingest, `cli/collection.py:282–286`) vs. REST `/reindex` (reingest over existing rows, NO drop, `routes_collections.py:300–325` → `_default_ingest_task` → `ingest_directory`)**: these do **not** operate on the same table state and therefore **cannot** be asserted to converge to the same value. The CLI form starts from an empty table so the sum rebuilds from zero; the REST form re-ingests over existing rows and **leaves orphaned rows** for any source file deleted / moved / excluded since the last index. Because the store-layer `(sum, count)` is a faithful tally of *actual* table rows (see "Partial-batch failure" below), the REST form keeps `sum == table` for the rows it touches — but the table itself still differs from CLI-reindex's by those orphans. So the **drift guard compares incremental-vs-full-recompute on the SAME table state**, not CLI-reindex vs REST-reindex. The CLI-vs-REST orphan-row behavioural difference is **pre-existing** (not introduced by B5) and **out of scope**. To guarantee an authoritative reset, an explicit full reindex job SHOULD end by calling `recompute_collection_meta` (full pass) rather than relying on incremental net-out (see Core Flow step 4).
- **Partial-batch failure mid-sequence (no divergence)**: because `(sum, count)` is maintained *inside* each store row-mutation's locked critical section, it is always a faithful running tally of the **current** table rows. A re-ingest is delete-then-add as two separate store calls (`pipeline.py:203–204`); if the `add` fails after the `delete` committed, **both** the table and the sum reflect "rows removed, not re-added" — so `sum == table` still holds (the collection merely has a missing document, which the watcher marks FAILED / retries). The only residual risk is a **hard crash between the row commit and the meta-row commit within a single store call**; this is bounded to one batch and reconciled by (a) the periodic recompute checkpoint (Core Flow step 6) and (b) the lazy/stale-marker reseed. Durability of the meta bytes across power loss is A7's concern, not B5's. Invariant: **`(sum, count)` always matches current table rows except for an at-most-one-batch window on hard crash.**
- **Pipeline early-returns cannot desync the tally**: `ingest_file` has three early returns before any store mutation — `.acl` skip (`pipeline.py:145`), parse error (`:151`), and zero chunks (`:182–183`, which returns *before* the `delete_document` at `:203`). None of these can desync the store-maintained `(sum, count)` from the table, precisely because maintenance is tied to store row ops (`ingest_chunks` / `delete_document`), **not** to the pipeline's batch vector collector — no row op fires, so neither sum nor table changes. This is a positive consequence of the store-layer decision. (Separately: a previously-chunked file that now parses to **zero** chunks hits the `:182` early return *before* the delete, so its stale chunks are not removed. That "emptied file leaves stale chunks" behaviour is **pre-existing and independent of B5** — out of scope — and does not desync the tally because no mutation occurs.)
- **NaN / inf vector poisoning**: a single NaN/inf element in an added/subtracted vector would propagate through `centroid_sum` permanently (NaN contaminates every future add and subtract), and the model/dim reseed triggers never fire on a well-formed-but-non-finite sum. B5 adds a NaN/inf guard on both per-vector input and the stored `centroid_sum` as an explicit reseed/guard trigger so one bad vector cannot permanently poison the running sum. A resulting near-zero / degenerate centroid (e.g. from catastrophic cancellation) makes the collection effectively unroutable — the router already returns `0.0` cosine for a zero-norm centroid (`router.py:28`); that pre-existing behaviour is **unchanged**, B5 only prevents the permanent-poison failure mode.
- **Eval harness coupling**: `eval/runner.py:484` currently calls `recompute_collection_meta` for setup — it may keep doing so (explicit recompute is sanctioned). Centroid-correctness and drift guards live in the **integration suite** (real LanceDB + real embedder); the eval harness is explicitly **not** the centroid-correctness gate — its deterministic, label-blind backends (`eval/backends.py`) would make a centroid/drift assertion vacuous, so it remains a routing-regression guard only. If any routing fixture's expected ordering depended on the *old* batch-only centroid, it is corrected following the threshold-change policy in `tests/eval/README.md` with a recorded rationale.

## Implementation Stacking Order (commit sequence)
The change spans schema, store, pipeline, sync, and docs; reviewability depends on a clean sequence. Each commit must independently pass the default pytest run.

1. **Schema — add `centroid_sum_json` to the meta table** (`store.py:_meta_schema`), thread it through `update_collection_meta` (write) and `get_collection_meta` (read, with malformed-JSON → `None` fallback), and add `centroid_sum` to `CollectionMeta`. No behaviour change yet (writers still pass `None`). Round-trip unit test + malformed-row test.
2. **Store-layer add path — accumulate sum + cumulative `chunk_count` on `ingest_chunks`** under the existing per-collection lock; derive and persist the mean centroid. Brand-new-collection bootstrap (absent meta row / absent `_META_TABLE` → `(0-vector, 0, 0)` seed, create the row reusing the lazy `_META_TABLE` create at `store.py:421–422`). Embedding-model/dimension guard + NaN/inf reseed trigger + reseed. Unit tests for accumulate, bootstrap-create, guard, lock serialization, no-full-scan.
3. **Store-layer delete path — vector-aware `delete_document`** that acquires the same per-collection lock (with `StoreBusyError` timeout translation, mirroring ingest), subtracts the document's vectors via the unlocked `_do_*`-style helpers, decrements counts, bumps `last_indexed`, and resets to empty state when the count hits 0. Unit + integration tests for subtract, re-ingest net-out, last-document reset, delete-only `last_indexed` bump, and lock contention/timeout.
4. **Pipeline — remove `ingest_directory` from the sum/count write path; route description through `store.update_description`.** The store-layer add path (commit 2) already folds sum / `chunk_count` / `doc_count` into existing meta, so `ingest_directory` no longer constructs a full `CollectionMeta` nor calls `update_collection_meta`. Add the locked partial-write `store.update_description(collection, description, last_described, described_at_doc_count, last_indexed)` — an **in-place partial update requiring the meta row to already exist** (created by commit 2's add path on the first `ingest_chunks`; a **no-op** if the row is somehow absent, never a row creator), and the writer of `last_indexed` on the add path — and have `ingest_directory` call it for the retained description-regen logic only, inside the `if all_vectors:` guard (`pipeline.py:278`) that guarantees ≥1 prior `ingest_chunks`. Unit test: `update_description` leaves sum/count/centroid untouched under a concurrent same-collection update; no-op when the row is absent. Integration test: multi-batch centroid correctness.
5. **Sync — stop calling `recompute_collection_meta` on the watcher hot path** (`sync.py:708`); rely on per-file incremental maintenance. Retain `recompute_collection_meta` as the explicit recompute/seed/recovery entry point and have it also populate `centroid_sum`. Test: incremental path issues zero full scans; explicit recompute issues exactly one.
6. **Periodic checkpoint + reindex/seed reconciliation** — the **store** maintains the "mutations since last full recompute" counter and `needs_recompute` flag on the meta row and **signals** the caller when the threshold is exceeded; the **caller** (`ingest_directory` / sync, outside the store lock where the embedder is available) checks the signal after the mutation and invokes `recompute_collection_meta` — the store never calls into the pipeline/embedder. Explicit full reindex jobs end with an authoritative `recompute_collection_meta`; lazy seed on pre-B5 collections. Drift-guard integration test compares **incremental-vs-full-recompute on the SAME table state** (not CLI-reindex vs REST-reindex, which differ by orphan rows — out of scope).
7. **Docs — reconcile `CON-4` in `530_…roadmap.md`, the B5 line in `03_world_class_roadmap.md`, add the `130_data_architecture` column note and the `210_performance` O(batch) note, and the `BREAKING.md` internal-schema entry.**

## Open Questions
- **What threshold / config key for the periodic recompute checkpoint?** The checkpoint itself is **decided** (default-on, Core Flow step 6 / Key Decisions) — it is no longer optional. The open part is only the concrete default value (~10k mutations is a starting point) and the config key name; calibrate against the drift-characterisation test for realistic dimensions and cycle counts.
- **Where exactly does the centroid division live** — store computes and persists both `centroid_sum` and derived `centroid` on every add/delete, or store persists only the sum+count and the read path divides? Default: persist both (the router reads `centroid` directly and a per-read division on a long list would add cost). Confirm in planning.
- **Is a `schema_version` marker on `CollectionMeta` warranted** to detect pre-B5 rows explicitly, rather than inferring from an absent `centroid_sum_json`? Same open question A1 deferred; absent-column inference is sufficient for B5 alone, but if A1's planning adds `schema_version`, B5 should reuse it.
- **Should the vector-aware delete return the subtracted vectors / sum** to callers (useful for B4 diagnostics and `/explain`), or keep the subtraction fully internal? Default: internal; expose later only if B4/A4 needs it.

## Future Iterations
- **B4 (stronger collection routing)**: summary-embedding / multi-centroid / clustered representations build directly on the now-correct single centroid B5 establishes. B5 is B4's correctness prerequisite.
- **C1 (per-collection embedding model)**: B5's embedding-model/dimension guard is the seam C1 extends; when a collection's model legitimately changes, C1 must trigger a reseed (or reject) using the same invalidation path.
- **A4 (`/explain`)**: could surface centroid freshness / `chunk_count` / drift-since-last-recompute as routing diagnostics; the vector-aware delete could optionally expose its subtracted sum.
- **Shared-router migration** (A6 future iteration): when the router becomes an `app.state` singleton, the same mutation sites B5 hardens (ingest, delete, reindex) must also call `invalidate()`; B5 keeps the persisted value correct so a stale-cache miss is the only remaining risk, owned by A6's funnel.
- **Cross-process meta locking**: if multi-process deployment becomes supported, the `(sum, count)` read-modify-write needs a file-lock or LanceDB-native guarantee — same limitation A1/A6 document.

## Recommendation
Build this before B4, and frame it as a **correctness fix that happens to also remove an O(chunks) hot-path cost** — not merely a performance optimisation. The debt register undersells it: the real defect is that the *common* ingest path (`ingest_directory`) silently clobbers the cumulative centroid with batch-only values, deletes ignore the centroid entirely, and only the *less-common* sync path pays the O(chunks) rescan the register describes. A `(centroid_sum, chunk_count)` pair on `CollectionMeta` fixes all three with one invariant. The hardest part is **the delete path**: incremental subtraction requires the deleted document's vectors, which today's `store.delete_document` discards — so the load-bearing decision is to make delete vector-aware at the store layer, and to keep the whole read-modify-write inside the existing per-collection ingest lock so concurrent ingests can't lost-update the sum. What must not be compromised: (1) **the full `get_all_vectors` recompute is kept** as the authoritative drift-reset and pre-B5 seed — incremental maintenance without a reconciliation path rots silently; (2) **the embedding-model/dimension guard** — summing across models or dimensions is worse than a stale centroid; (3) **`centroid_sum` stays internal** — no router-algorithm or public-contract change rides along, keeping B5 a clean hardening unit that B4 can safely build on.
