# Feature Brief: Provider-based collection descriptions and a shared LLM client

## Problem

Collection descriptions are generated by one hard-wired call to the `claude-agent-sdk` package (`archon_search/description_generator.py:98-129`) that works only when `ANTHROPIC_API_KEY` is set. The package is a core dependency (`pyproject.toml:15`), so every installation carries it, including installations that run only local models. Without the key `generate_description()` returns `None` (`description_generator.py:74-76`), every other failure is logged at DEBUG only (`description_generator.py:84-95`), and nothing in `/status`, `/ready` or the wizard says the feature is not working. The operator gets no description, no warning and no way to set one by hand (`PatchCollectionBody` accepts only `embedding_model` and `default_ttl_seconds`, `schemas.py:648-653`; MCP `update_collection` has no description argument, `mcp.py:1620`). Descriptions feed the routing prompt (`router.py:303`) and hybrid routing (`router.py:161-185`), so a missing description silently degrades routing under `routing_strategy = "hybrid"`.

The four places that call an LLM (HyDE, RAG Fusion, graph enrichment, description) also each carry their own provider code, with two different failure contracts (query-expansion adapters never raise; enrichment clients raise), and the Ollama enrichment client talks to `/v1/chat/completions`, where the context window cannot be set per request.

## Goal

An operator can turn on collection descriptions in the wizard exactly as they turn on HyDE: choose a provider (`anthropic`, `openai`, `ollama`, `claude_cli`, `llama_cpp`), a model and a host, and get descriptions from a fully local model with no Anthropic key and without `claude-agent-sdk` installed. When the feature is enabled but cannot work, the operator is told at startup, in `/status` and on the affected collection. All four LLM features go through one shared client layer, and each feature keeps its own provider, model and host. Every prompt is sized to the context window of the model that receives it.

## Users & Context

- Operators who install through the wizard and run local models (Ollama, llama-server) or cloud providers, often with several collections and namespaces.
- Existing operators who set `ANTHROPIC_API_KEY` today and currently get descriptions with no configuration.
- Operators of small local models, whose context window is as small as 4k to 8k tokens, and operators of cloud models with 200k or more.

## Core Flow

1. The wizard asks its own yes/no question, "Enable collection descriptions?" (default no), separate from the HyDE and RAG Fusion question. The banner states that for `anthropic`, `openai` and `claude_cli` excerpts of document text leave the machine.
   - Revised after implementation (2026-11-01): "default no" is not an Enter default: Enter re-asks ("Please answer y or n."), and only a closed stdin answers no.
2. On yes, the wizard asks for the provider, then the model, then the host for `ollama` or `llama_cpp`, as it does for HyDE. For `ollama` it also asks for the context window to use and suggests 8192. Last, it asks whether existing collections should be filled automatically at startup.
   - Revised after implementation (2026-11-01): for `ollama` and `llama_cpp` the wizard asks the host before the model (`anthropic` asks no model, `llama_cpp` asks no window). A blank model for `openai`, `ollama` or `llama_cpp` leaves the feature disabled (exit 0, nothing written); HyDE and RAG Fusion are untouched. The backfill question has no Enter default either: Enter re-asks, closed stdin means no.
3. The wizard writes a `[description]` section. API keys stay in `.secrets.env` as today.
4. At startup the server validates the setup. If the feature is enabled and the provider is unreachable, the key is missing or the context window is unknown, it logs a WARNING and still boots. If an operator has `ANTHROPIC_API_KEY` set and no `[description]` section, it logs a notice that descriptions are off and how to turn them on.
5. On ingest, when the existing regeneration rule fires (first ingest, or the document count moved by 20% or more), the pipeline samples excerpts that fit the model's context window and asks the configured provider for a 2-3 sentence description. This runs in the background, so ingest does not wait for the model.
6. The operator sees the description, where it came from (`generated` or `manual`) and its status (`ok`, `failed`, or `pending` while a run is in flight) through the collection metadata calls, and sees the description provider's health and effective context window in `/status`.
7. The operator can set a description by hand through REST, MCP and CLI. A manual description is never overwritten by generation. Clearing it returns the collection to automatic generation.
8. The operator fills missing descriptions in one of two ways. Either `collection describe <name>` or `collection describe --all` runs on demand and ignores `backfill_on_startup`; or the wizard-chosen `backfill_on_startup = true` makes the server do the same in the background at every startup, for collections that have no description. The command still needs a configured description provider; if there is none, the server refuses the describe call with that message (a 409) and the command prints it and exits 1.
   - Revised after implementation (2026-11-01): `collection describe --all` first reads `GET /status`; when `description` is null it prints the setup message and exits 1 before listing anything (any other `/status` answer is "unknown" and the per-collection 409 stays the authority). `collection describe <name>` relies on the 409.

## In Scope

- A `[description]` config section mirroring `[hyde]`: `enabled` (default `false`), `provider`, `model`, `ollama_base_url`, `llama_cpp_base_url`, `ollama_context_tokens`, `backfill_on_startup` (default `false`), `timeout_seconds` (default 30, per attempt), `max_sample_chunks` (default 100), `think` and `include_restricted_chunks`. `ollama_context_tokens` also appears in `[hyde]`, `[rag_fusion]` and `[graph]`.
- A wizard step with its own question and the HyDE-style follow-ups, written to the config by the existing config writer, with the same revert-on-failed-install handling the other provider sections have.
- A shared LLM client layer: one interface, thin wrappers over the existing provider SDKs (`anthropic`, `openai`, `ollama`), `httpx` for `llama_cpp`, and the `claude -p` subprocess for `claude_cli`. Calls are stateless (one user message, no history) and raise on failure; each feature's caller decides its fallback and logs the failure.
- Migration of HyDE, RAG Fusion, graph enrichment and the new description feature onto that layer, with a clean cutover: no shims, every caller moved, the old adapters, both protocols' old forms, the enrichment factory and `_build_query_expansion_provider` removed; prompt templates and variant parsing move to the consumers.
- Graph enrichment gains `claude_cli` on the shared client (reverses the C6 ADR deferral), with the prompt on stdin and `extraction_rate_limit_rpm` applied to it (the limiter moves into the shared client layer; today only the Anthropic enrichment client has one). Every feature on `claude_cli` sends its prompt on stdin, and the subprocess is locked down (tools disabled, no session saved, neutral working directory, no `CLAUDECODE`, killed on timeout and on cancellation).
- Context-window handling: cloud providers get no setting and no trimming; `llama_cpp` reads its window from `GET /props`; `ollama` takes an explicit `ollama_context_tokens` and sends it as `num_ctx`. Every prompt is sized ahead of time to the window minus the output reserve and the prompt template; there is no truncation detection after the call. The description sample keeps its ceiling of 100 chunks (`max_sample_chunks`) and is drawn across the whole collection, not from the first rows.
  - Revised after implementation (2026-11-01): HyDE and RAG Fusion queries are sized to the window with `archon_search/llm_client/fit.py`; no fixed 2000-character query cut remains, and cloud queries are sent untrimmed. The Ollama estimate also counts digits and emoji, and the `llama_cpp` budget counts the chat framing through `/apply-template` and honours `think`.
- Visibility: startup WARNING for a configured but unusable provider, a WARNING when `routing_strategy = "hybrid"` runs without descriptions, warn-once rate limiting, per-collection `description_source` and `description_status`, and description fields in `/status`.
- Manual description set and clear through dedicated REST routes, two MCP tools and CLI verbs; `collection describe` as an on-demand job that forces regeneration: the intent of the existing, currently unreachable `force_regenerate_description` flag (`pipeline.py:1232`), which lives only on `ingest_directory`, so the force path moves into the generation entry point and the parameter is removed.
  - Revised after implementation (2026-11-01): `force_regenerate_description` is removed from the pipeline (it was not only on `ingest_directory`: also in `_finalize_batch_ingest` and its callers). Every path that changes a collection's documents (single-file and batch ingest, sync and the watcher, removals through `finalize_after_removal`) requests a description through one routine, `SearchPipeline.finalize_collection_change`; import and the eval runner do not.
- Collection metadata gains `description_source` and `description_status` through a startup migration (no schema version bump); the same startup migration fix covers the missing `default_ttl_seconds` column.
- Export manifest version 2 carries `description` and `description_source`.
- Removal of `claude-agent-sdk` from `pyproject.toml`, `_ENV_LOCK`, the `CLAUDECODE` environment mutation, and the SDK assertion in `tests/test_cli_startup_latency.py`.
- A new ADR (next free number, 19 today and also claimed by another plan, so whichever lands second takes the next; ADRs are append-only, so it supersedes the relevant parts of `C6-local-llm-provider.md` and `12_local_prose_relations_enrichment_narrowed.md` instead of editing them), a `BREAKING.md` entry, and updates to the architecture, security, operator and user docs that name the SDK or describe description generation.
  - Revised after implementation (2026-11-01): the ADR is number 19, `Documentation/ADRs/19_shared_llm_client_and_provider_based_collection_descriptions.md`; the `BREAKING.md` entries are NR-54 to NR-68 in the breaking-changes index.

## Out of Scope

- A no-LLM description built from top terms and file types: dropped by the product owner for now.
- Conversation or session management for LLM calls: every call is already a single stateless message, so there is nothing to clear; statelessness becomes a tested contract of the client instead.
- A plain-HTTP rewrite of the Anthropic, OpenAI and Ollama adapters: the `anthropic`, `openai` and `ollama` SDKs stay as the way to reach those providers, and thin wrappers replace the old adapter modules (less code, simpler).
- A default limit on the context window for cloud providers: they have ample room, and the largest known prompt (about 51k tokens) fits.
- Changing the 20% regeneration rule or the routing algorithms. The description prompt wording changes only by adding the output rules in the Key Decisions ("Description output rules").
- Per-collection provider overrides and multilingual or customised prompts.

## Key Decisions

- **Own wizard question, default off**: descriptions send document text, not queries, so the privacy notice and the cost differ from HyDE and RAG Fusion.
- **Off by default, with a startup notice and a `BREAKING.md` entry**: nothing leaves the machine unless the operator chose it. The notice appears only when `ANTHROPIC_API_KEY` is set and `[description]` is absent, so an operator can silence it by writing `enabled = false`.
- **Shared client wraps the existing SDKs**: less new code than a plain-HTTP rewrite. Sharing means one interface and one failure contract, not one provider or model for everything; `[hyde]`, `[rag_fusion]`, `[graph]` and `[description]` each keep their own provider, model, host and context setting.
- **Raise-on-failure contract**: the never-raise adapters are what let the description failure go unnoticed. Callers keep their existing fallbacks (`hyde_applied: false`, `summary_text=None`) but log a WARNING, rate-limited to once per process.
- **Description output rules**: the description prompt tells the model the rules: one line of plain text, at most 600 characters. The result is cleaned (thinking tags removed, whitespace collapsed to one line) and accepted only if it is non-empty and within 600 characters. A rejected result is retried automatically once, with the same single stateless message plus a reminder of the limit; provider errors (server down, timeout, key rejected) are not retried. If the retry is also over the limit, the text is trimmed to the last full sentence within 600 characters and stored. If nothing usable remains (empty, or only thinking tags), the description is not stored, `description_status = failed`, any earlier description is kept, and a WARNING is logged. A failure never stops ingest, startup or the server. For cloud providers a retry sends the excerpts a second time.
- **Context window by provider**: cloud none; `llama_cpp` auto from `/props` with exact token counts from its tokenize call; `ollama` explicit (suggested 8192 because Ollama's own default is 4096 under 24 GiB of VRAM, which is tight for descriptions and enrichment, and one value across features avoids model reloads when features share a model), estimated with a gpt2-based token counter (a new component: the repository has none, gpt2 only appears as the tokenizer name the chunker hands to its chunking library) plus a 20% margin on top of the reserved answer space and template. Accepted risk: the margin was measured by the author on a small sample, and Ollama's real default window depends on VRAM and server settings, so an unset value (not sent) can be below or above the assumed 4096. A missing Ollama value assumes 4096, is not sent as `num_ctx`, and logs a startup WARNING (existing HyDE, RAG Fusion and graph Ollama users see it after upgrade); a failed `llama_cpp` probe assumes 4096 and logs a WARNING.
- **Size ahead, never detect after**: no post-call truncation detection and no safety net. The server also logs a startup WARNING when the configured Ollama window exceeds the model's real maximum (read from Ollama `/api/show`).
- **Reasoning models**: `[description].think` is `default` (send no thinking control), `true` or `false`; the answer ceiling is generous for all models so `default` works on reasoning models. A non-default value is ignored with a startup WARNING for providers with no verified switch (`anthropic`, `openai`, `claude_cli`); `think = true` on a model without thinking support gives a clear WARNING. A result still empty after the retry gets a WARNING that points to `think`.
  - Revised after implementation (2026-11-01): a description call that may think (`think` is not `false`) adds `DESCRIPTION_THINKING_HEADROOM_TOKENS` (3072) to its answer ceiling and pays for it out of its sample, because a reasoning model's thinking counts against the ceiling.
- **Legacy and pending state**: collections that already have a description read as source `generated`, status `ok`; an empty description reads as no source and no status. `pending` is held in memory only and overlaid while a generation runs; stored values are `ok`, `failed` or empty. A restart loses `pending`; the baseline is saved only on success.
- **Describe on a manual description**: REST 409 and CLI exit 1 with a message to clear it first; `describe --all` skips manual collections, lists them and exits 0, but exits non-zero on provider failures. `describe <name>` on a collection with a generated description forces a fresh generation; `describe --all` fills collections whose description is empty or whose stored status is `failed` and lists the manual ones and the other described ones as skipped.
- **Clearing is a reset only**: description, source, status, last-described and the document-count baseline go back to never; no immediate generation (the CLI hints at `collection describe`). Setting a manual description sets source `manual`, status `ok`, last-described now, baseline untouched.
- **One write path keeps the routing vector fresh**: generate, manual set, clear and import all go through one shared write-description operation that refreshes (or removes) the routing vector in the same step; if embedding fails the description is kept without a vector and a WARNING is logged.
- **On-demand describe is a job**: `POST /collections/{name}/describe` answers 202 with a job id; the CLI `--wait` polls the job. `--all` loops over the caller's namespace. No MCP describe tool.
- **Dedicated set and clear operations**: REST `PUT` and `DELETE /collections/{name}/description`, MCP `set_collection_description` and `clear_collection_description` (tool count 20 to 22 with the four key-management tools, which register only when a key store is passed; 16 to 18 without), CLI `collection set-description` and `clear-description`. Manual text follows the same limits as generated text (one line, 600 characters) but is rejected (422), never trimmed. Authorization is "the collection exists in the caller's namespace", so meta-only collections work; `PATCH` and `update_collection` stay unchanged.
  - Revised after implementation (2026-11-01): the counts are as stated (18 without a key store, 22 with one). MCP sessions are bound to the credential that opened them, and the return types of `ingest_directory`, `list_collections`, `get_collections_meta` and `list_documents` are now unions with the error object, so their `outputSchema` changed (NR-65). The 422 body of the REST `PUT` is FastAPI's validation list, and the new response fields are optional with a null default in OpenAPI.
- **Graph provider packages**: `anthropic` needs the `anthropic` package (extra `hyde`, already needed today), `openai` the `openai` package (extra `openai-provider`, already declared; only graph's use is new), `ollama` the `ollama` package (extra `ollama`, already declared; only graph's use is new), `llama_cpp` nothing, `claude_cli` the `claude` binary. A missing package at startup is a WARNING with the install hint and graph enrichment stays off; the server still starts (HyDE and RAG Fusion keep their refuse-to-start error). The wizard installs the matching extra and reverts on failure.
- **`claude_cli` for graph**: the prompt goes on stdin; `extraction_rate_limit_rpm` (default 60) applies because a Claude login has an account-level quota; HyDE and RAG Fusion `claude_cli` stay unthrottled.
- **Status block**: `/status` `description` is null when the feature is off, otherwise provider, key availability, reachability (own startup probe, null until probed, never part of `/ready`), effective context tokens and their source (`configured`, `probed`, `assumed`), `backfill_on_startup`, and the last attempt's result and time (in memory). `llama_cpp_ok` is unchanged.
- **Startup backfill hosting**: a background task started after the startup sync, registered with the other background tasks and cancelled and drained at shutdown. It walks every namespace one collection at a time, skips a collection already being generated, skips collections whose stored status is `failed` (ingest and describe still retry them; the rule lives on the stored value, so it holds after a restart), and fills only collections with no description. It waits for the startup sync (done or failed, or none when no sync task exists) and for the description provider's reachability probe before it starts. It is skipped for the whole run, with one INFO naming the reason, when the startup sync is suppressed by the crash-loop guard (the previous run died mid-ingest); a clean `POST /sync` re-enables it at the next start, and `collection describe` works meanwhile. All generation tasks (ingest-triggered, describe job, backfill) are owned by one lifecycle service that allows one generation per collection and one in the process at a time and cancels them at shutdown.
  - Revised after implementation (2026-11-01): the reachability probe runs whenever descriptions are enabled, independent of `backfill_on_startup` and of the sync state; it sends no prompt and no document text, so "no provider is called" while the sync is suppressed means no generation call. With a suppressed sync the backfill is skipped without waiting for the probe. A failed generation whose failure the busy store refused is remembered by the lifecycle and read as `failed` until the description version changes.
- **Export format version 2**: the manifest carries `description` and `description_source`; version 1 archives (every existing backup) are refused on import unless `ignore_schema_version` is set (that flag only skips the version comparison; the embedding-model check stays). A bypassed v1 description with no source imports as `generated`; source `manual` stays manual. An imported description gets status `ok`; the baseline stays unset. No dual-format code. Only `description_source` is new (version 1 manifests already carry `description`); every existing backup, including the automatic backup loop's, becomes a version 1 archive that needs `ignore_schema_version` to restore, which BREAKING.md and the backup and restore guide state.
- **ACL and descriptions**: the sample uses only open chunks (ACL unset); a chunk with any ACL, including deny-all, is never sampled or sent. `include_restricted_chunks` (default `false`) is allowed only for `ollama` and `llama_cpp`; for other providers it is ignored with a startup WARNING; when enabled a startup WARNING names provider and host, and a second WARNING fires if the host is not loopback; the WARNING also says that restricted text may then appear in descriptions every reader of the collection can see. With no open chunk and the switch off, no description is generated, status `failed`, WARNING "no unrestricted chunks to describe"; the operator can set one by hand.
- **Sampling fix**: the sample is drawn across the collection, not the first rows in insertion order.
- **Metadata columns by startup migration**: `description_source` and `description_status` are added at every server start, with no `STORE_SCHEMA_VERSION` bump and no migration spec, like the two newest metadata columns; the bump-policy text in `CLAUDE.md` and the comment next to the version are updated to state the real rule. Rolling back keeps the store openable (an older writer leaves the new columns untouched), though the stored source can then lag the text an older server wrote. A missing `default_ttl_seconds` startup migration is added in the same change (a metadata write on a table without that column fails today); it reverses the documented practice that version-1 migrations run only through `POST /collections/{name}/migrate`, so `CLAUDE.md`, the upgrade guide and BREAKING.md are updated, and the migrate route becomes a no-op for that spec.
- **No install flag**: no `--enable-description`; the wizard question is the install path, `config set` the scripted one, and `description` joins the `config` command's default sections.
- **Test strategy**: an auto-skipping live test for local models like `tests/integration/test_llama_cpp_e2e.py`; a real-subprocess fake-binary test for `claude_cli` (fake `claude` on PATH reading a very large stdin prompt); "SDK not installed" is proven by removing the package from `pyproject.toml` and `uv.lock` plus an import check and the existing `sys.modules` masking pattern (the unlocked-deps lane installs every extra and cannot prove absence). The implementing dev rewrites the pinned wizard prompt-order tests in the same change.
- **Manual wins**: a manual description is never overwritten; clearing it returns to automatic generation.
- **Background generation**: a slow local model must not stall ingest.
- **Backfill: wizard question saved to config, plus an explicit command**: the wizard asks whether to fill existing collections at startup and writes `backfill_on_startup` (default `false`; the wizard's default answer is No, so a surprise mass LLM run never happens unless chosen). `collection describe --all` always works on demand, whatever `backfill_on_startup` says.
- **Manual description needs no admin**: the key whose namespace owns the collection may set or clear it (see "Dedicated set and clear operations"); only collection creation is admin-only (`routes_collections.py:411`).
- **Import restores the description**: export writes `description` into the manifest (`routes_export.py:234,244`), but a search of `jobs/` and `routes_export.py` finds no code that reads it back, so a manual description is lost on export and import. Export and import will carry `description` and `description_source` (see "Export format version 2").
- **Description health is reported in `/status` and the startup log only, not in `/ready`**: descriptions are optional, and `/ready` answers whether the server can serve searches, so a flaky LLM must not flag the server.

## Edge Cases & Constraints

- **Delivery order**: group A (shared client and migration; the behaviour tests stay green and the tests pinned to the old adapter modules are rewritten onto the shared client), group B (the description feature, including its status columns and migration), group C (wizard, state exposure and operations).
- **Provider down at startup**: boot is never blocked (same rule as the C6 provider work); WARNING logged, `/status` reports the provider as not ok, and startup backfill is skipped.
- **Startup backfill scope**: only collections with no description, one at a time, in the background and cancellable at shutdown, across every namespace. Collections that were already described are never regenerated by backfill.
- **Server restart while a description is pending**: the pending state is lost; the next qualifying ingest or a `collection describe` call picks it up.
- **Local reasoning models**: output may be empty, contain thinking tags or ramble; the description output rules (Key Decisions) apply, so the result is cleaned, length-checked, retried once and then trimmed, and only a result with nothing usable sets `description_status = failed`.
- **Lock timeout when saving**: `store.update_description` currently returns silently when the collection lock times out (`store.py:1886-1888`); with this feature that must be reported as a failed description, not swallowed.
  - Revised after implementation (2026-11-01): `SearchStore.update_description` is gone; the guarded `SearchStore.write_description` returns `lockTimeout`, which the lifecycle records as a failed description (remembered in memory when the busy store refuses it). An aborted `/search` or `/explain` and the MCP search tools cancel the provider call.
- **Two Ollama features sharing a model with different context values**: Ollama reloads the model when the context value changes (measured load 9 to 13 s on the author's machine); the wizard asks per feature, suggests 8192 and offers the previous value as the default.
- **Hybrid routing without descriptions**: a WARNING at startup, because routing falls back to the centroid only for those collections.
- **Graph enrichment now needs packages**: the `openai` and `ollama` enrichment clients use `httpx` today; after the migration they need the `openai` and `ollama` packages (the `anthropic` client already imports its package). `_check_provider_deps` (`app.py:395`) guards only HyDE and RAG Fusion, so the graph provider gets a guard that warns and keeps graph enrichment off, and the wizard installs the extra (see "Graph provider packages").
- **Privacy**: cloud providers receive up to 100 chunk excerpts, not just a query; add a startup INFO as HyDE has (also for `ollama` or `llama_cpp` on a host that is not loopback), and update the security architecture doc. The telemetry no-raw-query rule is untouched.
- **Existing tests pinned to old behaviour** (`tests/test_description_generator.py`, `tests/test_anthropic_key_guards.py`, `tests/test_cli_startup_latency.py:146`, the wizard prompt-order e2e tests such as `tests/test_e2e_wizard_optional_features.py:376`) must be rewritten or deleted, not re-pinned.
- **Registry rules stay**: a new provider-consuming section must keep `tests/test_provider_registry_sync.py` green.

## Open Questions

None. The product decisions are folded into Key Decisions, In Scope and Edge Cases above, and the team plan records each resolved question.

## Future Iterations

- A deterministic description from top terms and file types for installations that run no LLM.
- Comparing Ollama's reported prompt token count with the sent estimate, as a post-call truncation guard.
- Scheduled or on-demand refresh of stale descriptions beyond the 20% rule.
- Per-collection provider or prompt overrides.
- Descriptions in the collection's dominant language.

## Recommendation

Build it, in the agreed order: the shared client and the migration of the three existing features first, because the new feature should sit on a client the existing tests already protect. The hardest part is context-window handling for local models, because the failure mode (silent truncation) is exactly the kind this feature exists to remove, so ahead-of-time sizing and the startup warnings must ship with the first version, not later. Do not compromise on three things: no silent failure anywhere in the path, no cloud transfer the operator did not choose, and each feature keeping its own provider and model.
