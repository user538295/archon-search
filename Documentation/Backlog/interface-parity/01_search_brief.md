# Feature Brief: Search on one implementation across REST, MCP, OpenAI shim and CLI

Slice S1 of the [interface parity roadmap](./roadmap.md), the pilot. It follows the rules C1-C14 of [Brief 00](./00_service_layer_foundation_brief.md). Roadmap S0 has landed: `archon_search/services/` (`authz`, `request_hyde`, `search_budget`, `validators`), the import-boundary test `tests/test_layer_import_boundary.py` and the parity registry `tests/parity/registry.py` already exist, so this slice edits them. This is the first consumer of the service layer, so it implements what Brief 00 deferred: `ServiceError`, the services container, the first service and the adapter error-mapping tables, none of which exist yet.

## Problem

Search is implemented three times. REST (`server/routes_search.py`, handler from line 292), the MCP `search` tool (`server/mcp.py`, from line 513) and the OpenAI shim (`server/routes_openai_shim.py`, `chat_completions` from line 152) all call `SearchPipeline.search` or `search_many`, and each re-implements everything around the call. A comparison of the three found 20 behavioral differences (table below), several of them visible to users: an MCP or shim single-collection search hands the embedder cache an unbounded wait where REST gives up after 0.5 seconds and degrades to full-text-only (the model weights are built later, in the bounded warm-up that MCP and the shim already call; the cache's own 120-second bound covers only a caller that waits behind another caller's in-flight load of the same model, and the caller that runs the load itself, queued in the thread pool, has no bound); a `ppr` search over several collections is a 422 on REST and silently runs on MCP; MCP records no telemetry when a search times out, and the shim records no telemetry for any outcome. The CLI has no search command at all.

The `top_k` parameter is worse than a drift. REST validates it (`1 <= top_k <= top_k_max`) and then never forwards it, because `pipeline.search` and `search_many` take no `top_k`; the result count comes only from `[database].top_k_return` (`tests/integration/test_s313_top_k_does_not_set_result_count.py` pins this). The OpenAI shim accepts `top_k` and ignores it. MCP has no `top_k`.

## Goal

The same query returns the same ordered results, the same derived fields and the same errors on REST, MCP and the CLI. The OpenAI shim runs on the same service, keeping its protocol-specific rendering. One `SearchService` owns validation, collection resolution, embedder selection, warm-up, HyDE and RAG Fusion, the budget, telemetry and derived fields. Operators can run `archon-search search` from a terminal. The parity registry reports Search as covered on REST, MCP and the CLI; the shim is a waived registry row (adapter policy, `tests/parity/registry.py` line 1142).

## Users & Context

- API clients (REST) that today depend on exact 422 strings.
- MCP agents (Claude Code and others) that call `search` with flat filter parameters.
- OpenAI-compatible clients using `model = "archon-search"` or `"archon-search/<collection>"`.
- Operators who want to try a query from a terminal without writing `curl`.

## Core Flow

The canonical order of steps, owned by `SearchService.search(command, caller)`:

1. Normalize and validate the command in REST's actual order. REST's Pydantic request model validates first (a framework-shaped 422): stripped non-empty `query`, exactly one of `collection` or `collections`, non-empty, stripped, de-duplicated `collections`, a known `graph_mode` value and `top_k >= 1` when given. The handler then checks, in this order: `collections` count within `max_fanout`; `top_k` within `top_k_max`; `scope_filter` syntax; `scope_filter` together with `graph_mode`; `ppr` together with `collections`; and `graph` enabled, last (`routes_search.py` lines 301-338). REST keeps its request model as transport parsing: its field and model validators (`routes_search.py` lines 170-208) call the one normaliser in the service (not `services/validators.py`, which holds only the scope-filter syntax check), so each rule exists once and the framework 422 list shape and every exact string stay.
2. Check each collection name with `is_valid_collection_name` (`store.py` line 174), then verify the collection exists in the caller's namespace (single path) or let `search_many` verify it (multi path); translate a missing collection and a metadata-store failure into `ServiceError`. A name that is not a valid collection name is `not_found`: the real store raises `ValueError` for it (`store.py` lines 790 and 1153), which REST answers as a 503 `metadata_store_error` today, so without the check it would be taken for a metadata-store outage and recorded as one.
3. Select the embedder (single path): wait at most the embedder cache handoff bound (`EMBEDDER_WARMUP_WAIT_SECONDS`, 0.5 s), then degrade to full-text-only with `embedder_cold` instead of failing.
4. Warm the models (`warmup_for_search`).
5. Resolve HyDE and RAG Fusion, suppressed by the existing rules (`hyde_suppressed`).
6. Run the pipeline under the search budget.
7. Derive response fields once (`expansion_used`, `expansion_warning`, the effective embedding model, applied filters, metadata projection, ACL gate when requested).
8. Record telemetry for every outcome the telemetry decision below lists.
9. Return a `SearchOutcome`; each adapter renders it.

CLI: `archon-search search "<query>" --collection docs [--collection other] ...` prints a ranked list (rank, score, collection, source path, text excerpt); `--json` prints the response re-serialised in the repo's `--json` format (`json.dumps(payload, indent=2, sort_keys=True)`, Brief 00 C10) with the same values as the REST body. One `--collection` selects the single-collection path; several select the multi-collection path.

Validation order and the 422 texts also follow REST, because clients and tests pin its exact strings (`test_e0c_be3_validation.py`, `test_e2h_t1_ppr_guard_paths_e2e.py`, `tests/server/test_search_explain_error_contract.py`).

Other decisions:

- **Single versus multi path stays visible.** `collection="x"` runs `pipeline.search` with the per-collection embedder; `collections=["x"]` runs `search_many` with the global embedder and excludes collections whose model differs. This is core behavior, not drift, so the service exposes both and the CLI maps one `--collection` to the first and several to the second.
- **Errors move into the service (C5)**: every `except` in the three search handlers (`GraphCommunitiesNotBuiltError`, `CollectionNotFoundError`, `FanoutTimeoutError` and `SearchBudgetExceeded`, `MetadataLookupError`, `EmbedderNotReadyError`) becomes one translation in the service plus one table per adapter. The HyDE and RAG Fusion dependency errors no longer exist (ADR 19 removed them; a HyDE generator failure reaches the generic failure path), so the service has no such error kind. Existing REST body shapes (plain `ErrorDetail` versus the coded `{"detail":{"code","message"}}`) are preserved unless the table row says otherwise; the `Retry-After: 30` header is set from one constant.
- **MCP filter parameters stay flat; REST's `filters` stays nested.** Both build the same `SearchFilters` inside the service from the same canonical field names. The existing superset guard `tests/server/test_mcp_search.py:262` keeps protecting this.
- **Existing tests that pin drifted behavior are rewritten, not re-pinned** (C13): for example the MCP `ppr` plus `collections` skip in `tests/test_mcp.py:614-624` (its comment claims MCP rejects it before HyDE, which is false), and the stale docstring in `tests/integration/test_mcp_error_paths.py:101-104`. The exact-string integration tests (`test_e0c_be3_validation.py`, `test_e2h_t1_ppr_guard_paths_e2e.py`) must keep passing for REST.
- **Telemetry (rows 10 and 11).** The service records success, timeout and internal error on every interface; an embedder-not-ready, a metadata-store failure and a HyDE failure are recorded as `internal_error`/`other`, the way REST's `_enqueue_error` already records embedder-not-ready and the HyDE failure (`routes_search.py` lines 105, 135 and 635; REST records no entry for a metadata-store failure today, so that one is new behaviour, and the incident runbook line that says so changes). Validation-class errors are not recorded: validation, the graph and scope-filter kinds, graph communities not built (a 422 that REST records nothing for today, `routes_search.py` lines 642-646), not-found and a name that is not a valid collection name (`not_found`, not a metadata-store failure). Stage timings follow REST (single path, flag on, also on its error branches). `TelemetryEntry.from_error` already accepts every non-`ok` status and error kind (`telemetry/entry.py` lines 71-86 and 246-256, `routes_route.py` already records `validation_error`), so the entry model does not change; only REST's `_enqueue_error` narrows the types, and it is deleted. Labels stay as today. Filter flags and hashed document ids are recorded on the single path only: `from_search_multi_result` takes neither (`telemetry/entry.py` lines 192-203) and stays unchanged, so the multi-path entry carries neither before and after this slice. Shim searches start appearing in the operator's telemetry stats with the same labels, which gets a `BREAKING.md` note.
- **Shim error and `top_k` policy.** An unexpected failure on either shim branch answers the 503 `Service temporarily unavailable.` envelope (defined behavior; the fan-out branch had none). The shim strips the collection name taken from the model name and answers its 404 not-found envelope for three cases: an empty name (`archon-search/`), a whitespace-only name and a name that is not a valid collection name (`is_valid_collection_name`, `store.py` line 174). Today the shim looks the name up unstripped (`routes_openai_shim.py` lines 198 and 282-292) and the real store raises `ValueError` for an invalid name (`store.py` lines 790 and 1153), which the shim's catch-all answers as a 503 (lines 284-285); the 404 for `archon-search/` holds today only with a mocked pipeline (`test_routes_openai_shim_be5.py` line 679). Against a real store an empty, whitespace-only or invalid name therefore changes from a 503 to a 404 (a `BREAKING.md` entry), and its test runs against the real app. The shim's schema accepts any integer `top_k` and the shim ignores it, as today (`schemas_openai.py` lines 77-79); that stays so by decision: no value of a request `top_k` gets a 4xx or changes the count, and the operator controls the shim's count through the `[openai_shim].top_k` key (see Resolved Questions).
- **MCP `search` response schema.** MCP cannot import REST's `SearchResultSchema` (`routes_*` rule 2) and `McpSearchResultSchema` is shared with `search_with_context` (`mcp_schemas.py` line 49), so `acl_gate` is added through a search-only subclass or schema.
- **Known trade-off: `acl_gate` content.** `acl_gate` carries `allowed_principals`, `source`, `sidecar_path` and `warnings` (`schemas.py` lines 975-978). The principals already ship per result as `acl` on REST and on MCP (`mcp_schemas.py` line 65), and MCP `explain` already returns the same `acl_gate`, with `sidecar_path`, `source` and `warnings`, on every candidate and not opt-in (`routes_explain.py` lines 192 and 215-220; MCP `explain` builds `ExplainResponse`, `mcp.py` lines 1200 and 1316). `sidecar_path` is a path relative to the collection root, or the bare file name when the sidecar lies outside it (`pipeline.py` lines 850-858). REST returns all of it to the same authenticated callers. MCP `search` therefore gets parity with MCP `explain` and REST, not a new exposure; it is opt-in (`acl_context`) under the same authorization, and no redaction is added in this slice.
- **Identity and error shapes.** In production a request with no identity is answered first by `APIKeyMiddleware` with a bodyless 401 (`middleware_auth.py` line 152, `_unauthorized`), which the shim's `OpenAI401Middleware` rewrites into the OpenAI envelope for `/v1`; the adapter-level checks are a second line reachable only without the middleware (a route mounted without it, as the tests do): REST's existing `caller_identity` 401 `authentication required` (`server/authz.py` lines 40-45) and the shim's OpenAI 401 envelope, both before the service. REST keeps its two distinct 500 shapes (a HyDE failure is JSON `search failed`, any other pipeline failure is plain text; declared in `routes_search.py` and the runbook), so the service has distinct kinds for them.
- **Composition.** One class and one code path, not one object. REST builds the service per request from `request.app.state` (there is no lifespan instance: tests build a `TestClient` without lifespan and swap `app.state.pipeline` after creation); the shim does the same (it reads `request.app.state.pipeline` and `.config`, `routes_openai_shim.py` lines 170-171); the MCP factory keeps its signature and builds the service lazily, on the first `search` call, from its existing arguments, because 135 test files reference the factory and several call it as `create_app(pipeline, "default", writer=None)` without a config (for example `tests/server/test_mcp_ingest_503.py` line 19, which uses only ingest tools), which an eager build would break. With no config `search` answers the fixed internal-error response (`search failed`, code `internal_error`), logs a distinct error event, and the other tools are unaffected. Only tests reach that branch, because `app.py` always passes the config (line 1044): the slice deletes the `config is None` fallbacks of the `search` tool and defines this failure in their place. Tests that call `search` must pass a collection and a real config: `tests/contract/test_mcp_search_response_shape.py` line 46 calls `search(collection=None)` on a factory without a config and fails both new rules. The rewrite covers 69 `search` tool lookups in 14 test files (counting rule: lines matching `tools["search"]` or `get_tool("search")` under `tests/`; the largest are `tests/server/test_mcp_search.py` with 15, `tests/server/test_e1a_fe3_mcp_search_graph_mode.py` with 13 and `tests/server/test_mcp_telemetry.py` with 9), plus the other access forms the rule does not match: `_get_tool_fn("search", …)` (`tests/test_e1b_be9_mcp_search_graph_mode.py`, 10 sites), `stub_mcp_tool("search", …)` (`tests/test_mcp.py`, `tests/test_fastmcp_stub.py` and the multi-line calls in `tests/test_integration_rag_fusion.py`), `_get_hyde_tool_fn("search", …)` and `_get_rag_fusion_tool_fn("search", …)` (`tests/test_mcp.py`). The REST fallback to the global embedder when no embedder cache exists stays. Brief 00 C2 ("built once at startup") needs an amendment note for this.
- **Decision records.** A dated Amendment to ADR 20 records the service, container and adapter tables (ADR 20 prescribes it; ADR 19 shows the pattern); the ADR 17 Amendment (fail-closed identity) is in this slice.

## Edge Cases & Constraints

- **Cold embedder.** REST degrades; `tests/integration/test_s299_prefix_filter_cold_embedder.py` pins that. After S1, MCP `search` and the shim degrade the same way, so a client can receive full-text-only results where it used to wait on the cache handoff. Only the single-path `search` tool is bounded here: `search_with_context` (`mcp.py` line 934) and `explain` (line 1273) keep the unbounded handoff until their slices. The degrade to keyword-only is already silent on every interface: MCP and the shim degrade through `warmup_for_search` (`fts_only=warmup.fts_only`), and REST has two causes, `warmup.fts_only` and `embedder_cold` (`fts_only = warmup.fts_only or embedder_cold`, `routes_search.py` line 549; `embedder_cold` is a local variable, no response field). S1 adds one more way into the same degrade for MCP and the shim, the bounded handoff. The pipeline drops `graph_mode` and `rag_fusion` when it runs `fts_only`; a RAG Fusion or graph request dropped that way shows only as `rag_fusion_applied` or `graph_expansion_applied` false, which a client cannot tell from "not requested", while a HyDE request under a cold embedder already sets `expansion_warning` (`request_hyde.py` lines 84-94 and 147-151). Accepted limitation (decided, see Resolved Questions): this slice adds no keyword-only signal, so a caller cannot distinguish a keyword-only answer and a dropped RAG Fusion or graph request looks like "not requested"; a later slice revisits it (see Future Iterations).
- **Pipeline assertions.** `search_many` asserts that `scope_filter` and `graph_mode` are not combined (`pipeline.py` lines 3367, 3453 and 3498); the service validates first so the assert stays unreachable. `ppr` with `collections` has no such assert: `search_many` returns `ppr_entities_matched=0` for it (line 3734), so this slice adds a pipeline-level assert for it, like the `scope_filter` one, to stop a later caller from regressing row 6.

- **Shim.** The shim has no tests for a `get_all_collections_meta` failure or `EmbedderNotReadyError`. A `get_all_collections_meta` failure on the all-collections model is unwrapped today (`routes_openai_shim.py` line 216), so it is a plain 500; `EmbedderNotReadyError` is not caught in the shim either, but the app-level handler in `server/app.py` (line 1507) already answers it with a 503. The service translates both: the metadata failure gains defined 503 behavior, the embedder-not-ready behavior is kept and moves into the service; add tests for both. The shim's catch-all is a 503 envelope only on the single-collection branch; the fan-out branch has none, so an unexpected failure there is an unhandled 500 today. Both branches answer the same 503 envelope after S1 (tests `test_routes_openai_shim_be5.py` and `_be7.py` pin the single-collection 503).

That test requires the metadata-store literal in docs `600`, `140`, `160_troubleshooting`, the incident runbook and `DeveloperGuide/06_error_handling.md` (not in `120`), and asserts that `BREAKING.md` does not quote it back-quoted (`in_breaking=False`, line 184), so update those docs in the same change and describe the metadata-store change in `BREAKING.md` without the literal. The `str(exc)` guard `tests/test_no_wire_str_exc.py` holds four search entries (`mcp.py` and `routes_search.py`, function `search`, `GraphCommunitiesNotBuiltError`, handlers 1 and 2) keyed by file and function, so moving the handlers makes them stale and the staleness test fails. The service builds that text from the typed `exc.collection` and a fixed template that `GraphCommunitiesNotBuiltError` exposes as a class constant (`pipeline.py` lines 218-226), instead of retyping it, the wire text stays byte-identical (no `BREAKING.md` entry), and the four entries are deleted; the `explain` entries stay.

## Resolved Questions

- **Q1 — `top_k`: decided A, make it real.** Add an optional `top_k` to `pipeline.search` and `search_many`, bounded by `top_k_max` (default 100). Omitted `top_k` means the configured `top_k_return` exactly as today (the REST schema default `5` goes away on REST, MCP and the CLI). Because "omitted means configured" needs an absent value, the request field becomes nullable: both OpenAPI snapshots change from an integer with default 5 (`tests/server/openapi_snapshot.json` lines 3545-3550) to an `anyOf` of an integer with minimum 1 and null, with no `default` key, like `scope_filter` (lines 3534-3544), so `top_k: null` also becomes valid. When `top_k` is given it replaces `_top_k_return` at every cutoff of `search` and `search_many` and the helpers they call (`pipeline.py` lines 1691 to 3722; none is in `explain`), including the shortfall warning that compares against it (lines 2224 and 2235, which uses the effective `top_k`; so a `grep _top_k_return` finds cutoffs and that warning). One rule for the pool: it is raised to at least `top_k`, so up to N results return, and exactly N when enough chunks survive the post-filters; prefix stability holds only while N and M fit the same pool, and the pool depends on the path (single path: the default pool of 45; multi path: the per-leg trim of 40, which becomes `max(40, N)`). The pool formula `max(top_k_retrieve * 3, 20)` (45 at the default `top_k_retrieve` of 15) appears at 13 sites in `pipeline.py`, but only 8 belong to `search` and `search_many` and change (lines 1635, 1919, 2145, 2212, 3210, 3385, 3503 and 3707); the other 5 (lines 2358, 2478, 2734, 2844 and 3092) are `explain` code and stay unchanged, gated by a test (plan S23). The per-leg trim `fanout_leg_trim` (default 40, `config.py` line 359) sits at 4 sites: lines 3273, 3388 and 3516 in `search_many`, and line 3776 in the shared helper `_fanout_merge_acl`, which `explain` also calls (line 2359); the helper takes an optional effective `top_k` that `explain` never passes. Up to `top_k` results return, all from the ranked pool; exactly `top_k` return when enough chunks exist, they pass the ACL, source-path glob and wildcard-scope post-filters (which run after the pool is fetched, `pipeline.py` lines 1922 and 2215-2222; `130_data_architecture_and_persistence.md` line 259 states the shortfall) and the search is not limited by an `fts_only` degrade. The pool depth feeds each leg's limit (`store.py` lines 3832 and 3848) and the reranker's candidate set (`reranker.py` lines 196-229), so the ranking can change when `top_k` exceeds the pool. The reranker scores every candidate under the fixed 30 s search budget, so a large `top_k` costs latency; a scenario covers it. REST, MCP and the CLI (`--top-k`) all honour it in the same final task as the core change, with no intermediate state; the shim keeps ignoring a request `top_k` (see the shim decision below). It is a separate task at the end of the slice, so the rest of S1 is not blocked. It is a core retrieval change: the existing eval gate in `tests/eval/` stays green (it builds pipelines with `top_k_return=10` and never passes `top_k`, `eval/runner.py` lines 701-702 and 842-843, so it proves only that the default is unchanged), and new default-lane integration tests prove exact-N under those preconditions and, for N and M that both fit the same pool (45 on the single path, 40 on the multi path), prefix stability (`results(N)[:M] == results(M)`); beyond the pool the guarantee is only "up to N results, all from the ranked pool". The eval runner is not changed. `tests/integration/test_s313_top_k_does_not_set_result_count.py` is rewritten, not re-pinned (C13). The shim ignores a request `top_k` and takes its count from the `[openai_shim].top_k` key (both decided, see below). MCP allows up to `top_k_max` chunks per call, which can fill an agent's context; no separate MCP cap.
- **Q2 — No collection given: decided A, required everywhere.** MCP loses its configured default and the literal `"default"`. `default_collection` is also used by the MCP tools `ingest_file`, `ingest_directory`, `list_documents`, `delete_document`, `search_with_context` and `explain`; after S1 MCP `search` differs from them until their own slices remove it. Automatic collection choice is a separate future feature (see Future Iterations); today `MultiCollectionRouter` ranks by centroid similarity (optionally blended with the description embedding), not by an LLM, and no search surface uses it. The shim keeps its own policy for the model-name collection: an empty name (`archon-search/`), a whitespace-only one and a name that is not a valid collection name answer a 404 (see the shim policy above; the empty case is pinned by `test_routes_openai_shim_be5.py` with a mocked pipeline), and padded names and queries reach the service stripped; both are listed in `BREAKING.md`.
- **Q3 — First field-level parity check: decided A.** It compares the command fields against the REST request schema, the MCP input schema and the CLI options, with an explicit mapping for the nested REST `filters` versus the flat MCP and CLI filter parameters, and compares values as well as names where that is cheap. This shapes Brief 00's C12 for the remaining slices.
- **Q4 — CLI human-readable output: decided A, then amended to D during task grounding (TQ1).** Standard output is one line per result: rank, score, collection, source path and an excerpt cut at a named constant (about 200 characters, whitespace collapsed). No excerpt-length flag. After the results the CLI writes notes to stderr: one cleaned note with the server's `expansion_warning` when it is present (a requested HyDE or RAG Fusion step did not run) and one cleaned note per entry of `excluded_collections` (collection name and reason), so a script that counts or parses the result lines is unaffected; when every collection was skipped, `No results found.` still prints on standard output and the reasons go to stderr. A keyword-only answer stays invisible (no response field reports it, see Q2 of the team plan). `--json` prints the response re-serialised in the repo's format (indent 2, sorted keys; same values as the REST body) and is unchanged. Every server-supplied string the CLI prints (excerpt, collection name, source path, the server's `detail`, the notes) goes through the shared `_helpers` text cleaner, so terminal escape sequences cannot be injected.
- **Former team plan Q1 — the shim's `[openai_shim].top_k` key: decided A.** The key's type becomes `int | None` and it is unset by default (it defaults to 5 today, `config.py` lines 312 and 327). When unset, the shim uses `[database].top_k_return` like every other interface; when set, it is the shim's result count (the shim never takes a count from the request). A set value above `top_k_max` is a config-load error (the key is loaded at `config.py` lines 1488-1489 and `top_k_max` is parsed at lines 893-897, earlier, so the cross-check runs once both are known). Why: `config.py` lines 321-322, `85_openai_compatible_api.md` line 27 and `30_configuration.md` line 299 define the key as the shim's result count, reserved for a runtime `top_k` that this slice adds; row 1 says the count defaults to `top_k_return` on every interface, which rules out a default of 5; the clean-cutover rule (roadmap principle 4, which speaks of callers and old code, not of settings) rules out keeping the key inert after the slice. The change is breaking because the key is inert today: a value an operator set now takes effect, and the default 5 becomes unset (`BREAKING.md`). Tests rewritten: the ones that pin the default, `tests/test_openai_shim_config.py` lines 24 and 63 (default 5) and 144 (the snapshot's `top_k: 5`) and `tests/test_config_defaults.py` lines 276-279; lines 91-118 (validation) and line 53 (an explicit `top_k = 10`) stay valid. Docs: `archon-search.toml.example` lines 793-797, `85_openai_compatible_api.md`, `30_configuration.md` line 299.
- **Team plan Q1 (renumbered; open in the previous revision) — how the shim treats a request `top_k`: decided C, ignore it.** The shim ignores a request `top_k`, as today: `schemas_openai.py` lines 77-79 keep accepting the field (`int` or `None`) for protocol compatibility and no value, in or out of range, gets a 4xx. REST, MCP and the CLI honour `top_k`; the shim ignores the request field by decision. The shim's result count comes from the optional `[openai_shim].top_k` key (unset by default, falling back to `[database].top_k_return`), which stays a real change: inert today, honoured after S1, a `BREAKING.md` entry. This reverses the earlier statement in brief Q1 that the shim forwards a request `top_k`. Why: the shim returns the full text of every hit to a chat model, and that chat clients forward a sampling-style `top_k` (an Ollama-style default of 40, or 0 or -1 for "disabled") is an [INFERENCE], since `85_openai_compatible_api.md` line 1 names Cursor, Continue.dev, LangChain and LlamaIndex as clients and none was verified to send it; ignoring the field is today's behaviour, so no client changes. Consequences: no out-of-range `top_k` 400 on the shim; `TestTopKRequestFieldIgnored` (`test_routes_openai_shim_be5.py` lines 653-672) stays valid and is not rewritten; the `top_k` comment in `schemas_openai.py` and the docs keep saying the field is accepted and ignored and point to the key for the count. Evidence: `schemas_openai.py` lines 77-79, `routes_openai_shim.py` lines 181-183 (the 400 pattern that is not used for `top_k`).
- **Team plan Q2 (renumbered; open in the previous revision) — a keyword-only signal in the search response: decided A, no new signal in this slice.** Callers cannot distinguish a keyword-only answer, and a RAG Fusion or graph request dropped under `fts_only` looks like "not requested"; this is an accepted limitation (see Edge Cases, Cold embedder) and a later slice revisits it (see Future Iterations). Why: it is the smallest change; the alternative would be a contract change on both OpenAPI snapshots, the MCP schema, the parity check and the CLI output. Evidence: `warmup_for_search` degrades silently on MCP and the shim (`mcp.py` lines 666 and 776, `routes_openai_shim.py` lines 245 and 311), REST through `routes_search.py` line 549, and `request_hyde.py` lines 84-94 and 147-151 already warns for HyDE only.

## Future Iterations

- `search_with_context`, `explain` and `route` on the same service (S2-S4).
- A telemetry `origin` dimension (REST, MCP, CLI).
- Making the search budget configurable.
- A keyword-only signal in the search response (a response field or a warning on REST, MCP and the CLI), so a caller can tell a keyword-only answer and a dropped RAG Fusion or graph request from "not requested"; it needs a contract change (both OpenAPI snapshots, the MCP schema, the parity check, the CLI output).
- Automatic collection choice for search: an opt-in way to omit the collection and let the router pick one or more, built once in the service and exposed on REST, MCP and the CLI. It needs decisions on how many collections to search, a confidence cutoff, behavior when descriptions are missing (`[description]` is off by default) and a response field naming the chosen collections. Plan it after S4 (`route`).

## Recommendation

Build it. Brief Q1 and Q2 are decided (see Resolved Questions) and both change the public contract and the characterization tests; every other question is decided too, none is open (see Open Questions). Start from the characterization gaps listed above; a pilot that cannot show before and after behavior proves nothing. The hardest part is the response unification (MCP response schema, OpenAPI snapshots, contract tests) and the string-patch re-pointing in the many MCP tests; do not shortcut either. Do not compromise on three things: one implementation per behavior, every drift row resolved or explicitly kept with a reason, and a smoke run that sends the same query through REST, MCP, the shim and the CLI against a real server and compares the results.
