# Feature Brief: Stronger Collection Routing (B4 — item 9)

## Problem
Collection routing today rests on a **single signal**: `MultiCollectionRouter.rank()` scores each collection by cosine similarity between the query embedding and `CollectionMeta.centroid` — the element-wise mean of every chunk vector in the collection (the cosine loop in `rank()`; centroid computed in `pipeline.py:_compute_centroid` lines 100–104). A confidence gate (`routing_confidence_threshold`, default `0.30`) and a shortlist cap (`routing_shortlist_size`, default `8`) sit on top (both inside `rank()`). The mean-of-all-chunks centroid is a blunt instrument: for a heterogeneous corpus it averages toward the centre of the embedding space and loses discriminative power, which ADR 04 itself flags as the primary recall risk (`ADRs/04_multi_collection_router_with_centroid_preranking.md:90`). 

Meanwhile a **second signal already exists but is never used for ranking**: each collection carries an auto-generated 2–3 sentence `description` (`CollectionMeta.description`, produced by Haiku in `description_generator.generate_description`). Today the description is injected verbatim into the decomposer prompt block (the `_build_block` loop in `router.py`) but **plays no part in centroid scoring**. The roadmap is explicit about where this goes next: keep centroids as the baseline and add summary embeddings plus description-aware routing (`Documentation/roadmap.md:46`, item 3), captured in the backlog as B4 / item 9: *"summary-embedding + description + centroid hybrid alternatives; centroid stays the baseline. Gated by the eval harness."* (`03_world_class_roadmap.md:64`).

ADR 04 actually argues *against* a naive version of this: it rejected "keyword / metadata routing" as the primary signal because "collection descriptions are too short and noisy to be reliable on their own" (`ADRs/04_multi_collection_router_with_centroid_preranking.md:112–114`), and rejected an LLM-based router for the default path (same ADR, lines 105–107). B4 takes that rejection seriously rather than overriding it: "descriptions are too short and noisy" is precisely the hypothesis the eval gate exists to test empirically, which is *why* description- and hybrid-routing are gated and *never* made the default until a measured lift clears the floor. And B4 honours the LLM-router rejection by embedding the **existing** description — no new LLM call on the routing path.

The blocker to building this is not the scoring math — it is the **evaluation gate**. Per the roadmap's sequencing rule, "any feature that touches ranking lands behind a benchmarked threshold in `tests/eval/`… No feature flag → no merge" (`03_world_class_roadmap.md:39`). But the eval harness **cannot currently evaluate any description- or summary-based routing signal**. The router metas the harness ranks come from `pipeline.get_all_collections_meta()` (`eval/runner.py:567`) — store-derived metas, written by `recompute_collection_meta` after ingest (`eval/runner.py:484`), which preserves `description = None` (`pipeline.py:405–407`: no `ANTHROPIC_API_KEY`, no Haiku in the deterministic harness). The committed routing descriptions in `tests/eval/routing/collections.jsonl` are **only consumed by the determinism hash** (`eval/_hashing.py:75`); they are never loaded into the metas that `_run_router_for_query` ranks (`eval/runner.py:487–510`). So a stronger routing signal has nothing to be gated against until the harness learns to inject and deterministically embed those descriptions.

## Goal
B4 ships a **strategy-selectable routing scorer** — centroid (baseline, unchanged default), description/summary-embedding, and a centroid+summary hybrid — plus the **eval-harness machinery that makes the two new strategies deterministically gateable**, with centroid remaining the shipped default until a measured eval lift justifies a flip. Success is observable as: (a) `CollectionMeta` carries a new nullable `summary_embedding` populated from the collection `description` wherever the centroid is computed; (b) `MultiCollectionRouter.rank()` / `rank_with_scores()` (the latter introduced by A4) produce a blended score under a configured `routing_strategy`, with `routing_strategy = "centroid"` reproducing today's behaviour byte-for-byte; (c) the eval harness loads the committed `routing/collections.jsonl` descriptions into router metas, embeds them with the deterministic backend, and computes `routing_accuracy` **per strategy**, each behind its own floor in `thresholds.toml`; (d) the centroid floor is held strictly unchanged (`0.9259259259259259`, the only default-path gate) and each non-centroid strategy gets a floor pinned to its **measured** synthetic-backend value — flagged if below centroid — with `≥ centroid` being the bar for a strategy to be *recommendable*, not the bar for the mechanism to merge (see "Per-strategy floors" in Key Decisions); (e) `/route` and routing telemetry report the configured strategy and a `ranking_applied` boolean (true only where centroid/summary ranking actually runs); (f) the eval harness still passes and the 85% coverage gate holds on the default pytest run.

**B4's production surface is operator-opt-in only and is not exercised by the default configuration.** The default `routing_strategy = "centroid"` reproduces today's behaviour byte-for-byte; even a *flipped* strategy only changes Tier 3 of `get_pre_context` (more than `routing_shortlist_size` routable collections), so most deployments never observe it. The scorer ships **dormant**. We land it now, ahead of the production-model lane (B6), deliberately: the load-bearing, large piece is the eval-harness machinery (description injection + deterministic embedding + per-strategy parametrisation + recalibrated baselines) and the `_score_collections` scorer seam. Landing and stabilising that offline-gated machinery first **decouples it from B6** so B6 can focus purely on real-embedding measurement rather than co-shipping the harness refactor and the scorer at once. B4 ships the mechanism and the offline gate; it does **not** flip the default strategy — that waits on a measured lift, ideally confirmed on real embeddings via B6.

## Roadmap Deviation (Item 9 → B4 v1)

The near-term roadmap line (`Documentation/roadmap.md:46`, item 3 — distinct from the Backlog `03_world_class_roadmap.md`) reads: *keep centroids as baseline; add summary embeddings, multi-centroid / clustered representations, and description-aware routing*. B4 ships everything except multi-centroid:

| Roadmap signal | v1 status | Reason |
|---|---|---|
| centroid baseline (unchanged) | **in** | Default strategy; byte-for-byte parity preserved |
| summary-embedding routing | **in** | Embeds the existing `description`; new `summary_embedding` field |
| description-aware routing | **in** | The `description` / `hybrid` strategies (same stored vector) |
| centroid + summary hybrid | **in** | The `hybrid` strategy, convex-blended by `routing_hybrid_weight` |
| multi-centroid / clustered representations | **deferred** | Heavier change (k-means over chunk vectors, list-of-centroids schema, different scoring loop) — a future iteration |

The multi-centroid deferral is the only deviation from the roadmap text and is intentional; the reconciliation forward-reference for it lives in `Documentation/roadmap.md` (item 3). (`03_world_class_roadmap.md:64`'s B4 line already omits multi-centroid.) See Out of Scope and Future Iterations.

## Users & Context
- **Maintainers tuning retrieval quality** who need a principled second routing signal and a benchmark that tells them whether it helps before it becomes default.
- **Operators of large multi-collection deployments** (more than `routing_shortlist_size` routable collections) where centroid pre-ranking actually fires (Tier 3 of `get_pre_context`) and a weak centroid silently drops a relevant collection.
- **Contributors building B3 (server-side multi-collection search) and A4 (`/explain`)**, who consume routing decisions and need them debuggable and signal-attributed.
- **Eval / benchmark workflows** that gate every ranking change and currently have no way to exercise non-centroid routing.

Triggered when a query is routed across more collections than the shortlist size, or when an operator/maintainer wants to evaluate or enable a description-aware routing strategy.

## Core Flow
1. **Signal storage**: `CollectionMeta` gains `summary_embedding: list[float] | None = None` (`collection_meta.py`), persisted as a new nullable `summary_embedding_json` column on the `_archon_collection_meta` table, serialized/deserialized exactly like `centroid_json` (mirror `store.py:444` write and `store.py:306–309` read, including the malformed-JSON → `None` guard). It shares the collection's existing single `embedding_model` tag — the summary is embedded with the same embedder that produced the centroid, so the existing model-match check covers both.
2. **Signal population**: wherever a `description` is set or refreshed and the centroid is (re)computed, the description text is embedded once via the active `Embedder` and stored as `summary_embedding`. Two call sites: the ingest batch path (`pipeline.py:277–309`, right after `generate_description` succeeds) and `recompute_collection_meta` (`pipeline.py:388–421`, which today preserves the existing `description` but recomputes the centroid — it now also (re)embeds that description). If `description is None`, `summary_embedding` stays `None`. No new LLM call is introduced — B4 embeds the **existing** description; it does not generate a new summary.
3. **Strategy-aware scoring**: two new config knobs — `routing_strategy: Literal["centroid", "description", "hybrid"] = "centroid"` and `routing_hybrid_weight: float = 0.5` (weight on the centroid term; `1 - weight` on the summary term) — are threaded into `MultiCollectionRouter.__init__`, which gains `routing_strategy` and `routing_hybrid_weight` parameters (the constructor body today is `router.py:36–52`). `rank()` and A4's `rank_with_scores()` are refactored to share a single `_score_collections(query_embedding, collections)` helper that, per collection, computes `centroid_sim = cosine(query, centroid)` and/or `summary_sim = cosine(query, summary_embedding)` and blends them per the router's configured strategy. With `routing_strategy = "centroid"` the helper returns exactly today's centroid score — **zero behavioural change in the default configuration** (pinned by a snapshot test). The confidence gate in `rank()`, the shortlist cap, the "unscored collections placed last" fallback, and the "all-unscored bypasses the gate" rule are preserved and apply to the blended score (a convex combination of two cosines stays in the same range, so `routing_confidence_threshold` keeps its meaning; see Edge Cases for the partial-signal hybrid caveat).
4. **Per-strategy fallback**: a collection missing the signal a strategy needs degrades gracefully rather than disappearing. `description` strategy with `summary_embedding is None` → that collection is treated as unscored (placed after scored ones, same mechanics as a `None` centroid). `hybrid` with one term missing → score falls back to the available term (centroid-only or summary-only) rather than dropping the collection. If a non-centroid strategy is configured but **no** collection has the required signal, the router logs a WARNING and falls back to centroid scoring for that call so routing is never worse than baseline.
5. **Eval-harness gating** (the load-bearing part): the deterministic harness is extended so non-centroid strategies are reproducible. The metas the harness ranks come from `pipeline.get_all_collections_meta()` (`eval/runner.py:567`) — store-derived, carrying `description = None` and therefore no `summary_embedding`, because the harness's `recompute_collection_meta` never sees a description (`pipeline.py:405–407`) and so never persists one. So the runner adds an **eval-only** join: after `get_all_collections_meta()` returns the store-derived metas, it loads `tests/eval/routing/collections.jsonl`, matches by collection `name`, sets `description` on each matching meta, and embeds that description via `EvalEmbedderBackend` (`eval/backends.py:47`) into the in-memory `summary_embedding`. This is the deterministic stand-in for production's ingest-time / re-describe-time population (Core Flow step 2) — it reconstructs in-memory exactly what production would have persisted, given the committed descriptions.

   `_run_router_for_query` (`eval/runner.py:487–510`) is modified to construct a `MultiCollectionRouter` **per strategy** (passing `routing_strategy` / `routing_hybrid_weight` to the new constructor params), so the strategy actually threads into the router under test. The routing eval is **parametrised over all three strategies in one run** — each parametrisation builds a router with that strategy and computes `routing_accuracy` via the existing `compute_routing_accuracy` (`eval/metrics.py:244`) — emitting `routing_accuracy_centroid` / `routing_accuracy_description` / `routing_accuracy_hybrid`, each with its own floor in `thresholds.toml`. `runtime.toml` gains `[routing].strategy`, but it only **records the production-default strategy for documentation**; it does **not** limit which strategies the gate floors — all three are floored every run regardless of the configured default. Because this changes determinism inputs (it now loads descriptions previously only hashed), the baseline is recalibrated and `baseline.json` / `baseline.md` / `thresholds.toml` are refreshed together per the documented refresh procedure (`thresholds.toml:10–13`).
6. **Observability**: `RouteResponse` gains two additive fields. `routing_strategy: str` always reports the **configured** strategy (`"centroid"` / `"description"` / `"hybrid"` — matching the config `Literal`), regardless of which tier ran. A separate `ranking_applied: bool` reports whether centroid/summary ranking actually executed — `false` for Tier 1/Tier 2 of `get_pre_context` (where no ranking runs at all — the tier logic in `get_pre_context()`) and `true` for Tier 3. The router exposes both via new side-effect properties — `last_strategy` and `last_ranking_applied` — mirroring the existing `last_routable_names` / `decomposer_was_invoked` properties (`router.py:54–62`); the route handler reads them the same way it already reads `last_routable_names` / `decomposer_was_invoked` (`routes_route.py:106–107`) to populate both `RouteResponse` and `TelemetryEntry.from_route_response`. The telemetry entry gains the same `routing_strategy` / `ranking_applied` fields (small enum string + bool; the no-raw-query invariant is untouched). Per-collection signal breakdown (centroid vs summary vs blended score) is surfaced through A4's `/explain` routing block, **not** through `/route` — see Out of Scope.
7. **Docs / ADR**: a new ADR (the next available ADR number — **06 today; confirm at planning, since A-phase ADRs may consume it**) supersedes the routing-strategy portion of ADR 04 (ADRs are append-only — ADR 04 gets a "Superseded by 0N" pointer, not an edit). `100_system_architecture_overview.md`, `110_component_catalog_and_layer_breakdown.md`, and `210_performance_and_scalability.md` (routing-knobs table) are updated; `03_world_class_roadmap.md` B4 is reconciled to record that multi-centroid / clustered representations are deferred (see Out of Scope).

## Out of Scope
- **Flipping the default strategy.** Centroid stays the shipped default (`routing_strategy = "centroid"`). A non-centroid strategy becomes default only after a measured eval lift — and the production-model lane (B6) is the honest place to confirm a real-embedding lift, since the deterministic backend's lift may not transfer. B4 ships the mechanism + offline gate, not a behaviour change for existing deployments.
- **Multi-centroid / clustered collection representations.** Deferred — the single roadmap deviation; see the Roadmap Deviation section for the rationale and Future Iterations for the shape of the follow-up. B4 ships single-vector signals only.
- **A new/longer summary generator.** B4 embeds the **existing** `description` (the 2–3 sentence Haiku output). A distinct, longer-form summarization pass is a future iteration; v1's "summary embedding" *is* the description embedding.
- **Per-collection routing weights / per-collection strategy.** `routing_hybrid_weight` is global in v1. Per-collection overrides on `CollectionMeta` are a future iteration.
- **Learned / calibrated fusion** (e.g., logistic blend, RRF over routing signals). v1's hybrid is a fixed convex combination. Calibration waits on B6 and real-model data.
- **Per-collection signal breakdown on `/route`.** `/route` returns only `routing_strategy` and `ranking_applied`. Surfacing per-collection centroid/summary/blended scores is A4's `/explain` job (its `rank_with_scores` already returns per-collection scores); B4 adds `routing_score` / `summary_score` siblings to A4's existing `centroid_score` there rather than duplicating any of it on `/route`.
- **Changing the three-tier `get_pre_context` policy.** Tier 1 (≤3 routable → search all, no ranking) and Tier 2 (4..shortlist → decomposer over all, no centroid ranking) are unchanged (the tier logic in `get_pre_context()`). B4 strengthens the **scoring** that Tier 3 (and the eval `select()` path) uses; it does not re-draw the tier boundaries.
- **Incremental centroid/summary recompute (CON-4 / B5).** B4 keeps the existing full-recompute path (`pipeline.py:_compute_centroid`). Summary embedding is one extra embed per re-describe, not per chunk, so it does not materially worsen CON-4; the incremental optimisation stays B5's job. (Interaction noted in Edge Cases.)
- **Metadata-cache invalidation (CON-2).** The router's forever-cached metadata (the `_cached_metadata` field, populated once in `fetch_metadata()`) is a known debt owned elsewhere; B4 does not fix it. Stale metadata means a stale `summary_embedding` is served until cache reset — same staleness surface centroids already have.
- **Removing the `max_parallel_collections` inert knob.** Documented as unwired (`config.py:44`, ADR 04 `#Unverified`); untouched here.

## Key Decisions
- **Centroid stays the baseline and the default; strategies are additive and selectable.** The roadmap is the source of this sequencing: "keep centroids as baseline; add summary embeddings… and description-aware routing" (`Documentation/roadmap.md:46`, item 3; `03_world_class_roadmap.md:64`). B4 adds alternatives behind a config knob that defaults to today's behaviour, with a snapshot test pinning byte-for-byte parity for `routing_strategy = "centroid"`. No existing deployment changes behaviour on upgrade.
- **The summary signal is the *embedded existing description*, not a new generation step.** This avoids a new LLM dependency on the routing path (ADR 04 rejected an LLM router for the default path) and reuses the description regeneration cadence (`_should_regenerate`, `description_generator.py:42`). It cleanly maps the roadmap's "summary embeddings" and "description-aware routing" onto a single stored vector.
- **Separate signal *generation* from signal *scoring* — this is what makes the feature eval-gateable.** Generation (Haiku description) is non-deterministic, network-dependent, and out of the eval harness. Scoring (cosine against a stored vector) is deterministic given fixed text. B4 makes the eval harness inject the committed `routing/collections.jsonl` descriptions and embed them with the deterministic backend, so the *scorer* — the thing B4 actually changes — is what the gate measures. Without this split there is no benchmark and, per the roadmap, no merge.
- **Per-strategy floors — a synthetic-signal regression guard, not a merge bar for the mechanism.** The eval emits one accuracy per strategy. The **centroid floor is the only default-path gate** and is held strictly unchanged at the current `0.9259…`. The description/hybrid floors are set to **each strategy's measured value** on the deterministic backend; "≥ centroid" is the bar for a strategy to be *recommendable* / safely flippable, not for its mechanism to merge. A non-centroid strategy that measures *below* centroid on the synthetic backend still lands — dormant, opt-in, with its floor pinned to its measured value and flagged in `thresholds.toml` as below-centroid — because the deterministic-backend lift is a regression guard, not a production SLA, and a synthetic shortfall does not prove the mechanism is wrong (that is B6's real-embedding job). What is non-negotiable: the centroid floor never moves, so the default path can never silently regress.
- **Graceful degradation over hard failure.** A missing summary embedding never *drops* a collection from routing; it falls back (unscored-last for description-only, other-term for hybrid, centroid for a fully-unsignalled call). Routing must never be worse than the centroid baseline because a description failed to generate.
- **One embedding-model tag covers both vectors.** The summary is embedded with the same embedder as the centroid, so the existing `embedding_model` match check in `rank()` gates both. No second tag, no cross-model summary routing in v1.
- **`/route` reports the strategy; `/explain` reports the scores.** Keeps `/route` lean and avoids duplicating A4's per-candidate score surface. `routing_strategy` always reports the *configured* strategy (matching the config `Literal`); a separate `ranking_applied: bool` is what is honest about Tiers 1/2, where it is `false` because no centroid/summary ranking runs. (No `"none"` strategy value — that would contradict the field's enum.)
- **`routing_hybrid_weight` is dormant-by-default but *not* half-built.** Like A1's rejected `language` / `custom_score`, this knob does nothing under the default `centroid` strategy. The decisive difference: it has an **immediate consumer in this same PR** — the parametrised `hybrid` eval run in the gate exercises it directly (the floor is computed at the configured weight). It is forward-wired *with* a live consumer, not a field that lies dormant with no path that reads it. That is why it ships now rather than waiting for a future hybrid-tuning item.
- **Default flip deferred to a measured lift (B6).** Deterministic-backend accuracy is a regression guard, not a production SLA (`thresholds.toml:6–8`, `210_*`). A lift on SHA-256 hash embeddings does not prove a lift on real embeddings, so B4 does not flip the default.

## Edge Cases & Constraints
- **Pre-B4 collections (no `summary_embedding_json` column / value)**: read as `summary_embedding = None`; under `description`/`hybrid` they fall back per the matrix above; under the default `centroid` strategy nothing changes. The column is additive and nullable — no migration, lazy backfill on next ingest/re-describe (mirrors A1's lazy-backfill philosophy).
- **Collection with a centroid but no description** (Haiku failed, or no `ANTHROPIC_API_KEY` — `description_generator.py:76`): `summary_embedding = None`; behaves as above. Common in CI and air-gapped deployments — must not break routing.
- **Stale summary embedding**: `summary_embedding` is recomputed only when the description is regenerated (`_should_regenerate` at ≥20% doc-count drift) or on `recompute_collection_meta`. Between those, it can lag the corpus — the same staleness centroids already have, compounded by the router's forever-cache (CON-2). Documented, not fixed here.
- **`embedding_model` mismatch**: a `summary_embedding` produced under a different model is treated as unscored, identical to the centroid rule (the model-match check in `rank()`). Because both vectors share one tag, a mismatch invalidates both together.
- **L2 normalisation of `summary_embedding` (resolved precondition, not an open question)**: production `ModelEmbedder`/`Embedder` (`embedder.py`) does **not** explicitly L2-normalise its output; the deterministic `EvalEmbedderBackend` **does** (`backends.py:36–40`). B4 therefore L2-normalises the `summary_embedding` before storage, putting it on the same scale as eval embeddings and the (fastembed-normalised) chunk vectors. The router's `_cosine_similarity` computes full cosine (dividing by both norms — `router.py`), so it is robust to unnormalised inputs and the result is unchanged either way; storing normalised is purely to keep eval and prod vectors on one scale and avoid a future foot-gun if any consumer assumes unit vectors.
- **Hybrid score range and partial-signal comparability**: a convex combination of two cosine similarities stays within the cosine range, so `routing_confidence_threshold` (calibrated for centroid cosine) keeps a comparable meaning. Caveat: under partial-signal hybrid, a full two-term blend and a single-term fallback (one term missing) are *both* in the cosine range but are **not strictly comparable magnitudes within one ranking** — a blended score and a fallback single-term score for two different collections sit on slightly different scales. So `routing_confidence_threshold` is an **approximate gate** under partial-signal hybrid, not an exactly calibrated one. Constraint: do **not** introduce a score normalisation that changes the gate's calibration without recalibrating the threshold.
- **All collections unscored under a non-centroid strategy** (e.g., description strategy, zero descriptions present): WARNING logged once per call, ranking falls back to centroid; if centroids are also all absent, the existing all-unscored-bypass rule in `rank()` returns up to `shortlist_size` unscored collections. Routing degrades to today's behaviour, never below it.
- **Tier 1 / Tier 2 paths**: no centroid or summary ranking runs (the tier logic in `get_pre_context()`); `summary_embedding` is irrelevant, `routing_strategy` still reports the configured strategy, and `ranking_applied` is `false`. B4's scoring change is observable only at Tier 3 and on the eval `select()` path (which runs with `shortlist_size = len(collections)` and `confidence_threshold = 0.0`, exercising `rank()` for all collections — `eval/runner.py:500–510`).
- **CON-4 / B5 interaction**: B4 adds one description embed per re-describe (not per chunk), so it does not change the O(chunks) centroid recompute cost class. When B5 lands incremental `(sum, count)` centroid maintenance, the summary embedding (a single vector embedded from a single short string) updates on the same re-describe trigger and does not need incrementalisation.
- **Eval determinism inputs change**: loading `routing/collections.jsonl` descriptions into routing alters the harness's behaviour. Per `thresholds.toml:10–13`, `baseline.json`, `baseline.md`, and `thresholds.toml` must be re-derived from one calibration run and committed together; the harness-hash test is updated in the same commit.
- **Coverage on net-new code**: `_score_collections`, the summary-embedding population at two call sites, config validation, the router's `last_strategy` / `last_ranking_applied` properties, and the new `RouteResponse` fields are all default-marker-covered. Eval-marker tests do not count toward the 85% gate; the gate must hold on unit + contract tests alone.
- **A4 ordering dependency**: A4 (Phase A) ships `rank_with_scores()`, the shared `_score_collections` helper, and a stable ascending-name tie-break in `rank()` (A4 brief, In Scope) before B4 (Phase B). When A4 has landed, B4 **extends the existing `_score_collections` helper** with strategy-aware blending rather than introducing it, and the centroid-parity snapshot (commit 4) is pinned against the **post-A4** `rank()` output — i.e. *with* A4's alpha tie-break already in place, not the pre-A4 undefined-tie ordering. If A4 has **not** shipped when B4 starts, B4 introduces `_score_collections` for `rank()` only (including the alpha tie-break, so the snapshot is still deterministic) and the `rank_with_scores` refactor moves into A4's or a follow-up's scope. Planning verifies A4's status first.

## Recommendation
This is the right next routing step, and it is **more eval-engineering than scoring math**. The scorer change is small and low-risk: a shared `_score_collections` helper, a stored description embedding, two config knobs, and a default that reproduces today's behaviour exactly. The genuinely hard, load-bearing part is **making description- and summary-based routing deterministically gateable** — today the eval harness has no descriptions on its router metas and the committed `routing/collections.jsonl` is only hashed, never loaded, so there is nothing to benchmark against. B4's central act is the signal-generation-vs-scoring split that lets the deterministic backend embed committed descriptions and the harness floor each strategy. What must not be compromised: **the centroid floor is held strictly unchanged and centroid stays the default until a measured lift justifies otherwise** (ideally confirmed on real embeddings via B6) — this, plus the dormant opt-in posture, is what guarantees the default path can never silently regress; **each non-centroid strategy is floored at its measured value** (flagged if below centroid; `≥ centroid` is the recommendable bar, not the merge bar) so its synthetic accuracy can never silently slip either; and **a missing description must degrade gracefully, never drop a collection**. The three guardrails that keep B4 from rotting are the centroid-parity snapshot test, the per-strategy eval floors, and the graceful-fallback matrix.
