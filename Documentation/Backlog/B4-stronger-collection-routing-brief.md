# Feature Brief: Stronger Collection Routing (B4 — item 9, minimum slice)

## Problem
`MultiCollectionRouter.rank()` (`router.py:127`) ranks collections by a **single signal**: cosine similarity between the query embedding and one mean-pooled `centroid` per collection (`_compute_centroid` is an element-wise mean, `pipeline.py:100`). ADR-04 already records the failure mode this creates: "Recall can drop when a genuinely relevant collection has a weak centroid (e.g., very heterogeneous corpus)" — a single mean vector washes out a multi-topic collection, so the query lands closer to a narrow, off-topic collection's tight centroid. The collection `description` already exists (Haiku-generated, `description_generator.py:61`) and is a strong, human-legible topic signal, but it is used **only** to render the decomposer prompt block (`router.py:_build_block`, line 215) — it never participates in *ranking*. There is no summary-embedding, no description-embedding, and no multi-representation alternative; the only knobs are `routing_shortlist_size` and `routing_confidence_threshold`.

Worse, the regression gate the roadmap assumes ("B4 … Gated by the eval harness") **cannot currently detect a ranking change at all.** The offline router (`_run_router_for_query`, `runner.py:487`) constructs the router with `shortlist_size = max(1, len(collection_metas))` and `confidence_threshold = 0.0`, then scores `router_correct = bool(set(shortlist_names) & gold)` (`runner.py:1054`). With the committed fixture of **three** collections (`tests/eval/routing/collections.jsonl`) and a shortlist sized to *all* collections, `rank()` returns every scored collection regardless of order, so the intersection is non-empty whenever the gold collection merely *has* a usable centroid. `routing_accuracy = 0.9259…` (`thresholds.toml:22`) is therefore a coverage check, not a ranking-quality check: reordering the collections, improving the top-1 hit, or regressing it leaves the number unchanged. Any B4 ranking change would land against a gate that is, by construction, blind to ranking.

## Goal
B4 ships a **minimum, end-to-end "stronger routing" slice**: (1) a second ranking signal — the embedding of each collection's generated `description` (the "summary embedding") — blended with the centroid baseline under a config-selected strategy, and (2) the **rank-sensitive eval metric** that makes the routing gate able to see a ranking change in the first place. Centroid-only stays the default and the baseline; the hybrid strategy is opt-in and must clear the eval bar before anyone considers flipping the default (a flip is explicitly out of scope here). Success is observable as: (a) ingesting a collection that produces a description persists a `description_embedding` (same dimensionality and `embedding_model` tag as the centroid); (b) with `routing_strategy = "hybrid"`, `rank()`'s score for a collection is a documented blend of centroid-cosine and description-embedding-cosine, falling back to centroid-only when the description embedding is absent or model-mismatched; (c) the eval harness computes a **rank-sensitive** routing metric (P@1 / MRR over the gold collection's position) that *moves* when ranking order changes; (d) under that metric the committed baseline shows hybrid ≥ centroid on the (expanded) routing fixture, and the `thresholds.toml` floor guards against regression; (e) the existing default (centroid) run is unchanged — `routing_strategy = "centroid"` reproduces today's behavior byte-for-byte; (f) the 85% coverage gate holds on the default pytest run; (g) `get_collections_meta` MCP consumers see the new field documented in `BREAKING.md`.

## Users & Context
- **End users / agents issuing queries** through `/route` (and the downstream search path) who lose recall today when a relevant heterogeneous collection has a diffuse centroid.
- **Operators with many collections** who tune `routing_*` knobs blind because the only ranking signal is the centroid; they gain an opt-in strategy and a documented blend weight.
- **Contributors changing ranking** who need an eval gate that actually responds to routing-order changes (rule 2 of the roadmap: "No feature flag → no merge"), instead of a metric that is invariant to the thing they changed.
- **Maintainers of the eval harness** who own `tests/eval/routing/` and the routing-metric contract.

## Core Flow
1. **New routing artifact at ingest.** When the ingest path (re)generates a description (`pipeline.py:290`, gated by `_should_regenerate`'s 20%-doc-count rule, `description_generator.py:42`), it also embeds that description text via the same `Embedder` used for chunks and stores the result as `CollectionMeta.description_embedding: list[float] | None`. The embedding is tagged implicitly by the collection's existing `embedding_model` field — no new model tag. When no description exists (e.g., `ANTHROPIC_API_KEY` unset, generation returned `None`), `description_embedding` stays `None` and the collection is centroid-only under hybrid.
2. **Recompute / backfill path.** `recompute_collection_meta` (`pipeline.py:388`) — already the centroid-refresh entry point and the one the eval harness calls (`runner.py:484`) — is extended to also (re)embed the *preserved* description into `description_embedding`. Pre-B4 collections (no stored embedding) populate it on the next recompute/reindex; until then they fall back to centroid-only. There is no auto-migration; backfill is the existing recompute/reindex surface.
3. **Persistence.** `CollectionMeta` grows `description_embedding`. `SearchStore._meta_schema` (`store.py:203`) gains a `description_embedding_json` utf8 column alongside `centroid_json` (`store.py:210`); `_row_to_meta` (`store.py:302`) parses it with the same malformed-JSON-→-`None`-with-warning handling the centroid already has (`store.py:306`); `update_collection_meta` (`store.py:444`) serializes it the same way. Old meta tables lacking the column read back as `None` (see Edge Cases for the schema-evolution handling).
4. **Router consumes the artifact.** `MultiCollectionRouter` gains two constructor params: `strategy: Literal["centroid", "hybrid"]` and `description_weight: float`. `_ROUTING_FIELDS` (`router.py:21`) adds `description_embedding` so `fetch_metadata` deserializes it. `rank()` (`router.py:127`) computes, per collection with a usable centroid (`embedding_model` matches, `router.py:142`): `score = cos(q, centroid)` under `"centroid"`; `score = (1 - w)·cos(q, centroid) + w·cos(q, description_embedding)` under `"hybrid"` **when `description_embedding` is present and same-model**, else `cos(q, centroid)` (centroid-only fallback, per-collection). The confidence gate, the unscored-fallback ordering, and the all-unscored bypass (`router.py:148`–158) are unchanged and operate on the blended score. Tiering in `get_pre_context` (Tiers 1–3, `router.py:193`) is unchanged; only the Tier-3 ranking function changes.
5. **Server wiring.** `_build_router` (`routes_route.py:35`) passes `config.routing_strategy` and `config.routing_description_weight`. `RouteResponse` (`routes_route.py:28`) is **unchanged** — rich per-collection score exposure is A4/B1's job, not B4's.
6. **Eval gate made rank-sensitive.** This is load-bearing, not optional. The harness records the router's **full ranked order** (not just a shortlist-membership bool) and computes a rank-sensitive routing metric — `routing_mrr` (reciprocal rank of the first gold collection) and/or `routing_precision_at_1` (is the top-ranked collection gold). The existing shortlist-intersection `routing_accuracy` is rank-insensitive under `shortlist_size = len(collections)` and is either retained as a coverage check or superseded; the *gate for ranking changes* becomes the rank-sensitive metric. The routing fixture (`tests/eval/routing/collections.jsonl`, currently 3 collections) is expanded enough that rank order is discriminating, and `thresholds.toml` gains a floor for the new metric. Baselines regenerated per `tests/eval/README.md`.

  - Record the router's full ranked collection order per query in the trace (extend `QueryEvalTrace` beyond the current `router_correct: bool | None`).

  - Expand `tests/eval/routing/collections.jsonl` and the corpus/queries enough that ranking order is discriminating (the gold collection should not be trivially top-1 for every query under both strategies). Document the new fixtures in `tests/eval/README.md`.
  - `thresholds.toml` gains a floor for the new metric; baseline regenerated and committed per the README's "Refreshing thresholds" procedure. If hybrid's measured metric is below centroid's, B4 does **not** merge with hybrid as a recommended path (rule 2).
  - `_run_router_for_query` (`runner.py:487`) constructs the router with the strategy/weight under test; its existing `confidence_threshold = 0.0`, never-truncate divergence is preserved and documented (the rank-sensitive metric reads the full order, so shortlist truncation no longer hides ranking quality).
- Tests:
  - Unit: `rank()` under `"centroid"` reproduces today's ordering exactly (regression pin); under `"hybrid"` a collection whose description embedding aligns with the query but whose centroid is diffuse out-ranks a collection with a tight off-topic centroid (the ADR-04 failure mode, pinned).
  - Unit: per-collection centroid-only fallback — a collection with `description_embedding is None` is scored by centroid alone even when `strategy == "hybrid"`; a model-mismatched description embedding is ignored (same guard as centroid, `router.py:142`).

  - Unit: confidence gate still fires on the **blended** max score; all-unscored bypass unchanged; unscored collections still ordered after scored ones.
  - Unit: config — `routing_strategy`/`routing_description_weight` parse, defaults, and bounds errors (`routing_description_weight` outside `[0,1]`, unknown strategy).
  - Unit: `_ROUTING_FIELDS` round-trips `description_embedding` through `fetch_metadata` (mock JSON-RPC response carrying the field).

  - Unit (eval): the new rank-sensitive metric *changes* when the ranked order changes (the property today's `routing_accuracy` lacks) — feed two synthetic orderings, assert the metric differs.
  - Unit: MCP `list_collections` payload contains neither `centroid` nor `description_embedding`; `get_collections_meta` contains both.

## Out of Scope
- **Making hybrid the default.** Default stays `"centroid"`. Flipping the default is a separate decision gated by **B6** (the production-model eval lane) — deterministic-stub lift (see Edge Cases) is suggestive, not conclusive. B4 ships the strategy opt-in and proves no-regression + offline lift only.
- **Multi-centroid / clustered representations** (k-means sub-centroids, max-over-clusters scoring) — the heaviest of the roadmap's three listed alternatives (storage of k vectors, clustering at ingest, recompute cost). Deferred to a B4-follow-up / its own item; the `strategy` Literal is designed to admit a future `"multi_centroid"` member without re-plumbing.
- **Rich routing explainability** (per-collection vector/FTS/blended scores, routing path on a response) — that is **A4** (`/explain`) and **B1** (stage-level tracing). `RouteResponse` shape is unchanged here.
- **LLM-based routing as the default signal** — ADR-04 rejected this; B4 does not revisit it. The decomposer LLM already runs downstream over the shortlist; B4 only improves the pre-rank that feeds it.
- **Incremental maintenance of the new artifact** — the description embedding follows the same full-recompute path as the centroid; making *either* incremental is **B5** (`CON-4`). B4 notes the interaction (the description embedding changes far less often than the centroid — only on description regeneration — so it is cheap even under full recompute).
- **Activating `max_parallel_collections`** — inert config per ADR-04 §Knobs; unrelated to routing-signal quality, not B4's problem.
- **Free-form `description` content/length changes or a new summarizer** — B4 embeds whatever `generate_description` already produces; no prompt or sampling changes (`description_generator.py` untouched except its output is now also embedded by the caller).
- **`schema_version` on `CollectionMeta`** — same open question A1 deferred; if B4 needs migration signaling it is decided in planning, not assumed here.

## Key Decisions
- **Blend, don't replace; centroid is the baseline and the default.** The roadmap is explicit ("centroid stays the baseline"). `"centroid"` is the default `routing_strategy` and must reproduce today's ranking exactly — a regression test pins this. Hybrid is purely additive and opt-in.
- **The summary embedding is the embedding of the existing generated description.** No new summarizer, no new model. This reuses an artifact that already exists and is currently *only* used for prompt rendering, and it keeps the new signal in the same vector space as the centroid (same `embedding_model`), so the existing same-model guard (`router.py:142`) covers it.
- **Per-collection centroid-only fallback.** Under `"hybrid"`, a collection missing a usable description embedding is scored by centroid alone — never dropped, never penalized. This makes B4 safe on mixed/old corpora: pre-B4 collections behave exactly like today until recomputed.
- **The eval gate must be made rank-sensitive or B4 is ungateable.** This is the non-obvious core of the work. The current `routing_accuracy` (shortlist-intersection with `shortlist_size = len(collections)`) is invariant to ranking order and cannot detect a routing change. B4 introduces a rank-sensitive metric (P@1 / MRR over the gold position) and expands the routing fixture so order is discriminating. Without this, "gated by the eval harness" is vacuous.
- **No `/route` contract change; MCP `get_collections_meta` gains a key.** REST `/route` shape is untouched (additive richness belongs to A4). The MCP metadata tools that already expose the centroid will additionally expose `description_embedding`; `list_collections` strips it exactly as it strips the centroid. This is the only external-contract change and it is documented in `BREAKING.md`.
- **Offline lift is suggestive, not the merge bar for defaulting.** The deterministic eval embedder is a SHA-256 bag-of-words (`eval/backends.py`, `model_name = "eval-sha256-v1"`); description-aware blending *does* produce signal there (description tokens overlap query tokens), so the harness can show movement. But real-model lift is a **B6** question; B4 gates on *no regression + offline lift*, and defers the default flip.

## Edge Cases & Constraints
- **Pre-B4 collections (no stored embedding).** `description_embedding_json` column is absent or empty → `_row_to_meta` yields `None` → centroid-only under hybrid. Populated on next ingest-with-regeneration or explicit recompute/reindex. Documented, not auto-migrated.
- **Schema evolution on the meta table.** Adding a column to `_meta_schema` means old `_archon_collection_meta` tables predate it. The read path must tolerate a missing column (treat as `None`/empty), mirroring how A1 handles read-boundary defaults. An integration test pins "old table without the column reads back `None`."
- **Description is `None`** (no API key, generation failed/timed out — `description_generator.py:76`, `:88`): no description embedding is computed; collection is centroid-only. Logged at DEBUG, consistent with existing description-generation logging.
- **Description embedding staleness vs. centroid.** The centroid is recomputed on every ingest batch (`pipeline.py:279`); the description (and thus its embedding) only on the 20%-doc-count `_should_regenerate` trigger. The description embedding is therefore a coarser, slower-moving signal — acceptable by design (a topic summary is meant to be stable), but noted so it is not mistaken for a bug. Recompute/reindex always refreshes it from the current description.
- **Embedding-model change / mismatch.** A collection whose `embedding_model` no longer matches the active one is already treated as unscored for the centroid (`router.py:142`); the description embedding shares that tag, so it is ignored under the same condition. No separate guard.
- **`w` boundary values.** `routing_description_weight = 0.0` must be exactly centroid-only (pinned to equal `"centroid"`); `1.0` is pure description-embedding. Out-of-range values are a `ConfigError` at load, consistent with `routing_confidence_threshold` validation (`config.py:175`).
- **Confidence gate semantics under blending.** The gate compares `max(blended_score)` to `routing_confidence_threshold`. Because the blend is a convex combination of two cosines (each in `[-1, 1]`), the threshold's meaning shifts slightly under hybrid; the default `0.30` is re-confirmed against the eval fixture, and any needed retune is config-only (no code change) and recorded in the baseline.
- **Eval `shortlist_size = len(collections)` divergence (`runner.py:503`).** Retained — but it no longer hides ranking quality once the metric reads the *full ranked order* rather than shortlist membership. The divergence comment is updated to say so.
- **Latency.** One extra cosine per collection per query (O(collections·dim)). Negligible versus embedding + rerank, but the eval latency floors (`thresholds.toml`) must still pass; pinned.
- **Routing fixture expansion must not break retrieval metrics.** `tests/eval/routing/collections.jsonl` feeds routing; adding collections/queries must keep the retrieval-scope fixtures and their `nDCG@10`/recall floors intact (the routing and retrieval scopes share the corpus loader). The README's fixture-schema rules govern this; changes go through the documented baseline-regeneration step.

## Implementation Stacking Order (commit sequence)
Each commit independently passes the default pytest run.
1. **Eval gate first — rank-sensitive metric + fixture expansion.** Add `routing_mrr`/`routing_precision_at_1` to `eval/metrics.py`, record the full ranked order in the trace, expand `tests/eval/routing/` fixtures, add the `thresholds.toml` floor, regenerate the baseline. *No router change yet* — this commit measures **today's** centroid routing under the new, rank-sensitive metric and establishes the baseline the feature must beat. (Building the gate before the feature is the whole point: A1's analog was "don't ship half-built fields"; B4's analog is "don't ship a ranking change behind a blind gate.")
2. **Persistence — `description_embedding` field + column.** `CollectionMeta` field; `_meta_schema` column; `_row_to_meta` parse (with malformed-JSON warning); `update_collection_meta` serialize; schema-evolution read tolerance. Integration round-trip + old-table tests. No ranking change.
3. **Producer — embed the description at ingest + recompute.** Wire `pipeline.py` ingest and `recompute_collection_meta` to compute and persist the embedding. Unit + integration tests. Still no ranking change (artifact is written but unused).
4. **Router — `strategy`/`description_weight` + blended `rank()`.** Add constructor params, extend `_ROUTING_FIELDS`, implement the blend with per-collection fallback. Unit tests including the `"centroid"` regression pin and the ADR-04-failure-mode case. Default config still `"centroid"` → no behavior change for existing deployments.
5. **Config + server wiring.** `routing_strategy`/`routing_description_weight` in `config.py` (parse + bounds) and `_build_router`; `archon-search.toml.example`. MCP `list_collections` strip + `get_collections_meta` exposure. Config and MCP-shape tests.
6. **Eval run + baseline under hybrid.** Run `-m eval` under both strategies; record both metrics in the baseline; confirm the floor holds and hybrid ≥ centroid offline. If not, the feature does not merge as recommended (rule 2).
7. **Docs.** New ADR (post-ADR-05) superseding/extending ADR-04; `BREAKING.md` entry; `tests/eval/README.md` updates; `03_world_class_roadmap.md` B4 annotation.

## Open Questions
- **Which rank-sensitive metric is the gate — P@1, MRR, or both?** P@1 is the sharpest statement of "did routing pick the right collection first"; MRR is more forgiving for multi-gold queries. Lean toward shipping both and gating on MRR (multi-gold tolerant), with P@1 reported. Resolved in planning against the expanded fixture's gold cardinality.
- **Default `routing_description_weight`?** `0.3` is a starting guess by analogy to `routing_confidence_threshold = 0.30`; the eval sweep in commit 6 should pick the value that maximizes the offline metric without over-fitting the 3→N fixture. The chosen value is recorded in the baseline rationale.
- **Retain or supersede `routing_accuracy`?** It still answers a real question ("does the gold collection have a usable centroid"). Lean toward retaining it as a coverage check and adding the rank-sensitive metric as the *ranking* gate, rather than deleting a committed baseline number.
- **How many collections in the expanded routing fixture?** Enough that no strategy is trivially top-1 on every query, few enough to keep eval fast and the corpus reviewable. Decided in planning; the README's fixture rules constrain it.
- **Should `recompute_collection_meta` re-embed the description even when the description text is unchanged?** Cheapest correct behavior: re-embed only when the description string differs from what produced the stored embedding (needs a stored marker), else skip. Minimum slice may always re-embed (one short text, negligible); planning decides whether the marker is worth it.

## Future Iterations
- **Multi-centroid / clustered representation** — k sub-centroids per collection, max-over-clusters scoring; the `strategy` Literal already reserves room for `"multi_centroid"`.
- **B5 (`CON-4`)** — incremental centroid *and* description-embedding maintenance; B4 leaves both on the full-recompute path.
- **B6** — production-model eval lane; the real-model lift number that would justify flipping the default to `"hybrid"`.
- **A4 / B1** — surface per-collection blended scores and the routing path on `/explain` / stage traces; B4 deliberately keeps `RouteResponse` minimal.
- **C7 (`API-4`)** — wrapping MCP responses in Pydantic models; once landed, adding routing fields to `get_collections_meta` stops being a breaking change.
- **Description-aware lexical routing** — token overlap between query and description as a third, cheap signal independent of the embedder; a candidate additional `strategy` member if the embedding blend underperforms on the prod-model lane.

## Recommendation
This is the right shape for "stronger routing now": it adds the **cheapest strong signal** (an embedding of a description that already exists and is currently wasted on prompt-rendering only), blends it behind an opt-in strategy with centroid as the untouched baseline, and — critically — **fixes the gate before the feature.** The hardest part is not the blend math; it is that the routing eval is currently rank-insensitive (`shortlist_size = len(collections)` makes `routing_accuracy` a coverage check, `runner.py:503`), so a ranking change today lands against a blind regression guard. B4's load-bearing commit is the first one: a rank-sensitive metric and an expanded fixture, measuring today's centroid routing, so the feature has a real bar to beat. What must not be compromised: **centroid-only stays the exact default** (regression-pinned), the **per-collection fallback** keeps hybrid safe on old/mixed corpora, and the **default flip waits for B6's prod-model lane** — offline lift on a SHA-256 bag-of-words backend is enough to gate against regression and to justify shipping the strategy, but not to declare it the production default.
