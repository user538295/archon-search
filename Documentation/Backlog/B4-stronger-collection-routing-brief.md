# Feature Brief: Stronger Collection Routing (B4 — item 9)

## Problem
Collection routing today rests on a **single signal**: `MultiCollectionRouter.rank()` scores each collection by cosine similarity between the query embedding and `CollectionMeta.centroid` — the element-wise mean of every chunk vector in the collection (`router.py:127`, centroid computed in `pipeline.py:_compute_centroid` lines 100–104). A confidence gate (`routing_confidence_threshold`, default `0.30`) and a shortlist cap (`routing_shortlist_size`, default `8`) sit on top (`router.py:148–158`). The mean-of-all-chunks centroid is a blunt instrument: for a heterogeneous corpus it averages toward the centre of the embedding space and loses discriminative power, which ADR 04 itself flags as the primary recall risk (`ADRs/04_multi_collection_router_with_centroid_preranking.md:90`). 

Meanwhile a **second signal already exists but is never used for ranking**: each collection carries an auto-generated 2–3 sentence `description` (`CollectionMeta.description`, produced by Haiku in `description_generator.generate_description`). Today the description is injected verbatim into the decomposer prompt block (`router.py:225`) but **plays no part in centroid scoring**. ADR 04 explicitly lists "summary-embedding alternative routers" and "description + centroid hybrid alternatives" as the planned next step with "centroid remains baseline for v1" (`100_system_architecture_overview.md` routing section; ADR 04 Alternatives). The roadmap captures this as B4 / item 9: *"summary-embedding + description + centroid hybrid alternatives; centroid stays the baseline. Gated by the eval harness."* (`03_world_class_roadmap.md:64`).

The blocker to building this is not the scoring math — it is the **evaluation gate**. Per the roadmap's sequencing rule, "any feature that touches ranking lands behind a benchmarked threshold in `tests/eval/`… No feature flag → no merge" (`03_world_class_roadmap.md:39`). But the eval harness **cannot currently evaluate any description- or summary-based routing signal**: the eval router metas are built from `pipeline.recompute_collection_meta()` after ingest (`eval/runner.py:484`), which preserves `description = None` (no `ANTHROPIC_API_KEY`, no Haiku in the deterministic harness — `pipeline.py:405`); and the committed routing descriptions in `tests/eval/routing/collections.jsonl` are **only consumed by the determinism hash** (`eval/_hashing.py:75`), never loaded into the metas that `_run_router_for_query` ranks (`eval/runner.py:508`). So a stronger routing signal has nothing to be gated against until the harness learns to inject and deterministically embed those descriptions.

## Goal
B4 ships a **strategy-selectable routing scorer** — centroid (baseline, unchanged default), description/summary-embedding, and a centroid+summary hybrid — plus the **eval-harness machinery that makes the two new strategies deterministically gateable**, with centroid remaining the shipped default until a measured eval lift justifies a flip. Success is observable as: (a) `CollectionMeta` carries a new nullable `summary_embedding` populated from the collection `description` wherever the centroid is computed; (b) `MultiCollectionRouter.rank()` / `rank_with_scores()` (the latter introduced by A4) produce a blended score under a configured `routing_strategy`, with `routing_strategy = "centroid"` reproducing today's behaviour byte-for-byte; (c) the eval harness loads the committed `routing/collections.jsonl` descriptions into router metas, embeds them with the deterministic backend, and computes `routing_accuracy` **per strategy**, each behind its own floor in `thresholds.toml`; (d) the centroid floor is unchanged (`0.9259259259259259`) and the description/hybrid floors are set no lower than it (a non-regression gate); (e) `/route` and routing telemetry report which strategy ran; (f) the eval harness still passes and the 85% coverage gate holds on the default pytest run. **B4 ships the mechanism and the offline gate; it does not flip the default strategy** — that waits on a measured lift, ideally confirmed by the production-model eval lane (B6).

## Users & Context
- **Maintainers tuning retrieval quality** who need a principled second routing signal and a benchmark that tells them whether it helps before it becomes default.
- **Operators of large multi-collection deployments** (more than `routing_shortlist_size` routable collections) where centroid pre-ranking actually fires (Tier 3 of `get_pre_context`) and a weak centroid silently drops a relevant collection.
- **Contributors building B3 (server-side multi-collection search) and A4 (`/explain`)**, who consume routing decisions and need them debuggable and signal-attributed.
- **Eval / benchmark workflows** that gate every ranking change and currently have no way to exercise non-centroid routing.

Triggered when a query is routed across more collections than the shortlist size, or when an operator/maintainer wants to evaluate or enable a description-aware routing strategy.

## Core Flow
1. **Signal storage**: `CollectionMeta` gains `summary_embedding: list[float] | None = None` (`collection_meta.py`), persisted as a new nullable `summary_embedding_json` column on the `_archon_collection_meta` table, serialized/deserialized exactly like `centroid_json` (mirror `store.py:444` write and `store.py:306–309` read, including the malformed-JSON → `None` guard). It shares the collection's existing single `embedding_model` tag — the summary is embedded with the same embedder that produced the centroid, so the existing model-match check covers both.
2. **Signal population**: wherever a `description` is set or refreshed and the centroid is (re)computed, the description text is embedded once via the active `Embedder` and stored as `summary_embedding`. Two call sites: the ingest batch path (`pipeline.py:277–309`, right after `generate_description` succeeds) and `recompute_collection_meta` (`pipeline.py:388–421`, which today preserves the existing `description` but recomputes the centroid — it now also (re)embeds that description). If `description is None`, `summary_embedding` stays `None`. No new LLM call is introduced — B4 embeds the **existing** description; it does not generate a new summary.
3. **Strategy-aware scoring**: two new config knobs — `routing_strategy: Literal["centroid", "description", "hybrid"] = "centroid"` and `routing_hybrid_weight: float = 0.5` (weight on the centroid term; `1 - weight` on the summary term) — are read by the router. `rank()` and A4's `rank_with_scores()` are refactored to share a single `_score_collections(query_embedding, collections)` helper that, per collection, computes `centroid_sim = cosine(query, centroid)` and/or `summary_sim = cosine(query, summary_embedding)` and blends them per strategy. With `routing_strategy = "centroid"` the helper returns exactly today's centroid score — **zero behavioural change in the default configuration** (pinned by a snapshot test). The confidence gate, the shortlist cap, the "unscored collections placed last" fallback (`router.py:145–157`), and the "all-unscored bypasses the gate" rule (`router.py:148–150`) are preserved and apply to the blended score (a convex combination of two cosines stays in the same range, so `routing_confidence_threshold` keeps its meaning).
4. **Per-strategy fallback**: a collection missing the signal a strategy needs degrades gracefully rather than disappearing. `description` strategy with `summary_embedding is None` → that collection is treated as unscored (placed after scored ones, same mechanics as a `None` centroid). `hybrid` with one term missing → score falls back to the available term (centroid-only or summary-only) rather than dropping the collection. If a non-centroid strategy is configured but **no** collection has the required signal, the router logs a WARNING and falls back to centroid scoring for that call so routing is never worse than baseline.
5. **Eval-harness gating** (the load-bearing part): the deterministic harness is extended so non-centroid strategies are reproducible. The eval corpus loader reads `tests/eval/routing/collections.jsonl` descriptions into the `CollectionMeta` objects used by `_run_router_for_query` (`eval/runner.py:487–510`), and the deterministic `EvalEmbedderBackend` (`eval/backends.py:47`) embeds each description into `summary_embedding`. `runtime.toml` gains `[routing].strategy`; the runner computes `routing_accuracy` for the configured strategy via the existing `compute_routing_accuracy` (`eval/metrics.py:244`). To gate all three strategies in one run, the routing eval is parametrised over `{centroid, description, hybrid}` and emits `routing_accuracy_centroid` / `routing_accuracy_description` / `routing_accuracy_hybrid`, each with its own floor in `thresholds.toml`. Because this changes determinism inputs (it loads descriptions previously only hashed), the baseline is recalibrated and `baseline.json` / `baseline.md` / `thresholds.toml` are refreshed together per the documented refresh procedure (`thresholds.toml:10–13`).
6. **Observability**: `RouteResponse` gains `routing_strategy: str` reporting which strategy produced the shortlist (`"centroid"` / `"description"` / `"hybrid"`, or `"none"` for Tier 1/Tier 2 of `get_pre_context` where no centroid ranking runs at all — `router.py:194–201`). `TelemetryEntry.from_route_response` gains the same field (a small enum string; the no-raw-query invariant is untouched). Per-collection signal breakdown (centroid vs summary vs blended score) is surfaced through A4's `/explain` routing block, **not** through `/route` — see Out of Scope.
7. **Docs / ADR**: a new ADR (`ADRs/06_*`) supersedes the routing-strategy portion of ADR 04 (ADRs are append-only — ADR 04 gets a "Superseded by 06" pointer, not an edit). `100_system_architecture_overview.md`, `110_component_catalog_and_layer_breakdown.md`, and `210_performance_and_scalability.md` (routing-knobs table) are updated; `03_world_class_roadmap.md` B4 is reconciled to record that multi-centroid / clustered representations are deferred (see Out of Scope).

## Out of Scope
- **Flipping the default strategy.** Centroid stays the shipped default (`routing_strategy = "centroid"`). A non-centroid strategy becomes default only after a measured eval lift — and the production-model lane (B6) is the honest place to confirm a real-embedding lift, since the deterministic backend's lift may not transfer. B4 ships the mechanism + offline gate, not a behaviour change for existing deployments.
- **Multi-centroid / clustered collection representations.** `roadmap.md:46` and item 3 list "multi-centroid / clustered representations" alongside summary embeddings; that is a heavier change (k-means or similar over chunk vectors, a list-of-centroids schema, a different scoring loop) and is deferred. B4 ships single-vector signals only. Roadmap B4 reconciled to record this.
- **A new/longer summary generator.** B4 embeds the **existing** `description` (the 2–3 sentence Haiku output). A distinct, longer-form summarization pass is a future iteration; v1's "summary embedding" *is* the description embedding.
- **Per-collection routing weights / per-collection strategy.** `routing_hybrid_weight` is global in v1. Per-collection overrides on `CollectionMeta` are a future iteration.
- **Learned / calibrated fusion** (e.g., logistic blend, RRF over routing signals). v1's hybrid is a fixed convex combination. Calibration waits on B6 and real-model data.
- **Per-collection signal breakdown on `/route`.** `/route` returns only `routing_strategy`. Surfacing per-collection centroid/summary/blended scores is A4's `/explain` job (its `rank_with_scores` already returns per-collection scores); B4 generalises that field rather than duplicating it on `/route`.
- **Changing the three-tier `get_pre_context` policy.** Tier 1 (≤3 routable → search all, no ranking) and Tier 2 (4..shortlist → decomposer over all, no centroid ranking) are unchanged (`router.py:194–201`). B4 strengthens the **scoring** that Tier 3 (and the eval `select()` path) uses; it does not re-draw the tier boundaries.
- **Incremental centroid/summary recompute (CON-4 / B5).** B4 keeps the existing full-recompute path (`pipeline.py:_compute_centroid`). Summary embedding is one extra embed per re-describe, not per chunk, so it does not materially worsen CON-4; the incremental optimisation stays B5's job. (Interaction noted in Edge Cases.)
- **Metadata-cache invalidation (CON-2).** The router's forever-cached metadata (`router.py:69`, `_cached_metadata`) is a known debt owned elsewhere; B4 does not fix it. Stale metadata means a stale `summary_embedding` is served until cache reset — same staleness surface centroids already have.
- **Removing the `max_parallel_collections` inert knob.** Documented as unwired (`config.py:44`, ADR 04 `#Unverified`); untouched here.

## Key Decisions
- **Centroid stays the baseline and the default; strategies are additive and selectable.** ADR 04 mandates "centroid remains baseline for v1." B4 adds alternatives behind a config knob that defaults to today's behaviour, with a snapshot test pinning byte-for-byte parity for `routing_strategy = "centroid"`. No existing deployment changes behaviour on upgrade.
- **The summary signal is the *embedded existing description*, not a new generation step.** This avoids a new LLM dependency on the routing path (ADR 04 rejected an LLM router for the default path) and reuses the description regeneration cadence (`_should_regenerate`, `description_generator.py:42`). It cleanly maps the roadmap's "summary embeddings" and "description-aware routing" onto a single stored vector.
- **Separate signal *generation* from signal *scoring* — this is what makes the feature eval-gateable.** Generation (Haiku description) is non-deterministic, network-dependent, and out of the eval harness. Scoring (cosine against a stored vector) is deterministic given fixed text. B4 makes the eval harness inject the committed `routing/collections.jsonl` descriptions and embed them with the deterministic backend, so the *scorer* — the thing B4 actually changes — is what the gate measures. Without this split there is no benchmark and, per the roadmap, no merge.
- **Per-strategy floors, non-regression by construction.** The eval emits one accuracy per strategy; the centroid floor is held at the current `0.9259…`; description/hybrid floors are set ≥ centroid. A strategy that underperforms the baseline cannot quietly ship — it either clears the floor or stays out.
- **Graceful degradation over hard failure.** A missing summary embedding never *drops* a collection from routing; it falls back (unscored-last for description-only, other-term for hybrid, centroid for a fully-unsignalled call). Routing must never be worse than the centroid baseline because a description failed to generate.
- **One embedding-model tag covers both vectors.** The summary is embedded with the same embedder as the centroid, so the existing `embedding_model` match check (`router.py:142`) gates both. No second tag, no cross-model summary routing in v1.
- **`/route` reports the strategy; `/explain` reports the scores.** Keeps `/route` lean and avoids duplicating A4's per-candidate score surface. `routing_strategy = "none"` is honest about Tiers 1/2 where no ranking runs.
- **Default flip deferred to a measured lift (B6).** Deterministic-backend accuracy is a regression guard, not a production SLA (`thresholds.toml:6–8`, `210_*`). A lift on SHA-256 hash embeddings does not prove a lift on real embeddings, so B4 does not flip the default.

## Edge Cases & Constraints
- **Pre-B4 collections (no `summary_embedding_json` column / value)**: read as `summary_embedding = None`; under `description`/`hybrid` they fall back per the matrix above; under the default `centroid` strategy nothing changes. The column is additive and nullable — no migration, lazy backfill on next ingest/re-describe (mirrors A1's lazy-backfill philosophy).
- **Collection with a centroid but no description** (Haiku failed, or no `ANTHROPIC_API_KEY` — `description_generator.py:76`): `summary_embedding = None`; behaves as above. Common in CI and air-gapped deployments — must not break routing.
- **Stale summary embedding**: `summary_embedding` is recomputed only when the description is regenerated (`_should_regenerate` at ≥20% doc-count drift) or on `recompute_collection_meta`. Between those, it can lag the corpus — the same staleness centroids already have, compounded by the router's forever-cache (CON-2). Documented, not fixed here.
- **`embedding_model` mismatch**: a `summary_embedding` produced under a different model is treated as unscored, identical to the centroid rule (`router.py:142`). Because both vectors share one tag, a mismatch invalidates both together.
- **Hybrid score range**: a convex combination of two cosine similarities stays within the cosine range, so `routing_confidence_threshold` (calibrated for centroid cosine) keeps a comparable meaning. Constraint: do **not** introduce a score normalisation that changes the gate's calibration without recalibrating the threshold.
- **All collections unscored under a non-centroid strategy** (e.g., description strategy, zero descriptions present): WARNING logged once per call, ranking falls back to centroid; if centroids are also all absent, the existing all-unscored bypass returns up to `shortlist_size` unscored collections (`router.py:148–150`). Routing degrades to today's behaviour, never below it.
- **Tier 1 / Tier 2 paths**: no centroid or summary ranking runs (`router.py:194–201`); `summary_embedding` is irrelevant and `routing_strategy` is reported as `"none"`. B4's scoring change is observable only at Tier 3 and on the eval `select()` path (which runs with `shortlist_size = len(collections)` and `confidence_threshold = 0.0`, exercising `rank()` for all collections — `eval/runner.py:500–510`).
- **CON-4 / B5 interaction**: B4 adds one description embed per re-describe (not per chunk), so it does not change the O(chunks) centroid recompute cost class. When B5 lands incremental `(sum, count)` centroid maintenance, the summary embedding (a single vector embedded from a single short string) updates on the same re-describe trigger and does not need incrementalisation.
- **Eval determinism inputs change**: loading `routing/collections.jsonl` descriptions into routing alters the harness's behaviour. Per `thresholds.toml:10–13`, `baseline.json`, `baseline.md`, and `thresholds.toml` must be re-derived from one calibration run and committed together; the harness-hash test is updated in the same commit.
- **Coverage on net-new code**: `_score_collections`, the summary-embedding population at two call sites, config validation, and the `RouteResponse` field are all default-marker-covered. Eval-marker tests do not count toward the 85% gate; the gate must hold on unit + contract tests alone.
- **A4 ordering dependency**: A4 (Phase A) ships `rank_with_scores()` and the `/explain` routing block before B4 (Phase B). B4 refactors `rank()`/`rank_with_scores()` to share `_score_collections`; if A4 has **not** shipped when B4 starts, B4 introduces `_score_collections` for `rank()` only and the `rank_with_scores` refactor moves into A4's or a follow-up's scope. Planning verifies A4's status first.

## Open Questions
- **Hybrid weight scope**: global `routing_hybrid_weight` in v1. Promote to a per-collection override on `CollectionMeta` later? Deferred — adds a constructor field with test blast radius (every `CollectionMeta(...)` in tests), echoing the A1 `schema_version` concern.
- **`/explain` routing-candidate field naming (depends on A4)**: A4's brief surfaces `centroid_score` per candidate. Under B4 the ranking signal may be a blend. Rename to `routing_score` (with optional `centroid_score` / `summary_score` components) — a small `/explain` contract change — or keep `centroid_score` and add siblings? Lean toward `routing_score` + components for honesty; resolve against A4's shipped schema in planning.
- **Per-strategy eval floors vs single configured-strategy floor**: parametrising over all three strategies every run is the safest gate but triples the routing eval's cost. Alternative: gate only the `runtime.toml`-configured strategy and require a deliberate config change + recalibration to evaluate another. Lean toward parametrised (cheap on the small routing fixture) unless planning finds the cost material.
- **Should the description embedding be L2-normalised before storage?** `EvalEmbedderBackend` normalises (`backends.py:36–40`); the production `Embedder` path should be confirmed to match so cosine is consistent across both. Verify in planning.
- **Does `recompute_collection_meta` need a `--re-embed-summary` opt-out** for operators who want centroid refresh without re-embedding descriptions? Default: always re-embed (one cheap embed). Revisit only if it shows up in ingest latency.

## Future Iterations
- **Multi-centroid / clustered collection representations** (remainder of item 3 / `roadmap.md:46`): k-means (or similar) over chunk vectors, a list-of-centroids schema, max-over-clusters scoring. The next routing leap after B4.
- **Dedicated longer-form summary generation** distinct from the short `description`, with its own embedding — if description-embedding routing shows lift but the 2–3 sentence description proves too thin.
- **Per-collection routing weights / per-collection strategy** on `CollectionMeta`.
- **Learned / calibrated signal fusion** (logistic or RRF over routing signals), gated by B6's real-model lane.
- **B6 production-model eval lane** validates whether the offline lift transfers to real embeddings; the trigger for a possible default-strategy flip.
- **B3 server-side multi-collection search** consumes the stronger shortlist; co-design the routing-decision surface so B3's single embed/merge/rerank pass can attribute which signal selected each collection.
- **CON-2 metadata-cache invalidation** would let a fresh `summary_embedding` take effect without a router restart.

## Recommendation
This is the right next routing step, and it is **more eval-engineering than scoring math**. The scorer change is small and low-risk: a shared `_score_collections` helper, a stored description embedding, two config knobs, and a default that reproduces today's behaviour exactly. The genuinely hard, load-bearing part is **making description- and summary-based routing deterministically gateable** — today the eval harness has no descriptions on its router metas and the committed `routing/collections.jsonl` is only hashed, never loaded, so there is nothing to benchmark against. B4's central act is the signal-generation-vs-scoring split that lets the deterministic backend embed committed descriptions and the harness floor each strategy. What must not be compromised: **centroid stays the default until a measured lift justifies otherwise** (ideally confirmed on real embeddings via B6); **non-centroid strategies must clear an eval floor no lower than the centroid baseline**, so the feature can never silently make routing worse; and **a missing description must degrade gracefully, never drop a collection**. The three guardrails that keep B4 from rotting are the centroid-parity snapshot test, the per-strategy eval floors, and the graceful-fallback matrix.
