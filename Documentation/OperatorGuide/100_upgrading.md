# Upgrading

`archon-search` is published to PyPI from tagged releases (`release.sh` + the `archon-search-release.yml` workflow). CalVer in the version string encodes time only; it does **not** signal compatibility. The compatibility contract is `BREAKING.md` at the repo root, and structured release notes live in `CHANGELOG.md` plus the GitHub Releases page.

Since the D3 schema-migration tooling shipped, additive schema changes apply automatically at startup, and data-rewrite changes run as an explicit, observable `MigrationJob`. The full migration reference is the [MigrationGuide](../MigrationGuide/); this page gives operators the "when upgrading, run migrations" pointer.

## Principles

1. **CalVer encodes time, not compatibility.** Versions look like `YY.M.<rev-count>` (e.g. `26.7.412`). A higher version is not automatically safer to roll forward to — read `BREAKING.md`.
2. **`BREAKING.md` is the contract.** Every release that changes an existing REST/MCP/CLI/config surface adds an entry there. No entry means no contract change. `CHANGELOG.md` and the GitHub Release summarize *what shipped*; `BREAKING.md` tells you *what you must change* — they are separate by design.
3. **Backup before upgrade.** Stop the service, snapshot `~/.archon-search/`, then upgrade. See [40_backup_restore_disaster_recovery.md](40_backup_restore_disaster_recovery.md).
4. **Run pending schema migrations after upgrading.** In-place (additive-column) migrations apply silently at startup; rewrite migrations are surfaced but never auto-applied — you run them via `POST /collections/{name}/migrate` or `archon-search collection migrate`. Detail below and in [../MigrationGuide/05_data_migration.md](../MigrationGuide/05_data_migration.md).

## CalVer at a glance

Versions are produced by `hatch-vcs` from the latest git tag (`pyproject.toml`). Format: `YY.M.<commit-count-since-anchor>`.

- `YY` = two-digit year of the tag.
- `M` = month of the tag (1–12, no leading zero).
- `<commit-count>` = monotonic across the repo's history.

Two consequences for operators:

- You **cannot** tell from the version whether a bump removes or changes an API surface. Read `BREAKING.md`.
- Releases are manual (`bash release.sh`) and gated on the eval harness in CI. Plain pushes to `main` do not publish. See [../Architecture/510_release_and_environment_strategy.md](../Architecture/510_release_and_environment_strategy.md).

## Where to read release notes

Every `bash release.sh` run produces two artifacts operators can read:

- **`CHANGELOG.md`** in the repo root — one section per release, grouped by Conventional-Commit type (Features / Bug Fixes / Documentation / Refactoring). It is generated by `git-cliff` and committed automatically; do not hand-edit it.
- **GitHub Releases page** — the CI `github-release` job posts the same changelog section as the release body on the tag after the eval gate passes and PyPI publish succeeds. A GitHub Release therefore only ever exists for a build that shipped.

Read `CHANGELOG.md` (or the GitHub Release) to decide *whether* to upgrade; read `BREAKING.md` to decide *what to change* when you do.

## Pre-upgrade checklist

1. Read the diff in `BREAKING.md` between your current version and the target. Each entry lists the surface, the change, and the migration path.
2. Skim the target release's `CHANGELOG.md` / GitHub Release section for context.
3. Verify the service is healthy before touching it: `curl -fsS http://127.0.0.1:8765/health` and `curl -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" http://127.0.0.1:8765/status`. `GET /status` reports `store_schema_version` and `collections_schema_behind` — note the latter now so you know how many collections need a migration after the upgrade.
4. Take a cold backup — see [40_backup_restore_disaster_recovery.md](40_backup_restore_disaster_recovery.md).
5. Pin the current version somewhere you can reach it offline: `pip download archon-search==<current>` into a side directory.

## Upgrade procedure

```bash
# 1. Stop the service.
archon-search stop

# 2. Cold backup (mandatory).
DEST="/backups/archon-search/$(date -u +%Y-%m-%dT%H-%M-%SZ)"
mkdir -p "$DEST" && cp -a ~/.archon-search "$DEST/"

# 3. Upgrade the package. Use the same installer you used originally:
#    - uv tool:        uv tool upgrade archon-search
#    - pipx:           pipx upgrade archon-search
#    - plain pip:      pip install --upgrade archon-search
#    - pinned version: pip install archon-search==<target>
#    All four keep the optional extras (graph, code, multilingual, ...) the
#    wizard installed — for uv tool, only when the receipt records them; see
#    "Optional extras and the PyTorch build" below.

# 4. Re-run install ONLY if BREAKING.md notes a service-definition change
#    (the launchd plist / systemd unit is rewritten by `archon-search install`).
archon-search install

# 5. Start. In-place startup migrations apply automatically on boot.
archon-search start
curl -fsS -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" http://127.0.0.1:8765/status | jq -r .version
archon-search --version    # confirms the new version is live

# 6. Apply any pending REWRITE schema migrations (see next section).
```

Verification:

- `GET /status` reports the new version string (`/health` returns only `{"status":"running"}` and no version).
- `/status` lists the expected collections without new error entries, and `collections_schema_behind` is `0` once you have run pending migrations.
- A known-good search query returns hits.
- If telemetry is on, `/telemetry/stats` returns numbers, not `{"enabled": false}`.

### Optional extras and the PyTorch build

- **uv tool.** `uv tool upgrade` re-syncs the environment to the requirements recorded in the uv tool receipt and removes everything else. The current wizard records the extras it installs, so they survive the upgrade. Extras installed by an older wizard, or with `uv pip install`, are not recorded and are removed. Record them before you upgrade, repeating the options of your original install: `uv tool install "archon-search[graph,code,multilingual]"` (list every extra you use; on Linux with a `+cpu` or `+cu132` torch build, add `--torch-backend cpu` or `--torch-backend cu132`). See [Optional extras](../UserManual/10_installation.md#optional-extras).
- **uv tool on Linux with a non-default PyTorch build.** The receipt does not record `--torch-backend`, so `uv tool upgrade` can replace a CPU-only (`+cpu`) build or the wizard's CUDA 13.2 (`+cu132`) build with PyPI's default Linux build (also CUDA 13.2 for torch 2.15). Upgrade with `uv tool install --upgrade --torch-backend cpu "archon-search[<extras>]"` (or `--torch-backend cu132`) instead. See [Linux: install the CPU-only PyTorch build](../UserManual/10_installation.md#linux-install-the-cpu-only-pytorch-build).
- **pipx.** `pipx upgrade` keeps the extras. `pipx reinstall` keeps only the extras named in the original `pipx install`.
- **pip in a virtual environment.** `pip install --upgrade archon-search` keeps the extras installed in the environment.
- **Docker.** Keep the `/pip-packages` volume; you do not need to remove it. The entrypoint (`scripts/docker-entrypoint.sh`) stamps the volume with a fingerprint of `ARCHON_EXTRAS`, the Python version and the image's installed packages, which include the archon-search version. On the first start of a new image the fingerprint differs, so the entrypoint installs only the packages the extras add to the new image into a staging directory and, once that succeeds, replaces the volume's content with them — removing any archon-search copy that an older image's entrypoint left there. archon-search itself is never installed into the volume, so the container runs the new image's code. Until the install succeeds the volume holds the previous image's packages and the staged new ones at the same time, so `/pip-packages` needs free space for both sets at once. If the install fails (for example, because the volume lacks that space), the container exits and the volume keeps the previous image's packages and stamp, so rolling back to the previous image needs no reinstall. Allow for that network-bound install on the first start (see [Entrypoint and runtime extras installation](../UserManual/140_running_with_docker.md#entrypoint-and-runtime-extras-installation)), then check that `GET /status` (authenticated) reports the new version; `/health` carries no version.

## Schema migrations

The chunk-table schema is versioned by `STORE_SCHEMA_VERSION` in `archon_search/store.py`. A collection stores its own `schema_version` in `_archon_collection_meta`; a migration is *pending* when its `introduced_at` version is above the collection's current version.

Migrations are classified into three kinds (`archon_search/store.py`, `_all_migrations()`):

| Kind | What it does | When it runs | Rollback |
|---|---|---|---|
| `in_place` | Adds nullable columns only (no data rewrite) | Automatically at startup (`_run_startup_migrations`) | Automatic — old code ignores unknown nullable columns |
| `rewrite` | Rewrites every chunk (e.g. field backfill, re-embed) | Explicit operator action; runs as a checkpointed `MigrationJob` | Restore from backup (gated by `backup_confirmed`) |
| `export_rebuild` | Column rename/drop — impossible in-place (LanceDB is append-only) | Not executed by the tool — **re-ingest manually** | Restore from backup |

**Not everything is automatic.** Only `in_place` migrations apply on boot. As of `STORE_SCHEMA_VERSION = 1`, the two version-1 migrations (`migrate_expires_at_and_scopes`, `migrate_default_ttl_seconds`) are **not** applied at startup — an operator must run them via the migrate route after upgrading. Do not assume an upgrade left every collection at the current schema; check `collections_schema_behind` and the per-collection pending list.

### Inspect and apply

```bash
# List pending migrations for a collection (read-only default — no mutation).
archon-search collection migrate <collection>
#   → proxies GET /collections/<collection>/migrations/pending

# Apply pending migrations.
#   - in_place only        → applied synchronously, returns 200
#   - rewrite present      → requires --backup-first, creates a MigrationJob (202)
archon-search collection migrate <collection> --apply --backup-first --wait
#   → proxies POST /collections/<collection>/migrate
```

The equivalent REST calls (Bearer token required):

```bash
# Dry-run / pending list.
curl -fsS -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" \
     http://127.0.0.1:8765/collections/<collection>/migrations/pending | jq

# Apply (rewrite kind requires backup_confirmed: true).
curl -fsS -X POST -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" \
     -H 'Content-Type: application/json' \
     -d '{"dry_run": false, "backup_confirmed": true}' \
     http://127.0.0.1:8765/collections/<collection>/migrate
```

Notes:

- A `rewrite` request without `backup_confirmed: true` is rejected with `422`. This is a deliberate forcing function — the tool does **not** take the backup for you.
- `export_rebuild` migrations always return `422` with instructions to re-ingest manually; the tool classifies them but never executes them.
- Rewrite migrations run as a `MigrationJob` — observable and resumable through the standard jobs surface (`GET /jobs/{id}`, `POST /jobs/{id}/resume`) exactly like export/import. A crashed job preserves its checkpoint (100-chunk granularity); resume re-enqueues from there.
- A `409` means a `ReindexJob` is already active on the same collection — wait for it to finish.

The authoritative, worked-example reference is [../MigrationGuide/05_data_migration.md](../MigrationGuide/05_data_migration.md), with the end-to-end upgrade narrative in [../MigrationGuide/02_upgrade_procedure.md](../MigrationGuide/02_upgrade_procedure.md).

## Configuration drift

The config loader in `archon_search/config.py` ignores unknown keys silently and uses defaults for missing ones, with one deliberate exception: a key a release **removed** (the `REMOVED_KEYS` list, e.g. `[database].providers`) stops `serve`, `start`, `install` and `wizard` with a one-line `ConfigError` naming the replacement. Implications:

- Adding new keys to your `archon-search.toml` is safe across upgrades; old versions ignore them.
- Renamed keys that are not on the removed list may stop applying without warning. Check `BREAKING.md` for any `[section].key` renames and update before restart.
- Diff `archon-search.toml.example` against your live config after every upgrade to pick up new keys and comments (recent additions: `[maintenance].version_retention_hours`, `[server].cors_origins`, `docs_enabled`, `max_request_body_mb`, `graceful_shutdown_seconds`, and the `[ingest]` limits `allowed_roots`, `max_concurrent_tasks`, `parse_timeout_seconds`, `parse_timeout_seconds_per_mb`, `max_zip_entries`, `max_zip_uncompressed_mb`, `max_discovered_files`).

## Rolling back

Roll back is **pip install the old version + restore the backup**. Restore `~/.archon-search/` whenever `BREAKING.md` (or a rewrite migration you applied) changed the on-disk shape — a newer schema version may be unreadable by older code.

```bash
# 1. Stop the service.
archon-search stop

# 2. Reinstall the previous version.
pip install archon-search==<previous-version>

# 3. Restore ~/.archon-search/ from the pre-upgrade backup. Mandatory when you
#    applied any rewrite migration or BREAKING.md announced an on-disk change.
mv ~/.archon-search ~/.archon-search.failed-upgrade
cp -a /backups/archon-search/<timestamp>/.archon-search ~/

# 4. Re-run install only if the service definition changed for the older version.
archon-search install

# 5. Start and verify as in the upgrade procedure.
archon-search start
```

If nothing touched the on-disk data (no rewrite migration applied, no storage-related `BREAKING.md` entry), you may roll back the package only and leave `~/.archon-search/` in place. When in doubt, restore.

## Major upgrade patterns

### MCP `search` response shape

The relevant `BREAKING.md` entry changes the MCP `search` tool from a bare list to `{"results": [...], "acl_filtered": bool}`. Operator action: notify MCP consumers; no server-side migration needed.

### REST `/search` per-request `top_k`

Where a release ignores the per-request `top_k` field in `POST /search`, set `[database].top_k_return` in `archon-search.toml` to the desired value before upgrading.

### C2 — multilingual retrieval

Upgrading to the C2 release activates language tagging at ingest time when `multilingual = true`:

1. `SearchResult.language` (and the same field on `ScoredSearchCandidate` / `ExplainResult` / `ExplainNearMiss`) now returns `""` instead of `None` for untagged chunks, and serializes as `""` (not `null`) over REST. Update any `is None` guards and client type stubs.
2. The `language` filter, previously rejected with `422`, now accepts valid ISO codes and `"unknown"`.
3. Existing collections have `language=""` on all chunks — `GET /status` warns per collection when `multilingual = true` and untagged chunks are present. Re-ingest to populate language tags.
4. Enabling multilingual on an English-only install: run `archon-search install --multilingual` to download `lid.176.ftz`, set `multilingual = true`, and restart. Switching between an English profile and a multilingual profile still requires re-ingesting all data.

### PyTorch runtime upgrade

Embedding and reranking now run on PyTorch instead of fastembed / ONNX Runtime. Read the matching `BREAKING.md` entry for the full contract. The steps below were run on macOS arm64 (2026-10-25) against copies of a real fastembed-era data directory; the old index opened in the new build with no re-index (stored vectors vs a torch re-embedding of the same text: cosine ≥ 0.9999999 on `cpu` and `mps`, and 12 of 12 test queries returned identical ranked lists, max reranker score difference 3.8e-6).

1. **Stop the service first** (`archon-search stop`). A removed config key makes `serve`, `start`, `install` and `wizard` exit 1, so a launchd/systemd unit would crash-loop.
2. **Upgrade the tool** (`uv tool upgrade archon-search`, or the installer you used; see [Optional extras and the PyTorch build](#optional-extras-and-the-pytorch-build)).
3. **Migrate the config.** Either let `archon-search wizard` do it (it tolerates the removed keys, prints `Dropping removed config keys …`, writes `device`, and keeps the old file as `.bak`; it still stops at its "changing the embedding model requires rebuilding the index" prompt if your profile differs), or by hand. By hand: back up the file, delete the single-line `providers = [...]` and `reranker_providers = [...]` entries in `[database]` and `providers = [...]` in `[graph]`, then `archon-search config set database.device auto --config <file>` (or `cpu`). `config set` now validates the whole file through the loader and writes only if it passes; `config show` on an old file prints a warning naming the removed keys and still exits 0. A hand-wrapped multi-line array needs a manual edit.
4. **Check the model names.** Your `embedding_model`, `reranker_model` and every collection's `embedding_model` must be in the supported registry; others fail validation.
5. **Start** (`archon-search start`). The first start downloads the PyTorch weights into the same `models/` folder (measured: a 557 MB reranker, server ready 55 s after start; with the weights cached, ready in 6-7 s for `multilingual-e5-large` + jina on `mps`). Existing collections need no re-index.
6. **Verify**: `curl -s localhost:8765/ready` returns `ready: true`, and `GET /status` shows `model_validation.embedder_ok` and `reranker_ok` true with `provider_warnings: []`.

Operationally:

- **Every model is downloaded again.** The weights are a different file format, fetched from Hugging Face at pinned revisions into `<data dir>/models`. Per-profile downloads (embedder plus reranker): English minimal 225 MB, balanced 572 MB, max 2453 MB; multilingual minimal 471 MB, balanced 1670 MB, max 2797 MB. Allow for them, or run `archon-search wizard` to pre-warm while you watch.
- **Old ONNX files are orphaned, and they are not safe to `rm -rf`.** `models--Qdrant--*`, `models--Xenova--*` and the `onnx/` files inside shared repos such as `models--jinaai--jina-reranker-v2-base-multilingual` are no longer read (on a real directory 2.7 GB plus a 1.1 GB `onnx/model.onnx`; old Docker volumes also carry `/data/fastembed-cache`). With `huggingface_hub` 1.x all blobs live in one shared `models/blobs/` and the per-repo entries are symlinks into it, so deleting the repo directories frees almost nothing (2.66 GB of ONNX-only blobs stayed in a symlink analysis). Use the hub CLI, which reference-counts the blobs, after step 5 has succeeded: `HF="$(uv tool dir)/archon-search/bin/hf"; D=~/.archon-search/models; "$HF" cache ls --cache-dir "$D"` to review, then `"$HF" cache rm --cache-dir "$D" -y model/Qdrant/<repo> model/Xenova/<repo> …` for the ONNX-only repos and, in a separate call per file, `"$HF" cache rm --cache-dir "$D" -y hf://models/jinaai/jina-reranker-v2-base-multilingual/onnx/model.onnx`. On a copy of a real 11.3 GB models directory this left 5.6 GB and the server restarted offline with identical rankings.
- **Config keys changed.** `[database].providers`, `[database].reranker_providers` and `[graph].providers` are replaced by `[database].device` and `[graph].device` (`auto|cpu|mps|cuda`). A config file that still holds a removed key fails to load with `<section>.<key> was replaced by <section>.device (auto|cpu|mps|cuda); see BREAKING.md`. The `FASTEMBED_CACHE_PATH` variable is gone; models live under `ARCHON_SEARCH_DATA_DIR`.
- **Only registry models load.** Any embedding or reranker name outside the supported registry is rejected (`unsupported model '<name>'; supported: ...`): a collection gets `422`, and a server-wide `embedding_model` or `reranker_model` leaves the server up with `/ready` at `503` and `checks.models: "fail"`. Check your `embedding_model`, `reranker_model` and per-collection models before upgrading.
- **Scores shift slightly.** Vectors for a few models differ in small amounts from the old ones (see `tests/fixtures/runtime_parity/README.md`).
- **Defaults changed in the same release train.** `[ingest].max_file_mb` is 100 (was 0), docling runs on CPU on macOS, `serve` binds loopback outside containers, `/docs` and CORS are off, and several routes need an admin key; see `BREAKING.md` and the [Hardening checklist](../SecurityGuide/06_hardening_checklist.md). Archives and backups made before the manifest carried a namespace still import from the caller's own directory (see [40_backup_restore_disaster_recovery.md](40_backup_restore_disaster_recovery.md#single-collection-from-a-targz-archive)).

### Dependency matrix: torch and transformers

`pyproject.toml` now allows `torch>=2.9,<3.0.0` (2.9.0 is the first torch with Python 3.14 wheels; the package needs Python 3.14 or later) and `transformers>=5.21,<6`; `uv.lock` pins torch 2.15.0 and transformers 5.21.1 (its test requires at least 5.10.0, which clears the `transformers` advisory PYSEC-2026-3929). `gliner` caps `transformers` below 5.17.0, so `[tool.uv] override-dependencies` lifts that cap for `uv lock` and `uv sync`; pip and `uv tool install` users who add the `graph` extra still get gliner's own cap. The matrix below was measured on 2026-10-25 for the earlier range (`torch>=2.4`, `transformers>=4.57,<5.14`) and has not been re-run on transformers 5.21 or torch 2.15. It was tested on Apple silicon (Python 3.13, torch 2.13.0) with `tests/test_embedder.py`, `test_reranker.py`, `test_reranker_loading.py`, `test_torch_runtime.py` and `test_model_store.py` ("unit"), 9 models on CPU and `mps` ("rep"), and the full 145-case parity lane ("full"):

| transformers | unit | rep | full |
|---|---|---|---|
| 4.57.1 (lowest allowed) | 141 passed | 50 passed, 4 skipped | 139 passed, 6 skipped |
| 5.0.0 | 141 passed | 50 passed, 4 skipped | not run |
| 5.8.1 | 141 passed | 50 passed, 4 skipped | not run |
| 5.10.4 | 141 passed | 50 passed, 4 skipped | not run |
| 5.13.1 (highest allowed, in the lock) | 141 passed | 50 passed, 4 skipped | 139 passed, 6 skipped |

The skips are truncation cases the corpus has no text for. Versions between the rows were not run. The torch floor is 2.4 (it used to be docling's 2.2.2): on Python 3.12+, torch 2.2.2 and 2.3.1 cannot load ModernBERT (`granite-embedding-small-english-r2`: "Dynamo is not supported on Python 3.12+"), and transformers 5.13 treats torch below 2.4 as absent. Torch 2.4.1 passed the unit and rep lanes on transformers 4.57.1 and 5.13.1. A defect found by this matrix is fixed: concurrent model builds on transformers 4.57.1 failed with `Cannot copy out of meta tensor` on CPU and CUDA, so builds are now serialized by `TRANSFORMERS_LOCK`.

**Dependency audit.** `pip-audit` of the dependency set before the bump reported 83 vulnerabilities in 12 packages (pillow, docling, pyjwt, filelock, urllib3, fastmcp, certifi, opentelemetry-api, setuptools, transformers and others); after `uv lock --upgrade-package` (docling 2.142.1, pillow 13.0.0, transformers 5.13.1, pyjwt 2.15.1, filelock 4.2.4, urllib3 2.8.0, fastmcp 3.4.11) it reports no known vulnerabilities (2026-10-25). It is a manual check, not a CI gate. The container image installs **unlocked latest** dependencies on purpose (an unlocked-deps CI lane tests that resolution), so its package set differs from `uv.lock` (torch 2.14.1 in the image at the time of writing); audit the image you ship.

## Version probing

```bash
# Server version (from the running process).
curl -fsS -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" http://127.0.0.1:8765/status | jq -r .version

# Installed package version (from the CLI host).
archon-search --version

# Available versions on PyPI.
pip index versions archon-search
```

If the `/status` version and `archon-search --version` disagree, the supervisor is still running the old binary — restart the service.
