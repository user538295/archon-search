# Upgrading

`archon-search` is published to PyPI from tagged releases (`release.sh` + the `archon-search-release.yml` workflow). CalVer in the version string encodes time only; it does **not** signal compatibility. The compatibility contract is `BREAKING.md` at the repo root, and structured release notes live in `CHANGELOG.md` plus the GitHub Releases page.

Since the D3 schema-migration tooling shipped, additive schema changes apply automatically at startup, and data-rewrite changes run as an explicit, observable `MigrationJob`. The full migration reference is the [MigrationGuide](../MigrationGuide/); this page gives operators the "when upgrading, run migrations" pointer.

## Principles

1. **CalVer encodes time, not compatibility.** Versions look like `YY.M.<rev-count>` (e.g. `26.7.412`). A higher version is not automatically safer to roll forward to — read `BREAKING.md`.
2. **`BREAKING.md` is the contract.** Every release that changes an existing REST/MCP/CLI/config surface adds an entry there. No entry means no contract change. `CHANGELOG.md` and the GitHub Release summarize *what shipped*; `BREAKING.md` tells you *what you must change* — they are separate by design.
3. **Backup before upgrade.** Stop the service, snapshot `~/.archon-search/`, then upgrade. See [40_backup_restore_disaster_recovery.md](40_backup_restore_disaster_recovery.md).
4. **Run pending schema migrations after upgrading.** In-place (additive-column) migrations apply silently at startup; rewrite migrations are surfaced but never auto-applied — you run them via `POST /collections/{name}/migrate` or `archon-search collection migrate`. Detail below and in [../MigrationGuide/05_data_migration.md](../MigrationGuide/05_data_migration.md).

## CalVer at a glance

Versions are produced by `hatch-vcs` from the latest git tag (`pyproject.toml`). Format: `YY.M.<commit-count-since-anchor>`.

- `YY` = two-digit year of the tag.
- `M` = month of the tag (1–12, no leading zero).
- `<commit-count>` = monotonic across the repo's history.

Two consequences for operators:

- You **cannot** tell from the version whether a bump removes or changes an API surface. Read `BREAKING.md`.
- Releases are manual (`bash release.sh`) and gated on the eval harness in CI. Plain pushes to `main` do not publish. See [../Architecture/510_release_and_environment_strategy.md](../Architecture/510_release_and_environment_strategy.md).

## Where to read release notes

Every `bash release.sh` run produces two artifacts operators can read:

- **`CHANGELOG.md`** in the repo root — one section per release, grouped by Conventional-Commit type (Features / Bug Fixes / Documentation / Refactoring). It is generated by `git-cliff` and committed automatically; do not hand-edit it.
- **GitHub Releases page** — the CI `github-release` job posts the same changelog section as the release body on the tag after the eval gate passes and PyPI publish succeeds. A GitHub Release therefore only ever exists for a build that shipped.

Read `CHANGELOG.md` (or the GitHub Release) to decide *whether* to upgrade; read `BREAKING.md` to decide *what to change* when you do.

## Pre-upgrade checklist

1. Read the diff in `BREAKING.md` between your current version and the target. Each entry lists the surface, the change, and the migration path.
2. Skim the target release's `CHANGELOG.md` / GitHub Release section for context.
3. Verify the service is healthy before touching it: `curl -fsS http://127.0.0.1:8765/health` and `curl -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" http://127.0.0.1:8765/status`. `GET /status` reports `store_schema_version` and `collections_schema_behind` — note the latter now so you know how many collections need a migration after the upgrade.
4. Take a cold backup — see [40_backup_restore_disaster_recovery.md](40_backup_restore_disaster_recovery.md).
5. Pin the current version somewhere you can reach it offline: `pip download archon-search==<current>` into a side directory.

## Upgrade procedure

```bash
# 1. Stop the service.
archon-search stop

# 2. Cold backup (mandatory).
DEST="/backups/archon-search/$(date -u +%Y-%m-%dT%H-%M-%SZ)"
mkdir -p "$DEST" && cp -a ~/.archon-search "$DEST/"

# 3. Upgrade the package. Use the same installer you used originally:
#    - uv tool:        uv tool upgrade archon-search
#    - pipx:           pipx upgrade archon-search
#    - plain pip:      pip install --upgrade archon-search
#    - pinned version: pip install archon-search==<target>

# 4. Re-run install ONLY if BREAKING.md notes a service-definition change
#    (the launchd plist / systemd unit is rewritten by `archon-search install`).
archon-search install

# 5. Start. In-place startup migrations apply automatically on boot.
archon-search start
curl -fsS http://127.0.0.1:8765/health | jq -r .version
archon-search --version    # confirms the new version is live

# 6. Apply any pending REWRITE schema migrations (see next section).
```

Verification:

- `/health` reports the new version string.
- `/status` lists the expected collections without new error entries, and `collections_schema_behind` is `0` once you have run pending migrations.
- A known-good search query returns hits.
- If telemetry is on, `/telemetry/stats` returns numbers, not `{"enabled": false}`.

## Schema migrations

The chunk-table schema is versioned by `STORE_SCHEMA_VERSION` in `archon_search/store.py`. A collection stores its own `schema_version` in `_archon_collection_meta`; a migration is *pending* when its `introduced_at` version is above the collection's current version.

Migrations are classified into three kinds (`archon_search/store.py`, `_all_migrations()`):

| Kind | What it does | When it runs | Rollback |
|---|---|---|---|
| `in_place` | Adds nullable columns only (no data rewrite) | Automatically at startup (`_run_startup_migrations`) | Automatic — old code ignores unknown nullable columns |
| `rewrite` | Rewrites every chunk (e.g. field backfill, re-embed) | Explicit operator action; runs as a checkpointed `MigrationJob` | Restore from backup (gated by `backup_confirmed`) |
| `export_rebuild` | Column rename/drop — impossible in-place (LanceDB is append-only) | Not executed by the tool — **re-ingest manually** | Restore from backup |

**Not everything is automatic.** Only `in_place` migrations apply on boot. As of `STORE_SCHEMA_VERSION = 1`, the two version-1 migrations (`migrate_expires_at_and_scopes`, `migrate_default_ttl_seconds`) are **not** applied at startup — an operator must run them via the migrate route after upgrading. Do not assume an upgrade left every collection at the current schema; check `collections_schema_behind` and the per-collection pending list.

### Inspect and apply

```bash
# List pending migrations for a collection (read-only default — no mutation).
archon-search collection migrate <collection>
#   → proxies GET /collections/<collection>/migrations/pending

# Apply pending migrations.
#   - in_place only        → applied synchronously, returns 200
#   - rewrite present      → requires --backup-first, creates a MigrationJob (202)
archon-search collection migrate <collection> --apply --backup-first --wait
#   → proxies POST /collections/<collection>/migrate
```

The equivalent REST calls (Bearer token required):

```bash
# Dry-run / pending list.
curl -fsS -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" \
     http://127.0.0.1:8765/collections/<collection>/migrations/pending | jq

# Apply (rewrite kind requires backup_confirmed: true).
curl -fsS -X POST -H "Authorization: Bearer ${ARCHON_SEARCH_API_KEY}" \
     -H 'Content-Type: application/json' \
     -d '{"dry_run": false, "backup_confirmed": true}' \
     http://127.0.0.1:8765/collections/<collection>/migrate
```

Notes:

- A `rewrite` request without `backup_confirmed: true` is rejected with `422`. This is a deliberate forcing function — the tool does **not** take the backup for you.
- `export_rebuild` migrations always return `422` with instructions to re-ingest manually; the tool classifies them but never executes them.
- Rewrite migrations run as a `MigrationJob` — observable and resumable through the standard jobs surface (`GET /jobs/{id}`, `POST /jobs/{id}/resume`) exactly like export/import. A crashed job preserves its checkpoint (100-chunk granularity); resume re-enqueues from there.
- A `409` means a `ReindexJob` is already active on the same collection — wait for it to finish.

The authoritative, worked-example reference is [../MigrationGuide/05_data_migration.md](../MigrationGuide/05_data_migration.md), with the end-to-end upgrade narrative in [../MigrationGuide/02_upgrade_procedure.md](../MigrationGuide/02_upgrade_procedure.md).

## Configuration drift

The config loader in `archon_search/config.py` ignores unknown keys silently and uses defaults for missing ones. Two implications:

- Adding new keys to your `archon-search.toml` is safe across upgrades; old versions ignore them.
- Renamed keys may stop applying without warning. Check `BREAKING.md` for any `[section].key` renames and update before restart.
- Diff `archon-search.toml.example` against your live config after every upgrade to pick up new keys and comments.

## Rolling back

Roll back is **pip install the old version + restore the backup**. Restore `~/.archon-search/` whenever `BREAKING.md` (or a rewrite migration you applied) changed the on-disk shape — a newer schema version may be unreadable by older code.

```bash
# 1. Stop the service.
archon-search stop

# 2. Reinstall the previous version.
pip install archon-search==<previous-version>

# 3. Restore ~/.archon-search/ from the pre-upgrade backup. Mandatory when you
#    applied any rewrite migration or BREAKING.md announced an on-disk change.
mv ~/.archon-search ~/.archon-search.failed-upgrade
cp -a /backups/archon-search/<timestamp>/.archon-search ~/

# 4. Re-run install only if the service definition changed for the older version.
archon-search install

# 5. Start and verify as in the upgrade procedure.
archon-search start
```

If nothing touched the on-disk data (no rewrite migration applied, no storage-related `BREAKING.md` entry), you may roll back the package only and leave `~/.archon-search/` in place. When in doubt, restore.

## Major upgrade patterns

### MCP `search` response shape

The relevant `BREAKING.md` entry changes the MCP `search` tool from a bare list to `{"results": [...], "acl_filtered": bool}`. Operator action: notify MCP consumers; no server-side migration needed.

### REST `/search` per-request `top_k`

Where a release ignores the per-request `top_k` field in `POST /search`, set `[database].top_k_return` in `archon-search.toml` to the desired value before upgrading. (`BREAKING.md` may refer to this as `[search] top_k_return`; the key the code actually reads is `[database].top_k_return` — follow the code.)

### C2 — multilingual retrieval

Upgrading to the C2 release activates language tagging at ingest time when `multilingual = true`:

1. `SearchResult.language` (and the same field on `ScoredSearchCandidate` / `ExplainResult` / `ExplainNearMiss`) now returns `""` instead of `None` for untagged chunks, and serializes as `""` (not `null`) over REST. Update any `is None` guards and client type stubs.
2. The `language` filter, previously rejected with `422`, now accepts valid ISO codes and `"unknown"`.
3. Existing collections have `language=""` on all chunks — `GET /status` warns per collection when `multilingual = true` and untagged chunks are present. Re-ingest to populate language tags.
4. Enabling multilingual on an English-only install: run `archon-search install --multilingual` to download `lid.176.ftz`, set `multilingual = true`, and restart. Switching between an English profile and a multilingual profile still requires re-ingesting all data.

## Version probing

```bash
# Server version (from the running process).
curl -fsS http://127.0.0.1:8765/health | jq -r .version

# Installed package version (from the CLI host).
archon-search --version

# Available versions on PyPI.
pip index versions archon-search
```

If the `/health` version and `archon-search --version` disagree, the supervisor is still running the old binary — restart the service.
