# Feature Brief: Deeper Health and Readiness (B2 — item 22)

## Problem
`archon-search` exposes exactly one dependency-blind health signal and one auth-gated status dump, with nothing in between. `GET /health` (`server/routes_health.py:18`) returns a hard-coded `{"status": "running", "version": <vcs>}` the instant the event loop can answer — it never touches the LanceDB connection, the embedder, the reranker, the indexing state, the job store, or the watcher. `GET /status` (`server/routes_status.py:22`) is richer but (a) requires a Bearer token, (b) reports a *static* `watching = config.watch` flag (`routes_status.py:64`) that reflects configured intent, not a live watcher, and (c) leaves `path`, `doc_count`, and `chunk_count` as `""`/`0` placeholders (`routes_status.py:68-70`). There is **no `/ready`, `/readyz`, or `/livez` endpoint anywhere** in the tree. The consequence is that a supervisor, load balancer, or operator cannot distinguish "the process answers TCP" from "the process can actually serve a search" — the storage connection could be down (`SearchStore._db is None`), the models could be cold, a collection could be mid-reindex, or the job queue could be backed up, and `/health` would still cheerfully return `200 running`. Item 22 ("operators need this before scaling load") and the operational-readiness doc both call for distinguishing **live** from **ready** and surfacing storage connectivity, model warm-status, index build state, watcher state, and queue depth — none of which is observable today without holding the API key and parsing a placeholder-laden `/status` body.

## Goal
B2 ships a typed, documented **liveness-vs-readiness split**: `GET /health` is retained unchanged as the liveness probe (the install flow at `cli/install_cmd.py` already polls it for up to 60s — that contract must not break), and a new `GET /ready` endpoint reports whether the service can actually serve traffic. Readiness gates on **storage connectivity ONLY** — the one cheap, must-be-true serving dependency (storage connection alive) — and *reports* every other dimension (model warm-status, per-collection index-build state, watcher liveness, job-queue depth) as **informational**, without gating on it. The indexing-state file is progress/observability metadata, not a serving dependency — search reads LanceDB, not the state file — so a corrupt/unreadable state file must not take the service out of rotation; gating on it would be a false-negative readiness signal that needlessly reduces availability. Forcing a model load to satisfy readiness would likewise violate the lazy-load startup contract that D6 explicitly preserves. The unauthenticated `/ready` body is deliberately **terse** (overall `ready` bool + the single `storage` check status) so it does not leak collection names, paths, counts, or topology to an unauthenticated caller; the **rich** readiness numbers (warm booleans, queue-depth integers, live-watcher set, per-collection index-state counts, storage-connected bool) are added to the existing **authenticated** `/status` response under a new `readiness` sub-object. Success is observable as: (a) `GET /ready` returns `200 {ready: true, ...}` once `SearchStore` is connected, and `503 {ready: false, ...}` when the storage ping fails (storage is the sole gate); (b) `/ready` requires no Bearer token (it is added to `_EXEMPT_PATHS`); (c) `/ready` leaks no collection names/paths/counts (pinned by a negative test); (d) authenticated `/status` now carries a `readiness` block with `embedder_warm`, `reranker_warm`, `storage_connected`, `jobs.pending`/`jobs.running`, `collections_indexing`/`collections_failed`, and a `watcher` report; (e) reading model warm-status does **not** trigger a model load (pinned by a test asserting the backend stays cold); (f) a `failed` collection is reflected only as `collections_failed` on authenticated `/status` and does **not** change `/ready` (pinned by a test); (g) the eval harness still passes; (h) the 85% coverage gate holds on the default pytest run.

## Users & Context
- **Supervisors / orchestrators / load balancers** (systemd, launchd, k8s probes, reverse proxies) that need an unauthenticated, status-code-driven readiness signal to decide when to route traffic or restart — without holding the API key.
- **Operators** running the daemon who currently cannot tell "up" from "serving", and who today must `curl` an auth-gated `/status` full of placeholder zeros to guess at readiness.
- **Contributors** who need a single canonical definition of which dependencies gate readiness versus which are merely reported, so future subsystems plug into a known seam rather than inventing ad-hoc health checks.

## Core Flow
1. **Liveness (`GET /health`, unchanged, unauthenticated).** Stays exactly as-is: returns `{"status": "running", "version": <vcs>}` the moment the event loop responds, touching no dependency. It remains the supervisor/installer liveness probe. B2 adds no fields and changes no behavior here — only documentation clarifying that `/health` == liveness.
2. **Readiness (`GET /ready`, new, unauthenticated).** Added to `_EXEMPT_PATHS` (`middleware_auth.py:16`) so it is reachable without a Bearer token, and surfaced in OpenAPI without the `BearerAuth` annotation (the `_configure_openapi` loop in `app.py:67` already skips `_EXEMPT_PATHS`). The handler runs a **single gating check**: a **storage ping** — a new `SearchStore.ping()` that calls `(await db.list_tables()).tables` under an `asyncio.wait_for` timeout and returns a bool (it never creates or mutates a table); cached with a short TTL (default ~1s) so frequent probes do not hammer LanceDB. State-store readability, model warmth, watcher state, index-build state, and queue depth are **not** part of the gating path — they are reported only on authenticated `/status`. If the storage ping passes, the endpoint returns `200` with `ReadinessResponse{ready: true, checks: {storage: "ok"}}`; if it fails it returns `503` with `ReadinessResponse{ready: false, checks: {storage: "fail"}}`. The body is the `ReadinessResponse` model itself — **not** the `ErrorDetail` envelope — because a 503 here is an expected "not ready yet" signal, not a pipeline error (contrast with A3's `/search` failure semantics). The only signals disclosed to an unauthenticated caller are the overall `ready` bool and `checks.storage: ok/fail` — acceptable under security doc 150's threat model (`150:24`, in-scope "casual misuse by a second local client that doesn't have the API key"; `150:28-29`, out-of-scope "hostile processes running as the same OS user (can read … the LanceDB files … directly)"), since the same local actor that can reach the unauthenticated port can already `lsof` it and read the LanceDB directory.
3. **Rich readiness on authenticated `/status`.** `StatusResponse` (`schemas.py:29`) gains a `readiness: ReadinessDetail` sub-object populated by the handler in `routes_status.py`: `storage_connected` (from `SearchStore.ping()`), `embedder_warm` / `reranker_warm` (observational — see step 4), `jobs: {pending, running}` (preferably the existing `JobStore.list()` filtered inline by `JobStatus`, since D1 may redesign the job API; a `count_by_status()` helper is optional convenience only), `collections_indexing` / `collections_failed` (counts derived from `IndexingStateStore.read()` collection statuses `in_progress` / `failed`), and a `watcher` report (step 5). These richer numbers stay behind Bearer auth because they expose operational topology.
4. **Model warm-status (observational, non-gating).** `ModelEmbedder._model` and `ModelReranker._model` are `None` until first use (lazy-loaded under a lock — `embedder.py`, `reranker.py`). B2 adds public, side-effect-free accessors: `is_warm` on `Embedder`/`ModelEmbedder` and `Reranker`/`ModelReranker` returning whether `_model is not None`. The `_model` attribute is symmetric across both backends (only `_model` matters for warmth), even though the model-NAME attributes differ — `ModelEmbedder.model_name` is public while `ModelReranker._model_name` is private; `is_warm` keys off `_model` on both, not the name. Readiness reads these via `app.state.embedder` and the reranker reachable through `app.state.pipeline`. **Reading `is_warm` must never trigger a load** — a cold model is *reported as cold but does not fail readiness*, because the service is still able to serve its first (slow) request, and forcing a load would break the lazy-load startup contract (D6).
5. **Watcher state (reporting-only, against a new app.state slot).** The `WatcherManager` (`watcher.py:197`) with `is_watching()` / `watching_names()` is **defined but never instantiated in the running server** today (no production call site; `cli/start.py` only invokes the OS supervisor). B2 therefore introduces a single `app.state.watcher_manager` slot (default `None`) that readiness and `/status` read: when it is `None`, the `watcher` report is `{running: false}`; when a manager is present, it is `{running: true, watching: <sorted watching_names()>}`. The new report drops a `configured` field — that would duplicate the legacy per-collection `watching` flag (`routes_status.py:64`, = `config.watch`), which B2 keeps as-is for backward compatibility. B2 does **not** take on wiring a live watcher into the server lifecycle — it only defines the readiness hook so that whichever future item starts the watcher populates a known slot. The legacy per-collection `watching` flag and the new `readiness.watcher` report will be reconciled when the live watcher lands.
6. **Index build state (reporting-only).** Derived from `IndexingStateStore.read()`: surfaced on `/status.readiness` as `collections_indexing` (count of `in_progress`) and `collections_failed` (count of `failed`). A collection mid-index does **not** make the service un-ready (other collections still serve); a `failed` collection likewise keeps `/ready` at `200`/`ready: true` — it is surfaced only as the `collections_failed` count on authenticated `/status`, never on the unauth `/ready` body.
7. **Docs reconciliation.** Adding a second unauthenticated endpoint is a **deliberate, documented change** to the "only `/health` is unauthenticated" invariant, not an application of it. Security doc 150 owns that invariant (`150:16` principle 2 "Bearer auth on every endpoint except `/health`"; `150:59` "Only `GET /health` is intended to be reachable without auth on the data path") and ops doc 160 (principle 4) restates it; both are edited to read `/health` **and** `/ready`, with the info-leak/threat-model rationale recorded in 150. `Documentation/Architecture/160_operational_readiness_monitoring_and_reliability.md` also gains a `/ready` row in the HTTP-endpoints table, an updated observability mermaid diagram, a paragraph defining the gating-vs-informational split, and a `GET /ready` triage step in the "Search returns nothing" runbook (before the auth-gated `/status` step). Error-taxonomy doc 140 gains a status-code-table row noting `/ready` `503` intentionally returns the `ReadinessResponse` body (not a `{detail}` body). The docs reference the code as source of truth. `BREAKING.md` records the additive REST changes (new `/ready` endpoint; new `readiness` sub-object on `/status`). No MCP surface changes (there is no health/status MCP tool — the 9 MCP tools are search/ingest/collection-meta/document operations only).

## Out of Scope
- **Wiring a live watcher into the server lifecycle.** `WatcherManager` is unwired in the running server today. B2 adds only the `app.state.watcher_manager` readiness *hook* and reports `running: false` until a future item starts the watcher. Actually starting watchers in-process is a separate concern (touches `app.py` lifespan, sync orchestration) and would balloon B2.
- **Per-stage latency timings / tracing / correlation IDs** — that is B1 (item 24). Readiness check durations are **not** emitted as stage timings here; B1 owns the tracing surface. B2 stays self-contained; the seam to B1 is noted, not built.
- **Configurable readiness gating** (e.g. `require_warm_models = true` to gate readiness on warm models for pre-warmed deployments) — deferred. B2 ships a fixed, documented gating set (storage only). A config knob is a clean follow-up once a deployment actually needs strict readiness.
- **Queue-depth thresholding / backpressure** ("too many pending jobs ⇒ not ready") — B2 *reports* counts; it does not define a depth threshold that flips readiness. Backpressure policy is D1's concern (job contract completion).
- **Forcing/triggering a model load to warm readiness** — explicitly forbidden; it would break the lazy-load startup contract (D6). Warm-status is observational only.
- **Install-time / background provider validation (D6)** — separate item; B2 reports warm-status but does not validate provider configuration at install or warm-up.
- **Surfacing a state-store-health field (`state_store_ok` or similar)** — deferred. Today `IndexingStateStore.read()` returns `None` for missing, corrupt, and unreadable files alike (it never raises — `progress.py:88-105`), so B2 cannot distinguish a corrupt state file from a fresh one; shipping a `state_store_ok` flag would be a half-built signal that reads healthy on a corrupt file. Surfacing real state-store health requires a read path that distinguishes corrupt-from-empty — a natural extension of A6's `IndexingStateStore` hardening, but B2 does not assume A6 delivers it.
- **Populating the `path` / `doc_count` / `chunk_count` placeholders on existing `/status` per-collection entries** (`routes_status.py:68-70`) — deferred for reviewability/commit-size: B2 is already touching `/status`, and folding a store-backed count fill into the same slice would balloon the diff and blur the readiness review. `SearchStore.count_documents` already exists, so the fill is cheap. **Risk noted:** a new `readiness` block shown next to a misleading `doc_count: 0` placeholder could confuse operators about empty-vs-unpopulated — so this is recommended as a **fast-follow**, not an open-ended backlog item. Kept out of B2's slice, but should land soon after.
- **Authenticating `/ready` / making it rich** — deliberately rejected. The probe must work without the API key (supervisors don't hold it), and an unauthenticated rich body would leak topology. Rich numbers live behind auth on `/status`.
- **MCP health/readiness tool** — no MCP surface change; the MCP tool set stays at 9 (search/ingest/collection-meta/document operations). A readiness MCP tool is not requested by item 22.
- **Structured-log / log-rotation work (B7)** and **production-model eval lane (B6)** — sibling Phase B items, independent of B2.
- **Cross-process readiness aggregation** — single-process local daemon; out of scope, consistent with the rest of the architecture.

## Key Decisions
- **`/health` stays the liveness probe, unchanged; `/ready` is the new readiness probe.** The install flow polls `GET /health` for up to 60s (`cli/install_cmd.py`) and supervisors already depend on it; renaming or enriching it would break that contract. Liveness = "the loop answers"; readiness = "dependencies are serviceable".
- **Readiness gates on storage connectivity only; state-store, model-warmth, watcher, index-build-state, and queue-depth are all informational.** The storage connection is the one cheap, must-be-true serving dependency — search reads LanceDB, not the indexing-state file. The indexing-state file is progress/observability metadata, not a serving dependency, so a corrupt/unreadable state file must **not** take the service out of rotation; gating on it would be a false-negative readiness signal that needlessly reduces availability. B2 deliberately surfaces **no** `state_store_ok` field either: `IndexingStateStore.read()` is hardened to never raise — it returns an indistinguishable `None` for missing, corrupt, and unreadable files alike (`progress.py:88-105`) — so such a flag could not actually surface corruption and would read healthy on a corrupt file. A meaningful state-store-health signal is deferred (see Out of Scope). This is the single most important design call: it preserves the lazy-load startup contract (a cold model is not an outage) and keeps the probe fast and deterministic.
- **Reading model warm-status must be side-effect-free.** `is_warm` returns `_model is not None` and never constructs a model. A readiness probe that lazily loaded a several-hundred-MB model on first call would turn a health check into a multi-second block — exactly the failure B2 must not introduce. Pinned by a "stays cold" test.
- **`/ready` is unauthenticated and terse; `/status` is authenticated and rich.** Adding `/ready` is a **deliberate, documented change** to the auth invariant — security doc 150 (principle 2 "Bearer auth on every endpoint except `/health`"; `150:59` "Only `GET /health` is intended to be reachable without auth") and ops doc 160 (principle 4) currently assert exactly **one** unauthenticated endpoint, and B2 adds a **second**. This is not an application of that invariant; it is an amendment to it, justified by the supervisor-without-key argument (a load balancer or systemd unit must read readiness without holding the API key). The unauth body leaks no collection names, paths, or counts — only the overall `ready` bool and `checks.storage: ok/fail`. **Threat-model reconciliation:** the only signals disclosed to an unauthenticated caller are `ready` and `checks.storage`. This is acceptable under security doc 150's threat model: the in-scope threat is a "casual misuse by a second local client that doesn't have the API key" (`150:24`), and 150 explicitly puts "hostile processes running as the same OS user (can read … the LanceDB files … directly)" **out** of scope (`150:28-29`) — so the same local actor that can reach the unauthenticated port can already `lsof` it and read the LanceDB directory. The terse body discloses strictly less than that.
- **`/ready` returns `503` (not `200`-with-`ready:false`-only) when a gating check fails, and the body is `ReadinessResponse`, not the error envelope.** Status-code-driven probes (k8s, LBs, systemd) act on the code; a 503 here is a healthy, expected "not ready yet" signal, deliberately distinct from A3's pipeline-failure 5xx that uses the `ErrorDetail` envelope.
- **Watcher readiness is reporting-only against a new `app.state.watcher_manager` slot.** Because no live watcher runs in the server today, B2 reports `running: false` until a future item populates the slot, rather than pretending to observe a watcher that isn't there. Honest over aspirational.
- **Storage ping is cached with a short TTL.** Readiness probes can fire every 1–2s; an uncached `list_tables()` per probe is wasteful. A ~1s TTL bounds cost while keeping the signal fresh.
- **No MCP change; REST is additive.** `/ready` is new; `/status` gains a sub-object. Both additive for tolerant JSON consumers. `BREAKING.md` documents them as additive.

## Edge Cases & Constraints
- **Probe during startup**: `SearchStore.connect()` + `migrate_namespace()` + `migrate_acl()` run in the lifespan *before* `yield` (`app.py:88-92`). The app does not accept connections until they complete, so a probe either gets connection-refused (supervisor reads as not-ready) or, once serving, sees `storage_connected: true`. There is no window where `/ready` returns `200` over an unconnected store.
- **Storage disconnected mid-flight**: if `disconnect()` has run (shutdown) or the connection dropped, `ping()` returns `False` → `/ready` `503`. Tested in the integration lane.
- **Cold models at steady state**: `embedder_warm: false` / `reranker_warm: false` is normal immediately after start and is **not** a readiness failure. `/ready` stays `200`. Only the informational fields reflect coldness.
- **`ping()` timeout**: `await db.list_tables()` wrapped in `asyncio.wait_for`; a timeout is treated as `False` (storage not ready), not an unhandled exception. The timeout default must be comfortably above normal LanceDB latency but well below typical probe intervals.
- **TTL cache staleness**: a cached `True` could lag a just-dropped connection by up to the TTL (~1s). Acceptable for a readiness signal; documented. The cache is per-process and not shared.
- **Failed collection**: a collection with indexing status `failed` keeps `/ready` at `200`/`ready: true` — the service can still serve healthy collections. It is surfaced only as the `collections_failed` count on authenticated `/status`, never on the unauth `/ready` body.
- **In-progress reindex**: `collections_indexing > 0` is informational; readiness stays `true`. Consistent with A1's reindex (other collections unaffected) and with serving partial corpora.
- **Empty / missing state file**: `IndexingStateStore.read()` returns `None` (no exception) → `collections_indexing`/`collections_failed` are `0`. Readiness is unaffected — the state store never gates `/ready`.
- **Corrupt / unreadable state file**: `IndexingStateStore.read()` swallows missing, corrupt, and unreadable files into an indistinguishable `None` — it never raises; it logs a WARNING and returns `None` (`progress.py:88-105`). B2 therefore cannot tell a corrupt state file from a fresh/empty one and surfaces **no** state-store-health field; either way readiness is unaffected, because the state store never gates `/ready`. Surfacing corruption is deferred (see Out of Scope).
- **`watcher_manager is None`** (the current reality): `watcher` report is `{running: false}`. No exception, no readiness impact. Note: the legacy per-collection `watching` flag (`= config.watch`) being `true` while `readiness.watcher.running` is `false` is the **expected** state until a future item wires a live watcher into the server — operators should not file it as a bug. The legacy `watching` flag and the new `readiness.watcher` report will be reconciled when the live watcher lands.
- **Reranker reachability**: the reranker is constructed inside `SearchPipeline` (`app.py:131-139`), not directly on `app.state`. B2 exposes its warmth via a `SearchPipeline` accessor rather than reaching into pipeline privates from the route.
- **`is_warm` keys off `_model`**: warmth is `_model is not None` on both `ModelEmbedder` and `ModelReranker` (symmetric), even though their model-NAME attributes differ (`ModelEmbedder.model_name` public vs `ModelReranker._model_name` private) — only `_model` matters for warmth, never the name attribute.
- **Job store consistency**: counting `pending`/`running` reads the in-memory `_jobs` dict (via an inline `JobStore.list()` filter, or the optional helper); counts are a point-in-time snapshot and may race with a concurrent transition — acceptable for a status/readiness report (no lock required for a count).
- **OpenAPI exemption**: `/ready` must be in `_EXEMPT_PATHS` so `_configure_openapi` (`app.py:67`) omits the `BearerAuth` annotation; otherwise the published contract would wrongly advertise auth on an unauthenticated endpoint.
- **Coverage gate**: the new route, `ping()`, `is_warm` accessors, and the job-count aggregation (inline filter or optional helper) are net-new lines; the named unit + contract tests must keep `store.py`, `embedder.py`, `reranker.py`, the route module, and `jobs/store.py` above the 85% gate without relying on integration-marker tests.

## Open Questions
- Should the storage-ping TTL and timeout be configurable (`[health]` config block), or fixed constants in `constants.py` for B2? Lean fixed for the minimum slice; promote to config only when a deployment needs it.
- ~~Should `/ready`'s `checks` enumerate every gating subsystem by name, or collapse to a single `ready` bool?~~ **Resolved:** with storage as the sole gate, `checks` collapses to the single `storage` check (`{storage: "ok"|"fail"}`), reported alongside the overall `ready` bool. The name `storage` leaks no topology; informational subsystems stay off the unauth body.
- ~~Should a `failed` collection set `degraded: true` on `/ready`?~~ **Resolved:** no. `degraded` is dropped from the unauth `/ready` body entirely — a `failed` collection is surfaced only as the `collections_failed` count on authenticated `/status`. The unauth `/ready` body stays `{ready, checks: {storage}}` and is never flipped by a failed collection.
- Should `archon-search status` (CLI) gain an HTTP `--probe`/`--ready` flag that hits `/ready` and exits non-zero when not ready? The ops doc flags that `archon-search status` is OS-supervisor-only today; a scriptable readiness probe is attractive but is proposed as a Future Iteration to keep B2's surface tight.
- Should `live` semantics be surfaced as an explicit `live: true` field on `/health`, or is the existing `status: "running"` sufficient? Lean: leave `/health` byte-for-byte unchanged to protect the install-poll contract.

## Recommendation
This is the right Phase-B foundation to build before load grows: it converts "the process answers TCP" into a real, status-code-driven readiness signal that supervisors and load balancers can act on, without forcing the API key into probe paths and without breaking the lazy-load startup contract. The hardest design call — and the one that must not be compromised — is the **gating-vs-informational split**: readiness gates only on the cheap, must-be-true serving dependency (storage connectivity) and merely *reports* the rest (model warmth, watcher state, index-build state, queue depth) — search reads LanceDB, not the indexing-state file, so a corrupt state file must not take the service out of rotation (and because `read()` cannot today distinguish corrupt from empty, B2 deliberately surfaces no state-store-health field — deferred), and gating on a cold model would either lie about readiness or trigger a multi-second model load inside a health check. The second subtlety is the **honest watcher story** — `WatcherManager` is unwired in the running server, so B2 ships the readiness *hook* (`app.state.watcher_manager`) and reports `running: false` rather than feigning observation. The three guardrails that keep B2 from rotting: the **side-effect-free `is_warm` test** (a probe must never warm a model), the **no-info-leak negative test** on the unauthenticated `/ready` body, and the **`503`-is-a-state-not-an-error** body-shape test that keeps readiness semantics distinct from A3's pipeline-failure envelope.
