## Bug: `top_k_retrieve` and `top_k_return` are independent `[database]` keys (the "echoed in `/status`" claim is UNDOCUMENTED)

**ID**: S489-explain_pool_is_bounded_by_top_k_retrieve
**Scenario**: S489
**Severity**: medium
**Version**: archon-search, version 26.8.1848

### What happened
assert (5 + 20) <= 12

### What should happen
- **The bullet's claim — "separate values echoed in `/status`" — is UNDOCUMENTED.** The documented `/status` inventory (`OperatorGuide/20_monitoring_and_alerts.md:24`) lists service fields `running`, `pid`, `version`, the per-collection fields, and the `readiness` / `model_validation` / `backup` / `maintenance` / `telemetry` / `graph` sub-objects — no `top_k_retrieve` or `top_k_return` echo. Neither key occurs anywhere in that document. No assertion is invented for the echo.
- **Documented, exercisable assertions (what IS specified):**
  - `POST /search` returns **HTTP 200** with **exactly 3** results — "the pipeline returns `[database].top_k_return` results" (`60_searching.md:12`), and `top_k_return = 3` here. Three is not the default (`5`, `30_configuration.md:63`), so the TOML value demonstrably drives the count.
  - `POST /explain` returns **HTTP 200** and `len(results) + len(near_misses) <= 12` — `top_k_retrieve` is the "first-stage candidate pool size" (`30_configuration.md:62`) and near-misses come from that same pool without widening retrieval (`80_explain_and_debugging.md:166`). Twelve is not the default (`15`, `:62`), and 25 candidates are available, so this bound is only satisfiable if the independently-set `top_k_retrieve` took effect.
  - `GET /status` returns **HTTP 200** and carries the documented service fields `running`, `pid`, `version` (`OperatorGuide/20_monitoring_and_alerts.md:24`) — the nearest documented `/status` observable that stands in for the bullet's invented echo.
- **Doc-gap reopening gate:** neither `top_k_retrieve` nor `top_k_return` appears in `OperatorGuide/20_monitoring_and_alerts.md`, the document that defines the `/status` contract. If either ever does, the paired test flips **red** so S489 is re-implemented against the then-documented `/status` field. No bug is filed *for the missing echo* — a missing doc is not an app defect.
- **Note (observed 2026-08-06, archon-search 26.8.1848):** the `top_k_retrieve` bound above is **not** met — `/explain` returns 5 results + 20 near-misses (the full 25-document corpus) with `top_k_retrieve = 12`, and identically with a control instance at `top_k_retrieve = 2`, while `top_k_return` demonstrably drives the `/search` count. That is a documented-behavior deviation and is filed as a bug; the assertion stays as the documentation specifies it.

### Steps to reproduce
1. Start an isolated instance, set `top_k_retrieve = 12` and `top_k_return = 3` in its `[database]` block, restart it, and ingest 25 single-chunk documents that all match one query term.
2. `POST <base>/search {"collection": "<seeded>", "query": "<shared term>"}` with `Authorization: Bearer <key>`.
3. `POST <base>/explain {"collection": "<seeded>", "query": "<shared term>", "rerank": true}` with the same header.
4. `GET <base>/status` with the same header.
5. `grep -n "top_k_retrieve\|top_k_return" docs/OperatorGuide/20_monitoring_and_alerts.md`.
