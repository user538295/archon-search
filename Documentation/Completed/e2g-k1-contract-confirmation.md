### §3b Risks flagged for downstream tasks (C1-I-E)

**`extraction_method` field vocabulary overload risk (BE-1):** `archon_search/graph_types.py:170-173` (the `GraphEdge.extraction_method` field, `str | None = None`, at line 170) currently documents its vocabulary via docstring example values only: `"How the edge was extracted (e.g. \"ner\", \"embedding\")."` (lines 171-173) — i.e. a technique-scoped vocabulary (which extraction mechanism produced the edge). BE-1 (`e2g-code-defref-graph-team-plan.md:369`) proposes documenting two additional values on this same field: `"extracted"`/`"inferred"` — a confidence/provenance-scoped vocabulary (whether the edge was directly observed in code vs. best-guess inferred), used for Q11's extracted-over-inferred precedence rule. Both vocabularies are free strings on the same untyped `str | None` field with no discriminator between them — nothing in the type or schema prevents a future writer from setting `extraction_method="ner"` on a def/ref edge (mixing an E2f-style technique tag onto an E2g-style provenance tag) or vice versa. This is a real overload risk worth flagging to whoever implements BE-1/BE-2/BE-4: consider documenting both vocabularies as clearly distinct in the docstring (which values come from which subsystem) or, more robustly, using a separate field/enum for provenance vs. technique. Not a blocker for K1 — flagged as a design risk for the implementing tasks to address.
