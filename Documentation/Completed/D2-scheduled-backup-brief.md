# Feature Brief: D2 — Scheduled Backup & Export/Import Completion

## Problem

The export/import machinery built in D1-D2 is silently broken in production: a no-op dispatch closure causes every export and import job to immediately fail with `workers_not_deployed`. Operators also have no automated way to back up collections — they must trigger exports manually and manage archive rotation themselves.

## Goal

A collection can be exported to a portable archive, imported on any compatible instance, and automatically backed up on a configurable interval — with operators confident that data is recoverable and disk usage is bounded.

## Users & Context

DevOps engineers and developers running archon-search as a persistent service who need disaster recovery, migration between instances, or periodic snapshots of collection data. They interact via the REST API, CLI, or MCP tools and treat archon-search as infrastructure.

## Core Flow

1. **Export** — User runs `archon-search export COLLECTION [--output-dir PATH] [--wait]` or calls `POST /collections/{name}/export` → job created as QUEUED → scheduler promotes it (dispatch closure now real) → export worker streams chunks to `.tar.gz` (with `lancedb_version` in manifest) → job completes with archive path.
2. **Import** — User runs `archon-search import COLLECTION PATH [--wait]` → job created as QUEUED → scheduler promotes it → import worker validates archive, ingests chunks with checkpointing → job completes.
3. **Resume** — If export or import fails, `POST /jobs/{job_id}/resume` re-queues it → worker picks up from last checkpoint automatically.
4. **Scheduled backup** — Operator sets `[backup] interval_hours = 24, keep = 7` in `archon-search.toml` → in-process `BackupLoop` wakes on interval → enqueues an `ExportJob` (flagged as `source = "backup"`) for each collection not in `exclude` list → backup jobs sort behind manual jobs in the FIFO queue → after each successful backup, rotation deletes archives beyond `keep` count for that collection.
5. **Immediate backup** — Operator runs `archon-search backup --now` → calls `POST /backup/trigger` → enqueues backup ExportJobs for all non-excluded collections → prints job IDs (non-blocking by default, `--wait` polls).

## In Scope

- Fix dispatch closure in `archon_search/server/app.py` — replace no-op with real `_export_task` / `_import_task` wiring. The dispatch closure must be `async`-compatible: it wraps `_export_task(job, job_store, search_store, config)` or `_import_task(job, job_store, search_store, pipeline, embedder_cache, config)` in `asyncio.create_task()`, then calls `scheduler.register_task(task)`. The dispatch closure is built inside the FastAPI `lifespan` handler (not in `run_server()`), where `app.state.search_store`, `app.state.pipeline`, `app.state.embedder_cache`, `app.state.job_store`, and `config` are all available. The closure must be set on the scheduler after lifespan startup — either by making `JobScheduler.dispatch_fn` a mutable attribute that can be assigned post-construction, or by passing a late-binding wrapper that reads from `app.state` at call time. The planning phase must choose between these two patterns and specify the scheduler constructor change if needed.
- `[backup]` config section: `interval_hours` (int, 0 = disabled), `keep` (int, 0 = keep all), `exclude` (list of collection patterns; each pattern is either `{namespace}/{collection}` for an exact namespace-scoped match, or a bare `{collection}` that matches across all namespaces), `output_dir` (path, defaults to `get_data_dir() / "backups"`).
- In-process `BackupLoop` background task: runs two independent loops (trigger loop and completion loop — see Key Decisions); calls `await search_store.list_collections()` on each trigger tick to enumerate eligible collections; groups results by namespace; tracks last-backup time in a state file (see below).
- **BackupLoop state file** at `get_data_dir() / '.backup-state.json'`: JSON object mapping `{namespace}/{collection} → ISO-8601 last_backup_at timestamp`. For example: `{"default/docs": "2026-06-13T08:01:23Z", "tenants/docs": "2026-06-13T09:00:00Z"}`. This prevents key collisions when two namespaces share a collection name. Read on startup to determine when the next backup is due. Written atomically (write to `.tmp` then `os.replace`) after each successful tick.
- **BackupLoop lifecycle**: BackupLoop is instantiated inside the FastAPI `lifespan` handler (same as `JobScheduler`), where both `app.state.search_store` and `app.state.job_store` are accessible. BackupLoop's `run()` method uses `asyncio.gather(self._trigger_loop(), self._completion_loop())` so that cancellation of the parent task propagates to both loops cleanly. Only ONE task (the `BackupLoop.run()` task) is added to `app.state._background_tasks`. It runs two independent loops: (1) a **trigger loop** that wakes every `interval_hours` to enumerate eligible collections per namespace and enqueue new backup jobs, and (2) a **completion loop** that wakes every 60 seconds to poll `_in_flight` jobs for terminal status and trigger rotation when a job reaches `DONE`. When `interval_hours = 0`, the trigger loop exits after a single startup check (no periodic ticks); the completion loop continues draining any `_in_flight` jobs from a prior session.
- **BackupLoop exposure**: BackupLoop is stored on `app.state.backup_loop` so the `POST /backup/trigger` route handler can use two methods:
  - `is_collection_in_flight(namespace: str, collection: str) -> bool` — pre-check before enqueuing; checks `_in_flight` dict and returns `True` if any in-flight job matches the given namespace and collection.
  - `track(job_id: str, namespace: str, collection: str) -> None` — post-enqueue registration; adds the new job to `_in_flight` so BackupLoop's deduplication check covers it immediately. After `job_store.create_export()` returns, the route handler calls `app.state.backup_loop.track(job_id, namespace, collection)` to register the manually-triggered job. This ensures BackupLoop's scheduled tick cannot enqueue a duplicate while the manually-triggered job is RUNNING (state not visible to `list_queued_bulk()`).
- **BackupLoop completion tracking**: BackupLoop maintains an internal `_in_flight: dict[job_id, tuple[namespace, collection]]` (or equivalently `dict[job_id, str]` where the value is `"{namespace}/{collection}"`) of in-flight backup jobs it launched. The completion loop (waking every 60 seconds) polls `JobStore` for terminal status (`DONE`/`FAILED`/`CANCELLED`). The deduplication match compares both namespace AND collection — bare collection name alone is insufficient since `default/docs` and `tenants/docs` are distinct collections sharing the name `"docs"`. When a job reaches `DONE`, rotation is triggered for that collection. This ensures rotation fires within ~60 seconds of a backup completing, independent of `interval_hours`. This avoids requiring a scheduler completion callback and keeps BackupLoop self-contained.
- **BackupLoop namespace pass-through**: For each eligible collection, BackupLoop passes `CollectionInfo.namespace` to `job_store.create_export()` explicitly, so backup jobs are created in the correct namespace. Failing to pass namespace would default all jobs to `DEFAULT_NAMESPACE` and produce empty archives for non-default-namespace collections.
- `job_store.create_export()` and `job_store.create_import()` gain a `source: Literal['user', 'backup'] = 'user'` parameter. BackupLoop passes `source='backup'` when enqueuing. All existing callers (routes, CLI) default to `source='user'` without code changes.
- Priority field on bulk jobs: `source: Literal["user", "backup"] = "user"` added to **both** `ExportJob` and `ImportJob` so the priority sort works uniformly across all bulk job types.
- `list_queued_bulk()` sort order changes to `(source_priority, created_at)` where `source="user"` sorts before `source="backup"`. This is a `JobStore` API contract change.
- `source` field added to `job_to_dict()` and `JobResponse` so operators can distinguish backup-initiated jobs in `GET /jobs` output. `job_to_dict()` is refactored to serialize subclass-specific fields: `source` (nullable, `null` for `IngestJob`/`ReindexJob`/`DeleteJob`), `collection` (nullable), `output_path` (nullable, for `ExportJob`), `archive_path` (nullable, for `ImportJob`). These fields are added to `JobResponse` as optional nullable fields. These are additive fields (new optional nullable values). A `BREAKING.md` entry is required for both the `JobResponse` field additions and the `StatusResponse` `backup` field addition. Note: this `job_to_dict()` refactor also fixes a pre-existing D1-D2 bug where `collection`, `output_path`, and `archive_path` were silently omitted from export/import job API responses.
- `GET /jobs` gains an optional `source` query filter (`user` | `backup`).
- Backup rotation: after each backup ExportJob completes (detected by BackupLoop polling), delete the oldest archives in `{output_dir}/{namespace}/` for that collection beyond `keep` count. Rotation matches only `{collection}.backup.*.tar.gz` within `{output_dir}/{namespace}/`. Rotation logs every deleted archive path at INFO level (audit trail).
- Backup archive naming: backup-initiated archives are placed in `{output_dir}/{namespace}/` and named `{collection}.backup.{timestamp}.tar.gz`; manual export archives are named `{collection}.{timestamp}.tar.gz` in `output_dir`. The per-namespace subdirectory ensures `default/docs` archives live in `output_dir/default/` and `tenants/docs` archives in `output_dir/tenants/`, preventing filename collisions when two namespaces share a collection name. The literal `.backup.` substring acts as an unambiguous separator — collection names use alphanumeric + hyphens/underscores only, so this cannot collide even if the collection name contains the word "backup". Rotation only deletes files matching `{collection}.backup.*.tar.gz` within `{output_dir}/{namespace}/`, never manual exports.
- `POST /backup/trigger` REST endpoint: enqueues backup `ExportJob`s for all non-excluded collections in the caller's namespace (using `request.state.namespace`). Returns 202 with a `BackupTriggerResponse` Pydantic model (defined in `schemas.py`) with fields `queued: list[str]` (job IDs) and `skipped: list[SkippedItem]` where `SkippedItem` is a Pydantic model with `collection: str` and `reason: str`, defined in `schemas.py` alongside `BackupTriggerResponse`. This is consistent with the project's typed API surface. The `archon-search backup --now` CLI calls this endpoint, consistent with the existing export/import CLI pattern. After creating each job via `job_store.create_export()`, the route handler calls `app.state.backup_loop.track(job_id, namespace, collection)` to add it to BackupLoop's `_in_flight` dict. This ensures BackupLoop's own deduplication check blocks a scheduled tick from creating a duplicate while the manually-triggered job is RUNNING.
- `GET /status` response extended to include a `backup` object. The `backup` object contains both global fields (from the single BackupLoop that covers all namespaces) and namespace-filtered fields:
  - **Global** (same value for all callers): `enabled`, `interval_hours`, `last_tick_at`, `next_run_at`, `collections_excluded`
  - **Namespace-filtered** (scoped to caller's namespace): `collection_status`

  ```
  {
    enabled: bool,
    interval_hours: int,
    last_tick_at: str|null,  # time BackupLoop last ATTEMPTED a trigger tick (success or failure)
    next_run_at: str|null,   # last_tick_at + interval_hours; if in the past, the next tick is overdue
    collections_excluded: list[str],
    collection_status: list[{collection: str, last_backup_at: str|null, archive_count: int}]
  }
  ```
  `collection_status` shows all collections in the caller's namespace — both those that appear in `.backup-state.json` (with their timestamps) and those that don't (with `last_backup_at: null`). This requires merging the live collection list from `search_store.list_collections()` with the state file. `archive_count` is 0 if `{output_dir}/{namespace}/` does not exist yet. The `collection_status` items are filtered by iterating `.backup-state.json` keys and selecting those where the prefix before the first `/` matches the caller's namespace; the collection name for display is the substring after the first `/`. BackupLoop updates `last_tick_at` on every tick attempt (success OR failure). `next_run_at` is computed as `last_tick_at + interval_hours`; if the result is in the past (after a slow or failed tick), it shows the originally-scheduled time, which is correct — it means the next attempt is overdue.
- `archon-search backup status` CLI subcommand: prints backup enabled/disabled, interval, next scheduled run, last run time per collection (from `.backup-state.json`), and count of archives on disk. Output is human-readable text by default; `--json` flag emits a JSON object matching the `GET /status` backup object schema. This allows scripted monitoring (e.g., Nagios check, Datadog custom check) to parse the output reliably. When backups are disabled (`interval_hours = 0`), prints `Backup: disabled`. When no backups have ever run, `last_backup_at` shows `never` (text) or `null` (JSON). The `backup status` command reads `.backup-state.json` and counts archives directly from the filesystem — it does NOT require the server to be running. When the server is running, it additionally shows `last_tick_at` and `next_run_at` by calling `GET /status`; if the server is unreachable, these fields show as unavailable but the collection-level timestamps and archive counts are still displayed.
- Write `lancedb_version` to export manifest at export time via `importlib.metadata.version('lancedb')`. If `PackageNotFoundError` is raised, the field is written as `null` and a WARNING is logged. No enforcement on import — forensic trace only.
- `archon-search backup --now` CLI command.
- `archon-search.toml.example` updated with `[backup]` section.
- Documentation updated: CLAUDE.md, API reference, architecture docs.

## Out of Scope

- External scheduling (systemd timer, launchd) — in-process handles v1; OS-level wiring deferred.
- Per-collection backup config overrides — global + exclude list is sufficient for v1.
- LanceDB version compatibility enforcement on import — version is written to manifest for forensics only.
- Remote backup destinations (S3, GCS, etc.) — local filesystem only in v1.
- Backup integrity verification (re-open archive, validate doc count) — deferred.
- Disk space pre-flight check before backup export — deferred to v2; operators should monitor disk usage independently.
- Dedicated `max_concurrent_backup` setting — deferred to Future Iterations.

## Key Decisions

- **In-process backup loop, not external cron**: fits the existing daemon pattern (watcher, scheduler); missed backups while the server is down are acceptable for v1.
- **Manual jobs have higher priority than backup jobs**: prevents a scheduled backup from blocking an interactive import. Implemented via `source` field on both `ExportJob` and `ImportJob`, not a separate queue.
- **Keep N most recent archives per collection**: simpler and more predictable disk usage than time-based retention.
- **`keep = 0` means never rotate — keep all archives**: intentionally different from `interval_hours = 0` (which disables the backup loop). The config loader emits a WARNING if both `interval_hours > 0` and `keep = 0` (backups enabled but rotation off) to prevent accidental unbounded disk growth.
- **Backup vs manual archive naming**: backup-initiated archives go into `{output_dir}/{namespace}/` and are named `{collection}.backup.{timestamp}.tar.gz`; manual export archives remain in `output_dir` named `{collection}.{timestamp}.tar.gz`. The per-namespace subdirectory is the primary collision guard — `default/docs` archives live in `output_dir/default/` and `tenants/docs` archives in `output_dir/tenants/`. The literal `.backup.` substring is a secondary separator distinguishing backup archives from manual exports within the same directory. Collection names use alphanumeric + hyphens/underscores only, so this pattern cannot collide even if a collection name contains the word "backup" (e.g., `logs-backup`). Rotation scans only `{output_dir}/{namespace}/{collection}.backup.*.tar.gz` and never touches manual exports.
- **Global backup config with exclusion list**: avoids per-collection TOML sections, which are new configuration territory.
- **LanceDB version in manifest, no import-time check**: LanceDB's on-disk format has been stable; a forensic trace gives operators useful debug info at near-zero implementation cost. Acquired via `importlib.metadata.version('lancedb')` in `_build_manifest()`; written as `null` on `PackageNotFoundError`.
- **Dispatch fix is part of this brief**: it is a defect, but scoping it here keeps D2 fully self-contained rather than shipping a one-line fix as a standalone commit without a surrounding feature.
- **Dispatch closure construction order**: the dispatch closure is built inside the FastAPI `lifespan` handler (not in `run_server()`), where `app.state.search_store`, `app.state.pipeline`, `app.state.embedder_cache`, `app.state.job_store`, and `config` are all available. The planning phase must choose between making `JobScheduler.dispatch_fn` a mutable attribute assigned post-construction, or passing a late-binding wrapper that reads from `app.state` at call time.
- **BackupLoop deduplication uses a two-part check**: (1) the BackupLoop's internal `_in_flight: dict[job_id, tuple[namespace, collection]]` (for jobs it launched in the current server session), and (2) `JobStore.list_queued_bulk()` filtered for `source="backup"`, `namespace`, and `collection` match (for jobs that survived a restart). The deduplication match compares both namespace AND collection — bare collection name is insufficient because `default/docs` and `tenants/docs` share the name `"docs"`. Both checks are synchronous (no awaits between check and enqueue), ensuring atomicity within the asyncio event loop.
- **`POST /backup/trigger` deduplication**: the route handler checks `app.state.backup_loop.is_collection_in_flight(ns, col)` (covers RUNNING jobs in the current session) AND `JobStore.list_queued_bulk()` filtered by `source='backup'`, `namespace`, and `collection` (covers QUEUED jobs). Both checks are needed since `_in_flight` is in-memory (lost on restart) and `list_queued_bulk()` only covers QUEUED, not RUNNING.
- **Backward compatibility for `source` field**: When loading persisted jobs from `archon-search-jobs.json`, `_load()` must call `item.setdefault('source', 'user')` before constructing `ExportJob`/`ImportJob` instances, so that jobs persisted before D2 (which have no `source` key) are treated as user-sourced. This follows the existing pattern of `item.setdefault('progress', None)` already in `_load()`.
- **`output_dir` validation uses the resolved directory itself**: `validate_export_path(output_dir, allowed_base_dirs=[get_data_dir(), config.backup.output_dir])` — the configured directory is added to the allowlist directly, not its parent. Using `.parent` would be too permissive (e.g., `output_dir = /tmp/backups` would allow any path under `/tmp`). This allows operators to configure `/mnt/nfs/backups` without `validate_export_path()` rejecting it. Note: when `config.backup.output_dir` is in its own allowlist, the allowlist check is tautological — any absolute path passes. The dotdot and absolute-path checks in `validate_export_path` still apply (protecting against relative or traversal paths). The allowlist is a defense against programmatic path injection, not against operator misconfiguration of `output_dir`. This is accepted for v1.
- **BackupLoop construction order**: BackupLoop is instantiated inside the FastAPI `lifespan` handler (same as `JobScheduler`), where both `app.state.search_store` and `app.state.job_store` are accessible. It is not created at `run_server()` startup — `SearchStore` is created inside `create_app()`, not `run_server()`.
- **BackupLoop two-loop design**: BackupLoop runs two independent loops: (1) a **trigger loop** that wakes every `interval_hours` to enqueue new backup jobs, and (2) a **completion loop** that wakes every 60 seconds to poll `_in_flight` jobs for terminal status (`DONE`/`FAILED`/`CANCELLED`) and trigger rotation when a job reaches `DONE`. This ensures rotation fires within ~60 seconds of a backup completing, independent of `interval_hours`.
- **Backup scheduling model is global tick, not per-collection cadence**: The trigger loop wakes every `interval_hours` and enqueues ALL eligible collections on each tick. Per-collection `last_backup_at` timestamps in the state file are used ONLY for: (1) the overdue-backup check on startup (if any collection is overdue, fire an immediate catch-up tick), and (2) the `collection_status` display in `GET /status`. There is no per-collection scheduling — all collections back up together or not at all on each tick. This means `last_backup_at` does not affect when a backup fires; it affects only startup catch-up and status display.
- **Namespace-aware backup**: BackupLoop calls `search_store.list_collections()` and groups results by namespace. Each namespace gets its own backup cadence using the same global `[backup]` config. The `exclude` list matches `{namespace}/{collection}` patterns (or bare `{collection}` which matches across all namespaces). `POST /backup/trigger` operates within the caller's namespace (using `request.state.namespace`), enqueuing only collections in that namespace. The `GET /status` backup object is namespace-scoped to the caller's namespace: `collection_status` shows only collections in that namespace.
- **`archon-search backup` Click group**: `archon-search backup` is a Click group with `invoke_without_command=True`. The `--now` flag triggers an immediate backup when invoked without a subcommand. `status` is a subcommand. When invoked without `--now` and without a subcommand (bare `archon-search backup`), the group prints its help text — no action is taken.

## Edge Cases & Constraints

- **Backup fires while an import is running**: backup job queues normally; scheduler promotes it only when a slot is free and no user-sourced jobs are waiting.
- **Server restarts mid-backup export**: job transitions to FAILED on startup; `POST /jobs/{job_id}/resume` re-queues it; worker resumes from checkpoint.
- **Exclude list contains unknown collection**: silently skipped — collection may not exist yet at config load time.
- **`interval_hours = 0`**: BackupLoop is instantiated but exits after a single startup check; no ExportJobs are enqueued automatically. The `--now` command and `POST /backup/trigger` still work.
- **`keep = 0`**: rotation is disabled; archives accumulate indefinitely. Config loader emits WARNING when combined with `interval_hours > 0`.
- **`output_dir` outside allowed paths**: must pass `validate_export_path(output_dir, allowed_base_dirs=[get_data_dir(), config.backup.output_dir])`; config load warns and falls back to default if validation fails.
- **Dangerous `output_dir` values** (e.g., `/`, `/tmp`, `/var`): The `validate_export_path` allowlist check is tautological for `output_dir` (the directory is in its own allowlist), so any absolute path passes. The config loader should additionally reject `output_dir` values that are fewer than 3 path components deep (e.g., `/`, `/tmp`, `/backup`) with an ERROR and fall back to the default. This prevents rotation from scanning root-level directories.
- **`output_dir` does not exist**: BackupLoop creates it (`mkdir(parents=True, exist_ok=True)`) on first use, before writing the first archive.
- **All scheduler slots occupied when backup tick fires**: backup ExportJob queues normally; scheduler promotes it on the next available slot.
- **Two backup ticks fire before the first export completes**: BackupLoop deduplication (two-part check: `_in_flight: dict[job_id, tuple[namespace, collection]]` + `JobStore.list_queued_bulk()` filtered for `source="backup"`, `namespace`, and `collection`) prevents duplicate enqueues for the same namespace/collection pair. A bare collection name match is not sufficient — `default/docs` and `tenants/docs` must be treated as distinct.
- **Server restart after overdue backup**: BackupLoop reads `.backup-state.json` on startup. If `now - last_backup_at >= interval_hours`, the loop fires an immediate backup tick before entering the periodic sleep. A server that was down for 3 days with `interval_hours = 24` will trigger a backup within seconds of startup.
- **Disk full during backup export**: the export worker raises `OSError`; the job transitions to FAILED. BackupLoop does not pre-check available disk space (out of scope for v1). Operators should monitor disk usage independently.
- **Backup job FAILED**: BackupLoop's completion loop detects the FAILED status, logs at ERROR level (`Backup failed for collection '{collection}': {error}`), removes the job from `_in_flight`, and updates `.backup-state.json` to record the failure (does NOT update `last_backup_at` — the previous successful backup timestamp is preserved). The collection will be re-attempted on the next trigger tick.
- **Backup job CANCELLED**: BackupLoop's completion loop detects `CANCELLED` status and removes the job from `_in_flight` without updating `.backup-state.json`. The collection will be re-attempted on the next trigger tick. Failure to handle `CANCELLED` would cause `_in_flight` to accumulate stale entries, blocking future deduplication checks for that collection.
- **BackupLoop tick error** (e.g., `list_collections()` raises due to database disconnection): BackupLoop logs at ERROR level and skips the tick. No backup jobs are enqueued. The loop sleeps for `interval_hours` and retries on the next tick. Repeated failures do not stop the loop.
- **Orphaned `.export-*.jsonl.tmp` files from failed backup jobs**: BackupLoop does not clean these up — they are handled by the existing resume mechanism. Operators should periodically check `get_data_dir()` for orphaned tmp files and can safely delete them if the corresponding job is in FAILED state. This should be documented in the User Manual.
- **Large number of collections**: BackupLoop enqueues one ExportJob per eligible collection per tick. With `max_concurrent_bulk = 1` (default), 20 collections means 20 queued backup jobs that drain serially. Operators with many collections should increase `max_concurrent_bulk` or accept that a backup cycle takes `N × export_time`. A dedicated `max_concurrent_backup` setting is deferred to Future Iterations.
- **`archon-search backup --now` when some collections already have active backup jobs**: the `POST /backup/trigger` endpoint returns `{queued: [...], skipped: [{collection: 'X', reason: 'already_queued'}]}`. The CLI prints which collections were skipped.
- **Manual import job and backup export job both QUEUED**: scheduler promotes the manual import first (`source='user'` priority), then the backup export.
- **`archon-search backup --now` only covers the caller's namespace**: `POST /backup/trigger` uses `request.state.namespace` (the caller's namespace from their API key). The CLI command uses the default API key and therefore only triggers backups for the default namespace. Operators with multiple namespaces must call `POST /backup/trigger` once per namespace using the appropriate API key for each. The automatic `BackupLoop` covers all namespaces regardless.
- **Dispatch fix acceptance criteria**: after the fix, a `POST /collections/{name}/export` call must result in: job created as QUEUED → promoted to RUNNING within 5 seconds → archive written to `output_path` → job status transitions to DONE. An integration test must verify this end-to-end flow without mocking the dispatch closure.

## Recommendation

Build this now. The dispatch bug is a silent defect that makes D2 appear shipped when it does nothing — fixing it is non-negotiable and unlocks everything built in the last sprint. The scheduled backup is the right next layer: it reuses the existing job + scheduler infrastructure with minimal new surface (one config section, one background loop, one priority field). The hardest design decision is the priority field on `ExportJob` and `ImportJob` — get that right first, because it determines how `BackupLoop` enqueues and how the scheduler promotes. Don't compromise on the deduplication check (no duplicate backup jobs per collection) — without it, a slow export plus a missed tick will pile up QUEUED jobs indefinitely.
