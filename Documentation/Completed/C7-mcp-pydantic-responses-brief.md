# Feature Brief: C7 — MCP Responses Behind Pydantic Models

## Problem
MCP tools return raw `dataclasses.asdict()` payloads with no schema validation; when a domain dataclass field is added or removed, MCP clients silently absorb the shape change with no error.

## Goal
Every MCP tool return value passes through a Pydantic model before serialization — making future dataclass shape changes fail loudly instead of silently drifting the MCP contract. This catches both field removals (missing required field → `ValidationError`) and field additions (extra field rejected with `extra='forbid'`).

## Users & Context
Internal and third-party MCP clients consuming `archon-search` tools. The risk surfaces during development: a developer changes a domain dataclass, all REST tests pass (Pydantic-gated), and MCP tests pass too — because there are none at the schema boundary. The change ships and MCP clients break in production.

## Core Flow
1. Developer makes a change to a domain dataclass (e.g., renames a field in `SearchResult`)
2. FastAPI REST route fails at the `response_model` validation boundary → developer is forced to update the schema
3. MCP tool also calls `model_validate()` against its Pydantic schema → same failure, same fix required
4. Developer updates both schema files (or the shared one), adds a `BREAKING.md` entry if the MCP contract changed
5. All tests pass; shape change is explicit and tracked

## In Scope
- Replace all `asdict()` calls in `mcp.py` with Pydantic model construction (via `from_result()` classmethods for types with internal/transient fields, or `model_validate()` for flat types), then serialize with `.model_dump(mode='json')` (or direct Pydantic model return if the MCP framework supports it — see Key Decisions)
- Reuse existing REST schemas only where shapes are verified identical — see per-tool audit in Edge Cases
- Create `server/mcp_schemas.py` for tools whose shape diverges from REST (e.g. `list_collections` strips internal `CollectionMeta` fields)
- Update MCP tool function return type annotations from `dict[str, Any]` to the concrete Pydantic schema type
- All new Pydantic models in `mcp_schemas.py` use `model_config = ConfigDict(extra='forbid')` — catches both added and removed fields; internal fields are excluded via explicit `from_result()` classmethods or pre-filtering, not silently dropped
- Tests: one test per distinct return shape per MCP tool asserting the return value validates against its schema; one integration-level test per MCP tool verifying that when a required schema field is missing from the dataclass (simulated by passing a dict missing the field), the tool function returns `McpErrorResponse` with the correct error code; one test per schema verifying that `model_validate` raises `ValidationError` when given an unexpected extra field (e.g., `MySchema.model_validate({...valid fields..., 'surprise_field': 42})` raises) — this confirms `extra='forbid'` is active and would catch a silent change to `extra='ignore'`; one unit test per `from_result()` classmethod verifying correct field exclusion and mapping; one schema field-coverage test per MCP schema asserting `set(MySchema.model_fields.keys()) == {expected_field_set}` (validates schema shape without snapshot tooling — no new deps required, stable across Pydantic versions, catches field additions and removals in the schema itself)

## Out of Scope
- Changing the MCP protocol wire format or adding new fields to existing tools — this is schema enforcement, not schema expansion
- REST schema changes — REST is already Pydantic-gated; this task does not touch REST routes
- `BREAKING.md` entries for *newly added* schemas where no contract fields change. However: field stripping for tools that currently leak internal `CollectionMeta` fields IS a potentially breaking change — add `BREAKING.md` entries for all five tools where the response shape narrows relative to what clients currently receive: `get_collection_meta` and `update_collection` (currently return all `CollectionMeta` internal fields via `asdict(meta)`); `list_collections` (currently leaks `centroid_sum`, `mutations_since_recompute`, `needs_recompute`, `described_at_doc_count`, `needs_reindex`, `reindex_job_id`, and `namespace` in addition to the already-stripped `centroid` and `description_embedding`); `get_collections_meta` (same internal fields as `list_collections` currently leak); and `search_with_context` (context chunks currently include `start_offset`, `end_offset`, and `custom_score` — only `vector` is stripped today by `_chunk_to_context_dict`)
- Aligning MCP and REST shapes where they intentionally differ — the divergence is correct by design

## Key Decisions
- **Reuse REST schemas only where shapes are verified identical**: requires per-tool audit during planning; `search` diverges from `SearchResponse` (see Edge Cases), so a `McpSearchResponse` is needed; do not assume REST and MCP shapes match without verifying
- **`mcp_schemas.py` for divergent tools**: clean separation without polluting `schemas.py`; the divergence (e.g. stripped internal fields) is an explicit MCP contract choice, not a bug
- **`extra='forbid'` validation posture**: the goal is to fail loudly on both field additions *and* field removals; `extra='ignore'` would only catch removals (missing required fields) while silently allowing new internal fields to leak into the MCP contract — that contradicts the stated goal. Use `extra='forbid'` on all new MCP schemas. The `ExplainResponse` reference implementation (in `routes_explain.py`) already uses `extra='forbid'`; this task extends that posture to all tools
- **Exclude internal fields explicitly, not silently**: for types with transient or internal fields (e.g. `CollectionMeta`, `ChunkRecord`), prefer `from_result()` classmethods that declare exactly which fields belong to the public MCP contract. `model_validate(asdict(x))` is acceptable only for flat types with no transient or internal fields. `from_result()` makes inclusion explicit and grep-able
- **`from_result()` classmethods use Pattern A — direct constructor**: `cls(field1=obj.field1, field2=obj.field2, ...)` rather than filtered `asdict()`. This makes field inclusion grep-able, avoids `asdict()` pitfalls (datetime objects, transient fields), and `extra='forbid'` serves as a safety net for direct model construction from validated input dicts (e.g. deserialized from JSON). Do NOT use Pattern B (`model_validate({k: v for k, v in asdict(obj).items() if k in cls.model_fields})`) — it defeats the purpose of explicit field mapping
- **Shared schemas must live in `schemas.py` or `mcp_schemas.py`**: `mcp.py` must not add new imports from `routes_*.py`. The existing import of `ExplainResponse` (and its nested types `ExplainResult`, `ExplainNearMiss`, `RoutingExplain`) from `routes_explain.py` is accepted as-is in this task — moving these to `schemas.py` is a separate refactor that should be scoped independently. Before reusing any REST schema in MCP, verify it lives in `schemas.py` (or move it there)
- **CollectionMeta public contract**: the MCP-public fields are `name`, `doc_count`, `chunk_count`, `last_indexed`, `last_described`, `embedding_model` (mapped from `active_embedding_model`), `description`, `pending_embedding_model`. The internal fields excluded from ALL MCP responses are: `centroid`, `centroid_sum`, `description_embedding` (see exception below), `mutations_since_recompute`, `needs_recompute`, `described_at_doc_count`, `needs_reindex`, `reindex_job_id`, `namespace`. Note: `CollectionMeta` has no `created_at` or `acl` fields — do not add phantom fields to schemas. Three distinct schema projections are required: `CollectionListItemSchema` (for `list_collections` — excludes `description_embedding`), `CollectionDetailSchema` (for `get_collection_meta` and `update_collection` — also excludes `description_embedding` and all internal fields, which is a narrowing from today's `asdict()` output — BREAKING.md entry required for `centroid` removal from `get_collection_meta`), and `CollectionMetaMcpSchema` (for `get_collections_meta` — includes `description_embedding: list[float] | None = None` as conditionally-included field; also narrows from today by removing `centroid` — BREAKING.md entry required). All three exclude `centroid` — it is never part of the public MCP contract
- **Return Pydantic model objects from MCP tool functions**: annotation is `-> SomeSchema` (accurate), serialization is handled by the MCP framework; this is preferred over calling `.model_dump()` inside the function — **verify MCP framework supports Pydantic model returns before implementing** (check `mcp.py` tool registration decorator behavior); fall back to `.model_dump(mode='json')` + `-> dict[str, Any]` only if the framework requires it
- **`schema_validation_error` error code is in scope**: adding a `schema_validation_error` error code constant for `ValidationError` catch paths in each tool IS in scope — it adds a new error code, not a structural change to `McpErrorResponse`. Update the error-handling catch paths in each tool to use this code specifically for `ValidationError` (internal dataclass/schema drift), keeping `internal_error` for all other unexpected exceptions. `McpErrorResponse`'s structure (two fixed fields `error: str`, `code: str`) is otherwise out of scope for this task. The `schema_validation_error` string must be defined as a module-level constant in `mcp.py` (e.g., `_ERR_SCHEMA = 'schema_validation_error'`) alongside the existing error-code pattern in the file, so tests can import and assert the constant rather than matching a bare string literal

## Edge Cases & Constraints
- **MCP framework serialization**: if the framework does not natively serialize Pydantic models, each tool function must call `.model_dump(mode='json')` and return a plain dict; annotations revert to `-> dict[str, Any]` — document the choice in `mcp_schemas.py`; use `mode='json'` (not bare `.model_dump()`) to ensure `datetime` fields serialize to ISO 8601 strings
- **`search` diverges from `SearchResponse`**: `SearchResponse` (in `routes_search.py`) includes `embedding_model: str = ""` which the MCP `search` tool does not return. Reusing `SearchResponse` directly would silently inject `embedding_model: ""` into MCP responses — a contract expansion. A `McpSearchResponse` (or equivalent) is needed that omits `embedding_model`. Additionally, the `search` tool has two distinct return shapes: single-collection (no `excluded_collections` populated) and multi-collection fan-out (produces results across collections with `excluded_collections` populated). Both paths must be verified against `McpSearchResponse` in the test suite
- **`list_collections` field stripping**: currently strips only `centroid` and `description_embedding` inline. `CollectionMeta` also has `centroid_sum`, `mutations_since_recompute`, `needs_recompute`, `described_at_doc_count`, `needs_reindex`, `reindex_job_id`, and `namespace` — all internal fields. Use `CollectionListItemSchema` (see Key Decisions — CollectionMeta public contract) with `extra='forbid'` and a `from_result()` classmethod (Pattern A) that excludes ALL internal fields. The public-facing field list is declared explicitly in the schema, not derived from `asdict()` minus a pop list
- **`get_collections_meta` conditional `include_description_embedding`**: this tool has a parameter `include_description_embedding` that conditionally includes the description embedding vector. It must use `CollectionMetaMcpSchema` (same internal-field exclusion approach as the other CollectionMeta-returning tools). The schema must declare `description_embedding: list[float] | None = None` so the field appears in the schema even when normally excluded. All other internal fields (`centroid`, `centroid_sum`, `mutations_since_recompute`, `needs_recompute`, `described_at_doc_count`, `needs_reindex`, `reindex_job_id`, `namespace`) are always excluded regardless of the `include_description_embedding` flag
- **`get_collection_meta` and `update_collection` internal field leakage**: both currently return `asdict(meta)` for a full `CollectionMeta` including all internal fields. They must use `CollectionDetailSchema` (see Key Decisions — CollectionMeta public contract) — this narrows the current response shape, which is a potentially breaking change (document in `BREAKING.md`)
- **`update_collection`**: returns `asdict(meta)` where `meta` is a full `CollectionMeta` with all internal fields. Requires `CollectionDetailSchema` (same as `get_collection_meta`). The schema is constructed via `CollectionDetailSchema.from_result(meta)` using Pattern A
- **`datetime` fields in `CollectionMeta`**: `last_indexed: datetime | None` and `last_described: datetime | None` are raw `datetime` objects after `asdict()`. `model_dump(mode='json')` (not bare `.model_dump()`) must be used to get proper ISO 8601 serialization; schemas for `CollectionMeta`-derived tools must declare these as `datetime` fields and always call `model_dump(mode='json')` at the serialization boundary
- **`search_with_context` needs three nested schemas**: the actual structure is `list[{"result": SearchResult dict, "context_before": [ChunkRecord dict, ...], "context_after": [ChunkRecord dict, ...]}]`. `SearchResult` and `ChunkRecord` have different fields; `ChunkRecord` has `vector`, `start_offset`, `end_offset` (transient — not persisted to LanceDB), and `custom_score` that must not appear in MCP responses. Three schemas are required: `SearchWithContextResultSchema` (the wrapper), `SearchResultSchema` (the inner result), and `ContextChunkSchema` (`ChunkRecord` with `vector`, `start_offset`, `end_offset`, and `custom_score` excluded). All three schemas must have independent unit tests. In particular, `ContextChunkSchema` must be tested with a `ChunkRecord` that includes `vector`, `start_offset`, `end_offset`, and `custom_score` to verify they are excluded
- **`explain` partial precedent**: `explain` already calls `.model_dump(mode="json")` on `ExplainResponse` which uses `extra='forbid'`; treat this as the reference implementation pattern when auditing the other tools
- **`ingest_file` / `ingest_directory`**: no REST schema for `IngestResult`; new `IngestResultSchema` in `mcp_schemas.py`. `IngestResult` has `needs_recompute: bool` which is a pipeline-internal field (signals whether the collection centroid needs recomputing) and must not appear in the MCP response. `IngestResultSchema` must exclude it via a `from_result()` classmethod (Pattern A) that maps only `doc_id`, `chunks_created`, `status`, and `error`
- **`delete_document`**: returns `{"deleted": count}` — a plain dict hand-built in `mcp.py`, not `asdict()`-based. Add `DeleteDocumentSchema(deleted: int)` in `mcp_schemas.py` for consistency and to future-proof if the return shape expands. Construct via `DeleteDocumentSchema(deleted=count).model_dump(mode='json')`
- **`list_documents`**: no REST schema for `DocumentInfo`; new `DocumentInfoSchema` in `mcp_schemas.py`
- **`ValidationError` surfacing**: when `model_validate()` raises a `ValidationError` at the schema boundary (e.g. a required field was removed from a dataclass), the catch-all in each tool must return `McpErrorResponse(error=str(exc), code="schema_validation_error")`. This is distinct from `"internal_error"` (unexpected runtime failures) and `"validation_error"` (client input errors). The `schema_validation_error` code signals internal dataclass/schema drift — an issue the developer must fix. Adding this new code value is in scope (see Key Decisions). Integration-level tests must verify this: for each MCP tool, simulate a missing required field by patching the dataclass and assert the tool function returns `McpErrorResponse` with `code="schema_validation_error"` rather than swallowing the error silently or crashing the transport

## Open Questions
- Does the MCP framework used in `mcp.py` (verify decorator signature) accept Pydantic model return values natively, or does it require plain dicts? **This must be resolved during the planning phase by reading the `mcp` SDK source, not deferred to implementation.** Check the `mcp` package version in `uv.lock` and inspect `FastMCP.tool()` return value handling — the answer determines the annotation strategy for all 11 tools
- After per-tool audit: which tools can reuse REST schemas exactly as-is vs. which need MCP-specific models? (Confirmed divergence already: `search` needs `McpSearchResponse`; `CollectionMeta`-returning tools need three distinct schema projections — `CollectionListItemSchema`, `CollectionDetailSchema`, `CollectionMetaMcpSchema` — as decided in Key Decisions)

## Future Iterations
- Autogenerate MCP schema stubs from domain dataclasses to keep `mcp_schemas.py` maintenance minimal
- Expose MCP schema definitions as a discoverable endpoint (analogous to `GET /openapi.json`) for MCP client tooling
- Align MCP and REST shapes where divergence exists for historical rather than intentional reasons
- Convert `McpErrorResponse` from `TypedDict` to a Pydantic model for consistency

## Recommendation
This is the right task to do now — the cost is low, the risk of not doing it compounds with every future dataclass change, and A1 already shipped the last "acceptable" untyped MCP break. The task is more involved than it first appears: the per-tool audit reveals at least one confirmed REST/MCP shape divergence (`search` vs `SearchResponse.embedding_model`), `CollectionMeta` has multiple internal fields that currently leak through several tools, and `search_with_context` requires three distinct nested schemas with careful transient-field exclusion. The `extra='forbid'` posture is the right choice — it catches drift in both directions — but it requires explicit field lists for any type with internal or transient fields rather than relying on silent dropping. Do not skip the MCP framework Pydantic support check, the per-tool shape audit, or the `BREAKING.md` assessment for field-narrowing tools before starting implementation.
