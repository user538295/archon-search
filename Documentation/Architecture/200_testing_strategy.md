# Testing Strategy

Tests in `archon-search` are split across four pytest markers plus a default (unmarked) tier. The default tier runs on every push; the marked tiers are opt-in and target specific failure modes (live network, deterministic eval quality, performance, integration). This document is the canonical map. The retrieval-quality side of testing — fixtures, thresholds, baselines, waiver policy — is owned by `tests/eval/README.md`; this document only points at it.

## Principles

1. **TDD-first.** Per `CLAUDE.md` (Code Style): write tests first, start with happy paths, then edge cases. Maintain 85%+ coverage. Resolve all warnings.
2. **Default run includes every test except `live_benchmark`, `smoke`, `live_eval`, `docling`, `graph_real_artifact`, and `runtime_parity`.** `addopts` in `pyproject.toml` sets `-m "not live_benchmark and not smoke and not live_eval and not docling and not graph_real_artifact and not runtime_parity"` — these are the intentional marker exclusions. `live_benchmark` tests run the real PyTorch embedder and reranker (the default suite stubs `ModelEmbedder.encode` / `ModelReranker.predict`, see the test-infra bullet below) and need the cached model weights, so the default suite never collects them. `smoke` tests spawn a real `archon-search serve` subprocess and are excluded so the default suite never launches a live server. `live_eval` tests (`tests/eval/live/`) drive the full live-model eval with real PyTorch weights (`backend="live"`) and are excluded (via `norecursedirs` + the `-m` filter) so the default suite never loads real models or hangs on inference. `docling` tests invoke the real docling parser / RapidOCR (PDF & image OCR), which takes minutes per parse on macOS (Metal/RapidOCR); they are excluded so the default suite never hangs on OCR. `graph_real_artifact` tests load the real GLiNER prose-extraction checkpoint (a ~1.2 GB artifact — 1218 MB declared, `archon_search/install/extras.py` — whose steady-state process residency is ~2.9 GiB, measured in `tests/test_graph_ner_real_artifact_lane.py`); they are excluded so the default suite neither downloads it nor holds a torch model stack per worker. These run in dedicated CI steps or on demand instead. All other markers (`live`, `eval`, `benchmark`, `integration`) run on every `uv run pytest` and skip gracefully when the required infrastructure is absent (server-dependent benchmarks, `live` tests that gate on `ANTHROPIC_API_KEY` — which the autouse fixture in `tests/conftest.py` clears on every test, so these always skip on default runs even when the developer has the key exported in their shell; no clean shell-level workaround exists, see the `live` section below for how to run them), gated eval without `--thresholds-path`. Model weight downloads and the model forward passes are stubbed in `tests/conftest.py` (`_stub_model_backends`), and the chonkie tokenizer download is stubbed in `tests/_search_stubs.py`, before any test runs.
3. **Markers document intent, not exclusion — with six exceptions.** `live`, `eval`, `benchmark`, `integration` are registered markers used for explicit targeted runs (e.g. `uv run pytest -m integration`) but are NOT excluded from the default run. `live_benchmark`, `smoke`, `live_eval`, `docling`, `graph_real_artifact`, and `runtime_parity` are the six exceptions (see principle 2).
4. **Eval is the retrieval-quality gate, not the unit-test tier.** Retrieval, reranking, and routing changes are validated by the `eval` marker with committed thresholds in `tests/eval/thresholds.toml`. Latency in the harness is a regression guard, not a production indicator.
5. **Coverage gating is a single-run concept.** `--cov-fail-under=85` applies to the default single-run invocation. CI that runs multiple pytest invocations must accumulate coverage into a single dataset before applying the threshold — `.github/workflows/archon-search-pr.yml` does this by passing `--cov-append` to both the default and eval steps (writing into one `.coverage` file) and then running `coverage report --fail-under=85`. `coverage combine` is only needed when shards write parallel-mode files; the current PR workflow deliberately skips it. **Never bake `--no-cov` into `addopts`.**

## The pyramid

```mermaid
flowchart TB
  subgraph default[Default run — all markers included except live_benchmark, smoke, live_eval, docling, graph_real_artifact, and runtime_parity]
    U[Unit tests<br/>tests/**/test_*.py<br/>stubs from tests/conftest.py + tests/_search_stubs.py]
    I[integration<br/>real components<br/>local infra]
    E[eval<br/>tests/eval/<br/>deterministic backends]
    B[benchmark<br/>xdist_group serialised<br/>server tests auto-skip]
    L[live / live_eval<br/>autouse clears ANTHROPIC_API_KEY<br/>always skip on default runs]
  end
  LB[live_benchmark<br/>dedicated CI step<br/>real PyTorch models<br/>skips without model cache]
  RP[runtime_parity<br/>nightly / on demand<br/>real weights vs frozen fastembed outputs]
  SM[smoke<br/>real subprocess server<br/>CLI + REST assertions<br/>errors without model cache]
  default --> CI[CI: coverage gate ≥ 85%]
  LB --> CI2[CI: benchmark step<br/>p95/p90 gate]
  RP --> CI4[CI: runtime-parity workflow<br/>no coverage gate]
  SM --> CI3[CI: manual/pre-release step<br/>no coverage gate]
```

### Default tier (unit)

- Invocation: `uv run pytest`.
- No marker selector — all tests run.
- Parallelism: the default run uses `pytest-xdist` with `-n 8 --dist=loadgroup` (raised from 4 on 2026-07-20 — the default suite stubs the model backends, so each worker is ~0.3 GB, measured; `-n 8` is memory-trivial on the 14-core/48 GB machine, ~177 s vs ~239 s at `-n 4`). Never `-n auto` (=14) and never bump `-n` for the real-model lanes: `-n auto` on those model-loading paths, where each worker holds ~2 GB of torch and model weights, OOM-crashed the 48 GB machine on 2026-07-05. `bash scripts/test-fast.sh` runs the suite on a macOS RAM disk (the suite is I/O-bound on temp LanceDB writes) for a further ~24 s.
  - xdist groups: `--dist=loadgroup` distributes ungrouped tests individually across workers; tests sharing an `xdist_group` run on one worker. MCP test modules carry no group — a new MCP test needs none. The former `xdist_group("mcp")` (64 marks in 60 files) was removed on 2026-10-22 ([TEST-7](./530_technical_debt_refactoring_roadmap.md#test-guards)): it was added because some modules swapped `sys.modules["fastmcp"]` for a stub and reloaded `archon_search.server.mcp`, no test does that any more (the leak guard below fails the build on it), and those 60 files passed ungrouped under `-n 8 --dist=loadgroup`, in shuffled order and in a single `-n0` process.
  - FastMCP stub: a test that needs a tool-capturing FastMCP uses the `stubbed_fastmcp()` context manager, or `stub_mcp_tool()` to fetch one tool function (both in `tests/_fastmcp_stub.py`). Both `patch.object` `archon_search.server.mcp.FastMCP` with `StubFastMCP`, whose `tools` dict holds the registered tool functions, and restore it on exit. `StubFastMCP` also records the constructor keywords in `init_kwargs`. No test module keeps a local FastMCP stand-in class: the second test in `tests/test_no_leaked_fastmcp_stub.py` fails the build on any class outside `tests/_fastmcp_stub.py` that defines `custom_route` (TEST-6, resolved 2026-10-22).
  - Leak guard: the AST guard `tests/test_no_leaked_fastmcp_stub.py` fails the build when a test file adds, removes or patches the `sys.modules` entry of `fastmcp`, a `fastmcp.*` submodule or `archon_search.server.mcp`, assigns or patches a `FastMCP` attribute outside the sanctioned scoped forms, or reloads `archon_search.server.mcp`; see its module docstring for the exact patterns and accepted blind spots.
  - Install-lock isolation: `xdist_group("install")` is carried by 12 files: 9 via module-level `pytestmark`, 3 via per-test decorators (`tests/test_install_lock_per_worker_isolation.py`, `tests/integration/test_cli_e2e.py`, `tests/integration/test_wizard_e2e.py`). The install lock they exercise lives at `get_data_dir() / ".install.lock"` (`archon_search/install/lock.py`, `_install_lock_path`), and the autouse `_archon_isolated_data_dir` fixture (`tests/conftest.py`) points `ARCHON_SEARCH_DATA_DIR` at a per-worker `tmp_path_factory` directory, so these tests never touch `~/.archon-search/.install.lock` and workers cannot contend on one lock file; the group only keeps these tests sequential on a single worker (sharing that worker's data dir). It is not legacy in the TEST-7 sense: the install code also resolves the service unit from `Path.home()` (`archon_search/install/service_ops.py`, the launchd plist / systemd unit path), which the per-worker data dir does not relocate, so the group stays as a serialization backstop for that home-relative path.
  - Shared store: the `connected_store` fixture is session-scoped (one `SearchStore` per xdist worker); `col_name` mints a UUID-suffixed name to prevent cross-test collision.
- Test infra: `tests/conftest.py` calls `_search_stubs.install_stubs()` at module import time (thread-count env defaults and a fake `chonkie` chunker, so no tokenizer is downloaded). It also injects `ARCHON_SEARCH_API_KEY = "0" * 64` so `create_app()` always sees a known key. The PyTorch embedder and reranker are not replaced at import time: the autouse fixture `_stub_model_backends` patches `ModelEmbedder.encode` (zero vectors of the spec's dimension) and `ModelReranker.predict` (a uniform 0.5 score) for every test, so no torch, transformers or weights are touched. Construction is not stubbed: a model name outside the registry still raises `UnsupportedModelError`. A test of the real backends opts out with the `real_torch_backends` marker, applied as a module-level `pytestmark`; the real-weights lanes (`live_eval`, `live_benchmark`, `runtime_parity`) are opted out by their own marker. `tests/test_embedder.py`, `tests/test_reranker.py`, `tests/test_reranker_loading.py` and `tests/test_torch_runtime.py` carry `real_torch_backends` and run the real PyTorch code path on tiny synthetic models (random weights, a word-level tokenizer; `tests/_tiny_encoder.py`), so they need neither weights nor network. Import-boundary tests (e.g. `test_importing_the_embedder_module_does_not_import_the_ml_stack`) spawn a `sys.executable` child, because only a fresh interpreter can prove that `torch`, `transformers` and `onnxruntime` stay unimported.
- Hermeticity: a default-tier test never installs packages. Tests that drive the wizard patch the extras installers (`_install_code_extra`, `_install_graph_extra`, `_install_multilingual_extra`, `_install_query_expansion_extras`, `_install_cuda_torch` — defined in `archon_search.install.extras`, patched where `archon_search.install.installer` imports them) — unpatched, they run `uv pip install --python sys.executable …` from the repo root, which re-resolves the running environment under the repo's `[tool.uv]` constraints. A child pytest runs as `sys.executable -m pytest`, never `uv run pytest`, which would re-sync `.venv` from `uv.lock` and test the locked versions instead of the parent's. The [unlocked-dependency lane](#unlocked-dependency-lane--bash-scriptstest-unlocked-depssh) fails when a run changes its venv.
- Serial escape hatch: `uv run pytest -n0` produces identical results in serial mode. Use `-n0 -x` for fail-fast isolation (xdist workers continue until their current test finishes) and `-n0 -s` for stdout passthrough (suppressed by xdist).
- Coverage combining: `pytest-cov` natively supports xdist. Workers write `.coverage.workerN` files which the main process combines before applying `--cov-fail-under=85`. This applies to single-invocation runs only; CI requires `-n0` to avoid interference with multi-step `--cov-append` accumulation.
- Adding a test: place it under `tests/`, do not add a marker — the default selector will pick it up. Pipeline tests live under `tests/pipeline/` (`test_pipeline_ingest.py`, `test_pipeline_search.py`, `test_pipeline_multi.py`); shared helpers are in `tests/pipeline/conftest.py`.

### `tests/integration/` — multi-component integration and e2e tests

`tests/integration/` contains tests that exercise multiple real components collaborating end-to-end: real `SearchPipeline`, real `SearchStore`, real LanceDB in `tmp_path`, `TestClient` against a real FastAPI app. These are distinct from unit tests in `tests/` which rely on the ML stubs in `tests/conftest.py`.

**Why a separate directory?** Unit tests stub the embedder and reranker backends (`ModelEmbedder.encode` / `ModelReranker.predict`, `tests/conftest.py`), which is correct for fast isolated testing but leaves the wiring between HTTP→middleware→route→pipeline→store→JSON serialization untested. `tests/integration/` fills that gap: each test exercises a real component chain without mocking the system under test.

All integration tests run in the default `uv run pytest` suite (no extra flags required) and are marked `integration` so they can also be run in isolation with `uv run pytest -m integration tests/integration/`.

**The six cross-cutting gap themes addressed** (from plan E1, which added 19 test files under `tests/integration/`):

1. **HTTP layer** (phases 1.1–1.6) — `SearchResultSchema.from_result()` wiring, filter SQL-escaping, multi-collection search, per-collection embedding model lifecycle, content-enrichment metadata in responses, HyDE/RAG-Fusion kill-switch and dependency-absent errors.
2. **Job dispatch & scheduler** (phases 2.1–2.2) — real `JobScheduler` dispatch through a full `create_app` lifespan: export/import round-trip, backup trigger with on-disk `.tar.gz` verification, user-before-backup job priority.
3. **MCP tool error paths** (phases 3.1–3.2) — validation errors, typed-exception mapping (`FanoutTimeoutError`, dependency-absent errors), and schema-contract tests (`McpSearchResultSchema`, `CollectionListItemSchema`, transient-field exclusion).
4. **CLI e2e** (phases 4.1–4.2) — real Click wiring: path safety enforcement, container serve path, `DATA_DIR` key-file routing, `configure_logging` stderr handler, wizard dry-run idempotency, TOML config output.
5. **Centroid and routing** (phases 5.1–5.2) — multi-batch accumulation correctness, reingest net-zero, delete centroid update, incremental vs. recomputed routing equivalence, hybrid routing end-to-end.
6. **Feature-specific cross-cutting** (phases 6.1–6.5) — FTS delete with no phantom hits, container env + disk I/O (`atomic_write_json`, `JobStore` JSON roundtrip, key-file mode 600), health/status/observability (`X-Request-Id`, stage timings, telemetry drain, no-raw-query invariant at HTTP wiring level), ACL/namespace isolation, collection lifecycle deletion.

**Shared helpers** live in `tests/integration/conftest.py` (never modify `tests/conftest.py` from this directory):

- `make_real_app(tmp_path, monkeypatch, *, backup_enabled=False, namespaces=None)` — returns `(TestClient, config, api_key)` backed by real `SearchStore` + `SearchPipeline` in `tmp_path`. Uses `monkeypatch.setenv` for both `ARCHON_SEARCH_DATA_DIR` and `ARCHON_SEARCH_API_KEY` to auto-revert env vars after each test.
- `ingest_doc(client, col, text, path, *, timeout_s=10)` — POST ingest + poll until job DONE.
- `ingest_file_via_path(client, col, path, *, timeout_s=10)` — POST ingest by filesystem path + poll until DONE.
- `search(client, col, query, **filters)` — POST `/search`, assert 200, return items.
- `make_real_pipeline(tmp_path, monkeypatch)` — async helper that creates a real connected `SearchStore` + `SearchPipeline` for direct async pipeline/store calls without going through `TestClient`.

### `integration` — `uv run pytest -m integration`

Integration tests exercise real components against local infrastructure. They run in the default suite. Use this marker when a test needs a real `SearchStore`, real LanceDB index on disk, or real OS service interactions — anything that the stubs in `conftest.py` deliberately replace.

- CI triggers: `archon-search-pr.yml` runs the integration suite on every PR, and `archon-search-release.yml` re-runs it on every tag push (both with a disk-backed `--basetemp=/var/tmp/archon-search-it` because the GitHub-hosted runner's `/tmp` is tmpfs and crash-injection tests skip on tmpfs). Both workflows pass `-m integration tests/` with `--cov-append`, so integration coverage rolls into the same `.coverage` file as the default + eval steps before the `--fail-under=85` gate runs.
- **D1/D2 export/import tests** are marked `integration`: `tests/test_routes_export.py`, `tests/test_jobs_list_resume.py`, `tests/test_mcp_export.py`, `tests/test_export_worker.py`, and `tests/test_import_worker.py`. These use a real `SearchStore` and LanceDB on disk. Unit-only tests (`tests/test_job_store_queued.py`, `tests/test_export_archive.py`, `tests/test_scheduler.py`, `tests/test_path_safety_export.py`, `tests/test_cli_export.py`) are unmarked and run in the default tier with stubs.

### `eval` — `uv run pytest -m eval --thresholds-path tests/eval/thresholds.toml tests/eval/`

The eval marker runs the offline retrieval-quality harness. It is the **authoritative regression gate** for the retrieval, reranking, and routing pipelines.

- **Backends are deterministic and label-blind** (`archon_search/eval/backends.py`). `EvalEmbedderBackend` produces SHA-256-based token-hash vectors; `EvalRerankerBackend` is a BM25-inspired lexical reranker. These are corpus-aware (scores vary with text) but never see labels, so the harness measures the *pipeline* against fixed data — not a hand-tuned model.
- **Fixtures** live under `tests/eval/`: `documents.jsonl`, `queries.jsonl`, `labels.jsonl`, `corpus/`, `routing/`, plus the committed `runtime.toml` used by the harness.
- **Thresholds** in `tests/eval/thresholds.toml` are *floors* (quality metrics) and *ceilings* (latency, when set). Floors must be `≤` the measured baseline in `tests/eval/baselines/baseline.json` — never above. Current floors: `recall_at_1 = 0.86`, `recall_at_3 = 0.94`, `recall_at_5 = 0.98`, `mrr = 1.0`, `ndcg_at_5 ≈ 0.976`, `ndcg_at_10 ≈ 0.979`, `routing_accuracy ≈ 0.926`. Latency ceilings are intentionally unset in v1 — latency is report-only until production-comparable backends exist.
- **Lowering a floor by more than `policy.max_floor_drop_without_waiver` (0.05)** requires a written waiver under `baselines/baseline.json::waiver_ids` and a rationale in `baselines/baseline.md`.
- **Read `tests/eval/README.md` before changing thresholds, fixtures, or baselines.** That document is the authoritative maintenance guide; this section only pins down its place in the strategy.

Unmarked eval units (the fast contract / fixture / metric tests under `tests/eval/`) run under the default selector — they are not gated by the marker.

**`[graph]`/`[code]` extras ARE installed in every CI job** (corrected 2026-09-06 — this section previously claimed the opposite, and the `graph_real_artifact` lane could not run at all if the old claim were true). The workflows run bare `uv sync --dev` with no `--extra` flags, but the `dev` dependency group itself depends on `archon-search[multilingual,hyde,rag_fusion,ollama,openai-provider,graph,code]` (`pyproject.toml:85`), so `gliner`, `leidenalg`, `igraph` and `tree_sitter` are all importable in CI. Every test file gating on `leidenalg`/`igraph` (community detection) or `tree_sitter` (AST chunking, def/ref extraction) uses a module-level `pytest.importorskip(...)` guard and skips gracefully — this includes `tests/eval/test_e2e_graph_eval_gate_v2.py` and `tests/eval/test_code_lane_eval_gate.py`. The practical consequence: the graph/code-lane eval gates (including BE-10's `code_defref_recall_at_5` floor) never execute in CI today — they run only in a developer venv with the extras synced (`uv sync --dev --extra graph --extra code`, never `--all-extras` — see `tests/eval/README.md`). No CI job installing these extras exists anywhere in this repository as of 2026-07-10; this is a known gap spanning the entire graph/code-lane feature surface (E2d–E2g), not something specific to any one gate.

**BE-10 code-lane collections deviate from the "deterministic, label-blind backend" invariant.** `code-chunking`/`code-defref` are the first eval collections ingested through a REAL feature pipeline (`archon_search.eval.runner._build_code_lane_ingest_pipeline` — real `ASTChunker`, real `DefRefExtractor`, real `GraphStore`) when `run_eval_suite` is called with `lancedb_root` set, instead of the deterministic SHA-256-hash embedder/BM25-lexical-reranker stub path every other collection uses. This is intentional: it is the only way to prove AST chunking and def/ref graph edges genuinely affect retrieval (a stub pipeline has no AST/graph logic to regress). The embedder/reranker themselves remain the deterministic eval backends in both paths — only the chunker and graph-extraction layer are real.

### `benchmark` — `uv run pytest -m benchmark`

Performance benchmarks. The flagship file is `tests/benchmark_routing_latency.py`, which times `POST /route` (with the server's API key) over 100 iterations after 3 warmups against a running server. Run it with `-n 0` (the root conftest replaces `ARCHON_SEARCH_API_KEY` with the suite's test key and xdist workers inherit it, so under the default `-n 8` every call is a 401). It **auto-skips when the server is not reachable** (`pytest.skip` on a failed `GET /health` probe) or when `ARCHON_SEARCH_API_KEY` is not exported, so it is safe in CI. There is no in-process comparison: the router only has collection metadata when the server seeds it from its LanceDB store, and its own metadata fetch POSTs unauthenticated JSON-RPC to the server root (401 without a key, 404 with one), so such a run measured an empty router. See `Architecture/210_performance_and_scalability.md` for the targets and the co-located-embedder fallback path.

### `live` — `uv run pytest -m live`

Tests that hit real network or external services. They are collected by the default suite but skip because the autouse fixture in `tests/conftest.py` clears `ANTHROPIC_API_KEY` on every test — `live` tests that gate on the key (via `_skip_if_no_api_key()` or equivalent) therefore always skip on default `uv run pytest` runs, even when the developer has the key exported in their shell. To run them against a real key, temporarily comment out the `monkeypatch.delenv("ANTHROPIC_API_KEY", raising=False)` line in `tests/conftest.py` for the invocation — the root conftest is always loaded regardless of which test directory is targeted, so no pytest flag combination bypasses the autouse.

### `live_eval` — `uv run pytest -m live_eval tests/eval/live/ -v --no-cov`

Runs the eval corpus through **real PyTorch embedder and cross-encoder reranker weights** — the same models used in production. Collected by the default suite but skips when model weights are unavailable OR when the test gates on `ANTHROPIC_API_KEY` (which the autouse fixture in `tests/conftest.py` clears on every test, so these always skip on default runs even when the developer has the key exported in their shell — to run them against a real key, temporarily comment out the `monkeypatch.delenv("ANTHROPIC_API_KEY", raising=False)` line in `tests/conftest.py` — the root conftest is always loaded, so no pytest flag combination bypasses the autouse).

- Tests live under `tests/eval/live/`. The directory has its own `conftest.py` that no-ops the parent `_activate_deterministic_eval_backends` autouse fixture, ensuring `ARCHON_SEARCH_EVAL_BACKENDS` is never set to `"1"` (which would inject deterministic stubs). The root conftest's `_stub_model_backends` skips tests carrying the `live_eval` marker, so the real PyTorch backends run. The shared `tests/_live_model_cache.py` fixtures (`_pin_live_models_dir`, `live_models_dir`) link the isolated data dir's `models/` at the session's real `<ARCHON_SEARCH_DATA_DIR>/models`, so the backends load the cache CI restored instead of downloading into an empty per-worker dir. The parent `_archon_isolated_data_dir` autouse fixture (which clears `ANTHROPIC_API_KEY`) is NOT shadowed and still fires for all live_eval tests.
- Thresholds live in `tests/eval/live_thresholds.toml`. Until calibrated, the file is a comment-only stub and `load_live_thresholds()` returns `None`, making all runs **report-only** (no gates fire).
- The live baseline (`tests/eval/live_baselines/baseline.json`) is absent until the first calibration run. See `tests/eval/README.md` for the calibration procedure and threshold formula (quality floors: −0.02 pp; latency ceiling: 1.5× baseline).
- CI triggers: `archon-search-eval-live.yml` runs on every tag push (concurrently with the release workflow) and on manual `workflow_dispatch`. The test step uses `continue-on-error: true` and uploads the report artifact regardless of outcome — pre-calibration report-only mode must never block a release.

### `live_benchmark` — `uv run pytest -m live_benchmark tests/eval/live_benchmark/ --no-cov`

CI-gated latency benchmark using **the real PyTorch `BAAI/bge-small-en-v1.5` embedder and `Xenova/ms-marco-MiniLM-L-6-v2` cross-encoder reranker** — the production code path (`ModelEmbedder` / `ModelReranker` on CPU). This is one of only two markers **excluded from the default `addopts` run** (see principle 2; `smoke` is the other, below).

- Tests live under `tests/eval/live_benchmark/`. Two benchmark tests:
  - `test_real_model_search_steady_state_p95` — 100-iteration steady-state p95 latency for `pipeline.search()` end-to-end.
  - `test_real_model_search_cold_load_p90` — N=10 cold-load p90 latency for model construction (embedder + reranker together).
- **`xdist_group("live_benchmark")`** serialises both tests onto the same xdist worker, preventing concurrent model construction from inflating cold-load measurements.
- **Model-cache skip hook**: `tests/eval/live_benchmark/conftest.py` has a session-scoped autouse fixture `_require_model_cache` that calls `pytest.skip(...)`, naming the models dir it checked, unless both models have a complete snapshot at their pinned revisions (`missing_live_models()` in `tests/_live_model_cache.py`, which asks `model_store.model_path` for `BAAI/bge-small-en-v1.5` and `Xenova/ms-marco-MiniLM-L-6-v2`; a cached L-12 reranker does not satisfy it). The directory is `paths.get_models_dir()` resolved from the shell environment at session start (`<ARCHON_SEARCH_DATA_DIR>/models`, default `~/.archon-search/models`). A function-scoped autouse fixture, `_pin_live_models_dir`, re-links the isolated per-test data dir's `models/` at that same directory after the root `_archon_isolated_data_dir` fixture replaces the data dir, so the backends load from the directory the guard checked; `tests/eval/live/conftest.py` imports the same fixtures. On developer machines without the cache, the entire session skips gracefully rather than failing. `python -m tests._live_model_cache` downloads the two models at their pinned revisions (a no-op when cached); CI runs it as the prefetch step. In `archon-search-pr.yml` the `actions/cache` entry holds the two snapshot directories `~/.archon-search/models/models--BAAI--bge-small-en-v1.5` and `~/.archon-search/models/models--cross-encoder--ms-marco-MiniLM-L-6-v2` (plus `~/.cache/huggingface` for the docling lane), under a key that names the pinned revisions so bumping one invalidates the entry (`tests/test_workflow_model_cache_lint.py` enforces it). The benchmark step exports `HF_HUB_OFFLINE=1`, so a cache that does not hold what the backends load fails the step instead of silently downloading inside its 3-minute budget. `archon-search-eval-live.yml` (tag pushes and manual `workflow_dispatch`) has its own `actions/cache` entry for the same two snapshot directories and the same prefetch step.
- **Real backends, not stubs**: the `live_benchmark` marker opts out of the root conftest's `_stub_model_backends`, so the zero-vector and constant-score stubs never run. `test_real_backends_are_active_in_live_benchmark` fails if a stub ever sneaks in (it expects a unit-norm vector from the real embedder and a higher score for the relevant pair from the real reranker), and `test_models_dir_is_pinned_to_the_guarded_cache` checks that the backends load from the directory the guard checked. `norecursedirs` keeps the directory out of default collection, and the `-m "not live_benchmark"` filter is a second guard.
- Thresholds in `tests/eval/live_thresholds.toml` under `[real_model_search]`. Loaded by `load_benchmark_thresholds()` from `archon_search/eval/runner.py`. Unlike `load_live_thresholds()`, this function raises `ValueError` if the section is absent — the gate always requires explicit thresholds.
- CI step: `archon-search-pr.yml` runs `pytest -o addopts= ... -n0 -m live_benchmark` with `timeout-minutes: 3` after the integration step and before the coverage enforcement step. Uses `--no-cov` to avoid per-call coverage overhead biasing latency measurements. A `Verify benchmark tests ran` step after it parses the JUnit XML and fails if all tests were skipped (guards against a silently empty model cache).
- See `tests/eval/README.md` (live benchmark lane section) for calibration procedure and threshold update policy.

### `runtime_parity` — `ARCHON_RUNTIME_PARITY_DATA_DIR=/tmp/rt_data uv run pytest -m runtime_parity tests/runtime_parity/ --no-cov -q -p no:cacheprovider -o addopts= -rP`

Real-weights parity of `ModelEmbedder` and `ModelReranker` against the frozen fastembed 0.9.0 outputs in `tests/fixtures/runtime_parity/` (ADR 18), for every model in `archon_search/model_specs.py` (19 embedders, 5 rerankers). The fixtures are the reference and are never regenerated from another runtime; see `tests/fixtures/runtime_parity/README.md` for provenance and the measured worst values.

- Tests: `tests/runtime_parity/test_embedder_parity.py` and `test_reranker_parity.py`, each checking every registry entry on every device available on the host (`cpu`, `mps`, `cuda`). Thresholds: embedder cosine ≥ 0.99994 with the vector norm unchanged (ratio within 1e-3 of 1); reranker absolute score difference below 1e-4. Both files also compare batched against one-at-a-time runs and cover truncation on corpus texts and pairs that exceed a model's `max_length`.
- **Needs `ARCHON_RUNTIME_PARITY_DATA_DIR`**: a data directory whose `models/` holds the pinned snapshots; missing ones are downloaded on first use (the fixtures README puts the full set at about 15 GB). With the weights cached the whole lane (145 test cases on a host with `cpu` and `mps`) takes about 2 minutes: 139 passed, 6 skipped (the truncation cases for which the corpus has no text beyond a model's limit), identical on transformers 4.57.1 and 5.13.1. **Inside the Linux container the lane collects 73 cases** (69 passed, 4 skipped), not 145: a Linux container has no `mps`, so `available_devices()` yields only `cpu` and the 72 host-only ids are all `…-mps]` parametrisations. The container count is cpu-only by design, not a dropped test.
- **Exclusion**: `norecursedirs` lists `tests/runtime_parity`, and `addopts` carries `not runtime_parity`. The root conftest's `_stub_model_backends` skips tests carrying the marker, so the real backends run. `-o addopts=` in the command drops the default `-n 8`, coverage and `-m` filter; `-rP` prints the measured worst cosine or score difference per model.
- **CI**: `.github/workflows/archon-search-runtime-parity.yml` runs the lane nightly (03:41 UTC) and on `workflow_dispatch`, on the CPU of an `ubuntu-latest` runner. It downloads the weights into a fresh directory each run, so it is not a PR gate.
- **CPU throughput gate (not a pytest lane)**: `scripts/bench_runtime.py` and `.github/workflows/archon-search-runtime-bench.yml` (`workflow_dispatch` only, Ubuntu and Windows). The script measures one runtime on CPU per invocation: the PyTorch runtime, or fastembed 0.9.0 installed ad hoc with `uv run --with fastembed==0.9.0` (the only place fastembed still runs). Each profile model gets one warm-up run, then the best of `TIMED_RUNS` = 10 timed runs. `--runtime both` loads both runtimes per model in one process and times them **interleaved** (every runtime once per round, the order flipped each round, best of 10 each), which removes the drift of two separate runs on a loaded host; it writes one `both.json`, and the workflow runs a single `uv run --with fastembed==0.9.0 … --runtime both` step. `compare` (one `both.json` or two single-runtime files) prints a markdown table and exits non-zero when any model's torch throughput falls below 0.9 times fastembed's. The 0.9 rule is unchanged; its first Linux result (arm64) fails 3 of 10 models, see [`210_performance_and_scalability.md`](210_performance_and_scalability.md#linux-arm64-cpu-speed-gate-2026-10-25) and ADR 18.

### `smoke` — `uv run pytest tests/smoke/ --no-cov`

Live subprocess smoke suite that spawns a real `archon-search serve` process and drives it with real CLI subprocess invocations and real HTTP requests — the tier that catches CLI-layer and process-lifecycle bugs (slow startup, raw Python repr output, blocking behaviour) that `TestClient`-based tests structurally cannot detect. This is one of only two markers **excluded from the default `addopts` run** (see principle 2; `live_benchmark` is the other, above).

- Tests live under `tests/smoke/`: `conftest.py` (session fixture), `test_cli.py` (CLI subprocess assertions), `test_conftest.py` (fixture-format and server-startup tests), `test_rest.py` (REST assertions via `httpx`). The `tests/smoke/docker/` subdirectory (added in DCS) contains `test_docker_cli.py` — Docker-mode CLI smoke tests that inject `ARCHON_SEARCH_CONTAINER=1` into the subprocess environment and cover every CLI command in container mode (S1–S16, S18 from the DCS plan, plus T-1 telemetry parity). It carries `pytestmark = [pytest.mark.smoke, pytest.mark.xdist_group("smoke_e2e")]` — a list that extends the parent contract by also applying `pytest.mark.smoke` — and is covered by the same `norecursedirs = ["tests/smoke"]` exclusion; no `pyproject.toml` change was needed.
- **Real subprocess, not `TestClient`**: the session fixture binds a free port (port-0 socket trick, no TOCTOU), starts `uv run archon-search serve` through `_spawn_server` (its own session, so the `uv` parent and the server form one process group), polls `GET /health` then `GET /ready`, pre-seeds a tiny real collection (3 text files ingested via `POST /collections/`), and tears down through `_terminate`: SIGTERM (which `uv run` forwards), draining and closing both pipes, then SIGKILL to the whole process group after 10 s. SIGKILL cannot be forwarded, so killing `uv` alone would orphan the server.
- **`xdist_group("smoke_e2e")`** is set as module-level `pytestmark` in every smoke test file, serialising all smoke tests onto one xdist worker — this prevents two workers from spawning concurrent server subprocesses against the same fixture.
- **Timing budgets**: CLI commands (`--help`, `config show`) budget 2 s; other CLI/REST calls budget 5 s. These catch gross startup/latency regressions, not tight P99 bounds.
- **Output-format assertions**: no `CollectionMeta(` repr, no raw embedding-vector arrays (`"[0."`), no Python stack traces in stdout/stderr/response bodies.
- **Exclusion mechanism**: `norecursedirs = ["tests/smoke"]` in `pyproject.toml` is what actually prevents pytest from auto-traversing the directory (so the fixture's real-subprocess spawn is never triggered by default collection); `-m "not smoke"` in `addopts` is a secondary, belt-and-suspenders guard. `tests/smoke/test_cli.py::test_smoke_marker_in_pyproject` asserts both guards plus the registered marker are present in `pyproject.toml` — but like every smoke test it is itself `norecursedirs`-excluded, so it only runs when `tests/smoke/` is invoked explicitly, not as a default-suite regression net.
- **Requires the shared model cache** (`~/.archon-search/models`, ~1.3 GB) on the host. Every model load resolves `paths.get_models_dir()` (`<ARCHON_SEARCH_DATA_DIR>/models`, the Hugging Face hub layout; `model_store.ensure_model` downloads missing snapshots there at the pinned revisions). The smoke fixtures point `ARCHON_SEARCH_DATA_DIR` at a throwaway directory, so reuse comes from `_link_model_cache` (`tests/smoke/conftest.py`), which symlinks the throwaway `ARCHON_SEARCH_DATA_DIR`'s `models/` at the fixed `~/.archon-search/models` (`_SHARED_MODELS_DIR`, independent of the shell's `ARCHON_SEARCH_DATA_DIR`). `_spawn_server` applies it to every smoke server, the Docker-mode fixtures and `test_s04` included: an unlinked server re-downloads its weights and took ~22 s to report ready on an idle machine, past the old 30 s readiness timeout under release-lane load. The readiness timeout (`_HEALTH_READY_TIMEOUT_S`) is 90 s in every mode, because `/ready` stays 503 until model warm-up and the background model validation finish (S631); validation is bounded by its startup probes (each only when configured) plus `[database].validation_timeout_seconds` (default 60 s) — full bound under [`validation_timeout_seconds`](../UserManual/30_configuration.md#database). On a machine without the cache, the first run triggers a cold download and may exceed that timeout.
- Run with `uv run pytest tests/smoke/ --no-cov` — not part of the coverage-gated default run; triggered manually or before a release, not on every PR.

### `docling` — `uv run pytest -m docling --no-cov`

The eight tests that exercise the **real** docling parser / RapidOCR OCR path — PDF text extraction and image OCR — end-to-end. Excluded from the default `addopts` run because a single parse takes minutes on macOS: docling loads RapidOCR + onnxruntime and runs OCR on every page (Metal shader compilation on first use). Left in the default suite they hang the run well past any reasonable budget; one of the original four had no timeout guard at all.

- Tests: `tests/test_parser.py::test_parse_with_docling_emits_page_marker`, `::test_image_ocr_still_reads_text_at_scale_one`, and `::test_pdf_ocr_reads_text_from_scanned_page` (added in the C1-B-1 cycle-1 review — a scanned/image-only PDF, since the other PDF test uses a real text layer that OCR contributes nothing to); `tests/test_parser_ocr_memory.py::test_image_ocr_memory_bounded_over_mixed_size_corpus` and `::test_build_docling_converter_effective_scale_is_one_image_only_default_pdf` (added in the same review — the real-docling-lane complement to the mocked `test_parse_path_requests_ocr_scale_one`); `tests/test_fixtures.py::TestThreePagePdfFixture::test_three_page_pdf_contains_expected_text`; and two in `tests/integration/test_http_enrichment_metadata.py` (`test_pdf_page_number_in_search_response`, `test_image_file_assigns_page_start_one`).
- **Exclusion mechanism**: `-m "... and not docling"` in `addopts` — the tests are scattered across four files rather than a dedicated directory, so there is no `norecursedirs` guard (unlike `live_benchmark`/`smoke`). Each CI step also repeats `not docling` on its own `-m` line, because every step passes `-o addopts=`, which wipes pyproject's filter per invocation.
- **It does run in CI, as its own step.** Both workflows carry a `Run docling parser lane` step — `uv run pytest -o addopts= --strict-markers --strict-config --no-cov -n0 -m docling tests/` (`archon-search-pr.yml:92`, `archon-search-release.yml:78`). Exclusion and execution are both true at once: the lane is out of the *default*, coverage-gated run and in a dedicated uncovered step. `tests/test_parser_ocr_memory.py::test_both_workflows_run_the_docling_lane` is the presence anchor that keeps the step from being deleted silently — every other guard in that file only asserts the lane is excluded, and all of them passed for months while `-m docling` ran nowhere.
- **PDF fixtures are generated, not committed** — the reportlab-based `three_page_pdf` / `substantial_three_page_pdf` / `scanned_pdf` fixtures in `tests/conftest.py` write into `tmp_path`. `scanned_pdf` is the image-only one (a rendered bitmap page with no text layer), so it is the only PDF fixture whose text can be recovered solely through docling's OCR path. The eval corpus deliberately contains **no** PDF/OCR document, so the deterministic eval harness (`tests/eval/`) never invokes docling; page-provenance parsing at the unit level is covered by `tests/test_enricher.py` without docling.
- Run locally with `uv run pytest -m docling --no-cov`. It is not part of the coverage-gated default run, but it is not on-demand-only: the dedicated CI step above runs it on every PR and every release.

### `graph_real_artifact` — `ARCHON_SEARCH_DATA_DIR="$HOME/.archon-search" uv run pytest -m graph_real_artifact --no-cov`

The five tests in `tests/test_graph_ner_real_artifact_lane.py` that drive the **real** `knowledgator/gliner-relex-multi-v1.0` checkpoint end-to-end — determinism across processes, non-vacuity, memory budget, throughput budget, and French span offsets. This lane exists because every other graph test in the suite runs against a stubbed engine, which certifies the fixture rather than the engine; that gap is exactly how `GRAPH-3` (a silent production no-op yielding zero entities and zero relations while ingest reported success) shipped.

- **Exclusion mechanism — three places, not one.** `-m "... and not graph_real_artifact"` in `pyproject.toml` `addopts` covers a plain `uv run pytest`. Both CI workflows override `addopts` per invocation (`-o addopts=`), so their own unit and integration steps each carry `and not graph_real_artifact` on their `-m` line — that filter, not `addopts`, is what actually keeps the lane out of CI's default steps.
- **`xdist_group("graph_real_artifact")`.** `addopts` mandates `-n 8 --dist=loadgroup`; an unpinned lane test would land on an arbitrary second worker and load a second copy of the model stack concurrently. Every `@pytest.mark.graph_real_artifact` test therefore also carries `@pytest.mark.xdist_group("graph_real_artifact")`. This protects the local parallel run only — CI passes `-n0`, where it is inert.
- **Three structural meta-guards, mirroring `docling`'s trio** (all in `tests/test_removed_engine_repo_guard.py`):
  1. `test_pyproject_default_lane_excludes_graph_real_artifact` — parses `pyproject.toml` and asserts the `addopts` `-m` filter carries the exclusion.
  2. `test_both_workflows_exclude_the_new_marker_on_the_same_filter_line` — **the one carrying real CI force.** It delegates to `assert_marker_excluded_on_step_lines` in `tests/test_parser_ocr_memory.py`, which locates each workflow's unit and integration step by the existing `_STEP_FILTER_MARKERS` tuple (used as a *locator*, deliberately never extended) and asserts the exclusion sits on that **same line**. Presence-somewhere-in-the-file would not prove coexistence on one `-m` invocation; this does.
  3. `test_every_graph_real_artifact_test_is_pinned_to_its_xdist_group` — delegates to `find_marker_tests_missing_xdist_group`, the same shared scan the `docling` lane's guard uses.
  Two further guards are **presence** anchors rather than exclusion guards, added after `GRAPH-4`: `test_both_workflows_run_the_graph_real_artifact_lane` (all three exclusion guards passed while the release workflow ran the lane nowhere at all — a tag can be cut from a commit that never met the PR gate) and `test_graph_artifact_cache_key_pins_the_model_revision` (a cache key that outlives a revision bump would restore the previous checkpoint and certify a model the shipped code no longer loads).
- **Per-worker memory budget.** `test_graph_ner_memory_budget` asserts RSS growth after warm-up across ≥1,000 prose chunks stays under `_RSS_GROWTH_BUDGET_MIB = 600`, with a `_RSS_CEILING_MIB = 6000` host-safety abort and a `_RUN_BUDGET_S = 900` wall-clock cap. **This budget binds the CPU configuration only** — an accelerator selected via `[graph].device` is permitted but entirely unmeasured, and no scenario asserts a ceiling for it. It is also a *growth* ceiling: the transient peak inside a single sub-batch forward pass is bounded by `GRAPH_NER_SUB_BATCH_SIZE`, never asserted. The numeric comparison carries `xfail(strict=False)` until a real CI measurement replaces the provisional dev-machine figure; the host-safety and wall-clock checks in the same function use `pytest.exit()` specifically so `xfail` cannot swallow them, and the always-blocking non-vacuity assertions live in a separate unmarked test. See `Architecture/210_performance_and_scalability.md` for both budgets.
- **The CI step uses `--no-cov`, so this lane contributes nothing to the 85% floor.** That is a deliberate trade (it mirrors the `live_benchmark` step; `tests/CLAUDE.md` reserves `--cov-append` for the three `--cov` steps), which makes it worth stating exactly what the **default stubbed** lane does and does not cover in `archon_search/prose_extraction_backend.py`. Two stub depths exist, both in `tests/_graph_engine_stub.py`: `install_graph_engine_stub` patches the `ProseExtractionBackend` *class* and therefore covers **none** of its code; `install_deep_gliner_stub` injects a fake `gliner` module at the package boundary and lets the real backend run.
  - **Covered by the stubbed lane** (`tests/test_prose_extraction_backend.py`, `tests/test_prose_extraction_backend_inference.py`): `_resolve_device` over the `[graph].device` vocabulary (`auto|cpu|mps|cuda`) including the unavailable-device step-down to CPU with a warning, and the guarantee that `GraphExtractor` hands `[graph].device` — never `[database].device` — to the engine; the whole `load()` lifecycle — idempotence, single-flight loader/waiter split, waiter timeout leaving the loader's bookkeeping untouched, failure latching, `CancelledError` never latching, the load timeout, a regression test that loading the model leaves the process's torch thread count unchanged (the old `torch.set_num_threads(1)` pin made PyTorch CPU embedding 3x slower, so the engine no longer pins), the `cache_dir` coming from `get_graph_models_dir()`, and `load_count` counting only real constructions; the assertion that importing the module pulls in no ML library; and all of `_infer_sync`'s own logic — `ceil(N / GRAPH_NER_SUB_BATCH_SIZE)` call counting, the per-call size cap, non-real-label span discarding, relation-endpoint filtering, `(head, tail, label)` dedupe, truncation (once-per-instance sanitized log, exact-prefix guarantee), both thresholds reaching the model unswapped, `adjacency_threshold` deliberately not passed, prompt-vocabulary coverage of every enum member, and the short-per-text-result and inference-before-load raises.
  - **Not covered by the stubbed lane — this is the whole reason the lane exists**: that `GLiNER.from_pretrained` can actually construct the pinned revision from that cache directory; that the real checkpoint's `inference(..., return_relations=True)` return shape still matches what the fake mirrors (the fake was recorded from the installed package and can drift with a revision bump); real `.to(device)` placement; that the model returns **non-vacuous** entities and relations on real prose (the `GRAPH-3` defect class, invisible to any stub); real memory residency and throughput; and multilingual span quality with correct character offsets.
- **The `[graph]` extra IS installed in CI.** Correcting a long-standing assumption to the contrary: `pyproject.toml:85` pulls `archon-search[multilingual,hyde,rag_fusion,ollama,openai-provider,graph,code]` into the `dev` dependency group, and both workflows run `uv sync --dev`. No graph- or code-gated test skips in CI for a missing extra. What the lane adds on top is the model *artifact*, which the dev group does not install — hence the workflows' separate cache-restore and prefetch steps, and the requirement that `ARCHON_SEARCH_DATA_DIR` point at a data dir whose `models/graph/` already holds the checkpoint.
- **Never `importorskip`.** A missing artifact must fail this lane loudly; a lane that skips itself is the `GRAPH-4` failure mode with extra steps.

### Unlocked-dependency lane — `bash scripts/test-unlocked-deps.sh`

Every other lane runs against `uv.lock`; end users never do. `pip install archon-search`, `uv tool install archon-search` and the Dockerfile's `pip install .` resolve the newest versions the wheel's metadata allows, so a transitive release can break users while CI stays green — S671 shipped that way (`huggingface_hub` locked at 1.26.0, user installs on 1.33). This lane installs the way users do and re-runs the release gate's lanes on top.

- **Install** (`install` step): fresh Python 3.12 venv, `uv pip install --no-config --no-sources --resolution highest . --group dev`, plus `--torch-backend cpu` on every Linux architecture (x86_64 and arm64; PyPI's Linux torch wheel pulls 15 `nvidia-*` packages, the CPU backend resolves `torch 2.14.1+cpu`). `--no-config` drops `[tool.uv] constraint-dependencies` and `--no-sources` drops the `[tool.uv.sources]` torch CPU pin, because neither reaches the wheel; the torch backend keeps the CI runner on the `+cpu` build the Docker image ships. It prints each distribution whose version differs from `uv.lock`.
- **Lanes** (`suite`, `docling`, `graph` steps): the full default suite with `pyproject.toml` `addopts` (unit + integration + eval, the 85% floor, disk-backed basetemp, `COVERAGE_FILE` in the work dir) minus `benchmark` — the step repeats the `addopts` `-m` filter with `and not benchmark` added, as the release `test` job deselects it, because latency ceilings measured under `-n 8` on a 4-vCPU runner fail on CPU contention, not dependency drift (`release.sh` lane 7 runs them serially) — then the `docling` and `graph_real_artifact` lanes with the release workflow's non-vacuity checks. Each step fails if the run changed the venv it tests.
- **CI**: `.github/workflows/archon-search-unlocked-deps.yml` — daily, on PRs touching `pyproject.toml`/`uv.lock`/the lane's files, on `workflow_dispatch`, and as the release workflow's `unlocked-deps` job that `publish` and `docker` need. `release.sh` runs it as lane 6. Trigger rationale and the fix policy (bounds go in `[project] dependencies`, never only in `[tool.uv]` or `uv.lock`): `510_release_and_environment_strategy.md` → *Locked vs unlocked dependencies*.
- **Local run**: `bash scripts/test-unlocked-deps.sh` (all steps) or one step by name. It never touches the repo's `.venv`; the work dir defaults to `/var/tmp/archon-search-unlocked` (`ARCHON_UNLOCKED_DIR`), and the graph step reads `ARCHON_SEARCH_DATA_DIR` (default `$HOME/.archon-search`) for the GLiNER checkpoint.

### Docker-gated lane — `ARCHON_SEARCH_RUN_DOCKER_SMOKE=1 uv run pytest tests/test_docker_smoke.py -n0 -o addopts= --no-cov`

Tests marked `docker` (plus the Dockerfile and compose lints, which need no daemon) build or run the real image. They are skipped unless `ARCHON_SEARCH_RUN_DOCKER_SMOKE=1` (`tests/_docker_support.py`); the real image build and run is also driven by `release.sh` (and `tests/test_multi_instance_e2e.py`, `tests/test_docker_gpu_image.py` behind the same variable). `test_docker_smoke.py` covers: the CPU image starts and serves `/ready`, uid 1000 can write the data dir, the compose smoke suite exits 0 in the test-runner image; the default image runs `--read-only` with only `/data`, `/tmp` and `/pip-packages` writable; a scanned PDF parses with `--network none --read-only` (docling models are prefetched into the image); and the graph-enabled image degrades to code symbols only. On 2026-10-25 the lane passed on the linux/arm64 image (126 passed with the lints; `test_docker_smoke.py` alone 8 passed). Without the opt-in variable the same selection gives 121 passed, 5 skipped. ## What each lane can and cannot detect

| Lane | Real weights | Detects | Cannot detect |
|---|---|---|---|
| default (unit, integration, eval) | no — `_stub_model_backends`, deterministic eval backends | wiring, API contracts, security rules, coverage ≥ 85% | any change in what the real PyTorch models compute or how fast |
| `runtime_parity` | yes | embedder cosine < 0.99994 or reranker score drift against the frozen fastembed outputs, on every available device | speed, memory, concurrency |
| `live_eval` | yes | retrieval-quality regressions of the real models on the eval corpus | latency under load; it is report-only until calibrated |
| `live_benchmark` | yes (bge-small + MiniLM, CPU) | steady-state p95 and cold-load p90 regressions | other models, accelerators |
| `smoke`, docker-gated | yes | process-lifecycle, CLI, container and read-only-filesystem bugs | per-model quality |

The deterministic eval harness (`tests/eval/`, `archon_search/eval/backends.py`) uses corpus-aware but label-blind hash backends, so **it cannot detect a PyTorch regression**: the PyTorch code path is covered by `runtime_parity`, `live_eval` and `live_benchmark`, none of which is part of the coverage-gated default run. The `live_eval` report of 2026-10-25 on the PyTorch runtime (162 queries, 216 documents) measured recall@1 0.8485, recall@5 0.9848, MRR 0.9848 (recall@3 0.9545, nDCG@5 0.9778, routing accuracy 1.0; latency p50 85.9 ms, p95 167.6 ms on a loaded host). `code_chunking_recall_at_5 = 0.0` in that lane is a fixture property, not a runtime defect: the live lane has no `lancedb_root`, so it ingests with `DocumentChunker(chunk_size=256)` instead of the AST chunker at 65 the fixture is calibrated for; the old fastembed build and the PyTorch build rank the files identically (see `tests/eval/README.md`). RAG-fusion recall@5 was measured at 0.5652 over 156 queries with `claude -p` (floor 0.45).

## CI and lint hygiene

- **Lint step.** `.github/workflows/archon-search-pr.yml` runs `uvx ruff@0.17.2 check .` (zero findings) before the tests; the rule set is pinned in `pyproject.toml [tool.ruff.lint]`, so the result does not depend on the ruff version installed.
- **Pinned actions.** Every `uses:` line in `.github/workflows/` is pinned to a commit SHA with a trailing `# <tag>` comment; `tests/test_workflow_action_pinning_lint.py` fails on an unpinned ref.
- **Workflows.** `archon-search-pr.yml` (lint, default, integration, docling and live-benchmark steps, coverage gate), `archon-search-release.yml` (tag push: tests, unlocked-deps, publish, docker), `archon-search-eval-live.yml` (tag push, report-only), `archon-search-unlocked-deps.yml` (daily and on dependency changes), `archon-search-runtime-parity.yml` (nightly 03:41 UTC and manual; real weights on CPU), `archon-search-runtime-bench.yml` (manual; Ubuntu and Windows; interleaved fastembed/PyTorch throughput), and `backfill-release-notes.yml`.

## Dependency matrix and audit (2026-10-25)

- **torch floor `>=2.4,<3.0.0`** (it was 2.2.2, copied from docling). On Python 3.12 torch 2.2.2/2.3.1 cannot load ModernBERT (`Dynamo is not supported on Python 3.12+`), and transformers 5.13 needs torch 2.4; torch 2.4.1 passes on transformers 4.57.1 and 5.13.1. `tests/test_pyproject.py::test_torch_floor_is_the_oldest_torch_the_runtime_works_on` guards it.
- **transformers `>=4.57,<5.14`** (locked 5.13.1). Verified on an M4 Pro, torch 2.13.0: unit lane and the 9-model parity sample pass on 4.57.1, 5.0.0, 5.8.1, 5.10.4 and 5.13.1; the full parity lane (139 passed, 6 skipped) on 4.57.1 and 5.13.1. A defect found on 4.57.1 — concurrent builds left meta tensors behind because `from_pretrained` swaps torch globals during a build — is fixed by `TRANSFORMERS_LOCK` around every `from_pretrained`; failing-first tests prove it (peak overlap 4, expected 1).
- **Locked versions** after the security upgrade: docling 2.142.1, transformers 5.13.1, pillow 13.0.0, PyJWT 2.15.1, filelock 4.2.4, urllib3 2.8.0, fastmcp 3.4.11, certifi 2026.10.23, opentelemetry-api 1.45.1, setuptools 84.2.1, accelerate 1.15.0. `pip-audit` before: 83 vulnerabilities in 12 packages; after: no known vulnerabilities. `test_pyproject.py` now requires the locked transformers to be ≥ 5.10.0 (PYSEC-2026-3929) instead of pinning 5.8.1. docling 2.132 and later fail on Apple `mps` ("Cannot convert a MPS Tensor to float64"), so the parse worker sets `DOCLING_DEVICE=cpu` on macOS.
- **The Docker image installs unlocked latest versions on purpose** (its pip layer avoids uv; the unlocked-deps lane tests that same resolution), so the image ships torch 2.14.1+cpu while `uv.lock` holds 2.13.0; the runtime-module unit lane (156 passed) and the cpu parity lane run inside the image.

## Known limitations

- x86_64 Linux, Windows, NVIDIA CUDA and Intel Mac are unmeasured for CPU speed and the parity lane; only macOS arm64 (CPU and `mps`) and Linux arm64 (CPU, in Docker) have results. The Windows guards (`fchmod`, `geteuid`, directory fsync, `O_NOFOLLOW`) are unit-tested but have never run on Windows.
- The Linux arm64 speed gate fails 3 of 10 models (ADR 18 decision: keep PyTorch, judge the pass rule per platform).
- The extras installed at container start (`ARCHON_EXTRAS`) are not hash-pinned. The only hashes available at runtime come from the same index in the same resolve, so they would stop only an artifact swapped between resolve and install; real protection needs a hashed catalog generated at build time for every extras combination, which would also make startup fail whenever the index moves on. `--index-url`-only installs are not possible either: PyPI does not carry Linux `torch+cpu`, so PyTorch's CPU index is required.
- Thread counts scale with concurrent load (peak about 500 OS threads on a 14-core host); the LanceDB runtime has no thread knob.

## Coverage

`pyproject.toml [tool.pytest.ini_options] addopts` includes `--cov=archon_search --cov-report=term-missing --cov-fail-under=85`.

- This threshold is intended for the **default single-run invocation**. A single `uv run pytest` produces a single coverage dataset, and 85% gates that dataset.
- **CI runs that invoke pytest more than once must accumulate coverage into one dataset before applying the threshold.** The PR workflow (`.github/workflows/archon-search-pr.yml`) does this by overriding `addopts` (`-o addopts=`) on each step, passing `--cov-append` so both the default and eval invocations write into the same `.coverage` file, and then running a separate `coverage report --fail-under=85`. CI also passes `-n0` explicitly to disable xdist parallelism — each invocation's internal combine step could otherwise overwrite `.coverage` with only the current run's worker shards, silently dropping coverage from prior invocations. If a future CI layout instead writes parallel-mode shard files (e.g. matrix shards each producing `.coverage.<id>`), it must `coverage combine` them first; the current workflow doesn't, because there's nothing to combine. Applying `--cov-fail-under=85` to an individual partial run would reject correct code, because each invocation only sees part of the codebase.
- **`--no-cov` is a local-only override.** Use it on the CLI when iterating (`uv run pytest --no-cov ...`). It must never be baked into `addopts` — doing so silently disables the coverage gate for every contributor.

## Parallel-test isolation (`archon_unset_data_dir` marker + `_archon_isolated_data_dir` autouse)

Every test runs under a per-worker, session-scoped `ARCHON_SEARCH_DATA_DIR` provided by the autouse fixture chain in `tests/conftest.py`:

- **`_archon_worker_data_dir` (session-scoped)** — calls `tmp_path_factory.mktemp("archon-data")` once per xdist worker. The result is a fresh temporary directory that is unique to that worker's lifetime.
- **`_archon_isolated_data_dir` (function-scoped, autouse)** — always clears `ARCHON_SEARCH_HOST`, `ARCHON_SEARCH_PORT`, `ARCHON_SEARCH_CONTAINER`, `ARCHON_SEARCH_KEY_FILE`, `ARCHON_SEARCH_CONFIG`. By default it also sets `ARCHON_SEARCH_DATA_DIR` to `str(_archon_worker_data_dir)`, directing every path accessor (`get_data_dir()`, `key_manager.get_key_file()`, `jobs.get_jobs_file()`, etc.) to an isolated temporary tree. Tests that need to exercise the `Path.home() / ".archon-search"` default-fallback codepath (e.g. `test_default_returns_home_archon`) must opt out by applying `@pytest.mark.archon_unset_data_dir`; the fixture then deletes `ARCHON_SEARCH_DATA_DIR` from the environment instead of setting it.

The **`archon_unset_data_dir` marker** is registered in `[tool.pytest.ini_options].markers` in `pyproject.toml`. It is intentionally narrow: apply it only to tests that explicitly assert on the `Path.home() / ".archon-search"` default. The exact set of authorized tests is enforced by `test_archon_unset_data_dir_marker_scope` in `tests/test_no_hardcoded_path_home.py` (see below); any test outside the `MARKER_ALLOWLIST` that acquires this marker will fail CI.

### `Path.home()` ratchet (`tests/test_no_hardcoded_path_home.py`)

`tests/test_no_hardcoded_path_home.py` is a structural CI ratchet that prevents new hardcoded `Path.home()` callsites from being introduced under `archon_search/` outside `archon_search/paths.py` (the one legitimate caller). Three test functions:

1. **`test_path_home_ratchet`** — scans every `*.py` under `archon_search/` (excluding `paths.py`) for `Path.home(` via a line-level regex. Performs a *bidirectional assertion* against `tests/path_home_allowlist.txt` (one `<relative_path>:<line_no>:<sha256>` entry per allowlisted callsite): forward direction catches new unallowlisted callsites; reverse direction catches dead or hash-mismatched allowlist entries. A cosmetic edit to any grandfathered line changes its SHA-256, triggering the reverse direction and forcing an explicit allowlist update.

2. **Meta-tests** (`test_meta_positive_match`, `test_meta_no_parens_negative`, `test_meta_lowercase_negative`, `test_meta_string_literal_positive`) — exercise the regex against in-memory fixtures so a pattern weakening (e.g. dropping `\b` or `\s*\(`) fails immediately, independent of the codebase scan.

3. **`test_archon_unset_data_dir_marker_scope`** — AST-walks `tests/` and asserts that `@pytest.mark.archon_unset_data_dir` appears on exactly the tests named in `MARKER_ALLOWLIST`. Paired with `test_meta_ast_finds_pytest_mark_decorator`, which validates the AST walker itself.

Grandfathered callsites (the two legacy launchd/systemd service-path `Path.home()` calls in `archon_search/install/service_ops.py:38-39`; `archon_search/config.py`; `archon_search/platform/linux.py` and `archon_search/platform/macos.py`) are pinned in `tests/path_home_allowlist.txt`, which is keyed by `(file, line, content-hash)` — so an entry must be re-pinned whenever the callsite moves (as the two `install.py` service-path pins were during the `install.py` → `install/` package split). Earlier `install.py` callsites were migrated to `get_data_dir()` in C17 and removed from the allowlist. The sibling ratchet for SQL f-string injection is `tests/test_no_fstring_sql.py`, which scans `store.py` and `graph_store.py` (see `Architecture/150_security_and_privacy_architecture.md`; the guard's module docstring is authoritative for the file list).
