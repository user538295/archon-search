# Error Handling Strategy

Errors in archon-search are classified at three layers: configuration, HTTP request handling, and background jobs. Each layer has a distinct contract — config fails the process, HTTP returns a typed status, jobs persist a terminal `FAILED` state. Telemetry only ever records a coarse `error_kind` from a fixed enum, never an exception message.

See also: [100_system_architecture_overview.md](100_system_architecture_overview.md), [120_services_and_integration_architecture.md](120_services_and_integration_architecture.md), [160_operational_readiness_monitoring_and_reliability.md](160_operational_readiness_monitoring_and_reliability.md).

## Principles

1. **Fail fast at config load.** Invalid TOML, out-of-range integers, wrong types → `ConfigError` raised by `config.py::load_config`. The process does not start.
2. **Propagate typed exceptions.** Domain layers raise `ValueError`, `KeyError`, `RuntimeError`, `NotImplementedError`, `ConfigError`. (`asyncio.TimeoutError` arises in the request path from `asyncio.wait_for(...)` in `routes_route.py`; it is not a typed domain exception raised by lower layers.) Route handlers translate these to HTTP status codes — exceptions never leak as raw 500s when a typed mapping exists. Pipeline failures on `/search` surface as HTTP 500 with a plain-text body `Internal Server Error` (Content-Type `text/plain`) — the route bare-re-raises and Starlette's `ServerErrorMiddleware` renders the default response; there is no JSON envelope. A timeout returns HTTP 504 with `{"detail": "Search timed out"}` after ~30s, matching the timeout-+-telemetry-+-504 shape of `routes_route.py` (note: the detail string and log `event_type` differ — `/route` uses `routing timed out` / `route_timeout`, `/search` uses `Search timed out` / `search_timeout`).
3. **Coarse, closed-set telemetry classification.** When telemetry records an error, it uses `ErrorKind ∈ {empty_query, slot_out_of_range, timeout, internal_error, validation_error, other}` (see `telemetry/entry.py::ErrorKind`). Never store exception messages, stack traces, or input strings.
4. **Auth failures are uniform.** The auth middleware returns `401` with `WWW-Authenticate: Bearer` and no body — same response for missing header, wrong scheme, and bad token. (Exception: a token that *does* resolve to a namespace but fails `_validate_namespace` returns `500`, not `401`; see "Authentication errors" below.)
5. **Jobs record terminal failure state.** A failed background job transitions to `JobStatus.FAILED` with a short `error` string; the HTTP layer remains `202` at submission time.
6. **Wire text is fixed, never exception text.** A caught exception whose message can embed internals (server paths, library internals, an install command, the rejected input) is logged server-side with its traceback; the REST `detail`, MCP `error`, job `error` or `result`, maintenance `last_error`, collection sync `error` or wire-facing warning (`provider_warnings`, ingest `warnings`) carries one sanitized constant defined next to the exception — a `*_DETAIL`, paired with a `*_CODE` where MCP needs one (e.g. `HYDE_DEPENDENCY_DETAIL` / `HYDE_DEPENDENCY_CODE` in `hyde.py`, `ROTATE_KEYS_JSON_FAILED_DETAIL` next to `RotationIncompleteError` in `key_manager.py`, `INTERNAL_ERROR_DETAIL` in `server/mcp.py`, `PARSE_FAILED_DETAIL` as `ParseError.detail` in `parser.py`, `collection_sync_failed_detail()` in `sync.py`). A curated exception whose message archon-search builds itself (e.g. `KeyRotationInputError`, `IngestPathNotFoundError`, `ArchiveRejectedError`) may surface its own text. An install command stays off the wire even when no exception carries it: `extra_install_hint()` in a `uv tool` install replays the receipt (`--index-url` credentials, `--find-links`, local source paths), so `GET /status` → `model_validation.provider_warnings` reports a missing `[graph]` extra as `graph prose entity extraction is disabled: gliner is not installed. Install archon-search[graph] to use graph prose entity extraction` (`GLINER_NOT_INSTALLED_WARNING`, `model_validation.py`) and `graph_ner_status` logs the command at WARNING; the only other surface that keeps it is the `ConfigError` raised by `create_app` at startup and by `create_pipeline`. `tests/test_no_wire_str_exc.py` enforces this structurally for `archon_search/server/`, `archon_search/jobs/` and the wire-feeding modules in its `_GUARDED_FILES` (`sync.py`, `pipeline.py`, `parser.py`, `model_validation.py`, `defref_extractor.py`, `graph_extractor.py`, `acl.py`): inside an `except … as <name>:` body, any `str()` / `repr()` / f-string of the caught exception — and `traceback.format_exc()` or `traceback.format_exception[_only]()` of it — outside a logging call (on `logger`, `_logger`, `log`, `logging` or `[logging.]getLogger(...)`) fails the build unless its (file, function, `except` type, ordinal) is in the test's `_ALLOWLIST`; the ordinal numbers that function's stringifying handlers of that type, so each entry covers exactly one handler. A stale entry fails too. The scan is syntactic, and its module docstring lists the blind spots (e.g. `exc.args`, `%` / `.format()`, the exception passed whole or re-bound to another name).

## Configuration errors

`archon_search/config.py::ConfigError` is raised for:

- TOML parse failure (`Failed to parse {path}: {exc}`, `load_config`)
- Wrong type — per-type messages, not slash-joined: `Expected integer for '{field}', got {type}` (`config.py` `_coerce_int`, `_coerce_bounded_int`), `Expected float for '{field}', got {type}` (`_coerce_float`, `_coerce_bounded_float`), `Expected boolean for '{field}', got {type}` (`_coerce_bool`). A TOML boolean is never coerced into a number key (`got bool`). Integer keys come in two strictness levels: `_coerce_int` keys (e.g. `port`, `top_k_return`, `[backup].keep`) reject a fractional or non-finite float instead of truncating it (`top_k_return = 5.9` → `got Float`) but still accept an integral float or numeric string (`5.0` and `"5"` load as `5`); `_coerce_bounded_int` keys and the inline-checked `[ingest].max_file_mb`, `[ingest].max_tasks_per_child` and `[graph].backend_threshold_edges` require a TOML integer and reject any float or string. A float key rejects `inf`, `-inf` and `nan` (also quoted) with `Expected finite float for '{field}', got {value}`, and an integer beyond float range with `Expected finite float for '{field}', got an int beyond float range`
- Out-of-range / non-empty checks:
  - `port must be between 1 and 65535, got {port}` (`config.py` `_apply_toml`, like every check below; `[server]`)
  - `chunk_size must be > 0, got {chunk_size}` (`[database]`)
  - `top_k_retrieve must be > 0, got {top_k_retrieve}` (`[database]`)
  - `top_k_return must be > 0, got {top_k_return}` (`[database]`)
  - `max_fanout must be >= 1, got {max_fanout}` (`[search]`)
  - `fanout_leg_trim must be >= 1, got {fanout_leg_trim}` (`[search]`)
  - `fanout_timeout_seconds must be > 0, got {fanout_timeout_seconds}` (`[search]`)
  - `top_k_max must be > 0, got {top_k_max}` (`[search]`)
  - `context_window_max must be >= 1, got {context_window_max}` (`[search]`; the floor is `constants.DEFAULT_CONTEXT_WINDOW`)
  - `routing_shortlist_size must be > 0, got {routing_shortlist_size}` (`[routing]`)
  - `routing_confidence_threshold must be in [0.0, 1.0], got {threshold}` (`[routing]`)
  - `[telemetry].retention_days must be >= 1` (`[telemetry]`)
  - `[telemetry].log_dir must be a non-empty string` (`[telemetry]`)
  - `[ingest].max_file_mb must be >= 0, got {raw}` — negative values raise `ConfigError`; `0` (the default) is valid and disables the size guard entirely. **E0d**: `IngestConfig` (`config.py`)
  - `[ingest].max_tasks_per_child must be >= 1, got {raw}` (`config.py`, `_apply_toml`, `[ingest].max_tasks_per_child` branch) — `0` is rejected too: it would mean "never recycle the docling parse worker", which is the unbounded-memory behaviour the key exists to prevent. Non-integers (and `bool`, rejected explicitly despite being an `int` subclass) raise `Expected integer for '[ingest].max_tasks_per_child', got {type}` (same branch) rather than being coerced.
- Invalid `[namespaces]` shape (non-string key or value; `_apply_toml`, `[namespaces]`)

`[telemetry].export_enabled = true` is **not** raised — `config.py` `_apply_toml` (`[telemetry]` branch) emits a warning and silently coerces to `false`. This is the documented v1 contract: external export is reserved and ignored, not rejected.

`ConfigError` is caught explicitly by the `archon-search start` subcommand (`cli/start.py` `start`, the `except ConfigError` around `load_config`), which prints `Error: {exc}` to stderr and exits with `SystemExit(1)`. Other entry points (e.g. importing the server module directly in tests) propagate the exception per Python defaults — "the process does not start" is enforced by the `start` path, not centrally.

## Authentication errors

`server/middleware_auth.py::APIKeyMiddleware`:

- Missing `Authorization` header, wrong scheme, or token that fails `secrets.compare_digest` against both the per-namespace key map and the default API key → `401`, header `WWW-Authenticate: Bearer`, empty body.
- Exempt paths (`/health`, `/ready`, `/docs`, `/openapi.json`, `/redoc`) bypass the middleware entirely.
- If a resolved namespace fails `_validate_namespace`, the middleware logs and returns `500` (defensive — should not occur if config validates).

The middleware iterates the full namespace map without short-circuit (`resolved_namespace = ns  # no break` — `middleware_auth.py:73`) to prevent timing-based token discovery.

**Model warm-up is outside the `/search` timeout budget (S184).** The ~30 s budget (`SEARCH_TIMEOUT_SECONDS = 30.0` in `server/_search_budget.py`, imported by `routes_search.py` as `_SEARCH_TIMEOUT_SECONDS`) covers the search itself, not one-off model initialisation. `ModelEmbedder` and `ModelReranker` both build their PyTorch models on *first* use, so before entering `asyncio.wait_for` the handler awaits `pipeline.warmup_models()` (in `routes_search.search`, on both the fan-out and the single-collection branch — the latter passes the request's resolved embedder in) — previously that load happened *inside* the budget and could consume it, turning the first search after a cold start into a `504`. `Embedder.warmup()` / `Reranker.warmup()` are idempotent, single-flight, and bounded by their own timeout, so the call is a cheap no-op once the backend is warm. (A *failed* warm-up is not latched — S283 removed that behaviour; the next caller retries.) Both warm-ups' single-flight guarantee holds *under cancellation* (`Reranker.warmup()` since S288, `Embedder.warmup()` since S290, which gave the embedder the same structure once its own bounded caller arrived): the build runs in one shared `asyncio.Task` owned by the model's `WarmupCoordinator` (`warmup_coordinator.py`) and every caller only `await asyncio.shield(...)`s it, so a caller that abandons a bounded wait cancels its own wait and nothing else — the build keeps running and the next caller joins the same task instead of starting a second model build (the fan-out of bounded waits in S288 would otherwise spawn one duplicate build per abandoned caller; on the embedder the duplicates would additionally pin one executor thread each behind `ModelEmbedder._lock`). A settled task is dropped, so the S283 retry-on-next-caller behaviour is unchanged. Warm-up failure is non-fatal: `warmup_models` logs a WARNING (`warm-up: embedder failed; first search will pay the init cost` / `warm-up: reranker failed; …`) and the search proceeds. It distinguishes three outcomes per leg, because they call for different operator responses: this caller's bounded wait expiring (`still cold after waiting 0.5s … the build continues in the background`), the build blowing its **own** 300 s ceiling (`RerankerWarmupTimeout` / `EmbedderWarmupTimeout` → `build exceeded its own 300.0s limit`, and no promise of a background build), and any other failure. The dedicated exception types exist for exactly that: since 3.11 `asyncio.TimeoutError` *is* the builtin `TimeoutError`, so a socket `ETIMEDOUT` during a model download is otherwise indistinguishable from a ceiling. The app lifespan performs the same warm-up from a background task on **every** startup (also WARNING-on-failure, and never delaying the port binding), and `/ready` answers 503 until it completes, so a request arriving after readiness pays no load at all. `[database].eager_load_embedders = true` only extends that task to every per-collection embedder; a model outside its scope is still built on first use, inside this same out-of-budget `warmup_models()` call (S279).

**The flip side: the warm-up sits outside the budget.** Because the warm-up is awaited *before* `asyncio.wait_for`, a request that pays a cold build is not protected by `SEARCH_TIMEOUT_SECONDS` at all — it does not degrade to a `504`, it simply produces no response until the build finishes, which a client reads as a connection failure rather than a timeout. Mitigations shrink the window: `/ready` gates on the lifespan warm-up task (S279); **S281** makes the ingest tasks in `routes_jobs.py` absorb the wait themselves — `_job_warmup.await_models_warm()` awaits `pipeline.warmup_models()` (capped at `JOB_WARMUP_WAIT_SECONDS = 180.0`, best-effort, never failing the job) before an ingest job reaches `DONE`, so `collection add --wait` no longer reports success while the cross-encoder is cold — and since **S288 (import)** `routes_export._import_task` calls the same `await_models_warm(pipeline, job_id, embedder)` with the cached embedder serving the imported collection, so an import's `DONE` no longer leaves that embedder cold for the first single-collection search to degrade to FTS-only on (multi-collection search embeds with the global embedder, which the lifespan warm-up builds); and **S286** closes the remaining gap for the single-collection search path itself — when the ingest job's own ceiling was too short for a real cold build, the very next `/search` used to inherit the rest of that unbounded wait. `routes_search.py`'s single-collection handler now caps the reranker leg through `_search_budget.warmup_for_search(pipeline, embedder)`, which calls `warmup_models(embedder, reranker_timeout=RERANKER_WARMUP_WAIT_SECONDS, …)` (0.5 s) and, on timeout, passes `rerank=False` into `pipeline.search(...)`: the request answers with the fused vector+FTS ranking (no cross-encoder score) instead of blocking, and the cold build keeps running in its worker thread so later requests get the full reranked pipeline once it lands. **S288** closes the same gap on every **fan-out** path (`routes_search.search`'s multi-collection branch, the MCP `search` tool in `mcp.py`, and the `/v1` shim's catch-all model in `routes_openai_shim.py`), all of which used to call `pipeline.warmup_models()` with no `reranker_timeout` (or none at all) and so still paid the unbounded wait on a first search against a **pre-existing** collection right after a restart — no fresh ingest, no `/ready` probe. All three now cap the reranker leg the same way, through the single shared entry point `server/_search_budget.warmup_for_search(pipeline[, embedder])` (`RERANKER_WARMUP_WAIT_SECONDS = 0.5`) and thread the result through as `search_many(..., rerank=...)`; `search_many()` binds `reranker = self._reranker if rerank else None` once and gates every `rerank_candidates(...)` call site on it (RAG-Fusion fallback and merged pass, naive/local/global graph passes, and the standard global pass), falling back to the RRF-fused ranking ordered by `(-rrf_score, chunk_id)`. **S288 also closes the same hole inside single-collection graph modes**: `search(rerank=False)` now threads the flag into `_search_graph_mode`, `_search_ppr_mode` and `_search_local_mode` (and their `_search_standard` fallbacks), which previously reranked unconditionally. Every one of the six call sites (single-collection and fan-out, across REST, MCP and `/v1`) wraps its pipeline call in `run_within_budget(..., timeout=SEARCH_TIMEOUT_SECONDS)` — `search_many`'s internal fan-out timeout covers only the per-leg gathers — and `SearchBudgetExceeded` maps to the same `504 {"detail": "Search timed out"}` as `FanoutTimeoutError` (`{"code": "timeout"}` on MCP, `504 Request timeout.` on `/v1`). **S290** closes the last leg: `warmup_for_search` now also passes `embedder_timeout=EMBEDDER_WARMUP_WAIT_SECONDS` (0.5 s) and, when that expires, threads `fts_only=True` into `pipeline.search(...)` / `search_many(...)`. The premise that the embedder leg had nothing to degrade to was wrong — hybrid retrieval has an FTS leg, so the store skips its vector leg (`query_vector=None`) and the request answers with the FTS ranking instead of parking the connection for the whole cold model build (the `status=0` / no-response symptom on the first search after a restart). RAG Fusion and graph modes are skipped in that mode because they exist only to embed something. So is HyDE, and for the same reason one layer up: `HyDEGenerator.generate` ends in `embed_one` on the embedder serving the search — the very model that is still cold — so generating a hypothesis there would park the connection outside any budget. The surfaces that degrade to FTS-only — REST `/search` and MCP `search` — therefore pass the answer of the `warmup_for_search` they just ran into `server/_hyde.RequestHyDE.resolve` (`embedder_warm`), which skips generation while the embedder is cold (so a cold model is waited on once); the request reports `hyde_applied=false` plus the standard `'HyDE expansion failed'` warning and goes on to degrade like any unexpanded one. `search_with_context` and both `explain` surfaces have no FTS-only degrade — their retrieval embeds on the cold model anyway — so they do not skip HyDE for coldness: its embed and the retrieval share one wait for the build, bounded for HyDE by the budget below. Only an already-computed `query_vector` cancels the degrade, since it needs no embedding at all. As with the reranker, giving up on the wait does not abandon the build — it finishes in its worker thread and later requests get the full hybrid ranking back. **S582** bounds the *other* leg of HyDE, the one the warmth check never covered: generation itself is an LLM call ceilinged only by `[hyde].timeout_seconds`, which `config.py` accepts unclamped and unrelated to the search budget, so a llama-server that accepts the connection but never answers (still loading its model) parked `/search` for that whole duration outside any server-side budget — the same `status=0`/no-response symptom. `RequestHyDE.resolve` wraps the call in `_hyde.resolve_hyde_within_budget(generator.generate(...), timeout=...)` — every caller passes its module's `_SEARCH_TIMEOUT_SECONDS` — for every HyDE call site — REST `/search` and `/explain`, MCP `search`, `search_with_context` and `explain` — which cancels the generation on overrun and returns `None` — a window of its own, awaited before (never inside) the search budget, so on REST `/search` and MCP `search` a `hyde=true` request can take ~60 s before its `504`; `search_with_context` and both `explain` surfaces have no search budget, so only HyDE is capped there — reported, like every other HyDE failure, as `hyde_applied=false`, with the search running on the plain query. Only the surfaces with an `expansion_warning` field — REST `/search`, MCP `search` and `search_with_context` — also carry the `'HyDE expansion failed'` warning; the `explain` responses have no such field.

Successful job submissions (POST collection-add, POST reindex, POST ingest) return `202 Accepted` with a `JobResponse`; the job's eventual outcome is observed via `GET /jobs/{job_id}`.

`OSError` from other durable-write sites is handled differently and never reaches a route: `_safe_state_update`-routed progress/manifest writes and `manifest_remove_entry` are intentionally swallowed and logged (partial state recovers on the next sync pass), as is telemetry's best-effort `_append`. `OSError` at startup from `key_manager._generate_and_write` is intentionally **fatal** — the server cannot serve requests without a key file, so the operator must intervene. The full per-site error-propagation matrix is in [130_data_architecture_and_persistence.md](130_data_architecture_and_persistence.md#error-propagation-matrix) (see also [ADR-06](../ADRs/06_durable_state_writes_via_fsync.md)).

### JobStore persist failures and `POST /sync`

Every JobStore-driving route listed in the table answers the sanitized `500` (`JSONResponse({"detail": "internal error"}, status_code=500)`) for any exception from the durable write (`archon_search/_durable_io.py`). On a failed persist, `JobStore.create_job` (which every `create*` method funnels through) removes the job from memory and re-raises; since `atomic_write_json` can raise after its `os.replace` (parent-directory fsync), it first rewrites the file from memory (best-effort, `_rewrite_after_failed_persist`, which catches any `Exception` from that rewrite and logs it as one WARNING line without a traceback, so the original error is re-raised and a persistently failing disk adds no second traceback per persist; a non-`Exception` `BaseException` such as `asyncio.CancelledError` propagates instead), so the file's content matches memory unless that corrective rewrite fails too (durability across a crash is not guaranteed: after a failed directory fsync, a later fsync that succeeds does not prove the earlier rename reached the disk (`_durable_io.py`: do not retry fsync), so a crash can still leave either version) — only then can the job stay on disk until the next successful write of any job, and a restart before that write loads it.

`JobStore.update` (and thus `update_progress`) keeps the update in memory and re-raises: the next successful write of any job persists it, but a restart before that write loads the last-saved status (a `RUNNING` one, or a `CANCELLING` one cancelled while it was running, as `FAILED` `process_restart`; a `CANCELLING` one cancelled while still `PENDING`, as `CANCELLED`).

`JobStore.transition` is a compare-and-set claim, so a failed persist instead restores the old status in memory, makes the same best-effort corrective rewrite of the file, and re-raises — the claim never happened. The rollback restores the job's old `updated_at` too, so the corrective rewrite's age eviction can drop a terminal job whose old `updated_at` is more than 7 days old. Its callers: the scheduler (`JobScheduler._tick`) logs it (the traceback only on the first failure of a streak per job) and leaves the job `QUEUED` for a later tick — under a persistent write failure each failed claim thus costs one extra write attempt (the corrective rewrite) and one store WARNING line (no traceback) per tick; `POST /jobs/{id}/resume` and `DELETE /jobs/{id}` catch any exception and answer the sanitized `500` with the job unchanged; the ingest and reindex runners' `PENDING → RUNNING` claim (`_default_ingest_task`, `_default_ingest_task_with_lock`, `_reindex_task`) logs it and marks the job `FAILED` (`INGEST_FAILED_DETAIL` / `REINDEX_FAILED_DETAIL`; `_reindex_task` first clears `reindex_job_id` while it still names this job, and writes `CANCELLED` instead when a `DELETE /jobs/{id}` landed meanwhile) without running anything, since nothing else would ever run the `PENDING` job; `MaintenanceLoop._end_retry_chain` catches it per job — logged at WARNING with its traceback, the job stays `FAILED` and the next pass retries the expiry, while the pass goes on with the key's other jobs and the other paths.

`migrate_collection` (rewrite), `reindex_metadata`, `rebuild_communities` and `trigger_sync` (`POST /sync`) create their job `RUNNING` in one write (`create_migration(status=RUNNING)`; `create_sync` / `create_metadata_reindex` / `create_community_rebuild` always create `RUNNING`), never `QUEUED`: any failed persist is logged and answers the sanitized `500`, and spawns nothing, and no `QUEUED` row is left for the scheduler to run a migration its caller was told failed (or, for a `SyncJob`, that nothing would ever run).

`trigger_sync` answers `409` whenever `app.state.sync_lock` is held or another acquirer (the lifespan's startup sync) is already queued for it, so it never waits on the lock; once it holds the lock it marks every legacy `QUEUED`/`PENDING` `SyncJob` (only older servers wrote those; nothing runs them) `FAILED` with `JOB_SUPERSEDED_DETAIL` (best-effort) before creating its own (`JobStore._load` already failed a `QUEUED` one when the server started). It releases `app.state.sync_lock` on a failed-create `500`, and when spawning `_sync_task` fails it marks the already-saved job `FAILED` with `error` `"sync failed"` (best-effort, `_persist_job_status`) before releasing the lock and answering the same `500`; if that write fails too, it is logged, memory holds `FAILED` but the file keeps the `RUNNING` row until the next successful write of any job, and a restart before that reloads it as `FAILED` `process_restart` — an ingest-family crash marker that, with collections configured, suppresses the startup sync until a clean `POST /sync`. `_sync_task`'s own terminal writes (`DONE` / `FAILED`, or `CANCELLED` when server shutdown cancels the task) go through `_persist_job_status` too, so a failed one is logged, never escapes the task and never turns `DONE` into `FAILED` — with the same consequence: the file keeps the `RUNNING` row until the next successful write, and a restart before that re-arms the startup-sync suppression.

`add_collection` catches any job-creation exception (not only `OSError`), logs it, and undoes its earlier steps via `_rollback_add` (removes the config entry if still present with a best-effort save, deletes the stub meta row) before releasing the per-collection lock, then discards the lock entry (`SearchStore.discard_lock`). `ingest` acquires the per-collection lock before creating its job (a `503` lock timeout leaves no job behind) and, like `add_collection`, catches and logs any job-creation exception, releasing the lock. `reindex_collection`, `reindex_metadata` and `rebuild_communities` do the same through `_collection_job.create_collection_job`: it answers the `404` (no meta row) and the route's `409` duplicate guard at once from the meta row read before the lock, then under the collection lock re-reads the row and runs both again (`404` when a `DELETE` dropped the collection meanwhile; the lock entry is then discarded after the release), creates the job (any exception: logged as `<route>: failed to create the job for collection '<name>'`, sanitized `500`, no job) and writes the job's meta pointer, always releasing the lock (a lock timeout answers `503` `store_busy` with no job). A `CollectionLockNotHeldError` from that pointer write is a bug, not a failed write: it propagates (an unhandled `500`) after the job, which no task will run, is marked `FAILED` `"internal error"` (best-effort). `reindex_collection` answers `503` "service not ready" (embedder cache, pipeline or search store missing) before any of that, and marks its already-created job `FAILED` with `error` `REINDEX_FAILED_DETAIL` when the `reindex_job_id` write fails (`500`, logged as `Failed to record the reindex job <id> on collection <name>`); a failure of that `FAILED` write is logged too and the `500` still returned. `reindex_metadata` and `rebuild_communities` only log a failed pointer write (WARNING, with its traceback) and answer `202`: the job runs, but without its pointer the route's `409` guard cannot see it.

## Job error handling

Defined in `archon_search/types.py`:

- `JobStatus ∈ {PENDING, QUEUED, RUNNING, DONE, FAILED, FAILED_EXPIRED, CANCELLED, CANCELLING}`.
- An `IngestJob` carries `result: dict | None` on success and `error: str | None` on failure.
- The cancellation handshake is `{PENDING, RUNNING} → CANCELLING → CANCELLED`. `DELETE /jobs/{id}` accepts either active origin state — `_ACTIVE_STATUSES = {JobStatus.RUNNING, JobStatus.PENDING}` (`routes_jobs.py`, applied by `delete_job`); the runner then observes `CANCELLING` and writes `CANCELLED`. The ingest and reindex runners (`routes_jobs.py` `_default_ingest_task`, `_default_ingest_task_with_lock`, `_reindex_task`) claim `RUNNING` with `transition({PENDING}, RUNNING)`, so a cancel that lands before the claim (for `_reindex_task`, also while its embedder loads, even if that load then fails) ends `CANCELLED` with no ingest and no model promotion, and a failed persist of that claim marks the job `FAILED` — for an ingest always (the failed claim raises into the runner's exception handler), for `_reindex_task` `CANCELLED` instead when a cancel landed meanwhile. `_reindex_task` clears `reindex_job_id` (while it still names this job) before every `CANCELLED` / `FAILED` write, so a client that sees `CANCELLED` can start a new reindex. A `RUNNING` reindex cancelled during its ingest ends `CANCELLED` without promoting its model (`FAILED` if the ingest fails); one cancelled after the ingest, during the model promotion, ends `CANCELLED` with the model already promoted — `DONE` is never written over `CANCELLING`. Only the lifespan shutdown cancels a runner task: the ingest runners catch that `asyncio.CancelledError` and write `CANCELLED`, while the import runner lets it propagate and leaves the job `RUNNING`, so crash recovery marks it `FAILED` (`process_restart`) and `POST /jobs/{id}/resume` can continue it from its checkpoint. No sync can be cancelled: `DELETE` on a non-terminal `SyncJob` — the startup sync's or a manual `POST /sync` one, legacy `QUEUED`/`PENDING` rows included — answers `409` `{"detail": "a sync cannot be cancelled"}` and leaves the job unchanged (a terminal one answers the idempotent `200`), so a manual sync ends `DONE` or `FAILED`, and `CANCELLED` only when server shutdown cancels `_sync_task`.

Job runners catch their own exceptions and write a short message into `error`; the next `GET /jobs/{job_id}` returns the terminal state. The export and import runners (`routes_export.py`) write a fixed, sanitized message for any unexpected exception — `EXPORT_FAILED_DETAIL` / `IMPORT_FAILED_DETAIL`, the original logged server-side — and otherwise write only text archon-search builds itself: an import refusal (`ArchiveRejectedError` from `jobs/export_archive.py` — schema-version or embedding-model mismatch, existing collection, or a `force_overwrite` drop refused because another job may still write the collection or the collection lock was not acquired in time — `force_overwrite refused: …`, `OVERWRITE_REFUSED_PREFIX`, the job ends `FAILED` unclaimed and drops nothing; a `manifest.json` that is not a regular file, not UTF-8 JSON (oversized integers and nesting past the parser's recursion limit included), not a JSON object, or missing required keys; `Corrupt line N: not valid UTF-8 JSON` / `Corrupt line N: not a JSON object`, a corrupt vector or malformed document named by its line; archive values are quoted truncated, never a library's exception text), the `PathUnsafeError` reason code (`unsafe_tar_member`), or `EMBEDDER_NOT_READY_DETAIL` for a still-loading embedder (retryable via `POST /jobs/{id}/resume`). Any other manifest or archive read failure in the job — a tarfile/gzip error, an `OSError` — is unexpected and reports `IMPORT_FAILED_DETAIL`. The import route and the MCP `import_collection` tool follow the same rule through `export_archive.manifest_error_detail`: the `ArchiveRejectedError` message or `PathUnsafeError` reason code, else `INVALID_MANIFEST_DETAIL` for any other `ValueError`; an archive that does not open as a tar.gz reports `INVALID_ARCHIVE_DETAIL`. The other job runners follow the same rule: an unexpected exception writes a fixed `*_FAILED_DETAIL` text (`INGEST_FAILED_DETAIL` / `REINDEX_FAILED_DETAIL` in `routes_jobs.py`, `MIGRATION_FAILED_DETAIL` / `METADATA_REINDEX_FAILED_DETAIL` in `routes_collections.py`, `COMMUNITY_REBUILD_FAILED_DETAIL` in `routes_graph.py`, `DISPATCH_FAILED_DETAIL` in `jobs/scheduler.py`), and only curated exceptions (`NoGraphNodesError`, `NoPendingRewriteMigrationError`, and `IngestPathNotFoundError` — `routes_jobs.py`, `INGEST_PATH_NOT_FOUND_PREFIX` plus the caller's `path` as submitted) surface their own message, logged as a WARNING without a traceback. `_reindex_task` also writes `not a ReindexJob` when its job id names another job type, and crash recovery (`JobStore._load`) writes `process_restart` for any job left `RUNNING`/`CANCELLING` (a `CANCELLING` job whose cancel landed while it was still `PENDING`, `cancelled_before_start`, never ran and becomes `CANCELLED`), and the fixed `NOT_STARTED_BEFORE_RESTART_DETAIL` = `"never started; the server restarted before it ran"` (`jobs/store.py`) for a base ingest or reindex job left `PENDING`. A failure to persist any of these terminal statuses is logged with its traceback and suppressed (`routes_jobs._persist_job_status`). The rebuild-communities, reindex-metadata and sync routes write the fixed `JOB_SUPERSEDED_DETAIL` = `"never started; superseded by a newer request"` (`routes_jobs.py`) when they supersede a legacy, never-run `QUEUED`/`PENDING` job of their kind. `CommunityDependencyError` (missing `leidenalg`/`igraph`) records the fixed `COMMUNITY_DEPENDENCY_DETAIL` (`community_builder.py`), its install-command message logged as a WARNING only. The maintenance loop's per-policy `last_error` (`GET /status`) uses the same pattern (`*_FAILED_DETAIL` in `jobs/maintenance_loop.py`), and so does its failed-ingest retry: when the injected `dispatch_retry` callback raises while starting a re-enqueued retry job, `MaintenanceLoop._start_retry_job` logs the exception at ERROR with its traceback and writes the job `FAILED` (best-effort) with the fixed `RETRY_DISPATCH_FAILED_DETAIL` = `"maintenance retry could not be started; see the server log for details"`; when that write fails too (also logged with its traceback), the collection's `last_error` (`GET /status`) gets the same text; the pass continues either way. A retry waiting for its collection lock (`routes_jobs._run_maintenance_retry`) has no time limit and so no lock-timeout failure; cancelled while it waits (shutdown), it writes nothing unless a client already requested its cancel — then `CANCELLING → CANCELLED`, written only while the job is still `CANCELLING`, so a settled job is never overwritten; otherwise the job stays `PENDING`, and the next start's recovery marks it `FAILED` with `NOT_STARTED_BEFORE_RESTART_DETAIL` (retryable, as the next attempt). A `POST /sync` job (`routes_sync.py`) fails only with the fixed `sync failed` (`_SYNC_FAILED_DETAIL`, also written by `trigger_sync` when its task cannot be spawned); when it completes, each collection whose sync raised appears in its `result["errors"]` as `collection_sync_failed_detail(name)` (`sync.py`, `sync of collection '<name>' failed; see the server log for details` — the same text as that collection's `error` on `GET /status` / `GET /indexing-state`), the exception logged at ERROR with its traceback. A collection the sync could not lock within `INGEST_LOCK_TIMEOUT_S` appears there as `collection_sync_busy_detail(name)` (`sync of collection '<name>' skipped: the collection is busy with another write; the next sync retries it`; nothing was written), and a collection gone from the config that the sync did not drop because a job or a registered writer may still write it, or its lock was not acquired, as `collection_drop_deferred_detail(name)` (`collection '<name>' is no longer configured but was not removed: it is busy; the next sync retries`; it stays in the sync manifest), each logged at WARNING; neither is a `FAILED` state. As of this writing, job runners do not push records into telemetry — telemetry is the request-path concern only. This is an unenforced convention (no test or lint barrier), not a contract: there is currently no call to `TelemetryEntry` from `archon_search/jobs/` or the default ingest task.

## Telemetry error contract

`telemetry/entry.py` defines a closed enum (`ErrorKind`) and a `from_error` factory that requires a non-`ok` status. The model is frozen and `extra="forbid"`, so callers cannot smuggle in additional fields. The factory takes no `query` parameter — by construction, raw query strings cannot end up in a telemetry record. This is reaffirmed in [150_security_and_privacy_architecture.md](150_security_and_privacy_architecture.md).

The mapping from internal exception to `ErrorKind` is the responsibility of the route handler when it calls `TelemetryEntry.from_error(...)`. The set is intentionally small and stable; new categories require a code change to the enum, not a runtime tag.

## What is intentionally NOT done

- Two (and only two) global FastAPI exception handlers exist, both registered in `server/app.py::create_app()`: `@app.exception_handler(EmbedderNotReadyError)` (see the row above — uniform 503 across every plain HTTP route not already handling it locally) and, only when `openai_shim.enabled = true`, `@app.exception_handler(RequestValidationError)` (reshapes 422s under `/v1/*` into the OpenAI error envelope; delegates to FastAPI's default handler for every other path). Beyond those two, there is no exception handler that rewrites *unknown* exceptions into rich JSON. An *unmapped* exception still becomes a plain `500` — preferable to leaking internals. Note that `OSError` from JobStore-driving route writes is **not** unmapped: it is caught explicitly and mapped to the `{"detail": "internal error"}` `500` envelope (see the row above), so that path is a deliberate, mapped `500` rather than a default re-raise.
- No retry middleware. The CLI and the watcher have their own retry semantics; the HTTP layer is a single attempt.
- No *global* structured-error envelope across all REST responses — the shape varies by route (see the table above for what each emits): a plain-string `detail` (e.g. the `400` "path is unsafe" on `POST /ingest`); a nested `{"detail": {"code", "message"}}` object (e.g. the `413` on `POST /ingest` and `graph_communities_not_built` on `/search`); or a string `detail` with a sibling top-level `code` (e.g. the `503` metadata-store error on `/search`). The `detail` value plus the HTTP status is the contract per route; breaking changes go in `BREAKING.md`.
