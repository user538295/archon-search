# Error Handling Strategy

Errors in archon-search are classified at three layers: configuration, HTTP request handling, and background jobs. Each layer has a distinct contract — config fails the process, HTTP returns a typed status, jobs persist a terminal `FAILED` state. Telemetry only ever records a coarse `error_kind` from a fixed enum, never an exception message.

See also: [100_system_architecture_overview.md](100_system_architecture_overview.md), [120_services_and_integration_architecture.md](120_services_and_integration_architecture.md), [160_operational_readiness_monitoring_and_reliability.md](160_operational_readiness_monitoring_and_reliability.md).

## Principles

1. **Fail fast at config load.** Invalid TOML, out-of-range integers, wrong types → `ConfigError` raised by `config.py::load_config`. The process does not start.
2. **Propagate typed exceptions.** Domain layers raise `ValueError`, `KeyError`, `RuntimeError`, `NotImplementedError`, `ConfigError`. (`asyncio.TimeoutError` arises in the request path from `asyncio.wait_for(...)` in `routes_route.py`; it is not a typed domain exception raised by lower layers.) Route handlers translate these to HTTP status codes — exceptions never leak as raw 500s when a typed mapping exists. Pipeline failures on `/search` surface as HTTP 500 with a plain-text body `Internal Server Error` (Content-Type `text/plain`) — the route bare-re-raises and Starlette's `ServerErrorMiddleware` renders the default response; there is no JSON envelope. A timeout returns HTTP 504 with `{"detail": "Search timed out"}` after ~30s, matching the timeout-+-telemetry-+-504 shape of `routes_route.py` (note: the detail string and log `event_type` differ — `/route` uses `routing timed out` / `route_timeout`, `/search` uses `Search timed out` / `search_timeout`).
3. **Coarse, closed-set telemetry classification.** When telemetry records an error, it uses `ErrorKind ∈ {empty_query, slot_out_of_range, timeout, internal_error, validation_error, other}` (see `telemetry/entry.py::ErrorKind`). Never store exception messages, stack traces, or input strings.
4. **Auth failures are uniform.** The auth middleware returns `401` with `WWW-Authenticate: Bearer` and no body — same response for missing header, wrong scheme, and bad token. (Exception: a token that *does* resolve to a namespace but fails `_validate_namespace` returns `500`, not `401`; see "Authentication errors" below.)
5. **Jobs record terminal failure state.** A failed background job transitions to `JobStatus.FAILED` with a short `error` string; the HTTP layer remains `202` at submission time.

## Configuration errors

`archon_search/config.py::ConfigError` is raised for:

- TOML parse failure (`Failed to parse {path}: {exc}`)
- Wrong type — per-type messages, not slash-joined: `Expected integer for '{field}', got {type}` (`config.py:98`), `Expected float for '{field}', got {type}` (`config.py:105`), `Expected boolean for '{field}', got {type}` (`config.py:110`)
- Out-of-range / non-empty checks:
  - `port must be between 1 and 65535` (`config.py:137`)
  - `chunk_size must be > 0` (`config.py:150`)
  - `top_k_retrieve must be > 0` (`config.py:161`)
  - `top_k_return must be > 0` (`config.py:166`)
  - `routing_shortlist_size must be > 0` (`config.py:173`)
  - `routing_confidence_threshold must be in [0.0, 1.0]` (`config.py:178`)
  - `[telemetry].retention_days must be >= 1` (`config.py:207`)
  - `[telemetry].log_dir must be a non-empty string` (`config.py:221`)
  - `[ingest].max_file_mb must be >= 0, got {raw}` — negative values raise `ConfigError`; `0` (the default) is valid and disables the size guard entirely. **E0d**: `IngestConfig` (`config.py`)
  - `[ingest].max_tasks_per_child must be >= 1, got {raw}` (`config.py`, `_apply_toml`, `[ingest].max_tasks_per_child` branch) — `0` is rejected too: it would mean "never recycle the docling parse worker", which is the unbounded-memory behaviour the key exists to prevent. Non-integers (and `bool`, rejected explicitly despite being an `int` subclass) raise `Expected integer for '[ingest].max_tasks_per_child', got {type}` (same branch) rather than being coerced.
- Invalid `[namespaces]` shape (non-string key or value)

`[telemetry].export_enabled = true` is **not** raised — `config.py:213–215` emits a warning and silently coerces to `false`. This is the documented v1 contract: external export is reserved and ignored, not rejected.

`ConfigError` is caught explicitly by the `archon-search start` subcommand (`cli/start.py:16-23`), which prints `Error: {exc}` to stderr and exits with `SystemExit(1)`. Other entry points (e.g. importing the server module directly in tests) propagate the exception per Python defaults — "the process does not start" is enforced by the `start` path, not centrally.

## Authentication errors

`server/middleware_auth.py::APIKeyMiddleware`:

- Missing `Authorization` header, wrong scheme, or token that fails `secrets.compare_digest` against both the per-namespace key map and the default API key → `401`, header `WWW-Authenticate: Bearer`, empty body.
- Exempt paths (`/health`, `/ready`, `/docs`, `/openapi.json`, `/redoc`) bypass the middleware entirely.
- If a resolved namespace fails `_validate_namespace`, the middleware logs and returns `500` (defensive — should not occur if config validates).

The middleware iterates the full namespace map without short-circuit (`resolved_namespace = ns  # no break` — `middleware_auth.py:43`) to prevent timing-based token discovery.

**Model warm-up is outside the `/search` timeout budget (S184).** The ~30 s budget (`_SEARCH_TIMEOUT_SECONDS = 30.0` in `routes_search.py`) covers the search itself, not one-off model initialisation. `ModelEmbedder` and `ModelReranker` both build their ONNX models on *first* use, so before entering `asyncio.wait_for` the handler awaits `pipeline.warmup_models()` (in `routes_search.search`, on both the fan-out and the single-collection branch — the latter passes the request's resolved embedder in) — previously that load happened *inside* the budget and could consume it, turning the first search after a cold start into a `504`. `Embedder.warmup()` / `Reranker.warmup()` are idempotent, single-flight, and bounded by their own timeout, so the call is a cheap no-op once the backend is warm. (A *failed* warm-up is not latched — S283 removed that behaviour; the next caller retries.) Both warm-ups' single-flight guarantee holds *under cancellation* (`Reranker.warmup()` since S288, `Embedder.warmup()` since S290, which gave the embedder the same structure once its own bounded caller arrived): the build runs in one shared `asyncio.Task` created under `_warmup_lock` and every caller only `await asyncio.shield(...)`s it, so a caller that abandons a bounded wait cancels its own wait and nothing else — the build keeps running and the next caller joins the same task instead of starting a second ONNX build (the fan-out of bounded waits in S288 would otherwise spawn one duplicate build per abandoned caller; on the embedder the duplicates would additionally pin one executor thread each behind `ModelEmbedder._lock`). A settled task is dropped, so the S283 retry-on-next-caller behaviour is unchanged. Warm-up failure is non-fatal: `warmup_models` logs a WARNING (`warm-up: embedder failed; first search will pay the init cost` / `warm-up: reranker failed; …`) and the search proceeds. It distinguishes three outcomes per leg, because they call for different operator responses: this caller's bounded wait expiring (`still cold after waiting 0.5s … the build continues in the background`), the build blowing its **own** 300 s ceiling (`RerankerWarmupTimeout` / `EmbedderWarmupTimeout` → `build exceeded its own 300.0s limit`, and no promise of a background build), and any other failure. The dedicated exception types exist for exactly that: since 3.11 `asyncio.TimeoutError` *is* the builtin `TimeoutError`, so a socket `ETIMEDOUT` during a model download is otherwise indistinguishable from a ceiling. The app lifespan performs the same warm-up from a background task on **every** startup (also WARNING-on-failure, and never delaying the port binding), and `/ready` answers 503 until it completes, so a request arriving after readiness pays no load at all. `[database].eager_load_embedders = true` only extends that task to every per-collection embedder; a model outside its scope is still built on first use, inside this same out-of-budget `warmup_models()` call (S279).

**The flip side: the warm-up sits outside the budget.** Because the warm-up is awaited *before* `asyncio.wait_for`, a request that pays a cold build is not protected by `_SEARCH_TIMEOUT_SECONDS` at all — it does not degrade to a `504`, it simply produces no response until the build finishes, which a client reads as a connection failure rather than a timeout. Mitigations shrink the window: `/ready` gates on the lifespan warm-up task (S279); **S281** makes the ingest tasks in `routes_jobs.py` absorb the wait themselves — `_await_models_warm()` awaits `pipeline.warmup_models()` (capped at `_INGEST_WARMUP_WAIT_SECONDS = 180.0`, best-effort, never failing the job) before an ingest job reaches `DONE`, so `collection add --wait` no longer reports success while the cross-encoder is cold; and **S286** closes the remaining gap for the single-collection search path itself — when the ingest job's own ceiling was too short for a real cold build, the very next `/search` used to inherit the rest of that unbounded wait. `routes_search.py`'s single-collection handler now caps the reranker leg of `warmup_models(embedder, reranker_timeout=_RERANKER_WARMUP_WAIT_SECONDS)` (0.5 s) and, on timeout, passes `rerank=False` into `pipeline.search(...)`: the request answers with the fused vector+FTS ranking (no cross-encoder score) instead of blocking, and the cold build keeps running in its worker thread so later requests get the full reranked pipeline once it lands. **S288** closes the same gap on every **fan-out** path (`routes_search.search`'s multi-collection branch, the MCP `search` tool in `mcp.py`, and the `/v1` shim's catch-all model in `routes_openai_shim.py`), all of which used to call `pipeline.warmup_models()` with no `reranker_timeout` (or none at all) and so still paid the unbounded wait on a first search against a **pre-existing** collection right after a restart — no fresh ingest, no `/ready` probe. All three now cap the reranker leg the same way, through the single shared entry point `server/_search_budget.warmup_for_search(pipeline[, embedder])` (`RERANKER_WARMUP_WAIT_SECONDS = 0.5`) and thread the result through as `search_many(..., rerank=...)`; `search_many()` binds `reranker = self._reranker if rerank else None` once and gates every `rerank_candidates(...)` call site on it (RAG-Fusion fallback and merged pass, naive/local/global graph passes, and the standard global pass), falling back to the RRF-fused ranking ordered by `(-rrf_score, chunk_id)`. **S288 also closes the same hole inside single-collection graph modes**: `search(rerank=False)` now threads the flag into `_search_graph_mode`, `_search_ppr_mode` and `_search_local_mode` (and their `_search_standard` fallbacks), which previously reranked unconditionally. Every one of the six call sites (single-collection and fan-out, across REST, MCP and `/v1`) wraps its pipeline call in `run_within_budget(..., timeout=SEARCH_TIMEOUT_SECONDS)` — `search_many`'s internal fan-out timeout covers only the per-leg gathers — and `SearchBudgetExceeded` maps to the same `504 {"detail": "Search timed out"}` as `FanoutTimeoutError` (`{"code": "timeout"}` on MCP, `504 Request timeout.` on `/v1`). **S290** closes the last leg: `warmup_for_search` now also passes `embedder_timeout=EMBEDDER_WARMUP_WAIT_SECONDS` (0.5 s) and, when that expires, threads `fts_only=True` into `pipeline.search(...)` / `search_many(...)`. The premise that the embedder leg had nothing to degrade to was wrong — hybrid retrieval has an FTS leg, so the store skips its vector leg (`query_vector=None`) and the request answers with the FTS ranking instead of parking the connection for the whole cold ONNX build (the `status=0` / no-response symptom on the first search after a restart). RAG Fusion and graph modes are skipped in that mode because they exist only to embed something. So is HyDE, and for the same reason one layer up: `resolve_hyde_vector` runs *before* `warmup_for_search` on both search call sites, and `HyDEGenerator.generate` ends in `embed_one` on `pipeline._global_embedder` — the very model that is still cold — so generating a hypothesis there would park the connection outside any budget. The routes therefore pass `may_embed=partial(_search_budget.hyde_may_embed, pipeline)` into `resolve_hyde_vector`, which skips generation and returns `(None, False)` while the embedder is cold; the request reports `hyde_applied=false` plus the standard `'HyDE expansion failed'` warning and goes on to degrade like any unexpanded one. Only an already-computed `query_vector` cancels the degrade, since it needs no embedding at all. As with the reranker, giving up on the wait does not abandon the build — it finishes in its worker thread and later requests get the full hybrid ranking back.

Successful job submissions (POST collection-add, POST reindex, POST ingest) return `202 Accepted` with a `JobResponse`; the job's eventual outcome is observed via `GET /jobs/{job_id}`.

`OSError` from other durable-write sites is handled differently and never reaches a route: `_safe_state_update`-routed progress/manifest writes and `manifest_remove_entry` are intentionally swallowed and logged (partial state recovers on the next sync pass), as is telemetry's best-effort `_append`. `OSError` at startup from `key_manager._generate_and_write` is intentionally **fatal** — the server cannot serve requests without a key file, so the operator must intervene. The full per-site error-propagation matrix is in [130_data_architecture_and_persistence.md](130_data_architecture_and_persistence.md#error-propagation-matrix) (see also [ADR-06](../ADRs/06_durable_state_writes_via_fsync.md)).

## Job error handling

Defined in `archon_search/types.py`:

- `JobStatus ∈ {PENDING, RUNNING, DONE, FAILED, CANCELLED, CANCELLING}`.
- An `IngestJob` carries `result: dict | None` on success and `error: str | None` on failure.
- The cancellation handshake is `{PENDING, RUNNING} → CANCELLING → CANCELLED`. `DELETE /jobs/{id}` accepts either active origin state — `_ACTIVE_STATUSES = {JobStatus.RUNNING, JobStatus.PENDING}` (`routes_jobs.py:24, 138-148`); the runner then observes `CANCELLING` and writes `CANCELLED` (or `asyncio.CancelledError` propagates and the runner writes `CANCELLED` directly).

Job runners catch their own exceptions and write a short message into `error`; the next `GET /jobs/{job_id}` returns the terminal state. As of this writing, job runners do not push records into telemetry — telemetry is the request-path concern only. This is an unenforced convention (no test or lint barrier), not a contract: there is currently no call to `TelemetryEntry` from `archon_search/jobs/` or the default ingest task.

## Telemetry error contract

`telemetry/entry.py` defines a closed enum (`ErrorKind`) and a `from_error` factory that requires a non-`ok` status. The model is frozen and `extra="forbid"`, so callers cannot smuggle in additional fields. The factory takes no `query` parameter — by construction, raw query strings cannot end up in a telemetry record. This is reaffirmed in [150_security_and_privacy_architecture.md](150_security_and_privacy_architecture.md).

The mapping from internal exception to `ErrorKind` is the responsibility of the route handler when it calls `TelemetryEntry.from_error(...)`. The set is intentionally small and stable; new categories require a code change to the enum, not a runtime tag.

## What is intentionally NOT done

- Two (and only two) global FastAPI exception handlers exist, both registered in `server/app.py::create_app()`: `@app.exception_handler(EmbedderNotReadyError)` (see the row above — uniform 503 across every plain HTTP route not already handling it locally) and, only when `openai_shim.enabled = true`, `@app.exception_handler(RequestValidationError)` (reshapes 422s under `/v1/*` into the OpenAI error envelope; delegates to FastAPI's default handler for every other path). Beyond those two, there is no exception handler that rewrites *unknown* exceptions into rich JSON. An *unmapped* exception still becomes a plain `500` — preferable to leaking internals. Note that `OSError` from JobStore-driving route writes is **not** unmapped: it is caught explicitly and mapped to the `{"detail": "internal error"}` `500` envelope (see the row above), so that path is a deliberate, mapped `500` rather than a default re-raise.
- No retry middleware. The CLI and the watcher have their own retry semantics; the HTTP layer is a single attempt.
- No *global* structured-error envelope across all REST responses — the shape varies by route (see the table above for what each emits): a plain-string `detail` (e.g. the `400` "path is unsafe" on `POST /ingest`); a nested `{"detail": {"code", "message"}}` object (e.g. the `413` on `POST /ingest` and `graph_communities_not_built` on `/search`); or a string `detail` with a sibling top-level `code` (e.g. the `503` metadata-store error on `/search`). The `detail` value plus the HTTP status is the contract per route; breaking changes go in `BREAKING.md`.
