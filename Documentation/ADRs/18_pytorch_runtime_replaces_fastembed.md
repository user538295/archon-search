## Context

The wizard writes `providers = ["CoreMLExecutionProvider"]` on Apple Silicon, and measurement on an M4 Pro (2026-10-23) showed that setting makes embedding **slower** than CPU, not faster:

- ONNX Runtime splits the e5-large graph into 146 CoreML partitions because its input shapes are dynamic; 8×128 tokens took 0.51–0.95 s against 0.34 s on CPU. A 12×512 batch got slower on every call (12 s, 71 s, 96 s, 127 s) at a 32 GB peak resident size.
- The Apple GPU is reachable through ONNX Runtime only with fixed input shapes, the `MLProgram` format and a compile cache: 0.11 s per 8×128 batch, but 220–366 s of compilation per shape, one compiled copy per shape, and fastembed 0.9.0 cannot set those session options (`fastembed/common/onnx_model.py` exposes only `enable_cpu_mem_arena`; its README offers GPU only through the CUDA package `fastembed-gpu`).
- The Neural Engine was 1.2× faster than CPU (0.28 s), the GPU 3.1×.

PyTorch on the Apple GPU (`mps`) matched the fixed-shape ONNX result with no compilation and any input shape. PyTorch is already a declared dependency (`pyproject.toml:34-35`), already runs the graph model in the server (`prose_extraction_backend.py`), and `torch_device.py` already maps `CoreMLExecutionProvider` to `mps`. The ONNX provider vocabulary is therefore reused for a runtime that is not ONNX.

ADR 02 rejected sentence-transformers because it "pulls a full PyTorch runtime" (`02_fastembed_for_dense_embeddings.md:51-53`). That rationale no longer holds: PyTorch is installed anyway (docling requires it).

## Decision

**Run the embedder and reranker on PyTorch (`transformers` model classes, `tokenizers` for tokenization), selected per host by one setting, `[database].device = "auto" | "cpu" | "mps" | "cuda"`. Remove fastembed and the ONNX provider layer.** `onnxruntime` stays in the environment for OCR (RapidOCR) and magika, but archon no longer configures it.

Binding rules, each measured (evidence below):

1. **Parity is the contract.** Stored vectors and exposed reranker scores must not change. The frozen reference is `tests/fixtures/runtime_parity/`. Thresholds: embedder cosine at least 0.99994 with the vector norm unchanged; reranker absolute difference below 1e-4.
2. **A model is a spec, not a name.** Each supported model is an entry in a registry carrying its weights repo, pinned revision, `max_length`, pooling, normalization, dimension and architecture. Nothing is inferred from `tokenizer.model_max_length` or sentence-transformers defaults.
3. **Raw `tokenizers`, not `AutoTokenizer`.** The `tokenizer.json` files are byte-identical to fastembed's; `transformers` 5.0–5.2 drops a separator in XLM-R pair encoding and `bge-reranker-base` differs on trailing whitespace through `AutoTokenizer`.
4. **fp32 everywhere.** `dtype=torch.float32` explicitly: the Jina checkpoint is bf16 and loads as bf16 by default, which changed scores by 1e-2 and ran 10–20× slower on CPU.
5. **No `trust_remote_code`.** The Jina reranker's repository code fails on `transformers` 5.0–5.20 (two independent breakages). Its checkpoint is converted in memory (fused `Wqkv` split into query, key and value; norms and MLP renamed) into stock `XLMRobertaForSequenceClassification`; this matched fastembed to 5.6e-6 on CPU, runs on `transformers` 4.57 and 5.20, and needs no `einops`.
6. **Length-sorted, token-budgeted batches** (default 4096 padded tokens per batch), restoring input order on return.
7. **Multilingual embedders are not normalized and keep their per-model truncation.** `paraphrase-multilingual-MiniLM-L12-v2` truncates at 128 tokens, `paraphrase-multilingual-mpnet-base-v2` at 512; `multilingual-e5-large` vectors have norm about 29. The chunk store searches with LanceDB's default squared-L2 metric and no vector index (`store.py:3306`, `store.py:2257`), so vector length is part of the stored contract.
8. **Supported set.** The registry (`model_specs.py`) holds exactly the models verified against frozen fastembed outputs: 19 embedders (the six profile models and 13 more) and 5 rerankers (the four profile ones and `bge-reranker-v2-m3`). Any other name fails validation with `unsupported model '<name>'; supported: …`; adding a model means adding a spec and its golden vectors. Quantized ONNX aliases (`…-Q`, `…-int8`) are not separate names.

## Consequences

### Positive

- Apple GPU embedding works, measured (passages per second, 32 passages of 60–200 words; fastembed CPU / PyTorch CPU / PyTorch `mps`): bge-small 52.8 / 133 / 329, bge-base 16.7 / 47.5 / 108, bge-large 10.4 / 14.4 / 32.6, multilingual-MiniLM 74 / 237 / 643, mpnet 19.8 / 30.3 / 82.9, e5-large 7.7 / 13.0 / 27.5. Reranking 45 pairs: MiniLM-L6 0.298 / 0.185 / 0.080 s, MiniLM-L12 0.564 / 0.357 / 0.147 s, bge-reranker-base 1.556 / 1.130 / 0.531 s, Jina 1.789 / 1.135 / 0.529 s. On realistic chunks (256 chunks, 413 tokens on average) e5-large ran 20.1 passages/s on `mps` against 9.2 on CPU. These numbers came from a loaded machine, so they are conservative.
- One runtime for embedder, reranker and graph model: the ONNX provider fallback (`onnx_providers.py`, 232 lines), the CoreML/CUDA wizard probes, the split-provider config, the `onnxruntime-gpu` Docker arm and the CUDA-major consistency check go away. CUDA works through the CUDA PyTorch build the wizard already installs for docling.
- Existing indexes stay valid: no re-embedding is needed, because rule 1 holds for every registry model (measured on 2026-10-25, below).
- `validate_embedding_model` stops downloading a model to learn its dimension; the spec carries it.

### Negative / Tradeoffs

- **Supported models shrink from 41 embedders and 8 rerankers to 19 and 5, and every other name is rejected.** Classified from each model's `config.json` (2026-10-24): of the 41 embedders, 19 are plain BERT, XLM-R, ModernBERT or Qwen3 models (the 6 profile models plus 13 more) that could be added one spec at a time with golden vectors frozen from fastembed beforehand, and all 19 were (the 6 profile models on 2026-10-24, the other 13 on 2026-10-25); 2 are the text towers of image-text models (CLIP, SigLIP); 13 need the vendor's custom modeling code (`nomic-embed-text-*`, six `jina-embeddings-v2-*`, `jina-embeddings-v3`, `jina-clip-v1`, `stella`, `snowflake-arctic-embed-m-long`); 7 are static word-vector tables (`potion-*`), ONNX-only or gated repositories. Of the 8 rerankers, 5 are plain (the three profile ones, `bge-reranker-v2-m3` and its int8 variant), Jina v2 multilingual works through the in-memory conversion, and the two English `jina-reranker-v1-*` need custom code. The registry therefore holds 5 rerankers: the three plain profile ones, `bge-reranker-v2-m3` and Jina v2 multilingual; the `-int8` and `-Q` variants are quantized builds of supported models, not separate names. A collection pinned to an unsupported model fails to load: this is a breaking change (`BREAKING.md`).
- **CPU speed on Linux x86_64 and Windows is unmeasured, and the Linux arm64 run of the gate FAILS for three models (decision recorded 2026-10-25: keep PyTorch).** On this Mac PyTorch CPU was 1.4–3.2× faster than fastembed (embedders and rerankers), but ONNX Runtime and PyTorch CPU kernels differ per platform. The gate is `scripts/bench_runtime.py` with the manual workflow `archon-search-runtime-bench.yml` (Plan Task 6.1); the pass rule is PyTorch CPU at least 0.9× fastembed for every compared model. Its final run (2026-10-25, `--runtime both`: the two runtimes alternate in one process, best of 10 rounds) was inside the `linux/arm64` CPU image (Docker Desktop VM on an M4 Pro, 14 vCPUs, torch 2.14.1+cpu, onnxruntime 1.31.0, fastembed 0.9.0; **not** x86_64, which was not available) on a host that other work shared. Seven of ten models pass (ratio 1.04–1.61: `bge-large-en-v1.5` 1.04, `paraphrase-multilingual-mpnet-base-v2` 1.23, `multilingual-e5-large` 1.20, `ms-marco-MiniLM-L-6-v2` 1.30, `ms-marco-MiniLM-L-12-v2` 1.38, `bge-reranker-base` 1.42, `jina-reranker-v2-base-multilingual` 1.61). Three fail: `BAAI/bge-small-en-v1.5` 0.77 (63.1 against 81.9 passages/s), `BAAI/bge-base-en-v1.5` 0.89 (22.8 against 25.7) and `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` 0.73 (105.7 against 145.6). Earlier single-runtime runs of the same image gave 0.66–0.90 for the two models they flagged, depending on host load: a ratio next to 0.9 is noise on a shared host, which is why the script now alternates the runtimes. Measured cause (replaces the earlier "fused graph" hypothesis): fastembed's `Qdrant/*-onnx-Q` graphs for these models store FLOAT16 weights (149 FLOAT16 initializers, no FLOAT weights) and ONNX Runtime executes their MatMuls in native fp16 on arm64 NEON: 1409 GFLOP/s for a 4096×768 by 768×3072 product against 803 for PyTorch fp32 and 658 for ORT fp32. fp32 is a binding rule above (rule 4), so this cannot be closed within the decision, and none of the levers tried (GELU variant, attention implementation, thread count, token budget, batching) gave a consistent gain. **Decision**: PyTorch stays the only runtime. The pass rule is evaluated per platform: on Linux arm64 it is not met for the three models above (accepted trade-off: those three are 11–27% slower there, every other model is faster); on Linux x86_64 and Windows it is pending the `workflow_dispatch` run, where ORT has no native fp16 MatMul kernel [INFERENCE, not measured]. If x86_64 or Windows fails the rule too, the "two runtimes" alternative reopens; its cost is concrete: commit e2900919 deleted `onnx_providers.py` (232 lines), about 1,830 test lines and the CoreML/CUDA ONNX probes. Per-model numbers are in the plan's Task 6.1 notes.
- **The GLiNER thread pin hurt the new CPU path (removed).** `prose_extraction_backend.py:325` called `torch.set_num_threads(1)` for the whole process; with a PyTorch embedder that made bge-small 3× slower on CPU (131 → 44 passages/s). `mps` is unaffected (335 → 335). The pin was removed during implementation.
- **Cold start.** `import torch, transformers` took 1.8 s against 0.23 s for fastembed, and peak resident size for e5-large on CPU was 2.19 GB against 1.88 GB. Imports stay lazy so CLI startup is unchanged.
- **Apple GPU memory.** A 256×512 batch (fastembed's default batch size is 256) held 12 GB of GPU memory afterwards; the token budget bounds this (4096 tokens: 3.2 GB; 65 536 tokens: 7.7 GB and 32% lower throughput).
- **Download sizes change.** PyTorch weights are fp32: bge-small 133 MB (ONNX 67 MB), bge-base 438 MB (218 MB), multilingual-MiniLM 471 MB (235 MB), Jina 557 MB (1.11 GB); the other models are within 1%.
- **Two tokenizer pitfalls stay live** and are pinned by tests: XLM-R pair encoding needs `transformers` at least 5.3 if `AutoTokenizer` is ever used, and `fix_mistral_regex=True` changes Jina token ids.
- **Test blast radius.** 112 test files mention fastembed, ONNX providers or the provider vocabulary (76 mention fastembed); `tests/_search_stubs.py` faked fastembed; it now fakes the model backends.

### Verified (2026-10-25)

- **Parity for the whole registry.** `tests/runtime_parity/` (marker `runtime_parity`, excluded from the default run) ran every registry embedder and reranker against the frozen fastembed 0.9.0 outputs, batched and one text at a time, on CPU and `mps` of an Apple M4 Pro: 144 test cases, 6 truncation cases skipped for lack of a corpus text beyond the limit. Worst embedder cosine 0.9999447 (`BAAI/bge-base-en-v1.5`); every other model is at least 0.9999921; reranker worst absolute difference 1.5e-05 against the 1e-4 threshold; vector norms unchanged (multilingual-MiniLM norm ratio 0.99933 to 1.00078). Per-model values: [`tests/fixtures/runtime_parity/README.md`](../../tests/fixtures/runtime_parity/README.md).
- **The cosine gaps are not quantization.** Six embedders (`bge-small-en-v1.5`, `bge-base-en-v1.5`, `paraphrase-multilingual-MiniLM-L12-v2`, `bge-base-en`, `bge-small-en`, `bge-small-zh-v1.5`) are below cosine 1 because fastembed runs ORT-optimized graphs that use the tanh approximation of GELU (`FastGelu`) and store FLOAT16 weights (executed with fp16 MatMuls on arm64, which adds about 5e-7 of cosine deficit on top of the GELU effect); PyTorch's published exact GELU is the whole deviation. With `hidden_act='gelu_new'` the worst cosine rises to 0.9999995 (`bge-small-en-v1.5`), 0.9999995 (`bge-base-en-v1.5`) and 0.9999993 (`paraphrase-multilingual-MiniLM-L12-v2`); with the published exact GELU it is 0.9999981, 0.9999447 and 0.9999921. The graphs were scanned and contain no integer-quantized operators (the `-Q` in the file name does not mean int8; the weights are fp16).
- **Tier 2 was frozen and verified.** The golden outputs of 13 further embedders and `BAAI/bge-reranker-v2-m3` were frozen from fastembed on 2026-10-25, before fastembed left the environment, and all pass; this is why the registry has 19 + 5 models rather than the 6 + 4 of the first proposal.

### Not verified

Linux x86_64 and Windows CPU throughput (the gate above has not been run there; on Linux arm64 it fails for three models, see the CPU speed bullet); NVIDIA GPU throughput and the CUDA path end to end (the wizard's `+cu126` swap and CUDA probe are unit-tested, never run on an NVIDIA host); Intel Macs (no `mps`); memory and thread behaviour of the Apple GPU in a long-running server; `transformers` 5.8–5.14 (the lock range) beyond the versions the parity runs used (5.8.1 for the second batch; 4.57 and 5.20 for the Jina conversion, per the plan); the eval and latency thresholds on the new runtime (Plan Task 8.3); `Qwen/Qwen3-Embedding-0.6B` at its 32768-token limit (not exercised), and the parity of the quantized ONNX aliases (not measured).

### Implementation notes

Decisions that changed or were added while implementing (the rules above stand):

- **No `backends.py`.** The proposed factory module was dropped: each construction site builds `ModelEmbedder(model, device=config.device)` / `ModelReranker(...)` itself, and the reranker is disabled by an empty `reranker_model`.
- **Loaders are split.** `torch_runtime.py` holds `resolve_device`, the tokenizer and the encoder loader (`load_encoder`); `reranker_loading.py` holds `load_cross_encoder` and the in-memory Jina conversion (`load_jina_reranker`), instead of one `reranker_adapters.py`. `torch_device.py` was folded into `torch_runtime.resolve_device`, which the graph engine uses too.
- **`[graph].device`.** `[graph].providers` became `[graph].device` (default `cpu`), and the wizard flag `--graph-providers` became `--graph-device`; `[database].providers` and `reranker_providers` became one `[database].device` (the CoreML split has no counterpart). A config file holding a removed key fails with a `ConfigError` naming the replacement.
- **A third pooling.** `Qwen/Qwen3-Embedding-0.6B` pools the last token (`last_token`), and `ibm-granite/granite-embedding-small-english-r2` pools `cls` without normalizing; the spec carries both.
- **Download sizes come from the specs.** `InstallProfile.download_mb` is derived from each spec's `weight_mb`, so the wizard's figures follow what `ensure_model` fetches.
- **The thread pin is gone** (`torch.set_num_threads(1)` in `prose_extraction_backend.py`), as the Negative section required.
- **The freeze script was deleted with fastembed.** The fixtures are the reference and are never regenerated from another runtime.
- **Apple GPU work is serialized.** Two models loading, or running their first inference, on `mps` from two threads at once hang the process forever (PyTorch 2.13 on an M4 Pro, 3 of 3 runs; a live server stayed at `/ready` 503 with `warmup_result` pending). Steady-state concurrent inference and lock-serialized loads never hung, and four threads gave no throughput over one. `torch_runtime.accelerator_lock(device)` is a process-wide re-entrant lock for `mps` (a no-op for `cpu` and `cuda`) held around every model load and every batch forward. Regression tests: `tests/test_torch_runtime.py` (lock semantics) and `tests/runtime_parity/test_mps_concurrency.py` (real cold start from two threads). After the fix a server became ready in 6–8 s on five consecutive starts.
- **The `mps` lock stays as wide as it is (measured 2026-10-25, Apple M4 Pro, PyTorch 2.13.0, host not quiet).** Without any lock the cold-start hang reproduces in 52 of 90 runs of the three failing model sets and a second failure mode, a SIGSEGV, in 33 (5 clean); two-thread sets of two different models passed 30 of 30 unlocked, so the product cannot rely on that. A narrower lock (load plus each model's first forward only) had 0 failures in 280 runs and the current one 0 in 140. Narrowing was rejected because it only re-divides a saturated GPU: during an ingest it lowered search p50 by 5–8% and p95 by 5–12% and made the ingest 12% slower, with steady-state search and throughput unchanged within 0–4%. One search spends about 655 of 709 ms in the rerank of 45 candidate chunks, so shrinking the candidate pool would help more than any lock change (not done).
- **Model construction is serialized on every device.** On `transformers` 4.57.1 two threads building models at once left meta tensors behind (`Cannot copy out of meta tensor`), because `from_pretrained` swaps torch globals for the length of a build; `accelerator_lock` only covered `mps`. `torch_runtime.TRANSFORMERS_LOCK` (a re-entrant lock, the former import lock) is now held around every `from_pretrained`, around the Jina route's hand-built model and around the lazy imports; the lock order is `accelerator_lock` then `TRANSFORMERS_LOCK`.
- **`torch` floor is 2.4, not docling's 2.2.2.** With Python 3.12 or later, torch 2.2.2 and 2.3.1 cannot load ModernBERT (`Dynamo is not supported on Python 3.12+`) and `transformers` 5.13 treats torch below 2.4 as absent; torch 2.4.1 passed the unit and parity lanes on `transformers` 4.57.1 and 5.13.1. The `transformers` range is `>=4.57,<5.14` (`pyproject.toml`). The unit lane and the parity lane (CPU and `mps`) were run on `transformers` 4.57.1, 5.0.0, 5.8.1, 5.10.4 and 5.13.1 and passed on all of them (the full parity lane on 4.57.1 and 5.13.1: 139 passed, 6 skipped); versions between these were not run. Guard: `tests/test_pyproject.py::test_torch_floor_is_the_oldest_torch_the_runtime_works_on`.
- **The Linux arm64 gate was re-run with an alternating benchmark.** See the CPU speed bullet under Negative / Tradeoffs for the numbers and the decision. `scripts/bench_runtime.py --runtime both` runs fastembed and PyTorch alternately in one process (best of 10 rounds), because on a shared host identical single-runtime runs differed by 20–60%.

## Alternatives Considered

- **Keep fastembed, default to CPU on Apple.** Safe and tiny (one wizard change), and leaves the GPU unused and keeps the ONNX provider layer.
- **ONNX Runtime with fixed shapes on the GPU.** 0.11 s per 8×128 batch, but needs per-shape model files and compile caches (220–366 s each), padding buckets, and bypassing fastembed to set session options. Fragile and no faster than PyTorch.
- **Two runtimes (fastembed for CPU, PyTorch for GPU).** Doubles download formats, tests and failure modes; rejected unless the Linux CPU benchmark (Plan Task 6.1) shows PyTorch losing there.
- **Separate embedding server (llama.cpp, Ollama, Text Embeddings Inference).** archon already talks to llama.cpp and Ollama for LLM features, but embeddings would need GGUF conversions (only community files exist for e5, 4-bit quantized, so vectors would differ), a second process to operate, and no reranker story.
- **sentence-transformers as the abstraction.** Mature multi-backend API, but its `Normalize` module would L2-normalize e5 vectors (`modules.json` of `intfloat/multilingual-e5-large`) and its `max_seq_length` disagrees with fastembed for two models, so every default would be overridden anyway.
